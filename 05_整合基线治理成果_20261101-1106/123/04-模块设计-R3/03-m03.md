# M03：记忆提取与候选生成模块

**版本：Draft 0.3 — Design Frozen**  
**状态：设计基线冻结**  
**适用范围：Memory Core**  
**冻结性质：仅冻结设计，不代表代码实现、测试通过或安全验证完成。**

## 1. 模块定位

M03（Retain / Memory Extraction）负责从输入的对话批次中识别值得进入记忆系统的信息，生成结构化的候选记忆。

M03 不负责直接写入正式记忆，也不负责最终决定记忆权限、共享范围和生命周期。

核心原则：

1. 模型负责理解和提出候选。
2. Core 负责确定性校验、评分计算和候选分流。
3. M04 负责候选与既有记忆的比较、去重、合并、冲突处理和价值复审。
4. M05 是权限与访问范围的最终裁决者。
5. M01 是正式记忆的唯一权威写入入口。

**M03 的产出是候选记忆，不是已经成立的用户事实。**

## 2. 输入与批次边界

### 2.1 输入

M03 接收 Bridge 提交的对话消息批次及可信上下文。

输入至少包含：

- conversation_id
- subject_id
- source_message_refs
- message_content
- event_time
- trusted_scope
- permission_context
- policy_version

身份、主体和权限上下文必须来自可信调用方，不允许由模型根据消息内容自行认定。

### 2.2 批次边界

默认批次必须满足：

- 同一个会话；
- 同一个记忆主体；
- 兼容的权限范围；
- 可追溯的消息来源。

不允许为了提高提取效果而直接混合不同会话、不同主体或不同权限范围的原始消息。

跨会话比较由 M04 根据需要执行，并在访问前经过 M05 权限检查。

### 2.3 批量处理

M03 采用异步批量处理，不对每条消息单独调用模型。

默认只读取当前批次，不主动加载全部历史记忆。

历史记忆比较由 M04 按需检索，避免 M03 的模型上下文无限扩大。

## 3. Memory Share 边界

私聊记忆向群聊记忆提供，**由 M05 的 Memory Share 授权机制统一管理**（见 **M05 §6**）。M03 的批次边界**不承担**共享职责，不得通过合并私聊与群聊原始消息实现共享。

M03 侧只保留以下边界约束：

1. **批次边界独立于共享**：私聊与群聊原始消息批次不得因为存在共享授权而合并。跨会话比较由 M04 按需执行，并在访问前经过 M05 权限检查。
2. **共享不改变归属**：共享记忆不得自动改变原始私聊记忆的归属和权限。原始记忆的所有权、权限范围与生命周期不因共享而改变。
3. **模型不能代替授权**：模型可以提出共享相关建议，但不能代替用户授权。
4. **授权记录与撤销由 M05 管理**：共享授权的字段定义、审批流程、撤销语义和失效传播不在 M03 定义，以 M05 §6 为准。

## 4. 候选记忆类型

M03 支持以下候选类型：

| 类型 | 说明 |
|---|---|
| fact | 相对稳定的事实 |
| preference | 用户偏好 |
| event | 重要事件 |
| plan | 计划及其进展 |
| goal | 长期或阶段性目标 |
| relationship | 人物关系及角色 |
| state | 短期状态 |

记忆类型用于指导价值评估和生命周期管理，不直接决定记忆永久保存期限。

例如：

- 计划完成后应更新状态或失效；
- 短期状态需要考虑时效；
- 偏好可能因用户后续表达而发生变化；
- 一次性重要事件即使没有重复出现，也可能具有长期回忆价值。

## 5. 候选事实属性

每个候选必须区分证据性质：

| claim_type | 含义 |
|---|---|
| explicit | 用户明确表达或可靠来源直接支持 |
| inferred | 根据上下文推断 |
| uncertain | 证据不足或存在歧义 |

约束：

1. inferred 不得伪装成 explicit。
2. uncertain 不得直接作为确定事实写入。
3. 模型置信度不能替代原始证据。
4. 候选必须保留 source_refs，支持后续追溯。
5. 用户明确纠正或确认的信息优先于模型推测。
6. 不允许仅凭语义相似度把不同主体、不同人物或不同关系合并。

## 6. 候选价值评估

### 6.1 评估目标

判断一条候选信息是否值得进入记忆审核流程。

评估不能只依赖重复次数，也不能只依赖模型认为内容是否重要。

采用五个维度：

| 维度 | 标识 | 判断内容 |
|---|---|---|
| 复用价值 | R | 未来对话是否可能用到 |
| 持续性 | P | 信息预计能够保持多久 |
| 证据质量 | E | 来源是否可靠、表达是否明确 |
| 时效价值 | T | 当前或近期是否具有记录价值 |
| 独特性 | U | 是否提供了新的有效信息 |

每个维度采用 0–5 分。

### 6.2 初始权重

采用统一基线：

| 维度 | 权重 |
|---|---:|
| R：复用价值 | 25% |
| P：持续性 | 20% |
| E：证据质量 | 25% |
| T：时效价值 | 15% |
| U：独特性 | 15% |

初始总分：

S = 0.25R + 0.20P + 0.25E + 0.15T + 0.15U

总分范围为 0–5。

权重和评分区间均为初始配置，不视为经过实际数据验证的最优参数。

### 6.3 评分解释

**R：复用价值**

- 0：未来几乎不会用到。
- 1：偶尔可能相关。
- 2：特定场景下有用。
- 3：多个场景可以复用。
- 4：经常影响互动方式。
- 5：对长期个性化或重要决策有明显帮助。

**P：持续性**

- 0：瞬时信息。
- 1：很快失效。
- 2：可能维持一段时间。
- 3：预计持续较久。
- 4：稳定偏好或长期状态。
- 5：长期稳定的信息。

**E：证据质量**

- 0：没有有效证据。
- 1：纯推测。
- 2：间接表达或上下文暗示。
- 3：一次明确表达。
- 4：多次独立表达或有直接证据支持。
- 5：明确确认且有充分来源支持。

**T：时效价值**

- 0：已经过时。
- 1：当前没有明显用途。
- 2：未来可能有用途。
- 3：近期事件或计划。
- 4：正在发生的重要事项。
- 5：存在明确的近期时间窗口或紧迫用途。

**U：独特性**

- 0：完全重复。
- 1：几乎没有新增信息。
- 2：补充少量细节。
- 3：新增有效信息。
- 4：修正或补充重要认知。
- 5：此前完全没有的关键内容。

### 6.4 硬性约束

总分不能覆盖硬性约束。

例如：

- 来源不可信：拒绝进入正式候选。
- 证据不足：不得作为确定事实处理。
- 明确重复：交由去重逻辑处理。
- 未经授权的私聊信息：不得进入群聊记忆。
- 敏感信息：必须遵循独立的授权、权限和保护规则。
- 已失效信息：不得仅因历史评分较高而恢复为当前事实。

高价值不代表自动获得保存权限。

### 6.5 类型差异

五维框架统一，但不同类型的评价重点不同：

| 类型 | 重点维度 |
|---|---|
| fact | E、P、R |
| preference | R、P、E |
| event | T、E、R |
| plan | T、E、R |
| goal | P、R、E |
| relationship | E、P、R |
| state | T、E |

一次重要事件不要求重复出现才有资格成为候选。

重复表达是持续性的证据，不是所有记忆的必要条件。

## 7. 候选分流

### 7.1 初始分流区间

| 分数 | 分流 | 处理 |
|---|---|---|
| 3.5–5.0 | review | 进入 M04 |
| 2.0–3.4 | observe | 暂存观察 |
| 0–1.9 | reject | 不进入记忆候选 |

以上是初始配置值，后续允许调整。

### 7.2 特殊分流

高价值但证据不足的候选，不得仅凭总分进入正式审核通道。

可以暂存为待观察信号，但必须保留 inferred 或 uncertain 属性。

暂存观察必须具备：

- 有限保存期限；
- 容量上限；
- 重复候选合并机制；
- 新证据到达后的重新评估机制；
- 到期清理机制。

暂存不等于正式记忆，也不自动参与正常 Recall。

### 7.3 暂存晋升

暂存候选不自动晋升。

只有新证据到达并触发重新评估后，才允许重新计算价值并进行分流。

多次独立表达可以提高证据质量，但短时间内同一来源的重复表达不能被当作多次独立确认。

## 8. 重复表达与证据累计

> **本节是「重复表达 / 证据累计」的唯一权威定义。**
> M02 D25（重复提及作为强化信号）、M04 §4.3（Observation 置信度）均引用本节口径，不另行定义时间窗口、来源独立性和批次合并规则。

采用以下规则：

1. 同一批次中的重复表达先合并证据。
2. 同一来源、短时间内的重复不显著提高证据等级。
3. 不同时间、不同场景的独立表达可以增强可信度。
4. 用户明确纠正或确认优先于模型推断。
5. 重复证据关联到同一候选，不生成大量相似记忆。
6. 证据累计必须保留来源引用和时间信息。

**关于"独立表达"的判定**：短时间内同一来源的重复表达不能被当作多次独立确认（见 §7.3）。重复提及本身只说明该信息被反复提起，**不能证明事实真实性**；真实性判定仍取决于证据性质（`claim_type`）与来源可靠性。

## 9. M03 与 M04 的职责边界

| 工作 | M03 | M04 |
|---|---|---|
| 消息批次处理 | 负责 | 不负责 |
| 候选提取 | 负责 | 不负责 |
| 候选价值初评 | 负责 | 可复核 |
| 候选分流 | 负责 | 不负责 |
| 与旧记忆比较 | 不负责 | 负责 |
| 去重与合并 | 提供候选 | 负责 |
| 新旧事实冲突 | 提供证据 | 负责 |
| 记忆价值复审 | 不负责最终决策 | 负责 |
| 正式写入 | 不负责 | 通过 M01 完成 |

M03 不得绕过 M04 和 M01 直接写入正式记忆。

## 10. 候选数据结构

以下为逻辑结构示例，实际字段名称可在 API Schema 阶段统一。

```json
{
  "candidate_ref": "candidate_001",
  "kind": "preference",
  "content": "用户偏好循序渐进的 C 语言讲解",
  "source_refs": ["src_001", "src_002"],
  "claim_type": "explicit",
  "value_assessment": {
    "reuse": 5,
    "persistence": 4,
    "evidence": 4,
    "timeliness": 3,
    "uniqueness": 4,
    "total": 4.15
  },
  "routing": "review"
}
```

约束：

- 模型负责提供候选内容和各维度评价建议。
- Core 根据实际配置重新计算总分。
- Core 执行硬性条件校验。
- Core 决定 routing。
- 原始证据与评分结果应可追溯。
- M04 可以重新评估候选。

## 11. 可调整接口

以下参数必须配置化，不应散落在模型 Prompt 或业务代码中。

| 配置项 | 当前默认值 | 调整目的 |
|---|---|---|
| weight.reuse | 0.25 | 复用价值权重 |
| weight.persistence | 0.20 | 持续性权重 |
| weight.evidence | 0.25 | 证据质量权重 |
| weight.timeliness | 0.15 | 时效权重 |
| weight.uniqueness | 0.15 | 独特性权重 |
| threshold.review | 3.5 | 进入 M04 的初始阈值 |
| threshold.observe | 2.0 | 暂存观察的初始阈值 |
| observe.ttl | 待定 | 暂存期限 |
| observe.capacity | 待定 | 暂存容量上限 |
| observe.recheck_policy | event-triggered | 新证据触发重新评估 |
| scoring.version | 1 | 评分规则版本 |

配置调整必须：

1. 有明确版本号；
2. 保留旧版本参数；
3. 能追溯候选使用的评分版本；
4. 不自动重写已有正式记忆；
5. 必要时通过离线评估比较新旧参数。

未来可以增加按记忆类型调整权重的配置，但当前不提前引入复杂的多套评分模型。

## 12. 模型接口与故障处理

M03 通过抽象 LLM Provider 调用模型，不直接依赖 DSH。

模型服务故障时：

- 当前聊天不应被阻塞；
- 已有记忆读取和管理不受影响；
- 尚未完成的提取任务进入可恢复状态；
- 不得将模型调用失败视为成功提取；
- 重试不得产生重复候选或重复写入。

任务应具备：

- 稳定任务标识；
- 批次标识；
- 幂等处理；
- 可追踪状态；
- 有限重试；
- 失败原因；
- 中断恢复能力。

模型输出必须经过 Schema 校验和确定性检查。

模型不能决定权限，也不能直接操作数据库。

## 13. 成熟方案参考与设计取舍

本模块参考了此前研究过的 Hindsight、Mem0、Graphiti 的相关设计，但不整体复制任何一个系统。

| 参考来源 | 借鉴点 | 在 M03 中的体现 |
|---|---|---|
| Hindsight | 证据与来源追溯 | source_refs、候选证据保留 |
| Hindsight | 异步任务与恢复 | 批量任务、幂等、重试和恢复 |
| Hindsight | 记忆价值复审 | M03 初评、M04 二次审核 |
| Mem0 | 候选提取与正式更新分离 | M03 只生成候选，不直接写入 |
| Mem0 | LLM Provider 可替换 | 不绑定 DSH |
| Graphiti | 时间与事实变化 | 为计划、事件和状态保留时效及后续更新空间 |
| Graphiti | 历史证据与来源 | 候选保留来源，不只保存摘要 |

### 未采用的做法

- 不把某个系统的完整评分算法直接移植为 M03。
- 不采用模型提取后直接写库的流程。
- 不允许模型自主授予共享权限。
- 不将所有历史消息一次性放入模型上下文。
- 不将向量相似度当作事实相同的证明。
- 不把短期状态一律转化为永久记忆。

以上是设计参考和取舍，不代表这些机制已在本项目中完成性能或安全验证。

## 14. 尚未冻结的实现参数

以下内容保留到实现和评估阶段：

- 各维度评分的实际一致性；
- 各类型的评分偏差；
- review、observe 的最佳阈值；
- 暂存 TTL 与容量；
- 不同模型对结构化候选的稳定性；
- 中文语义提取的准确率；
- 批次大小与模型资源占用；
- 重试和并发处理参数。

这些参数通过测试集、人工复核和实际运行数据调整，不应在没有验证的情况下宣称已经最优。

## 15. 冻结结论

本版确认：

1. M03 使用异步批量提取。
2. 批次边界为单会话、单主体、兼容权限范围。
3. Memory Share 独立于批次构造。
4. 候选必须保留来源与证据性质。
5. 使用 R、P、E、T、U 五维价值评估。
6. 评分权重和阈值配置化。
7. 规则硬性校验优先于总分。
8. 候选分为进入 M04、暂存观察、不进入候选三类。
9. 暂存候选只能在新证据到达后重新评估，不自动晋升。
10. M03 不直接写入正式记忆。
11. M04 负责与旧记忆比较及二次审核。
12. 模型服务与 DSH 解耦，支持异步任务恢复。

**冻结声明：**

M03 的职责、批次边界、候选价值评估框架、候选分流原则和模块间职责边界作为 R2 设计基线冻结。

评分权重、分流阈值、暂存期限和容量等保留配置调整接口。

本冻结不代表代码已实现、测试已通过、评分参数已验证或安全性已得到实际证明。

后续修改应通过版本变更记录进行，不应无记录地改变冻结基线。
