## 一、模块定位

M02 负责从长期记忆中找到当前聊天需要的信息，并将相关记忆交给 DSH，辅助大肥鱼进行连续、自然的对话。

核心目标：

1. **记得住**：能够找到过去留下的重要信息。
2. **想得起**：能够根据当前聊天自然唤起相关记忆。
3. **不乱说**：不确定时保留不确定性，找不到时不编造。

M02 是记忆检索与上下文构建模块，不是独立知识库问答系统，也不是复杂任务检索编排系统。

### 1.1 模块边界

- M02：检索、候选筛选、排序、扩展及上下文构建。
- M01：记忆数据存储与管理。
- M03：记忆提取和候选生成。
- M04：记忆整合、内部一致性维护与视图维护。
- M05：权限判断，是记忆访问的最终权限依据。
- Bridge：提供可信身份、当前会话及必要上下文。
- DSH：理解聊天意图、决定是否需要进一步查询，并组织最终回复。

M02 不直接修改正式记忆，不绕过 M05，也不直接向 QQ 发送消息。

**M02 不得直接访问底层数据库。** 关系数据的读取通过 M04 的关系查询能力完成，记忆数据的读写通过 M01 的 Storage API 完成，权限判断通过 M05 完成。M02 不直接拼接 SQL、不直接操作 LanceDB 或 FTS5 索引。

## 二、总体检索架构

### D1：两阶段混合检索

采用算法自动预检索与 DSH 主动检索相结合的混合架构。

**第一阶段：自动预检索**

当当前聊天确实需要历史记忆时，由系统进行算法检索，将少量高相关记忆注入 DSH 上下文。

**第二阶段：DSH 主动检索**

如果 DSH 判断现有上下文不足，可以主动调用 `memory_search`，进一步查询相关记忆。

设计原则：

- 不额外增加一个轻量 LLM 判断层。
- 第一阶段以算法为主。
- 第二阶段由 DSH 根据聊天需要决定。
- 两阶段共用检索服务和权限体系。
- 具体算法、候选数量和预算后续通过测试确定。

**两阶段均属于第一版设计范围。** 第二阶段为受控能力，实施约束见 D16。

### D2：自动预检索触发范围

不对每条消息执行检索。

以下情况可以触发预检索：

- 用户提及过去的经历、人物、偏好、计划或事件。
- 当前表达存在模糊指代，需要联系过去的聊天。
- 当前话题明显延续此前讨论。
- 当前问题需要历史信息才能合理回答。

普通闲聊、无关话题不主动检索。

DSH 仍然可以在后续对话中主动调用 `memory_search`。

### D3：多渠道检索策略

采用多渠道互补：

| 渠道 | 主要用途 |
|---|---|
| LanceDB 向量检索 | 语义相似度和模糊关联 |
| SQLite FTS5 | 精确关键词、名称、数字、型号 |
| SQLite 结构化查询 | 时间、类型、状态等条件 |
| Relation 关联扩展 | 按需寻找相关记忆 |

多渠道结果通过 RRF 进行融合。

保留各渠道的原始分数、排名和来源信息，便于后续评估和调整。

具体权重、候选数量和关联深度暂不固定。

### D4：候选排序

候选排序考虑五个因素：

1. 相关性：与当前聊天内容的匹配程度。
2. 时间适配性：记忆时间是否符合当前问题。
3. 记忆重要性：记忆本身的重要程度。
4. 证据可靠性：记忆来源及可信程度。
5. 多样性：避免重复内容占据过多位置。

第一版以规则排序为主，暂不引入 Cross-Encoder 或额外 LLM 重排序，但保留后续升级空间。

### D5：记忆扩展机制

采用分层扩展：

- **L0：直接命中**。默认只使用直接相关记忆。
- **L1：一跳关联**。当前记忆不足时，按需扩展一层关系。
- **L2：多跳关联**。仅在需要历史梳理、综合回忆等情况下使用。

约束：

1. 每次扩展都必须重新经过 M05 权限检查。
2. 关联关系不代表事实支持关系。
3. 扩展结果需要去重并受预算限制。
4. M02 不创建或修改正式关系。
5. 扩展过程中不得绕过 M04 直接访问关系数据。
6. 多跳扩展必须防止重复访问同一对象，并在预算耗尽时停止。

**关系扩展的职责与预算归属（跨模块统一）**

| 事项 | 负责模块 |
|---|---|
| 决定是否扩展关系 | M02 |
| 决定扩展方向 | M02 |
| L0/L1/L2 遍历控制 | M02 |
| 扩展结果去重 | M02 |
| 本轮关系扩展总预算 | M02（唯一持有者） |
| 决定何时停止扩展 | M02 |
| 提供指定记忆的一跳邻居 | M04 |
| 返回关系类型与关联对象 | M04 |

具体规则：

- **L0/L1/L2 的遍历由 M02 控制，多跳遍历由 M02 统一管理。**
- **M02 持有本轮唯一的关系扩展总预算**，M04 不持有、不二次裁剪该预算。
- M04 只提供关系查询能力，返回指定记忆的一跳邻居及其关系类型，**不自行递归遍历，不自行决定整个检索流程的总预算**。
- 每个新增对象仍必须接受 M05 权限检查。
- M02 不得绕过 M04 直接访问关系数据库。

> 关系查询接口的具体参数、数据结构与算法不在本文冻结。接口方向见 M04 §12.4。

## 三、完整检索流程与时序

本节定义一次普通聊天从收到消息到完成回复的完整记忆检索时序。

整体分为两条路径：

- **自动预检索路径**：发生在 DSH 开始生成回复之前。
- **主动检索路径**：发生在 DSH 生成回复的过程中，由 DSH 按需发起。

两条路径共用 M02 检索服务，不是两套独立的记忆系统。

### 3.1 总体时序

```text
用户发送 QQ 消息
       │
       ▼
① Bridge 接收消息
       │
       ├── 解析用户、群组、会话等可信身份
       ├── 获取当前消息和必要的聊天上下文
       └── 建立本轮请求上下文
       │
       ▼
② 判断是否需要自动预检索
       │
       ├── 不需要
       │     │
       │     ▼
       │   跳过自动检索
       │
       └── 需要
             │
             ▼
③ Bridge 将检索请求交给 M02
             │
             ▼
④ M02 执行检索
       │
       ├── 生成检索条件
       ├── M05 执行权限过滤
       ├── 向量 / FTS5 / 结构化查询
       ├── 多渠道结果融合
       ├── 排序、去重
       ├── 必要时进行关系扩展（M02 控制遍历与预算）
       ├── 扩展结果重新检查权限
       └── 按上下文预算选择结果
             │
             ▼
⑤ M02 返回 Memory Context
             │
             ▼
⑥ Bridge 将 Memory Context 注入 DSH
             │
             ▼
⑦ DSH 理解当前聊天并生成回复
       │
       ├── 当前上下文足够
       │      │
       │      ▼
       │   直接生成回复
       │
       └── 当前上下文不足
              │
              ▼
⑧ DSH 主动调用 memory_search
              │
              ▼
⑨ Bridge 将请求转交 M02
              │
              ▼
⑩ M02 再次执行权限检查和检索
              │
              ▼
⑪ 返回补充记忆给 DSH
              │
              ▼
⑫ DSH 结合已有上下文生成最终回复
              │
              ▼
⑬ Bridge 将回复发送至 QQ
              │
              ▼
⑭ 本轮结束
```

普通聊天不一定经过自动预检索，也不一定触发主动检索。两者均按需发生。

### 3.2 第一阶段：消息接收与请求准备

**时机：用户消息到达后，DSH 正式生成回复之前。**

1. Bridge 接收 QQ 消息。
2. Bridge 解析可信用户身份、群组身份、会话身份及必要的请求信息。
3. Bridge 整理当前消息和必要的聊天上下文。
4. 判断当前消息是否符合自动预检索触发条件。

身份和访问范围必须来自可信的 Bridge 请求上下文，不能由 DSH 自行指定。

如果当前只是普通闲聊，没有明显的历史记忆需求，则跳过自动预检索。

### 3.3 第二阶段：自动预检索

**时机：消息符合触发条件后，DSH 开始生成回复之前。**

1. Bridge 将当前聊天内容、必要上下文和可信身份交给 M02。
2. M02 根据当前聊天形成检索需求。
3. M05 对检索范围和访问权限进行检查。
4. M02 执行向量、FTS5 和结构化查询。
5. M02 对多渠道候选进行融合、排序和去重。
6. 如果直接命中不足以满足需求，可以按需进行关系扩展。
7. 扩展出来的每条记忆仍需经过权限检查。
8. M02 根据相关性、置信度和上下文预算选出少量结果。
9. M02 将 Memory Context 返回给 Bridge。

如果没有可靠结果，则返回空结果，不为了填充上下文而强行提供记忆。

### 3.4 第三阶段：上下文注入与 DSH 回复

**时机：自动预检索结束后。**

1. Bridge 将 Memory Context 注入本轮 DSH 请求。
2. DSH 同时获得当前聊天内容、原有系统人格设定及必要的记忆上下文。
3. DSH 自行理解用户当前意图。
4. DSH 判断已有记忆是否足以支持回答。

Memory Context 是辅助理解的背景信息，不是覆盖系统人格或聊天规则的新指令。

记忆应自然参与回复，不需要向用户展示数据库查询过程。

### 3.5 第四阶段：DSH 主动检索

**时机：DSH 已经开始处理当前消息，但发现现有上下文不足时。**

例如：

- 用户追问某件过去发生的事。
- DSH 需要确认某个人物或关系。
- 用户询问过去的偏好或决定。
- 当前注入的记忆无法回答问题中的关键细节。

处理顺序：

1. DSH 根据当前聊天形成 `memory_search` 请求。
2. Bridge 接收工具调用，并补充可信身份和请求上下文。
3. Bridge 将请求交给 M02。
4. M02 再次经过 M05 权限检查。
5. M02 执行检索、排序、去重和必要扩展。
6. M02 返回补充 Memory Context。
7. DSH 将结果结合当前对话上下文继续生成回复。

允许同一轮中进行有限的多次主动检索，但需要避免重复查询，并受到调用次数和总预算限制。

每次主动检索都必须重新检查权限，不能复用上一轮或上一次调用的授权结果。

> **本阶段属于第一版设计范围**，为受控能力。实施约束见 D16。

### 3.6 第五阶段：上下文复用与本轮结束

同一话题连续对话时：

- 已经注入当前会话上下文的相关记忆可以复用。
- 不需要每轮重复执行相同检索。
- 出现新问题、缺少信息或原有记忆已不适用时，再发起检索。
- 记忆发生更新、删除或撤销共享后，旧结果不能继续作为有效依据。

本轮检索结果只服务于当前请求及其连续对话，不自动成为新的长期记忆。

新会话需要时重新检索。

### 3.7 第六阶段：异步记忆处理

**时机：与本轮聊天回复解耦，不阻塞正常回复。**

用户消息及必要的对话事件可以按既定流程提交给 Core 的 Retain 流程：

```text
本轮聊天内容
      │
      ▼
异步提交 Retain
      │
      ▼
M03 提取记忆候选
      │
      ▼
M04 整合、判断与维护
      │
      ▼
M01 持久化正式记忆
      │
      ▼
更新相关索引与检索缓存
```

这条流程与当前轮 Recall 分开：

- Recall 负责读取和使用已有记忆。
- Retain 负责从聊天中提取可能值得保存的信息。
- 新聊天内容不会因为进入当前上下文就自动成为正式长期记忆。
- 异步处理失败不应阻塞正常聊天。
- 正式记忆发生变化后，相关旧检索缓存和结果需要失效或重新验证。

Dream 等后台反思任务也不属于当前轮同步检索流程。

### 3.8 关键时序约束

| 事项 | 必须发生的时机 |
|---|---|
| 可信身份解析 | Bridge 接收消息时 |
| 自动预检索触发判断 | DSH 生成回复之前 |
| 自动预检索权限检查 | 读取记忆之前 |
| 多渠道检索与排序 | 权限过滤之后 |
| 关系扩展 | 直接检索不足且确有需要时 |
| 扩展结果权限检查 | 每次扩展读取时 |
| Memory Context 注入 | DSH 正式处理回复之前 |
| 主动检索 | DSH 判断当前上下文不足时 |
| 主动检索权限检查 | 每次工具调用时 |
| 同话题结果复用 | 当前会话连续对话期间 |
| 旧结果失效 | 记忆更新、删除或授权撤销后 |
| Retain | 异步执行，不阻塞正常回复 |

**特别约束：**

1. M05 权限判断必须先于受保护记忆内容的读取和返回。
2. 检索结果不能绕过 M05，也不能因为已注入 DSH 就获得永久有效性。
3. 自动预检索与主动检索共用 M02，不重复建设检索引擎。
4. 检索失败可以降级为无记忆聊天，但不能降低权限要求。
5. Recall 与 Retain 是两条不同流程，不应将当前聊天内容直接当作已保存记忆。
6. 用户看到的是自然聊天回复，不需要看到内部检索步骤。

## 四、结果与上下文构建

### D6：检索结果格式

M02 向 DSH 提供结构化的 Memory Context，而不是自然语言检索报告。

结果可以包含一条或多条简洁的记忆内容。

应保留必要的信息：

- 事实与推断的区别。
- 当前信息与历史信息的区别。
- 必要的不确定性。
- 不改变原始记忆含义。

具体数据结构仅作设计方向，暂不冻结接口字段。

### D7：动态上下文预算

不采用固定返回条数。

分别控制四项预算：

1. **候选数量预算**：进入排序阶段的候选上限。
2. **最终返回预算**：注入 DSH 的最终条数上限。
3. **Token 预算**：注入内容的 Token 上限。
4. **关联扩展预算**：关系扩展可消耗的对象数与深度上限。

根据当前问题复杂程度动态分配，但必须有硬性上限。

先去重、排序，再选择最终结果。

**关联扩展预算由 M02 唯一持有**（见 D5）。M04 不持有、不二次裁剪该预算。

具体数值通过实际聊天测试确定。

### D8：缓存策略

第一版只缓存中间检索候选，不缓存最终授权结果或最终 Memory Context。

可以缓存：

- 向量候选 ID 和分数。
- FTS 候选 ID 和排名。
- 关系候选。

**缓存的归属与边界：**

- **M02 决定缓存哪些中间检索候选，以及何时失效。**
- **M01 负责缓存数据的持久化与清理**（Recall Cache 是可重建的持久化缓存，见 M01 D2 / D27）。
- 缓存命中不代表授权。
- 缓存命中后，仍然需要读取最新 SQLite 状态并执行 M05 权限检查。
- 同一 `request_id` 内，符合复用条件的对象可以复用已完成的判权结果；跨请求不得复用。
- 不缓存最终授权结果，也不缓存可以绕过最新状态验证的最终 Memory Context。
- 记忆、索引或权限发生变化时，失效相关缓存。

Recall Cache 不是正式记忆，不具有独立权限，不得作为授权依据。

### D9：检索失败与降级

不同检索渠道独立降级：

| 故障 | 降级方式 |
|---|---|
| 向量检索失败 | 使用 FTS5 和结构化查询 |
| FTS5 失败 | 使用向量和结构化查询 |
| 关系扩展失败 | 保留直接命中结果 |
| 单条记忆异常 | 跳过异常记忆并记录 |
| M05 权限检查失败 | 拒绝访问受保护记忆 |
| M02 整体不可用 | 正常聊天继续，不注入记忆 |

区分：

- 没有检索结果。
- 部分渠道降级。
- 检索服务不可用。

任何情况下都不能编造记忆，也不能因为降级而绕过权限检查。

### D10：检索质量评估

使用生活化测试集验证记忆召回、偏好变化、人物关联、近期事件、权限隔离和删除效果。测试集包括：

- 用户之前想买什么？
- 用户购买时看重哪些特点？
- 用户提到过哪个朋友？
- 用户最近在忙什么？
- 用户过去喜欢什么，后来有没有改变？
- 用户曾经纠结过什么？
- 不同权限范围的记忆能否正确隔离？
- 删除记忆后是否仍会被检索？

指标包括 Recall、Precision、错误召回率、延迟、Token 消耗和权限正确性。

权限正确性是硬性约束，不参与普通检索效果的权衡。

通过逐步增加检索渠道，比较各渠道带来的实际收益。

不增加独立评估 LLM。

## 五、检索输入与可信信息

### D11：检索输入来源

M02 的输入包括：

- DSH 提供的自然语言检索需求。
- Bridge 提供的必要当前聊天上下文。
- Bridge 提供的可信用户、群组和会话身份。
- 可选时间范围、记忆类型、人物关键词等条件。

DSH 不得自行指定可信身份或扩大访问范围。

当前聊天内容不自动等同于正式长期记忆。

### D12：来源与置信度传递

保留 M03、M04 已有的判断信息：

- Explicit：明确表达。
- Inferred：推断。
- Uncertain：不确定。
- Corrected：经过用户纠正。

保留必要的来源引用、时间和当前状态信息，供 Core 内部校验。

M02 不重新判断记忆真实性，只负责传递已有信息。

## 六、检索处理规则

### D13：去重策略

同一 `memory_id` 经多个渠道命中时需要去重，并保留各渠道排名和分数。

语义相似记忆可以在上下文构建阶段减少重复，但不能因此删除正式记忆。

时间不同、代表状态变化的记忆不能简单视为重复内容。

### D14：时间检索与有效性

区分记录时间与记忆有效时间。

明确时间查询使用结构化时间条件；模糊时间查询结合语义和时间；没有时间要求时优先当前有效记忆；历史查询允许检索已过期或被替代的历史记忆。

不自行推断精确日期。记忆生命周期与有效性以 M04 为准。

### D15：人物与实体检索

优先使用已有实体和 Relation 数据。

人物姓名、昵称、别名作为辅助匹配信息。身份存在歧义时保留多个候选，不强行合并，根据需要扩展相关事件和记忆。

M02 不负责创建或修改实体、关系。

第一版不引入正式图数据库依赖，使用 M01 SQLite 关系数据。

Neo4j 可以作为独立实验环境，用于比较关系检索效果，不直接接入正式 Core，也不向正式数据库回写。

### D16：DSH 主动检索规则

当 DSH 需要以下信息时，可以调用 `memory_search`：

- 过去的经历。
- 人物及人物关系。
- 历史事件。
- 过去的偏好。
- 当前上下文中缺失的历史信息。

允许同一轮进行有限的多轮检索。

限制：

- 避免重复相同查询和条件。
- 限制单轮调用次数和总检索预算。
- 每次调用重新执行 M05 权限检查。
- 不复用之前的权限授权结果。
- 没有可靠结果时，不编造记忆。

**实施约束（第一版）**

DSH 主动 Recall 为受控能力，必须满足：

1. **工具调用由 Bridge 转交**，DSH 不直接连接 Memory Core 内部服务。
2. **M02 负责检索**，主动检索与自动预检索共用同一检索服务。
3. **M05 负责权限**，是唯一权限判定权威。
4. **不允许 DSH 直接访问 SQLite、LanceDB** 或任何底层存储。
5. 限制单轮调用次数、总检索预算和重复调用。
6. 每次调用必须使用 Bridge 提供的可信身份，DSH 不得自行指定身份或扩大范围。
7. 权限检查失败时拒绝返回受保护记忆。
8. 检索失败或空结果时返回空，不编造，也不因降级绕过权限。

具体调用次数和预算后续通过测试确定。

### D17：检索结果对回答的影响

DSH 使用记忆时需要区分明确事实、推断、不确定和纠正后的信息。

优先使用当前有效记忆。对冲突信息保留差异，结合时间和来源判断。不确定的信息降低表达确定性。用户明确纠正的信息优先。

检索不会直接改变正式记忆。

发现冲突时，只能形成反馈或候选，交由 M03、M04 后续处理。

### D18：主动回忆程度

采用低主动程度：

- 用户明确提及过去的人、事、偏好时，可以主动回忆。
- 当前话题明显关联旧记忆且确实有帮助时，可以适当关联。
- 普通无关闲聊不主动翻旧记忆。
- 不为了展示记忆能力而刻意提起旧信息。
- 避免重复提醒用户已经知道的事情。

## 七、上下文精简与模糊召回

### D19：Memory Context 呈现原则

DSH 不需要接收数据库查询报告。

M02 应将检索到的记忆内容提供给 DSH，而不是直接暴露数据库记录。

默认不向 DSH 提供以下五项：

1. `memory_id`。
2. 数据库时间戳。
3. 来源编号。
4. 检索分数。
5. 内部查询过程。

Core 内部仍保留必要的来源、时间、权限和版本信息，用于验证、纠正和审计。

### D20：少而准，按需注入

记忆系统的目标之一是减少上下文消耗，避免无关信息注入。

原则：

- 准确性优先于相关性。
- 相关性优先于完整性。
- 完整性优先于数量。
- 只注入当前问题真正需要的信息。
- 一条记忆足以回答时，不额外注入大量关联记忆。
- 避免重复信息。
- 保留重要的时间变化、人物区别和用户纠正。
- 信息足够时停止检索，不为了填满 Token 预算而继续搜索。

允许返回较少信息，但要求准确。

### D21：模糊召回与置信度处理

允许使用模糊匹配、相似度和关联召回。

检索层内部保留匹配强度和置信度。

处理方式：

- **高置信度**：正常提供记忆内容。
- **中等置信度**：可以少量提供，但必须保留不确定性。
- **低置信度**：不进入普通上下文。
- **没有可靠结果**：返回空结果，由 DSH 自然表达不记得。

模糊结果可以作为第二阶段检索线索，但不能被包装成确定事实。

### D22：多样性控制

相关性仍然是排序第一原则。

- 相同事件或事实的重复结果，在上下文中合并。
- 不同主题只有在有助于当前回答时才保留。
- 不为了追求类别覆盖而牺牲高相关结果。
- 简单问题优先返回一条或少量记忆。

多样性是辅助排序机制，不是强制覆盖要求。

### D23：遗忘曲线与时间衰减

考虑引入时间衰减机制，影响记忆在检索中的权重。

基本方向：

- 时间衰减影响检索排序，不直接删除记忆。
- 历史查询可以调整时间因素，确保旧记忆仍然可被找到。
- 权限撤销、删除和无效状态优先级高于相似度。
- 不因检索权重下降就认定记忆失效。

初步研究方向：

\[
S_{\text{final}}=S_{\text{vector}}\times F(t)
\]

其中：

- \(S_{\text{vector}}\)：语义相似度。
- \(F(t)\)：随时间变化的衰减因素。
- \(t\)：时间变量。

**注意：该公式仅为初步研究方向，不是最终算法。**

以下内容暂不冻结：

- 衰减函数形式。
- 参数与衰减速度。
- 记忆强化机制。
- 不同记忆类别的衰减策略。
- 时间因素与其他排序因素的组合方式。

后续结合已有 A/B 信息加载机制和实际测试再研究。

## 八、多轮对话与检索反馈

### D24：多轮对话中的记忆复用

检索结果首先服务于当前请求。

同一话题连续对话时：

- 如果相关记忆已经存在于当前会话上下文，可以复用。
- 如果问题变化或信息不足，再调用 `memory_search`。
- 不将上一轮全部检索结果永久搬入后续会话。
- 记忆发生更新时，不能继续使用已经过期的旧内容。

### D25：检索反馈机制

M02 不直接修改正式记忆。

- 用户明确纠正记忆时，生成高优先级更新候选。
- 新信息与旧记忆冲突时，交由 M03、M04 判断更新、追加或保留历史。
- 重复提及可以作为重要性或遗忘曲线的强化信号。
- 重复表达本身不代表事实已经得到独立证实。
- 检索相关性低不代表记忆无效。
- 检索失败不能触发记忆删除。

**重复表达的判定口径以 M03 §8 为准。** M02 仅消费该信号，不重新计数、不重新定义时间窗口、来源独立性和批次合并规则。重复提及本身不能证明事实真实性。

### D26：检索结果生命周期

检索结果是临时上下文，不是新的正式记忆资产。

- 当前轮次的结果服务于当前请求。
- 同一话题连续聊天时，可以复用当前会话中已经注入的记忆。
- 新会话不自动继承上一会话的临时检索结果，需要时重新检索。
- 记忆被更新、删除或撤销共享后，旧结果不能继续作为有效依据。
- 复用结果前，必要时重新检查权限和有效状态。

核心原则：减少重复检索和重复注入，同时防止继续使用已经失效的记忆。

### D27：检索结果用途区分

检索结果按用途分为两类：

**回答型**

- 用于回答当前问题。
- 以直接相关的少量记忆为主。
- 满足当前问题即可，不额外扩大检索范围。

**探索型**

- 用于回忆、经历梳理或跨记忆关联。
- 可以适当扩大检索范围。
- 仍受 M05 权限和 M02 预算限制。

两类用途服务于聊天需求，不意味着引入复杂的独立检索工作流。

## 九、信息加载原则

当前信息加载体系继续沿用已有 A/B 结构：

- **A：长期记忆**。通过向量等检索方式按主题相关性找到事实、偏好、事件、人物印象等长期信息。
- **B：SocialV2 短期状态**。包括 `activeTopic`、`pendingThought`、`memberImpression` 等，根据唤醒和当前聊天需要加载。
- **C：原始聊天记录**。不作为 DSH 日常检索的独立上下文层。原始证据如有保留，主要用于 Core 内部来源追溯和必要验证。

A/B 的具体加载时机和数量沿用各自模块设计，不在 M02 中重复定义。

## 十一、设计结论

M02 采用轻量、按需的混合记忆检索架构：

- 普通闲聊不强制检索。
- 需要历史信息时进行算法预检索。
- DSH 可以根据聊天需要主动搜索。
- 多渠道互补，但结果必须去重、排序和控制预算。
- 允许模糊召回，但不能把不确定信息说成事实。
- 权限由 M05 最终控制。
- 记忆只在需要时注入，避免重复搬运。
- 检索结果不直接修改正式记忆。
- Recall 与 Retain 分离，异步记忆处理不阻塞正常聊天。
- 不把大肥鱼设计成复杂的知识库问答或检索编排系统。

**当前状态：M02 框架设计基本完成，待算法研究、实际聊天验证及跨模块一致性检查。**

本文件为设计文档，不代表功能已经实现、测试通过或完成安全验证。
