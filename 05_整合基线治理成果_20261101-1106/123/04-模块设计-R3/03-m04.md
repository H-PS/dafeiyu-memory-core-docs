# 一、模块定位

## 1.1 核心职责

M04 是 Memory Core 中负责记忆整合与维护的模块。

主要负责：

1. 接收 M03 提交的候选记忆。
2. 判断候选记忆与已有记忆的关系。
3. 维护 Fact/Event。
4. 生成、更新和修订 Observation。
5. 维护记忆之间的关系。
6. 构建当前记忆视图。
7. 管理视图版本和原子发布。
8. 执行**内部一致性维护**（`integrity_reflection`）、质量评估和依赖重算。
9. 管理记忆生命周期。
10. 协调后台任务和模型调用。

M04 不负责：

- 原始数据的权威存储：由 M01 负责。
- 最终权限判定：由 M05 负责。
- 完整 Recall 检索与排序：由 M02 负责。
- 原始消息接收与 QQ 消息发送：由 Bridge 负责。
- 模型本身的推理运行：由 Model Gateway 负责。
- 底层数据库的物理删除执行：由 M01 负责。
- 多跳关系遍历与关系扩展总预算：由 M02 负责。

> **术语说明**：M04 的"反思"指**记忆库内部一致性维护**（依赖重算、质量检查、视图校验），任务类型为 `integrity_reflection`。这与 Dream 的"记忆漫游与反思"（跨记忆联想探索并向用户反馈）是**不同功能**，不得共用任务标识或日志标识。

## 1.2 模块协作关系

| 模块 | 与 M04 的关系 |
|---|---|
| M01 | 正式数据读取、事务写入、版本与删除执行 |
| M02 | 请求当前视图、Observation 和关系扩展 |
| M03 | 提交候选记忆及来源证据 |
| M05 | 提供权限检查与授权结果 |
| Model Gateway | 提供模型调用、资源管理和模型路由 |
| Bridge | 负责请求编排、轮次管理和上下文注入 |

所有模块通过公开接口协作，不直接依赖其他模块的内部数据库结构。

# 二、总体数据模型

## 2.1 三层记忆结构

M04 使用三层逻辑结构：

### Evidence：证据层

保存记忆产生的原始依据。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| evidence_id | string | 唯一标识 |
| source_ref | string | 原始消息或来源引用 |
| subject_id | string | 信息主体 |
| conversation_id | string | 来源会话 |
| content_ref | string | 原始内容引用 |
| recorded_at | datetime | 系统记录时间 |
| source_type | enum | 消息、用户纠正、导入等 |
| permission_ref | string | 权限引用 |

证据层必须保留来源可追溯性。

Observation 不得被当作原始证据。

### Fact/Event：事实与事件层

将 Evidence 转换为结构化事实和事件。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| memory_id | string | 唯一标识 |
| subject_id | string | 主体 |
| memory_type | enum | fact / event |
| content | object | 结构化内容 |
| claim_type | enum | explicit / inferred / uncertain |
| valid_from | datetime | 现实有效起点 |
| valid_to | datetime/null | 现实有效终点 |
| recorded_at | datetime | 系统记录时间 |
| evidence_refs | string[] | 来源证据 |
| confidence | number | 置信度 |
| version | integer | 记录版本 |
| lifecycle_state | enum | 生命周期状态 |

Fact/Event 保留历史信息，不因新信息到来就直接覆盖旧记录。

### Observation：综合认识层

Observation 是多个 Fact/Event 的综合结果。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| observation_id | string | 唯一标识 |
| subject_id | string | 主体 |
| topic | string | 主题 |
| summary | string | 综合认识 |
| fact_refs | string[] | 关联事实 |
| event_refs | string[] | 关联事件 |
| evidence_refs | string[] | 来源依据 |
| confidence | number | 综合置信度 |
| valid_from | datetime | 有效起点 |
| valid_to | datetime/null | 有效终点 |
| recorded_at | datetime | 系统记录时间 |
| version | integer | 版本 |
| lifecycle_state | enum | 生命周期状态 |

Observation 可以被重新生成或修订，但必须保留来源和版本关系。

## 2.2 Cue Anchors：检索入口

Cue Anchors 属于派生检索数据，不是第四种权威记忆。

用于为同一条记忆建立多个语义检索入口。

建议字段：

- anchor_id
- target_memory_id
- target_memory_type
- anchor_text
- anchor_type
- source_refs
- created_at
- policy_version
- index_version

规则：

1. 一个记忆允许存在多个 Cue Anchors。
2. Cue Anchors 不得脱离目标记忆单独成为事实。
3. 可以重新生成和重建。
4. 删除目标记忆时同步失效。
5. 不允许通过 Anchor 绕过权限检查。

# 三、时间与版本模型

## 3.1 时间字段

必须区分：

- recorded_at：系统什么时候知道这件事。
- valid_from：这件事从什么时候开始成立。
- valid_to：这件事什么时候结束。
- superseded_at：这条记忆什么时候被新版本替代。

系统记录时间与现实有效时间不能混为一谈。

## 3.2 当前视图

M04 负责构建 Current Memory View。

视图包含：

- Current：当前有效信息。
- Historical：历史信息。
- Event：事件信息。
- Uncertain：尚未解决的信息。

不确定信息不能被自动选成确定事实。

无关当前问题的冲突不应全部暴露给对话模型。

## 3.3 版本发布

采用：

**独立构建 → 校验 → 原子发布。**

规则：

1. 旧稳定视图持续可读。
2. 新视图独立构建。
3. 校验失败时保留旧视图。
4. 校验通过后原子发布。
5. 旧任务不能覆盖更新版本。
6. 记录 Evidence、Provider 和 Policy 版本。
7. 支持失败恢复。

## 3.4 对话轮次快照

每轮 Recall 开始时固定一个视图版本。

建议轮次记录：

- turn_id
- view_version
- request_id
- policy_version
- created_at

同一轮对话的扩展请求使用相同视图版本。

下一轮才使用新发布的视图。

但权限撤销和删除优先于快照一致性。每次扩展都必须重新执行当前权限检查。

# 四、记忆整合与更新机制

## 4.1 Decision Provider

M04 使用可替换的 Decision Provider。

支持：

- Rule Provider
- LLM Provider
- Hybrid Provider

统一输出：

| 字段 | 说明 |
|---|---|
| relation_type | 判断出的关系 |
| target_memory_refs | 目标记忆 |
| confidence | 置信度 |
| evidence_refs | 证据引用 |
| explanation | 简要判断依据 |
| suggested_action | 建议动作 |
| provider_id | Provider 标识 |
| policy_version | 策略版本 |

Provider 只负责提供判断，不允许直接写入数据库。

## 4.2 更新判断

候选记忆进入 M04 后，判断：

1. 是否为新记忆。
2. 是否与已有记忆重复。
3. 是否补充已有信息。
4. 是否代表时间演变。
5. 是否与已有事实冲突。
6. 是否需要生成或更新 Observation。

冲突类型至少包括：

- duplicate
- complement
- temporal_evolution
- contradiction
- topic_related

主题相关不等于证据支持。

## 4.3 Observation 形成规则

- 单次清晰表达可以生成候选，但不自动代表稳定认识。
- 多次独立表达可以提高置信度。
- 跨场景重复证据可以增强稳定性。
- 用户明确要求记住的信息提高处理优先级。
- 冲突未解决时进入 uncertain 或 pending。
- Observation 必须能够追溯到 Fact/Event/Evidence。

> **口径引用**：**"独立表达"的判定口径（时间窗口、来源独立性、批次合并规则）以 M03 §8 为准**，M04 不另行定义。M04 只负责消费该口径产出的证据强度，用于判断 Observation 是否达到形成或更新条件。

## 4.4 纠正机制

明确用户纠正优先处理。

规则：

1. 保留原始记录。
2. 标记旧记录已修订。
3. 创建新版本。
4. 记录纠正时间和来源。
5. 更新依赖 Observation。
6. 复杂语义纠正可以使用 LLM。
7. 权限仍由 M05 判定。

模型建议的纠正不能直接覆盖正式记忆。

# 五、关系维护与依赖重算

## 5.1 关系类型

支持：

- support：证据支持。
- complement：信息补充。
- temporal_evolution：时间演变。
- topic_related：主题相关。

建议字段：

- relation_id
- source_ref
- target_ref
- relation_type
- evidence_refs
- confidence
- created_at
- provider_version
- lifecycle_state

## 5.2 依赖维护

Fact/Event 发生变化时，沿依赖关系寻找受影响的 Observation。

处理原则：

- 剩余证据仍然支持：保留 Observation。
- 证据不足：标记 uncertain。
- 内容已经变化：重新生成 Observation。
- 关系失效：标记失效并重新评估。

只重算受影响部分，不默认全量重建。

## 5.3 Dream 关系候选入口（设计边界预留）

Dream 可以提出关系候选，但**不直接写入 Relation**。

规则：

1. **M04 是关系候选的后续处理接收方**，候选进入 M04 既有的候选处理流程（`processCandidates`）。
2. Dream 提交的关系候选 `claim_type` **必须标记为 `inferred` 或 `uncertain`**，不得标记为 `explicit`。
3. **不得直接生成 `support` 关系**。Dream 的联想属于待确认线索，不是证据支持关系。
4. 候选必须保留来源引用（引用的原始记忆标识），并受 M05 权限约束。
5. Dream Report 本身的存储由 **M01** 负责（见 M01 D2），不在 M04 范围内。

> **实施边界**：本节只预留设计边界。第一版是否实际开放该入口，按 M04 既有阶段规划执行，不因本节增加实施任务。

# 六、模型调用与资源管理

## 6.1 Rule-first，LLM-enhancement

规则负责：

- 数据校验。
- 权限流程。
- 时间计算。
- 版本管理。
- 任务调度。
- 资源预算。
- 正式写入约束。

大模型负责：

- 复杂语义去重。
- 复杂关系判断。
- Observation 综合。
- 反思。
- 模糊表达理解。

模型提出判断，规则验证，M04 协调，M01 正式写入。

## 6.2 Model Gateway

统一模型调用入口。

负责：

- Provider 管理。
- 模型选择。
- 并发控制。
- 超时。
- Token 预算。
- 资源预算。
- 模型升级与降级。
- 调用日志。

不绑定 DSH 或特定模型厂商。

## 6.3 分级模型路由

- 普通语义判断：轻量模型。
- 复杂冲突判断：较强模型。
- 复杂 Observation 综合：较强模型。
- 高风险、低置信度任务：允许升级。

升级后仍不确定时进入待审核。

## 6.4 降级策略

模型失败时：

1. 能由规则完成的任务继续执行。
2. 必须依赖语义判断的任务进入待处理队列。
3. 达到等待上限后进入超时或人工检查状态。
4. 不得用低质量结果覆盖旧 Observation。
5. 当前聊天不得无限等待后台任务。

## 6.5 模型输出管理

调用记录至少包含：

- request_id
- task_id
- provider_id
- model_id
- model_version
- policy_version
- duration_ms
- validation_status
- result_status

原始模型输出与校验后的结构化结果分开保存。

格式错误可以有限修复或重试。

证据冲突或置信度不足进入待审核。

# 七、任务调度与恢复

## 7.1 统一任务队列

所有后台任务使用统一调度系统。

任务类型：

- candidate_processing
- observation_update
- `integrity_reflection`（内部一致性维护；原 `reflection`）
- relation_maintenance
- view_build
- index_maintenance
- quality_check
- backup_check

> **术语说明**：`integrity_reflection` 指 M04 的**记忆库内部一致性维护**（依赖重算、质量检查、视图校验）。它与 Dream 的"记忆漫游与反思"是不同功能，**不得共用任务标识**。Dream 相关任务不在此任务类型列表中。

## 7.2 优先级

| 优先级 | 任务 |
|---|---|
| P0 | 权限撤销、删除和安全状态变化 |
| P1 | 当前对话必要的记忆更新 |
| P2 | 普通提取、视图构建 |
| P3 | 内部一致性维护、整理、索引优化 |

P0 安全处理分为：

- 同步安全阶段：阻断访问、更新权限状态、缓存失效。
- 异步维护阶段：清理索引、关系、派生视图和物理数据。

P0 不得单纯依赖普通后台队列。

## 7.3 任务可靠性

支持：

- 任务去重。
- 幂等执行。
- 持久化任务状态。
- 阶段检查点。
- 指数退避重试。
- 最大重试次数。
- 任务取消。
- 任务过期。
- 死信处理。
- 崩溃恢复。
- 每类任务独立并发上限。
- 防止低优先级任务永久饥饿。

## 7.4 任务状态

建议状态：

`queued → ready → running → succeeded`

异常状态：

`retry_wait / paused / cancelled / expired / dead_letter`

每个任务记录：

- task_id
- task_type
- priority
- idempotency_key
- dependency_refs
- input_version
- checkpoint
- retry_count
- max_retries
- status
- created_at
- updated_at
- error_code

## 7.5 阶段恢复

每种任务定义自己的执行阶段。

失败后：

- 从有效检查点恢复。
- 检查输入版本。
- 检查依赖是否仍然有效。
- 保证重复执行不会产生重复副作用。
- 超过重试上限进入死信队列。

## 7.6 任务依赖 DAG

采用有向无环图描述任务依赖。

- 前置任务成功后，下游任务才可执行。
- 无依赖任务允许并行。
- 前置任务失败时，下游暂停。
- 上游版本变化时，使受影响的下游任务失效。
- 禁止循环依赖。
- 任务取消后检查已完成阶段和下游任务状态。

# 八、视图生产机制

## 8.1 触发策略

采用事件、定量、定时混合触发：

- 达到变更数量阈值时启动。
- 等待时间超过阈值时启动。
- 重要纠正、删除、权限变化立即触发。
- 定时检查遗漏任务和过期状态。

具体阈值由策略配置管理，不在业务代码中写死。

## 8.2 增量构建

优先只处理受影响的 Observation 和关系。

完整构建作为恢复和一致性重建手段。

## 8.3 发布

新视图必须完成：

- 字段完整性检查。
- 来源引用检查。
- 权限状态检查。
- 版本检查。
- 关系一致性检查。

全部通过后才能原子发布。

# 九、生命周期管理

## 9.1 状态拆分

不采用单一生命周期枚举覆盖全部状态。

分为四个维度：

| 维度 | 状态示例 |
|---|---|
| 审核状态 | candidate / pending / approved |
| 有效状态 | active / expired / superseded |
| 存储状态 | normal / archived / deleted |
| 权限状态 | authorized / revoked |

各状态组合必须经过合法性校验。

## 9.2 生命周期规则

M03 负责候选生成。

M04 负责生命周期判断和状态流转协调。

M05 负责权限判定。

M01 负责正式数据存储、修改和删除。

## 9.3 删除

**删除职责分工（跨模块统一）**

| 职责 | 模块 |
|---|---|
| 判断记忆是否应进入删除生命周期 | M04 |
| 检查删除操作是否有权限 | M05 |
| 持久化删除状态 | M01 |
| 执行物理清理 | M01 |
| 管理删除任务及其状态 | Core 统一任务体系 |

M04 可以提出逻辑删除、状态变更或清理请求，但**不能直接操作底层数据库物理删除**。

删除流程必须保留以下环节：

1. 逻辑删除立即阻断 Recall。
2. M05 权限检查。
3. M01 持久化删除状态。
4. 后台物理清理。
5. 索引、缓存和派生数据清理。
6. 失败恢复及防止删除内容复活。

必须考虑受影响的派生对象：

- Evidence
- Fact/Event
- Observation
- Relation
- Cue Anchors
- Recall 索引
- 缓存
- 历史版本
- 备份与恢复

已删除内容不得通过旧快照、索引或备份重新进入 Recall。

> **恢复与防复活的统一权威**：删除状态恢复与防复活校验的完整流程见 **M01 D8**。本节只定义 M04 侧的职责边界与受影响对象清单，不重复定义恢复步骤。

# 十、Recall 协作机制

M02 负责完整 Recall。

M04 提供：

- 当前 Observation。
- **关系一跳邻居查询**（不做多跳遍历，见 §12.4）。
- 历史版本查询能力。
- Evidence 引用扩展。
- 当前视图版本信息。

默认返回简洁结果。

内部保留结构化选择依据，包括：

- 相关性。
- 时间。
- 来源。
- 关系。
- 版本。
- Provider。

调试、审计和明确请求时才展开。

## 10.1 受控自主扩展

Chat LLM 可以请求 Bridge 追加 Recall。

Bridge 负责转发。

Core 最终决定：

- 是否允许访问。
- 返回哪些记忆。
- 使用哪个版本。
- 是否允许展开 Evidence。
- 是否超过调用预算。

**第一版纳入受控的 DSH 主动 Recall 能力**（与 M02 D1 / D16 一致）。该能力为受控能力，不是无限制工具开放。

实施约束：

1. **工具调用由 Bridge 转交**，DSH 不直接连接 Memory Core 内部服务。
2. **M02 负责检索**，主动检索与自动预检索共用同一检索服务。
3. **M05 负责权限**，是唯一权限判定权威。
4. **不允许 DSH 直接访问 SQLite、LanceDB** 或任何底层存储。
5. 限制单轮调用次数、总检索预算和重复调用。
6. 每次调用必须使用 Bridge 提供的可信身份。
7. 权限检查失败时拒绝返回受保护记忆。

所有扩展均为只读操作。

> **跨模块依赖**：DSH 主动 Recall 的实现依赖 M02 的检索服务与预算控制（M02 D7 / D16）、M05 的权限判定（M05 §10）、Bridge 的工具调用转交能力。M04 不承担检索与判权实现。

# 十一、备份与恢复

采用三层策略：

### 数据备份

保护 Evidence、Fact/Event、Observation 和关系数据。

### 任务恢复

保护任务队列、执行状态和检查点。

### 一致性重建

索引、缓存、Cue Anchors 和当前视图允许从权威数据重建。

## 11.1 防止删除内容复活

> **恢复顺序的权威定义见 M01 D8。** 本节不重复定义完整恢复步骤，只补充 M04 侧的派生数据要求。

M04 侧要求：

1. **清理已删除内容的派生索引**（Observation、Relation、Cue Anchors、当前视图中的相关引用）。
2. **重建缓存前先执行权限检查**，不得让缓存绕过最新删除状态。
3. **无法确认删除状态时拒绝读取**。
4. **权限状态不明确时默认拒绝访问**。
5. **已删除内容不得通过索引重建、缓存恢复或历史版本复活**。

备份需要版本、时间和校验值。

## 12.4 关系查询接口（一跳邻居）

`listNeighbors(memory_refs, relation_types)`

> **名称仅作设计示例，不代表最终 API 已冻结。**

职责定位：**M04 只提供关系查询能力，返回指定记忆的一跳邻居，不自行递归遍历，不持有关系扩展总预算。**

输入（方向示意，不冻结字段）：

- request_id
- turn_id
- view_version
- memory_refs：查询起点记忆集合
- relation_types：需要查询的关系类型

输出（方向示意，不冻结字段）：

- relation_refs
- related_memory_refs：**一跳**邻居
- evidence_refs
- status

**职责边界：**

| 事项 | 负责模块 |
|---|---|
| 是否扩展、扩展方向、L0/L1/L2 遍历 | M02 |
| 扩展结果去重 | M02 |
| 本轮关系扩展总预算 | M02（唯一持有者） |
| 何时停止扩展 | M02 |
| 提供一跳邻居、关系类型与关联对象 | M04 |

说明：

- 本接口**不接收** `depth_limit` 与 `result_budget`。多跳遍历与预算裁剪由 M02 在调用本接口的基础上自行控制。
- 每次调用本接口返回的关联对象，仍需由 M02 逐条提交 M05 权限检查。
- 本接口不创建或修改关系。

所有接口都需要：

- 参数校验。
- 权限检查。
- 请求幂等。
- 版本校验。
- 错误码。
- 执行日志。

# 十六、质量评估

采用三层评估：

1. 数据质量：字段、来源、权限、时间。

大模型辅助抽样。

# 十七、异常处理与恢复

| 异常 | 处理 |
|---|---|
| 模型不可用 | 规则降级或任务等待 |
| 模型格式错误 | 有限修复或重试 |
| 模型证据冲突 | pending / uncertain |
| 视图构建失败 | 保留旧版本 |
| 版本冲突 | 拒绝覆盖并重新评估 |
| 任务崩溃 | 检查点恢复 |
| 上游版本变化 | 使相关下游任务失效 |
| 权限撤销 | 立即阻断访问 |
| 删除失败 | 保持逻辑删除，重试物理清理 |
| 备份恢复 | 重放删除状态并重新校验权限 |

任何异常都不能导致未经授权的数据被读取，也不能让不确定模型输出覆盖稳定记忆。

# 十九、实施阶段规划

> **关于 DSH 主动 Recall**：第一版纳入受控的 DSH 主动 Recall 能力（见 §10.1）。M04 在本能力中的职责是**提供当前 Observation、关系一跳邻居查询、视图版本与权限协作**，不承担检索实现与判权实现。检索与预算由 M02 负责，权限由 M05 负责，工具转交由 Bridge 负责。

## Phase 1：基础记忆整合

必须实现：

- M03 候选接入。
- Fact/Event 更新。
- Observation 创建和更新。
- 基础关系维护。
- 规则优先机制。
- M01 写入接口。
- M05 权限协作。
- 基础日志。

## Phase 2：版本与任务可靠性

必须实现：

- 视图构建。
- 原子发布。
- 轮次快照。
- 统一任务队列。
- 幂等、重试和检查点。
- 依赖 DAG。
- 删除和权限撤销保护。

## Phase 3：模型增强

接入：

- Decision Provider。
- Model Gateway。
- 分级模型路由。
- 复杂语义判断。
- Observation 综合。
- 内部一致性维护（`integrity_reflection`）和质量评估。

保留规则降级。

## Phase 4：运行维护

实现：

- 集中配置与策略版本。
- 健康监控。
- 备份与恢复。
- 关系一跳邻居查询（`listNeighbors`，供 M02 的多跳遍历使用）。
- 自适应调优建议。
- 质量统计。

> **DSH 主动 Recall 的跨模块依赖**：本能力的可用前提是 M02 的检索服务与预算控制、M05 的权限判定、Bridge 的工具调用转交均已就位。M04 侧只需保证 §10.1 所列的只读扩展接口与权限协作可用，**不因此新增独立实施阶段**。具体排期以 M02、M05、Bridge 的实施进度为准。

## Phase 5：后续增强

预留但不要求首版完整实现：

- 更复杂的 Cross-Encoder 重排。
- 多模型协同。
- 高级自适应调优。
- 大规模压力测试。
- 更复杂的跨记忆推理。
- Dream 关系候选入口的实际开放（设计边界见 §5.3）。
