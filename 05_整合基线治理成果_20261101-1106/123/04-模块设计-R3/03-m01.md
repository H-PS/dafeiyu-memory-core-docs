# 一、模块定位

## 1.1 设计目标

M01 是 Memory Core 的基础存储模块，负责正式记忆及相关系统数据的持久化、索引维护、数据一致性、备份恢复和存储生命周期管理。

核心目标：

1. 正式记忆可靠保存。
2. 为语义检索、全文检索和结构化查询提供基础能力。
3. 保证 SQLite 与外部索引最终一致。
4. 支持记忆版本、历史追溯和删除。
5. 支持索引重建、数据迁移和备份恢复。
6. 提供统一的数据访问接口。
7. 保留未来存储和检索技术升级空间。

## 1.2 职责边界

| 模块 | 职责 |
|---|---|
| M01 | 数据持久化、索引、事务、备份、恢复 |
| M02 | Recall 查询理解、召回、排序及结果组织 |
| M03 | 记忆提取与候选生成 |
| M04 | 记忆整合、反思、Observation 与视图维护 |
| M05 | 权限判断、授权、撤销和访问控制 |
| Bridge | QQ 消息接入、身份上下文、调用 Core |
| DSH | 对话生成 |
| Dream | 记忆漫游、反思及 Dream Report 生成 |

M01 不负责判断记忆是否真实、是否值得保留、是否应该合并，也不自行决定权限。

# 二、存储总体架构

## 2.1 D1：双存储架构

采用 SQLite + LanceDB。

**SQLite 是唯一权威数据源。**

负责：
- 正式记忆；
- Evidence；
- Fact/Event；
- Observation；
- Relation；
- Cue Anchor 元数据；
- Dream Report；
- 权限关联及生命周期状态；
- 任务与检查点；
- Outbox；
- 变更记录。

**LanceDB 是检索型向量存储。**

负责：
- Embedding 向量；
- 向量检索元数据；
- 必要的检索文本投影；
- 向量索引管理。

LanceDB 不拥有正式记忆的最终解释权。

SQLite 与 LanceDB 不假设存在跨数据库原子事务，通过 SQLite Outbox、幂等同步、失败重试和索引重建实现最终一致性。

## 2.2 D2：存储对象

M01 提供以下对象的持久化能力：

| 对象 | 属性 | 主要来源 |
|---|---|---|
| Evidence | 原始证据 | Retain 流程 |
| Fact/Event | 正式事实与事件 | M03 候选及后续审核 |
| Observation | 综合理解和当前视图 | M04 |
| Relation | 记忆关联 | M04 |
| Cue Anchor | 辅助检索锚点 | M04 |
| Dream Report | 梦境报告 | Dream |
| Recall Cache | 可重建的持久化检索缓存 | Recall 流程 |
| Task/Checkpoint | 后台任务及检查点 | Core Scheduler |
| Change Log | 变更记录 | M01 |

这些对象不要求全部使用相同的数据表或存储形式。

**Recall Cache 的定位（D2 补充）**

Recall Cache 是**可重建的持久化缓存**，不是正式记忆：

- 可以持久化于 SQLite，以便进程重启后继续复用未过期且仍然有效的中间检索候选；
- 缓存内容全部可从权威数据重新生成，不属于不可重建数据；
- 不参与正式记忆备份（见 D8）；
- 不具有独立权限，不得作为授权依据；
- 权限、删除和状态发生变化时必须失效；
- 进程重启后复用缓存，仍必须经过最新状态校验与 M05 权限验证。

缓存内容与失效时机的策略由 M02 决定，持久化与清理由 M01 执行。

**Dream Report 的定位**

Dream Report 由 Dream 生成并提交，M01 只负责持久化。Dream Report 与正式事实记忆分开存放，不参与普通 Recall 的事实召回，具有独立生命周期（见 D27）。

## 2.3 D3：写入责任

采用统一存储入口、模块负责业务判断、M01 负责持久化的模式。

- M03 提交候选数据，但候选不能直接变成正式记忆。
- M04 负责正式记忆整合、Observation 和关联更新。
- Dream 负责提交 Dream Report。
- Core Scheduler 负责任务和检查点。
- M05 负责权限判断。
- M01 负责格式、完整性、事务和关联校验。

业务模块不得直接访问 SQLite 或 LanceDB。

## 2.4 D4：SQLite 数据组织

采用关系型核心表 + 有限 JSON 扩展字段。

建议的数据表：

```text
evidence
memories
observations
relations
cue_anchors
dream_reports
tasks
task_checkpoints
outbox
change_log
```

说明：

- `memories` 主要存放 Fact/Event。
- 核心字段必须结构化。
- 类型特有的非关键属性可以放入 JSON。
- 权限、版本、生命周期和关联约束不能仅依赖 JSON 保存。
- 具体 SQL Schema 尚需结合实现进行最终审查。

## 2.5 D5：ID 与关系

正式对象使用 UUIDv7。

要求：

- ID 不编码 QQ 号、群号或权限信息。
- 不使用 SQLite rowid 作为业务 ID。
- LanceDB 使用对应的稳定来源 ID。
- 关联通过显式关系表维护。
- SQLite 使用外键约束。
- 删除、撤销时能够定位受影响的派生对象。

数据库中存在关联，不代表获得了访问授权。权限仍由 M05 决定。

# 三、事务、一致性与生命周期

## 3.1 D6：事务和一致性

SQLite 负责权威数据的事务原子性。

以下操作应在 SQLite 事务中完成：

- 正式记忆变更；
- 版本更新；
- 关系变更；
- 删除状态变更；
- 任务及检查点更新；
- Outbox 事件写入。

索引同步由后台任务执行。

基础要求：

- WAL 模式；
- Busy Timeout；
- 短事务；
- 幂等操作；
- 乐观并发控制；
- 版本校验；
- 失败重试；
- Dead Letter 与人工检查。

旧任务不得覆盖新版本。

## 3.2 D7：删除、归档与生命周期

存储状态建议：

- Active；
- Archived；
- Superseded；
- Deleted。

注意：这些状态不替代 M04 的多维生命周期状态，也不替代 M05 的权限状态。

**删除职责分工（跨模块统一）**

| 职责 | 模块 |
|---|---|
| 判断记忆是否应进入删除生命周期 | M04 |
| 检查删除操作是否有权限 | M05 |
| 持久化删除状态 | M01 |
| 执行物理清理 | M01 |
| 管理删除任务及其状态 | Core 统一任务体系 |

M04 可以提出逻辑删除、状态变更或清理请求，但**不能直接操作底层数据库物理删除**。M01 负责删除状态的持久化与物理清理的执行，Core 统一任务体系负责删除任务及其状态的调度管理。

删除流程：

1. M04 判断该记忆是否应进入删除生命周期，并提出删除请求。
2. M05 检查删除权限。
3. SQLite 事务标记 Deleted。
4. 递增版本。
5. 创建清理任务（由 Core 统一任务体系调度）。
6. Recall 立即屏蔽该对象。
7. 后台清理 LanceDB、FTS5、缓存和派生数据。
8. 检查关联 Observation、Relation 和 Cue Anchor。
9. 清理失败继续重试，不能恢复访问。

归档数据保留，但不参与普通 Recall。

Superseded 数据保留历史，不默认作为当前事实返回。

删除和授权撤销不能被历史版本或索引重建绕过。

**删除与恢复的统一权威**：删除状态恢复与防复活校验的完整流程见 **D8**。M04、M05 只保留各自模块特有的要求，不重复定义完整恢复步骤。

## 3.3 D24：版本持久化

业务层的新旧记忆判断由 M04 负责。

M01 只提供：

- 版本递增；
- 历史版本持久化；
- 变更来源记录；
- 原子更新；
- 乐观并发控制；
- 冲突检测。

M04 已确定的规则包括：

- 用户纠正优先；
- 旧记录标记为 superseded/corrected；
- 保留来源和纠正关系；
- 区分记录时间与事实有效时间；
- Observation 独立构建、验证和发布；
- 旧任务不能覆盖新视图。

M01 不重复实现上述业务判断。

## 3.4 D36：读取一致性与快照

采用固定视图版本 + 实时权限复核。

- Recall 开始时由上层确定视图版本。
- M01 按指定版本读取。
- 同一轮扩展使用同一版本。
- 不长期占用 SQLite 读事务维持整轮对话。
- 权限撤销与删除状态实时生效。
- 版本不存在或无法确认时，不使用不可靠快照。

# 四、索引与检索基础设施

## 4.1 D14：多通道检索基础

提供三种基础检索能力：

| 通道 | 技术 | 职责 |
|---|---|---|
| 向量检索 | LanceDB | 语义相似检索 |
| 全文检索 | SQLite FTS5 | 关键词、名称、型号 |
| 结构化查询 | SQLite | 时间、类型、状态及范围 |

M01 提供检索基础能力。

多通道融合、排序、预算和最终召回策略由 M02 决定，不提前冻结。

## 4.2 D15：向量索引单位

主要以单条正式记忆对象为向量索引单位。

- Fact/Event：主要索引对象。
- Observation：主要索引对象。
- Evidence：必要时按语义边界切块。
- Relation：第一版不独立向量化。
- Cue Anchor：辅助索引。
- Dream Report：独立索引，不与正式事实混合。

Evidence 分块必须保留 `evidence_id` 和 `chunk_id`。

向量记录保留来源 ID、类型、版本及必要权限元数据。

## 4.3 D16：Embedding 模型管理

- 第一版使用一个默认模型。
- 模型可替换。
- 不同模型的向量不能混用。
- 记录模型名称、版本、维度和 Embedding 版本。
- 模型变更需要重新生成向量。
- 新索引单独构建，验证通过后切换。
- 保留旧索引用于回退。

记录模型版本、维度、索引迁移、失败、切换和回滚日志。

## 4.4 D17：Embedding 生成与更新

采用批量优先、增量更新、失败可恢复的模式。

- 初次从 SQLite 批量生成。
- 新记忆增量生成。
- 检索相关内容变化才重新计算。
- 仅修改无关字段不触发重新 Embedding。
- 删除与撤销操作优先更新索引。
- 失败保留待处理状态。
- 支持批次限制、并发限制、重试和断点恢复。

## 4.5 D18：向量索引类型

第一版采用 FLAT 精确向量检索。

暂不提前引入 ANN。

以后根据真实测试数据比较：

- 检索耗时；
- Recall 质量；
- 构建成本；
- 数据规模；
- 资源占用。

再决定是否采用 IVF、HNSW 等索引。

## 4.6 D19：向量记录结构

建议字段：

```text
vector_id
source_id
source_type
source_version
embedding
embedding_model
embedding_version
content_hash
created_at
updated_at
```

LanceDB 仅保存检索所需的数据，不保存完整权威记忆副本。

必要时可以保存精简检索文本，但最终正式内容必须回到 SQLite 获取。

检索流程：

```text
LanceDB 返回候选 ID
        ↓
SQLite 查询正式对象
        ↓
检查最新版本与生命周期
        ↓
M05 进行权限校验（本请求内符合复用条件的可复用）
        ↓
返回允许使用的记忆
```

> **权限校验的复用边界**：同一 `request_id` 内，对同一 `(actor, memory_id, action)` 且授权依据与权限状态未变化的，可以复用已完成的判定结果；新增对象、新请求、权限版本变化、授权撤销、删除或状态变化时必须重新判权。完整规则见 **M05 §10.4**。

## 4.7 D20：检索元数据与过滤

支持：

- `source_type`
- `status`
- `created_at`
- `valid_from`
- `valid_to`
- `embedding_version`
- `scope_type`
- `scope_id`

采用两阶段过滤：

1. **检索前过滤**：基于 LanceDB / FTS5 元数据减少无效候选，属于性能优化，不构成授权。
2. **检索后权威校验**：查询 SQLite 最新状态与生命周期，并由 M05 进行权威权限复核。

两阶段过滤的权限规则：

- 检索前过滤只能排除候选，不能授予访问权；
- 检索后必须进行权威权限验证，LanceDB 中的权限元数据不能作为权限依据；
- 同一 `request_id` 内，符合复用条件（见 M05 §10.4）的对象可以复用已完成的判权结果，避免对同一条记忆无限重复计算；
- 权限状态发生变化（撤销、删除、共享失效、权限版本递增）时，必须使相关已判定结果失效并重新判权。

## 4.8 D21：中文全文检索

采用 SQLite FTS5 + 可替换中文分词器。

定位：

**FTS5 是关键词补充检索，不是完整的记忆理解机制。**

主要场景包括：

- 生活化模糊查询；
- 人名、地点和专有名词；
- 精确关键词；
- 型号和数字；
- 用户无法准确描述的历史事件。

向量检索负责语义相似和模糊表达。

结构化查询负责时间、类型和状态条件。

分词器版本纳入升级日志，原始文本不因分词而改变。

## 4.9 D22：Search Document

建立统一 Search Document 投影，作为 LanceDB 和 FTS5 的共同输入。

内容包括：

| 字段 | 处理 |
|---|---|
| 标题 | 纳入 |
| 正文 | 纳入 |
| 摘要 | 视情况纳入 |
| 标签 | 纳入 |
| 时间 | 元数据 |
| 来源 ID | 元数据 |
| 权限信息 | 过滤元数据 |
| 内部状态字段 | 不纳入检索正文 |

内容、标题、摘要或标签变化时重新生成投影。

权限和生命周期变化不必重新计算 Embedding，但必须更新过滤元数据。

## 4.10 D23：索引同步与重建

SQLite Outbox 驱动 LanceDB 和 FTS5 更新。

要求：

- 幂等任务；
- 版本防覆盖；
- 失败重试；
- 删除优先；
- 进程重启恢复；
- 全量索引重建；
- 索引切换前验证。

重建采用新索引空间，验证通过后再切换，避免直接破坏正在使用的旧索引。

# 五、备份、迁移与恢复

## 5.1 D8：备份与恢复

SQLite 权威数据必须备份，包括：

- Evidence；
- Fact/Event；
- Observation；
- Relation；
- 权限及撤销状态；
- 删除状态；
- 任务和检查点；
- Outbox；
- 必要的版本信息。

LanceDB 可以备份，但必须可重建。

Recall Cache 不备份。

采用 SQLite Backup API 或一致性快照，不直接复制正在运行的数据库文件。

**恢复顺序（跨模块统一权威流程）**

本顺序是 Memory Core 数据恢复与防复活的**唯一权威定义**。M04、M05、Dream 只保留各自模块特有的要求，不重复定义完整步骤。

1. 恢复 SQLite。
2. 完整性与 Schema 检查。
3. 恢复删除状态。
4. 恢复权限与撤销状态。
5. 恢复或重建 LanceDB。
6. 恢复 Outbox 和任务状态。
7. 检查关联及派生数据。
8. 确认安全后开放 Recall。

约束：

- 不能恢复已撤销的授权或已删除的记忆；
- 已删除内容不得通过索引重建、缓存恢复或历史版本复活；
- 权限状态不明确时默认拒绝访问；
- 恢复旧备份时，必须以最新有效的删除状态与撤销记录为准，旧备份中的授权不得覆盖更新的撤销结果。

## 5.2 D9：Schema 与迁移版本

分别管理：

- SQLite Schema 版本；
- LanceDB Schema、向量模型和索引版本；
- Core 数据格式版本。

迁移必须：

1. 检查当前版本和目标版本。
2. 检查迁移路径。
3. 迁移前备份。
4. 执行版本化迁移。
5. 验证结果。
6. 成功后更新版本。

支持幂等检查和复杂迁移检查点。

不要求日常支持向后迁移，必要时恢复备份。

## 5.3 D10：物理目录

建议目录：

```text
memory-core/
├── data/
│   ├── memory.sqlite
│   └── lancedb/
├── backup/
│   ├── sqlite/
│   └── lancedb/
├── runtime/
│   ├── tasks/
│   └── locks/
├── logs/
├── temp/
└── manifest/
    ├── schema-version.json
    └── storage-manifest.json
```

要求：

- 根目录可配置。
- 数据、运行、备份、临时文件和日志分离。
- 文件权限保护数据和备份。
- 日志不记录凭据及不必要的完整私人内容。
- 迁移时保留旧目录直到新目录验证通过。

## 5.4 D26：导入与导出

第一版支持：

- 完整备份与恢复；
- 按范围导出 JSON；
- 基础 JSON 导入；
- 格式版本标记；
- 导入预览和校验；
- 冲突报告，不自动覆盖。

导出保留必要的 ID、类型、正文、时间、来源、版本、生命周期和权限范围。

不导出访问令牌、密码和密钥。

导入不能自动赋予新的共享权限，不能绕过 M05。

覆盖现有数据库前必须二次确认。

## 5.5 D37：目录迁移

支持受控本地目录迁移。

迁移期间：

- 停止接收新存储任务；
- 等待关键事务完成；
- 保存任务检查点；
- 关闭连接；
- 复制并校验数据；
- 在新目录验证索引与关联；
- 成功后切换；
- 保留旧目录作为短期回退来源。

不支持运行中直接修改数据库路径，不支持在线热迁移和云端自动同步。

# 六、完整性、维护与运行管理

## 6.1 D11：数据完整性检查

写入时检查：

- 必填字段；
- 数据类型；
- ID 唯一性；
- 外键及关联；
- 版本规则；
- 内容 Hash；
- 向量维度和模型 ID。

周期性检查：

- SQLite Integrity；
- 外键；
- 孤立关联；
- LanceDB 映射；
- Outbox 积压；
- 备份完整性。

异常分级：

| 等级 | 情况 | 处理 |
|---|---|---|
| P0 | 权限、删除或权威信任不确定 | 阻断受影响访问 |
| P1 | SQLite 结构或权威数据损坏 | 暂停受影响功能并恢复 |
| P2 | LanceDB 索引问题 | 暂停向量检索并重建 |
| P3 | 缓存或派生数据问题 | 清理或重新生成 |

Integrity Checker 负责检测、报告、提交修复任务和验证，不直接猜测修复权威数据。

## 6.2 D12：并发与连接

- SQLite 多读并发，单写入调度。
- WAL 模式。
- 短事务。
- Busy Timeout。
- 写入任务排队。
- 删除和权限变更高优先级。
- Schema 迁移和修复独占维护。
- 每个工作单元使用合适的连接。
- 不跨任务共享事务连接。

LanceDB 查询可以并发，索引更新由同步任务协调。

## 6.3 D13：数据保护与加密

第一版采用简单保护，不建设复杂密钥管理系统。

- 操作系统文件权限保护数据库。
- 备份采用同等级访问保护。
- 不存储访问令牌、密码和密钥。
- 日志避免凭据和不必要的完整私人内容。
- 如需加密导出或备份，使用成熟轻量方案，不自行设计密码算法。
- 不把加密当作权限控制的替代品。

暂缓 OS 密钥库、SQLite 加密扩展和复杂密钥管理。

## 6.4 D27：自动维护

自动维护以清理可重建数据为主。

| 数据 | 策略 |
|---|---|
| Recall Cache | 过期清理（可重建的持久化缓存，见 D2） |
| 临时文件 | 定期清理 |
| 失败任务 | 超过重试上限后待处理 |
| 已删除记忆 | 异步清理 |
| 旧索引 | 新索引验证通过后清理 |
| FTS5 | 支持重建与优化 |
| 正式记忆 | 不因低访问频率自动删除 |
| Dream Report | 独立生命周期 |

维护任务使用 Core 统一调度体系，不额外创建调度器。

Recall Cache 的清理依据 M02 定义的失效与过期策略执行；M01 负责实际的持久化清理动作。缓存清理失败不得影响正式记忆，也不得因清理失败而改变任何权限状态。

## 6.5 D28：健康检查

第一版提供轻量健康检查。

检查：

- SQLite 状态；
- LanceDB 可用性；
- FTS5 可用性；
- Outbox 积压；
- Embedding 失败；
- 最近备份时间；
- 存储空间。

健康状态：

- 正常；
- 降级；
- 异常。

异常时按影响范围暂停相关能力。

## 6.6 D29：故障降级与恢复

原则：

**普通聊天尽量不中断，记忆功能按故障范围降级；权威数据或权限不可靠时拒绝访问。**

| 故障 | 处理 |
|---|---|
| LanceDB 不可用 | 暂停向量检索 |
| FTS5 不可用 | 暂停全文检索 |
| Embedding 不可用 | 暂停新向量生成 |
| Outbox 堆积 | 保留任务并重试 |
| SQLite 繁忙 | 有限等待与重试 |
| SQLite 损坏 | 暂停受影响的记忆读写 |
| 权限不确定 | 拒绝受影响访问 |
| 磁盘空间不足 | 暂停非必要写入和维护 |

恢复时先验证 SQLite、权限和删除状态，再恢复索引和任务。

## 6.7 D30：容量与性能

第一版不提前设定未经实测的容量上限。

采用：

- 批量事务；
- 分页读取；
- 批量 Embedding；
- 增量索引；
- 后台重建；
- SQLite 结构化索引；
- 低优先级维护。

不提前引入分布式数据库、Elasticsearch 或高级 ANN。

根据实际检索耗时、准确性、索引构建成本和资源占用决定升级。

# 七、统一接口与运行规范

## 7.1 D25：数据库访问接口

业务模块统一通过 M01 Storage API。

内部划分：

1. Storage API：基础操作入口。
2. Repository：SQLite 表和事务操作。
3. Index Adapter：LanceDB、FTS5 索引操作。

不引入复杂 ORM，不允许业务模块拼接 SQL 或直接维护向量索引。

M02、M03、M04 的具体接口尚未冻结。

## 7.2 D33：配置管理

配置文件集中管理，启动时校验。

配置分类：

- 存储路径；
- 检索参数；
- Embedding 模型；
- 任务并发和重试；
- 维护周期；
- 性能限制。

安全硬约束与可调参数分离。

模型和插件不能关闭权限、删除和访问保护规则。

重要配置记录版本，非法配置拒绝应用。

## 7.3 D34：进程模型

第一版采用本地单实例运行。

- Memory Core 独立进程。
- 内部模块按职责划分。
- SQLite 单写入调度，多读并发。
- Bridge 调用本地 Core 接口。
- 同一数据目录默认只允许一个写入实例。
- 实例锁必须能识别有效进程，不能仅凭锁文件存在就判定实例存活。

正常关闭时停止新任务、完成关键事务、保存检查点、关闭连接并释放锁。

## 7.4 D35：错误处理

统一错误分类：

- 参数错误；
- 数据不存在；
- 版本冲突；
- 权限拒绝；
- 暂时性存储错误；
- 索引同步失败；
- 数据完整性异常；
- 内部错误。

基础返回结构建议：

```text
success
data
error_code
message
retryable
request_id
```

具体 API 字段和调用协议待接口设计阶段确定。

失败不能伪装成成功；重试必须考虑幂等性。

## 7.5 D39：变更记录与运行日志

两者分开。

**Change Log：**

记录对象 ID、类型、操作、旧版本、新版本、来源和时间。

**运行日志：**

记录操作类型、结果、耗时、错误代码、任务 ID 和请求 ID。

重要变更记录与正式数据更新应处于同一 SQLite 事务。

不默认保存完整新旧正文，不允许日志成为已删除内容的旁路。

# 九、跨模块一致性审查

## 9.1 与 M03

|---|---|

## 9.2 与 M04

|---|---|

| Observation 构建 | M04 负责 |
| 纠正与新旧事实 | M04 负责判断，M01 保存版本 |
| Relation | M04 负责语义关系，M01 保存 |
| Cue Anchor | M04 生成，M01 保存 |
| 固定视图版本 | M04 管理视图，M01 提供读取 |
| 删除与派生对象 | M04 提供依赖关系，M01 提供持久化和清理 |

结论：一致，M01 不重复 M04 的业务判断。

## 9.3 与 M05

|---|---|

| 删除 | M05 授权，M01 持久化状态 |

| 备份恢复 | 先恢复权限、撤销和删除状态 |
