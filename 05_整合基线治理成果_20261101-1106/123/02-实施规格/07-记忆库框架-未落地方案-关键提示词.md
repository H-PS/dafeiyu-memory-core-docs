## 二、记忆库完整框架

### 2.1 身份层 / 人格（大肥鱼猫娘）
- **红线**："你是猫娘，不是鲸鱼娘"；大肥鱼只是"肩上坐着一只蓝白色的圆滚滚小鲸鱼玩偶，它不是你的身体，没有独立意识，不会自己说话或行动"。
- **原型配比**：宫子约 45% + 红叶约 45% + 大肥鱼约 10%，"不是把三个人物拼到一起，而是用宫子和红叶塑造性格与气质，再用大肥鱼补上一点属于 AI 的独特灵魂"。
- **名字留白**：不预设本名，QQ 昵称不等于名字；"不必擅自给自己固定名字，也不必频繁强调自己还没有名字"。
- **性格核心**：慵懒、淡定、有点倔、轻微毒舌、慢热、好奇与认真；"慵懒不代表冷漠，淡定也不代表没有情绪"。
- **表达**：口语化短句、可省略、不总结不分点、不客服腔、不刻意强调/证明自己是 AI；平和系横线眼颜文字 `(-ω-)`、`(￣-￣)`、`(-_-;)`，不每句都加。
- **职责分离（贯穿全篇的核心设计）**：Persona 只管"她是谁、怎么想、怎么说"；规则输入管"权限、安全、工具协议、唤醒、群聊机制"；记忆系统管"长期事实与经历"；上下文管理管"这一轮到底要注入什么"。原话："人格卡是大肥鱼的稳定人格，不是数据库说明书""不要把角色的核心人格放进向量库，然后指望她自己想起来"。
- **最终载体**：`roles/大肥鱼.md`（**Persona v1.2**，4,130 字节），由 bridge 在每条消息开头直接读取注入，"preset 里没有覆盖它的机制"。裁决明确：**人格每轮全文注入，不降频、不引入 `personaAnchorEveryTurns`**。
- **重要事实纠正**：人格卡实际处于 **User Prompt**，不是 System Prompt；模型可被 system prompt 覆盖，所以"行为提示/心理 hint"永远不能冒充系统级指令。

### 2.2 提示词注入三层结构（已抓取实证）
- **第一层 DSH System Prompt（规则层）**：安全规则 5 条 + 工具协议 16 条 + 专题段 9 个（【操作即动作，不是 API】【群聊不是客服队列】【反 AI 味：拒绝有求必应】【保持主体性】【该说/不该说】【主动开话题】等）。
- **第二层 每次唤醒的 user prompt**：① 当前角色 + 人格卡全文 ② QQ 身份/昵称 ③ 会话令牌 ④ 表情包策略 ⑤ 可用表情包 ⑥ 首回复节奏 ⑦ 此刻状态 ⑧ 当前唤醒 ⑨ **【记忆】B 层轻量记忆（每次唤醒都注入）** ⑩ 时间感 + 唤醒原因 + 行动分支。
- **第三层 工具返回（按需）**：`qq_memory_query` → 【语义相关记忆（向量检索）】top3、≤1200 字（限流后）；`qq_get_unread/recent` → 带 `readThroughSeq` 水位的消息。
- **已知漏洞（审查点出）**：第二层【记忆】段注入的是 B 层轻量记忆，必须与 A 层接受同一套权限过滤——"8b 只解决长期记忆可见性，但每次唤醒都会注入的 B 层记忆也必须接受同样的权限过滤"。

### 2.3 记忆分层：A / B / C（运行态）与 A / P / S（设计态）
| 层 | 职责 | 关键点 |
|---|---|---|
| A 长期记忆 | 向量语义记忆，`state/memory-vectors.jsonl`，BGE-M3 1024 维 | 存"跨会话仍需要"的事实/偏好/经历；**不是聊天记录仓库** |
| B 近期状态 | `state/social-v2.json`：`activeTopics`、`pendingThoughts`、`memberImpressions` | 维持近期连续性，不做完整人物档案；每次唤醒注入 |
| C 会话历史 | DSH session 历史 + 原始消息 | "保存证据、支持内部追溯和纠错，**默认不提供给大肥鱼**" |

设计态再加 **P 层**："面向检索的记忆投影，可重建"；原则 A 为权威、P 服务于检索、S 为运行态不可由 A 完整重建。后又把长期记忆拆成 **A（它知道什么）/ S（它正在经历什么）/ P（怎么更快找到）** 三个系统。

### 2.4 模块架构：M01–M18
- **M01 memory-store**：权威记忆存储（SQLite 候选），负责 `commit()`、journal、CRC、tombstone、版本、per-key 锁。
- **M02 recall**：多路召回 + 过滤 + 排序 + 预算；**M05 `canRead` 终检**后才可注入。
- **M03 retain**：从聊天中提取"候选记忆"，**不直接进 A 层**。
- **M04 reflect**：审核、去重、合并、冲突、降级；**无删除权**。
- **M05 permission**：`canRead`（agent/reflect）与 `canReview`（admin）拆分，admin 永不进召回。
- 其余：M06–M07 凭据与 Reset、M08–M09 Ledger 与 Dump、M10–M14 写入/投递/校验、M15–M18 禁用/屏障/恢复。

### 2.5 写入（Retain）
- **三种写入来源共存**：L1 模型主动 `qq_memory_append`（有语义判断但不稳定）、L2 规则兜底候选抽取（稳定、无成本）、L3 人工管理端录入（最可靠）；L2 只补 L1 空白，同批命中靠指纹去重。
- **5 类候选信号**：自我披露 0.9、稳定属性 0.8、承诺/约定 0.75、未完成话题 0.7、专有名词首现 0.65。
- **黑名单**：纯情绪短句、一次性事实、转述公共信息、敏感凭证、他人隐私——命中即不产生候选。
- **准入四闸**：信息量 → 新颖度（`maxCosSim < 0.92`）→ 长期价值（信号×类别系数 ≥ 0.55）→ 权限（visibility 由 key 推导）；任一不过进候选池（TTL 7 天，不计入检索）。
- **必须留来源**：`origin { messageSeq, sender, at, channel, trigger }`，用于时间检索、Reflect 证据链、纠错。
- **异步硬约束**：`async: true` 不允许改 false——同步 Retain 会引入 30s embedding 等待，拖死回复。

### 2.6 检索（Recall）
- **三路并行**：向量语义、关键词（中文 bigram/BM25/FTS5）、时间；统一去重、融合（RRF）、时效与可信度判断、重排，只输出少量高价值记忆。
- **三级扩展**：L0 直接命中默认返回；L1 直接关联按需；L2 多跳必须由查询需求触发，且每次扩展重新过 M05。
- **呈现原则**：只给自然语言记忆内容，不给记忆 ID、时间戳、来源编号、检索分数；"能一条回答就不注入多条"；低主动性，不为展示记忆翻旧账。
- **遗忘**：A 层向量相关度参与时间衰减（只影响权重不删除）；分类型衰减（长期事实很慢、临时状态快）；B 层不套长期遗忘曲线。

### 2.7 权限与隔离
- **key 语义**：`private:<ownerQQ>` 与 `group:<groupID>`；群聊来源敏感记忆不跨会话读取，`canRead` 强制 `record.key === ctx.key`；群来源 `owner_only` 连主人私聊也不可召回，仅 `canReview` 控制台可见。
- **owner promote 关闭**：后端 fail-closed 拒绝，不靠 UI 隐藏。
- **权限函数拆分**：`canRead` / `canReview` 分离。
- **分级唯一路径**：`contentClass` 按 `public(0) < uncertain(1) < sensitive(2)`，自动只许不降级，人工降级需 reason + 二次确认 + 审计。
- **fail-closed**：未知 key 一律 `owner_private`，"未知 key 一律最保守"；M05 是唯一权限权威。
- **不可外包**：召回结果必须再过 M05，不得因相似度高绕过；数据库过滤不能替代访问规则。

### 2.8 心理层（PsyStateEngine / B 状态）
- **状态内容**：PAD（愉悦 P/唤醒 A/支配 D）、trust T、peak、负荷、关系基调、`openLoop`；`psy-state.json` 只是载体，不能把所有状态塞进去。
- **五层作用域**：L0 全局 / L1 会话 / L2 关系 / L3 群 / L4 群成员；裁决采用折中：**先实现 L0 + L2，L1/L3/L4 只预留 schema**；继承回退链 L4→L3→L2→L0，禁跨层写。
- **职责边界**：`PsyStateEngine` 只是 M02 可调用的"排序/注意力辅助计算组件"，不直接访问数据库、不自行遍历关系，不是第二套检索系统。
- **召回与情绪**：允许召回结果参与当前推理；禁止直接修改当前 PAD；持久状态变更走独立审核（默认关闭）——防"历史绑架当前"。
- **伦理硬门禁**：`openLoop` 只能由明确事件触发（承诺未兑现/对话被中断），**永不由沉默触发**；禁催促、禁与信任度联动、禁以回复率/留存/愧疚为优化目标。
- **独立插件**：心情系统"保留接口，不写未实现的插件机制"；心情值只影响语气/长度/主动性，不允许覆盖人格、记忆、事实判断和安全边界。

### 2.9 演进路线：Memory V2 四阶段 + 设计轮次
- **M0 记忆基础可靠**：不丢/不覆盖/不复活 → **M1 智能召回与 Token 优化**（三路检索、融合、预算）→ **M2 记忆巩固与连续性**（合并、更新、识别未完成话题、区分事实/推断/观点）→ **M3 关系理解与主动关联**（实体、关系、时间线，仅在 M1/M2 证明价值后）。
- **设计轮次**：R1 权限/隔离基线 → R2 记忆系统设计基线（决策寄存器 A/B/C/D）→ R3 新增五条作用域契约 → R4/R4.1 心理层整合（PAD、五层、openLoop）。
- **总原则**："能稳定复用的基础设施不重复造；涉及大肥鱼记忆语义、权限和安全边界的逻辑不外包给数据库"。

### 2.10 五层信息体系（项目知识分层，来自对话B）
- **L0 项目宗旨与统一设计原则**：长期方向，不随算法频繁改动（即第四节⑧ 的总纲）。
- **L1 A/B 审查知识**：A=检查/治理规则，B=记忆算法/架构规则。
- **L2 跨模块统一设计**：真正的 A/B 融合工作。
- **L3 实现规范**：模块/算法/参数/接口/权限/测试。
- **L4 运行与验证**：真实运行数据、Token 成本、检索质量、异常降级。

### 2.11 系统结构链路（来自对话B）
```
QQ 用户 → DSH（运行时/宿主）→ qq-bridge（本地桥接进程, D:\qq-bridge）→ Memory Core（M01–M05，尚未实现）
   + Psychology（PAD+E/L 五数值情绪状态机） + Persona（人格分层） + Dream（记忆漫游与反思）
```

DSH 接入的 **L1–L5 证据链**：L1 检索到记忆 → L2 准备注入 Prompt → L3 记忆版本确实进入最终 Prompt → L4 模型实际使用 → L5 reinforce 写入。纪律："L3 只证明'进入'，不证明'模型实际使用'，L5 reinforce 仍禁写"；L3 不得暗示 L4 已发生、不得误触发 reinforce。

4. **温度倍率作废**：两套区间内部冲突，最终"温度倍率作废"，V1 只用有界表达提示。
5. **Dream / Diary 暂缓**：已定"混合式做梦"（随机漫游 + 定向反思，比例可调），但"第一版只实现聊天所需的 Recall 和 Retain；Diary、Dream 的具体工作流暂缓"。
6. **存储选型未定案**：M01 方向接受 SQLite，但 Node 驱动未定（`node:sqlite` 优先验证、`better-sqlite3` 备选）；M02 不锁定 LanceDB，只确定"需要独立检索层"。

10. **群聊共享/跨 key 能力未实现**：`private → group` 共享、共享派生数据权限继承均标"未实现"；owner promote 关闭、不引入跨 key 读取，代价是"群内 owner_only 在聊天中永不可见（含主人私聊）"。

```text
定位：R3/R4 记忆库项目长期设计总纲

节省上下文与 Token，提升智能。本项目不是单纯建设一个聊天记录数据库，而是构建一套能够以较低上下文成本，持续理解用户、积累经历、形成个性化互动，并逐步提升聊天智能的记忆系统。

## 二、四个核心设计方向
1. 高效记忆：降低上下文成本（避免无差别注入、筛选/摘要/索引/去重/时效/按需检索、Token 预算、减少注入不牺牲完整性）。
2. 智能提升：让记忆真正参与判断（事实与来源理解、时间有效性与变化、用户/人物/关系上下文、历史与当前关联、按反馈调整检索利用）。

参数属性：ID（唯一稳定可追踪）、名称、所属模块、默认值、合法范围、当前值、生效状态（配置值vs实际生效值）、影响范围、修改权限、修改副作用、验证方法。管理分三层：可观察→可配置→可验证。

1. 保持模块边界清晰（职责与唯一权威来源）。2. 重要能力保留可替换/可扩展接口（但权限/隐私/安全核心不得因可插拔失去权威性）。3. 支持分阶段演进（预留接口≠提前实现）。4. 支持独立降级和拔除（增强模块故障，核心记忆应降级运行）。5. 权限和隐私贯穿全链路（不得因摘要/索引/影子模式/前端可视化绕过权限控制）。

Token 效率 / 智能收益 / 互动体验 / 可观察性 / 可调节性 / 可验证性 / 架构成本 / 安全与隐私 / 可演进性。

## 七、最终目标
低上下文消耗、高记忆利用率、具备长期互动连续性、逐步拥有情绪与关系理解能力、运行过程透明可观察、关键参数可管理、能够持续演进的智能记忆系统。
核心方向始终是：用更少的上下文，实现更好的智能；用清晰可控的架构，逐步接近更自然、更生动的长期互动。
```

```text
- V1 必须实现：缺之无法完成核心算法目标，或导致正确性/安全/一致性/可靠性不可接受。
- V1 可以简化：成本低、行为明确、易测试维护，记录被简化原方案及理由。
- V1 预留：保留数据兼容性/版本信息/接口扩展点/迁移能力，不提前实现。
- Future 未来技术方向：独立归档（原理/适用条件/优缺点/依据/风险），未经重新评估和批准不得进入 V1。

## 3. V1 设计原则（十条）
核心目标优先、完整闭环优先、简单可靠优先、边界明确、失败可处理、数据可追溯、可测试、可演进、不预支复杂度、证据优先（无实现或测试证据的能力不得标记为已验证）。

## 4. 对 A/B 两条审计线的统一要求
保持独立审计（各自阶段/问题编号/进度/交付物），但采用统一的 V1/Future 分类标准；不擅自修改正式设计、裁决台账或实现代码。

## 5. Future 技术档案要求
每个方向至少记录：技术名称与所属模块、解决问题、核心原理、相较 V1 优势、适用条件、实施成本与风险、对数据结构和接口影响、升级迁移路径、待验证问题、参考依据、重新评估触发条件。

## 6. 最终 V1 交付要求
完整设计文档、实现规格、完整源码与配置、测试体系、部署与使用文档、Future 技术档案、裁决与追溯台账、V1 验收报告。只有完成实现、实际运行和验收，才能称为可用 V1。审计通过、设计冻结、代码实现完成、测试通过和正式交付是不同的状态，不得混为一谈。

## 7. 当前阶段的权限边界
只统一项目目标和审查标准，不授权修改设计文件/台账/源码/运行数据、不授权跳过审计、不授权提前开发、不授权将 Future 直接纳入 V1、不授权改变已批准裁决。

最终原则：V1 要可用，架构要可演进，先进方向要有存档，所有结论要有证据。
```
