# M02 检索算法实现规约（三层结构 · 防自行发挥）

> 生成：2026-11-04 ｜ 维护位置：`E:\[PROJECT]\work-交付包\13-M02检索算法实现规约.md`
> 地位：**实现约束文件，效力高于代码 AI 的"合理发挥"**。m01/m02 原文仍是设计权威；本文把已定算法边界收拢成三层结构，并明确"哪些是已裁决方向、哪些只是默认配置、哪些完全禁止自创"。

## 〇、三层结构总览（召回 / 融合排序 / 上下文构建）

后续讨论算法优化时，**不得把召回、排序、上下文压缩混成一个问题**；任何优化提案必须先声明属于哪一层。

```
用户输入
   │
   ▼
查询向量生成（EmbeddingService，模型可配置，不写死）
   │
   ├── 召回层 L1a：SQLite 结构化过滤（时间/来源/权限/生命周期条件）
   ├── 召回层 L1b：FTS5 关键词召回（专有名词/关键词/精确表达）
   └── 召回层 L1c：LanceDB FLAT 语义召回（生活化表达/模糊描述/语义相似）
             │
             ▼
   融合排序层 L2：RRF 融合 → 首版规则排序 → 去重 → 候选记忆筛选
             │
             ▼
   上下文构建层 L3：M05 权限终检 → Token Budget 控制 → 最终 Prompt
```

---

## 一、召回层（L1）：三路各司其职，禁止合并职责

| 通道 | 技术 | 职责 | 禁止 |
|---|---|---|---|
| 结构化过滤 | **SQLite** | 时间、来源、权限、生命周期等条件过滤 | 不得用元数据过滤替代 M05 权限判定（检索前过滤只是性能优化，不构成授权） |
| 关键词检索 | **SQLite FTS5**（+ 可替换中文分词器） | 专有名词、关键词、精确表达 | FTS5 是关键词补充检索，**不是完整的记忆理解机制**；不得把它当语义主力 |
| 语义检索 | **Embedding + LanceDB（设计点名；原型经 VectorStoreAdapter 可先用 sqlite 后端）** | 生活化表达、模糊描述、语义相似内容 | FLAT 精确检索；禁止 IVF/HNSW/任何 ANN；禁止 Cross-Encoder |

### Search Document（统一、版本化检索文档）——两路索引的共同输入

**不是**把数据库整条记录原样塞进向量库，而是为每条记忆构建统一检索文档：

- 标题、正文、标签、摘要（可选）；
- 时间、来源、权限、生命周期等作为**元数据**。

硬性要求：

1. **同一份 Search Document 同时喂给 Embedding 与 FTS5**——避免两套索引检索的内容不一致；
2. **内容变化 → 重建检索文档**（并触发向量重算：正文变了旧向量必然对不上新文本）；
3. **权限/生命周期变化 → 只更新过滤元数据**（不必重算向量）；
4. 检索文档带版本号，与 `manifest/schema-version.json` 关联。

## 二、融合与排序层（L2）：算法已定，参数未裁，禁止自创

### RRF 融合（方向已裁决）

公式（无需再做尺度归一，这正是选 RRF 的原因——不用强行把 BM25 分数与向量相似度拉到同一数值尺度）：

```
RRF(d) = Σ_{r∈R} 1 / (k + rank_r(d))
```

- `d`：某条记忆；`R`：检索通道集合；`rank_r(d)`：该记忆在通道 r 中的排名；`k`：平滑参数。
- **k=60 只是默认配置，不是已批准的最终参数**（B-004 教训：寄存器曾把"已确认"写错方向）。k 必须外置为 `rrf.k`，敏感性可实验，改值需用户裁决。

### 规则排序（首版唯一排序器）

- 首版**只允许**按已讨论因素做**确定性规则排序**：RRF 得分、时间衰减 F(t)、importance 权重、时效/有效性判断；
- **禁止**引入：Cross-Encoder、学习排序(LTR)、自创加权公式、未经讨论的"看起来合理"的排序因子组合；
- 排序因子若有任何新增/调序，列入 `PROTOTYPE-PROGRESS.md` 偏差清单等待裁决，**不得静默实现**。

### 候选筛选与去重

- 去重在融合后执行；语义去重阈值沿用设计（≥0.92 只 `metaRev++`，真合并留给 M04）；
- 时间与有效性判断、可信度检查在筛选阶段完成；
- 最终输出**有限数量的高价值记忆**（"少而准、按需注入"，D19/D20）。

## 三、上下文构建层（L3）：两个不可逾越的边界

1. **权限终检**：M02 不得自行决定记忆权限，最终必须过 **M05 `canRead`** 接口；**失败、超时或不确定时一律拒绝（fail-closed）**。原型期 M05 未实现，`permissionCheck()` 挂载点的**接口契约默认返回 DENY**；仅显式隔离的测试环境允许测试授权替身（`15` §5.6：不得使用默认 allow-all 作为生产回退）。接口签名与调用位置现在就固定，P6 接入 M05 时零改动替换。
2. **Token 预算**：
   - 不是简单取 Top-K：需综合候选相关性、内容长度、预算限制动态裁剪；
   - **预算默认值 topK=5 / budgetTokens=1200 属于默认配置，不自动视为最终算法裁决**；
   - **⚠️ Token ≠ 字符**：现网"≤1200 字"是**字符**限流；Token 数取决于语言与分词器，与字符数不可互换。实现必须用 Tokenizer 估算 Token，且 **Token 预算与字符预算（`recall.budgetChars`）独立生效、取更严者**。**不得把 1200 字直接当作 1200 Token。**
   - 检索失败/低质量时允许正常回答，**不强行注入**（m01 §3.4）。

## 四、索引同步（Outbox）——影响检索算法正确性的地基

SQLite 是唯一权威数据源。写入记忆时**在同一事务中写入 Outbox 事件**，再由后台任务同步到 FTS5 与向量层。六条硬要求：

1. **幂等处理**（重复消费不产生副作用）；
2. **防止旧版本覆盖新版本**（版本号/单调序号比较后才落索引）；
3. **失败退避重试**；
4. **删除操作优先处理**（tombstone 先于同 key 的旧内容事件）；
5. **支持全量重建**（索引可随时从 SQLite 重建，T08）；
6. **支持索引追赶与一致性检查**（对账脚本报告 SQLite/FTS5/向量差异）。

## 五、两个未解决的算法问题（B-010 / B-011）——不是加字段就能过

| 编号 | 问题 | 需要补全的内容 |
|---|---|---|
| **B-010** | 向量空间定义不完整 | dim、metric、normalized、projection、chunker、chunk_id 等（能回答"某条记忆的某个向量，由哪个模型、哪套参数、哪种文本处理规则生成"） |
| **B-011** | Embedding 模型迁移方案不完整 | 索引空间、查询路由、迁移期写入、追赶、完成判据、回滚规则 |

**明确禁止**：以"加一个 `embedding_version` 字段"的方式宣称已解决 B-010/B-011——字段只是载体，缺失的是**空间定义与迁移不变量**。原型期只在 Schema 中**预留**这些字段位（V1 预留级），并保证：不同 embedding 模型的向量，**即使维度相同也不得混在同一语义空间排序比较**。

## 六、禁止自创清单（代码 AI 一票停止项）

以下任何一条出现，即停止实现并报告用户：

1. 自创排序算法/加权公式，或引入 Cross-Encoder、LTR；
2. 把 ANN（IVF/HNSW/…）作为默认路径；
3. 把 `rrf.k`、`topK`、`budgetTokens` 写死或宣称"已批准"；
4. Token 与字符混算（拿字符数冒充 Token 预算）；
5. 绕过 `permissionCheck()` 挂载点，或用数据库过滤冒充权限判定；
6. 绕过 Outbox 直写 FTS5/向量层；
7. 用"加 embedding_version 字段"宣称解决 B-010/B-011；
8. 让 Search Document 的两路输入内容不一致（Embedding 与 FTS5 各喂各的）。
