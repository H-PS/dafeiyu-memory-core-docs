# R3 框架结构优化：可拆卸 · 可升级 · 定点升级 · 规则/模型接口保留

- 生成时间：2026-11-02
- 性质：**设计建议文档，不是已批准决策**。文中所有接口名均为示例，不代表最终 API 已冻结（沿用 M04 §12"方向示意，不冻结"的纪律）。
- 输入依据：
  - R3 五模块设计（`m01.md`–`m05.md`、`dream.md`，含两轮修订）
  - `E:\gpt work\研究报告\` 四份研究（报告1 Hindsight / 报告2 Mem0+Graphiti / 报告3 DSH解耦审计 / 报告4 Memora）
  - 前两轮反馈：`M01-M05重复项处理优先级.md`、`Targeted-Consistency-Fix-Report.md`
- 用户需求（本文档的四项约束）：
  1. **每框架可拆卸**——每个组件/框架可以拔掉、换掉，不拖垮整体；
  2. **可升级**——组件有版本、可平滑升级、可回退；
  3. **定点升级**——升级某一项时不牵动全局；
  4. **规则/大模型处保留接口**——所有"既能用规则又能用大模型"的决策点都留出可替换接口。
- 最终目标：**省 AI 对话中的上下文与 token，同时保持较高智能**。

## 〇、结论摘要

1. **R3 的"插拔基因"已经相当好**：M04 D1（Decision Provider 可插拔）、D5（纠正策略可插拔）、D15（RRF 默认融合保留分数融合接口）、D24（Model Gateway）、M01 D16/D18/D21/D25（模型可替换/索引类型演进/分词器可替换/Index Adapter 三层结构）已覆盖大部分接缝。**缺的不是接口意识，是接口的显式化与升级语义**。
2. **"可拆卸"分三级**：L0 关闭降级（R3 已基本设计完整，M01 D29 + M02 D9 就是降级矩阵）、L1 同接口换实现（部分缺失）、L2 外部框架槽位化（完全缺失，但报告2 H.1.2 的 Graphiti 旁路索引建议就是现成范式）。
3. **"定点升级"需要一个统一分类法**：按数据依赖分四类（纯代码替换 / 派生层重建 / 权威层迁移 / 语义重放）。前两类 R3 已有机制（配置原子切换、蓝绿索引），第四类（Evidence 重放）是唯一需要**新增能力**的，也是"升级了更聪明的提取模型后，旧记忆能否重新提炼"的关键。
4. **必须划出"不可插拔区"**：权限判定（M05 9.2 明确不用 LLM 判权）、生命周期硬约束、安全硬约束、Fail-Closed。**插拔性不能延伸到安全边界**——这是四份研究里所有框架反面教训的总和（Graphiti 参考服务无鉴权、Memora 权限声明为零实现、Hindsight 异步阶段无复核）。
5. **对 token 目标的最大杠杆**仍是上一轮指出的双层检索与视图直读；本方案把它们纳入插拔体系（Reranker/QueryPlanner/DecayPolicy 接口），使"更省"和"更聪明"都变成**可定点替换的组件**，而不是写死在管线里。

## 一、需求判定口径

四项需求必须可验收，否则会退化成口号。

| 需求 | 判定口径（验收标准） |
|---|---|
| **可拆卸** | 拔掉组件后：①系统不崩溃，走声明过的降级路径；②普通聊天不中断；③权限测试项全通过；④恢复插回后无需人工修数据（或按声明重建）。对应 M01 D31 的 T10（故障降级）扩展为"逐组件拔除测试" |
| **可升级** | 每个组件有**版本标识**且可查询（扩展 M01 D10 的 manifest）；升级动作有声明过的**数据依赖**；升级失败有声明过的**回滚路径**；回滚不产生数据丢失或权限复活 |
| **定点升级** | 升级组件 X 时：①不改其他模块的代码；②不做未声明的数据迁移；③权威数据（`memory.sqlite`）除声明过的迁移外零改动；④升级期间系统可用（或按声明的窗口降级） |
| **规则/模型接口** | 每个"规则 or LLM"决策点：①有命名接口；②有至少一个非 LLM 默认实现（保证 LLM 不可用时系统仍完整可用）；③LLM 实现的输出必须经过与规则实现相同的校验通道（模型提议、规则裁决） |

## 三、插拔分层模型

引入四级分类，避免"可插拔"变成一笔糊涂账：

| 级别 | 含义 | 验收动作 |
|---|---|---|
| **L0 可关闭** | 组件可以被配置关闭，系统走声明过的降级路径 | 拔除测试：关闭后 T10 权限项全过、聊天不中断 |
| **L1 可换实现** | 同一接口下换另一个实现（如 LanceDB→pgvector、RRF→学习型融合） | 接口一致性测试 + 数据迁移声明 |
| **L2 可整体拆除** | 组件及其数据可以整体丢弃重建，权威数据不受影响 | 丢弃重建测试：删掉全部派生数据后从权威层重建（M01 D11 的 P3 级语义） |
| **L3 槽位化外部框架** | 第三方框架作为一个"槽位"插入，权威数据始终在 R3 自己手里；拔掉 = 丢弃旁路索引 | 旁路索引删除后主系统功能完整 |

**关键原则**：**权威数据永远不在可插拔件里**。这是报告2 G.2/G.3（Mem0 向量库即权威、Graphiti 图库即本体都是反面教材）与报告4 F（ChromaDB 单库混用）三条教训的合并结论。LanceDB/关系索引/缓存/图索引全部定位为"可重建派生层"，只有 `memory.sqlite` 是真相。

## 五、外部框架槽位设计（L3）

四份研究报告的核心价值在这一节兑现：**每个被评估的框架都能找到自己的槽位，且都有明确的"拔掉"路径**。

| 槽位 | R3 默认实现 | 外部候选 | 集成形态 | 拔掉代价 | 判定依据 |
|---|---|---|---|---|---|
| **向量索引** | LanceDB（经 Index Adapter） | pgvector / pgvectorscale | L1 换实现（进程内换库） | 重建向量（权威不动） | 报告1 I.1：若未来接受 PostgreSQL 技术栈可重评 |
| **全文索引** | SQLite FTS5 | Elasticsearch 等 | L1（暂缓，D40 已列） | 重建全文索引 | M01 D40 |
| **关系/时序索引** | SQLite 关系表 + `listNeighbors` | **Graphiti**（FalkorDB/Neo4j） | **L3 旁路服务**：权威事实留在 M01，图库作为可重建、可整体丢弃的派生索引，由 Outbox 事件驱动重建 | 整体丢弃、从权威层重放 | **报告2 H.1.2 原文建议**："类似 LanceDB 之于向量的地位……此选项保留但不启动" |
| **检索表示层** | abstract_index + cue_anchors 自研字段 | Memora（**只吸收思想，不引代码**） | 自研字段 + 检索键改造 | — | 报告4 K：检索表示思想第 1 参照，工程可用性最后 |
| **任务系统** | SQLite 单表队列（自研） | Hindsight async_operations（**设计参照**） | 参照其语义：停放/确定性失败/superseded_by/心跳 | — | 报告1 H.1 |
| **LLM / Embedding** | Model Gateway + Ollama/OpenAI 兼容端点 | 任意 OpenAI 兼容 provider | L1 provider 插件 | 无（路由切回） | 报告3 B9：DSH 无独立模型 API，必须自带通道 |
| **重排器** | 规则序（Noop） | 本地 MiniLM cross-encoder / flashrank | L1 进程内库（≈90MB 可承受） | 无 | 报告1 H.3 |
| **整机引擎** | 自研 R3 Core | Hindsight 整机 | ❌ 不采用；条件性重评（仅当接受 PostgreSQL） | — | 报告1 K 三条理由 |

**槽位接入协议（每个 L3 槽位必须声明五件事）**：

1. 槽位接口签名（数据进/出、幂等语义）；
2. 数据流方向：**权威 → 旁路单向**（旁路永远可从权威重建，禁止旁路回写权威——报告2 H.1.2"不向正式数据库回写"同款约束）；
3. 重建触发：Outbox 事件驱动（M01 D23 已有 Outbox 机制，直接复用）；
4. 一致性等级：旁路索引允许滞后（检索侧自行容错），不允许脏读权威；
5. 拔除剧本：停同步 → 标记槽位下线 → 检索路由剔除该路 → （可选）清数据。主功能验证不受影响。

## 六、升级体系：四类升级单元 + 版本清单

### 6.1 升级单元四分类（定点升级的核心分类法）

"定点"不等于"零重建"，**定点 = 影响范围被声明且可控**。按数据依赖分四类：

| 类别 | 定义 | 典型升级 | 数据动作 | 回滚方式 |
|---|---|---|---|---|
| **类1 纯代码替换** | 零数据依赖 | Reranker、FusionStrategy、DecayPolicy、QueryPlanner、provider 路由、M03 评分权重（§11） | 无 | 配置原子切换+回退（M04 §13） |
| **类2 派生层重建** | 只动可丢弃数据 | Embedding 模型（D16）、索引类型 FLAT→ANN（D18）、分词器（D21）、cue 重生成、缓存清空 | 蓝绿重建派生索引，权威不动 | 旧索引保留回退（D16/D23） |
| **类3 权威层迁移** | 动 `memory.sqlite` schema | 加列、加表、约束变更 | D9 版本化迁移（迁移前备份） | D8 备份恢复 |
| **类4 语义重放** | 从 Evidence 重新派生 | 抽取策略/prompt 升级（extraction_version）、评分规则重评旧候选 | 新候选走 M03→M04 审核通道，旧事实 supersede 不删 | 版本化候选 + supersede 链（M03 §7.3 暂存重评机制已有雏形） |

**现有文档已覆盖类1/类2/类3 的机制**；**类4 是唯一缺口**，需要新增"Evidence 重放"能力（见 6.3）。

### 6.2 组件版本清单（扩展 M01 D10 manifest）

```text
manifest/
├── schema-version.json        # 类3：memory.sqlite schema 版本（已有）
├── storage-manifest.json      # 存储布局（已有）
├── cache-schema-version.json  # 类2：cache.sqlite 版本（独立演进，不兼容即丢弃重建）
├── component-manifest.json    # 新增：组件级版本
│   {
│     "embedding":  { "model": "...", "version": 3, "dim": 1024 },
│     "index":      { "type": "flat", "built_at": "..." },
│     "tokenizer":  { "name": "...", "version": 2 },
│     "extraction": { "strategy_version": 4 },        # 类4 的版本锚点
│     "scoring":    { "version": 1 },                  # 对应 M03 §11 scoring.version
│     "policy":    { "permission": 12, "memory": 5 },  # 对应 M05 permission_version / M04 policy_version
│     "fusion":    { "strategy": "rrf", "version": 1 },
│     "decay":     { "policy": "noop", "version": 1 }
│   }
```

要点：
- 每个版本号都是**可查询、可记录到变更日志（M01 D39）**的，任务与 Recall 记录所用版本（M04 §13 已要求）；
- 版本号是**定点升级的定位器**：升级动作 = 修改清单中一项 + 执行该类升级单元的声明流程；
- 混用禁止规则沿用既有设计：不同 embedding 版本的向量不能混用（D16）、旧任务不能覆盖新版本（M01 D6）。

### 6.3 新增能力：Evidence 重放（类4 的落地机制）

**动机**：升级了更聪明的提取模型/抽取策略后，旧记忆是按旧策略提取的——不重放就永远享受不到新智能；全量重放又太贵。Evidence 层（M01 D2）恰好是为此准备的：**原始证据在，随时可以从源头重新推导**。

机制（全部复用既有件）：

1. 触发：手动指定范围（按 subject / 时间段 / memory 类型）或策略变更后按需执行；
2. 执行：新任务类型 `evidence_reprocess`（M04 §7.1 任务类型表追加）→ 读 Evidence 批次 → 以新 `extraction_version` 走 M03 提取 → 产出**新候选**（`claim_type` 继承证据性质，Dream 式约束：不得直接生成 support）→ M04 审核；
3. 新旧关系：新事实通过 **supersede 链**替代旧事实，旧事实保留不删（M04 9.1 有效状态已有 superseded；报告2 B.4 Graphiti "invalidated, not deleted" 是同款语义的工程证明）；
4. 成本闸门：重放是 token 大户，必须受预算约束（按批次限量、可暂停、断点续跑——M04 §7.3 检查点机制直接复用）；
5. 幂等：同一 Evidence + 同一 extraction_version 重放结果应可识别（content hash，M01 D11 已有内容 Hash 校验）。

**precedent**：Hindsight 的 documents-as-source-of-truth + reprocess（报告1 H.7："系统性错误修源头、个别错误修条目"的治理分工）。R3 的 Evidence 层粒度（消息级）比 Hindsight 的 document 级更适合 QQ 场景做小范围定点重放。

**难度**：四类升级单元里唯一的中高难度项，但它是"模型升级后旧记忆跟着变聪明"的唯一途径——直接服务"较高智能"目标。

### 7.2 不可插拔区（同等重要的另一半）

| 区域 | 规则 | 依据 |
|---|---|---|
| **权限判定引擎** | 永远是规则，**禁止 LLM 判权**；可版本化的是策略参数（M05 §15），不是判定引擎本身 | M05 9.2 明文 |
| 生命周期硬约束 | 状态流转合法组合校验（M04 9.1）为确定性规则 | 审计可追溯性要求 |
| 安全硬约束 | 不可被配置、模型、插件关闭（M01 D33 / M04 §13） | 既有明文 |
| 删除/撤销即时阻断 | P0 同步安全阶段不进普通队列（M04 7.2） | 既有明文 |
| Fail-Closed | 权限不确定即拒绝（M05 D12） | 既有明文 |

> 写这一节的原因：四份研究里权限失控是共同翻车点——Graphiti 参考服务"无认证无授权"（报告2 B.1）、Memora README 声称权限而代码为零（报告4 E）、Hindsight 异步阶段无复核（报告1 C4.5）。R3 的权限内核是差异化价值，**接口化运动不得波及此处**。

### 7.3 顺带收敛一个既有重复

M03 §12 的"抽象 LLM Provider"与 M04 §6.2 的"Model Gateway"是两套模型抽象（首轮审查已标记为重复）。插拔化改造应**收敛为一处**：M03 的提取调用改为**经 Model Gateway**（Gateway 已有 provider 管理、分级路由、升级降级、调用日志），M03 只保留"提取策略"层面的接口（ExtractionStrategy）。这样 LLM provider 的插拔点全系统唯一。

## 九、对"省 token + 高智能"的贡献映射

| 机制 | 省 token | 提智能 | 插拔属性 |
|---|---|---|---|
| **双层检索**（索引摘要+cue，不索引正文，前轮矛盾2 修复） | ★★★ 注入的是 2~3 句规范摘要而非原文；Memora 论文口径省 98%（未复现，报告4 J.3） | ★★ 检索精度随规模更稳 | 检索键=类2 升级单元（可重建） |
| **视图直读**（高频人设/偏好走当前视图，零检索零 embedding） | ★★★ 热点记忆零检索成本（Hindsight Mental Model 思想，报告1 H.4） | ★ 一致性更好 | M04 视图已有，补 M02 直读通道（前轮矛盾1 修复） |
| **max_tokens 硬约束** | ★★★ "以 token 思考而非条数"（报告1 H.3） | — | M02 D7 语义明确化 |
| **Token 计量组件** | ★★（度量本身不省，但没有它"省了多少"不可验证——R2-M08 被划出范围后的最小补偿） | ★ 评估闭环 | 常开组件 |
| **Cross-Encoder 重排（槽位）** | ★ 少注入无关项 | ★★★ 错误召回率最短改进路径（~90MB 本地模型） | 类1 纯代码定点升级 |
| **RE_QUERY 指针检索（槽位）** | ★ 按需深入而非一次灌入 | ★★ 关系型问题（"X 和 Y 什么关系"） | 类1；Memora prompted policy 参照 |
| **Evidence 重放** | —（耗 token，需预算闸门） | ★★★ 旧记忆随模型升级变聪明 | 类4 唯一路径 |
| **分级模型路由**（已有 D26） | ★★ 简单判断用小模型 | ★★ 复杂判断用强模型 | Gateway 已有 |

**组合判断**：省 token 的前三是"双层检索 + 视图直读 + max_tokens 硬约束"，全部不依赖更贵的模型；提智能的前三是"CE 重排 + Evidence 重放 + 分级路由"。两组互不冲突，且都被纳入同一套插拔/升级体系——这就是"省"与"智能"可以兼得的结构性原因。

## 十、实施顺序建议

| Phase | 内容 | 产出 | 前置 |
|---|---|---|---|
| **A 设计收口**（零代码，先做） | §8.1 的 D-1~D-10 文档增补；不可插拔区声明 | 接口名、版本语义、升级分类、验收用例全部落进 m0X | 无 |
