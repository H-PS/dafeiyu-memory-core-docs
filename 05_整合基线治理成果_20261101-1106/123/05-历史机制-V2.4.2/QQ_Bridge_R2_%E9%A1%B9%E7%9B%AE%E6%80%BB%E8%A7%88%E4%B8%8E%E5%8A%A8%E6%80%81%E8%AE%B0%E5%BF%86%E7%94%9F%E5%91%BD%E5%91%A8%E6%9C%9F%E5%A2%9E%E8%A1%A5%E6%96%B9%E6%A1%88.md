# 第一部分：项目目的与总体目标

## 1. 项目是什么

项目是在现有 QQ Bridge 上建设一套可控、可审计、可恢复的长期记忆系统。

它不是简单地把聊天记录全部存进数据库，也不是让聊天模型直接读取整个历史记录。

目标是让机器人能够：

-   从 QQ 对话中识别值得长期保留的信息；
-   将信息整理成结构化、有来源证据的候选记忆；
-   对记忆进行去重、合并、冲突处理和权限审核；
-   按当前对话检索少量真正相关的记忆；
-   区分长期事实、偏好、计划、事件与短期社交状态；
-   随时间调整记忆的召回优先级；
-   在用户重新提及旧信息时找到并重新激活旧记忆；
-   允许记忆更新、撤回、归档和恢复；
-   确保私人记忆不会因语义相关而泄漏到群聊；
-   即使记忆服务、向量索引或后台提取失败，也不应阻断正常聊天。

## 2. 设计原则

1.  **聊天与记忆处理解耦**：实时聊天优先，后台记忆提取不能阻断回复。
2.  **记忆不等于聊天历史**：只保留有持续价值的信息，不把每句话都永久保存。
3.  **候选与权威记录分离**：模型只能提出候选，不能直接写入权威记忆库。
4.  **权限优先于相关性**：高相似度不代表有权使用。
5.  **存储与召回分离**：记忆可以长期保存，但不必一直高频出现。
6.  **向量索引可重建**：向量库不是事实和权限的最终权威。
7.  **时间语义明确**：创建、确认、支持、检索、有效期不能混成一个时间字段。
8.  **失败可恢复**：写入、索引、Reset
    和启动恢复必须有明确状态与幂等设计。
9.  **可解释和可审计**：重要记忆应能追溯到原始消息证据。
10. **渐进式实施**：先定设计和验证接口，再实施；不因技术选型而重写原有安全边界。

# 第三部分：R2 目标架构与技术选型

## 7. SQLite + LanceDB 双存储方向

当前建议采用：

-   **SQLite：权威记忆存储**
-   **LanceDB：可重建向量检索索引**

二者不是平级的事实来源。

### SQLite 保存什么

-   记忆正文与规范化内容；
-   记忆 ID、主体、类型、来源；
-   创建时间、确认时间、有效时间；
-   记忆状态、版本和冲突关系；
-   可见性与权限元数据；
-   写入事务、Outbox、索引任务状态；
-   Prompt Ledger 等需要事务和结构化查询的数据。

### LanceDB 保存什么

-   embedding 向量；
-   向量检索所需的辅助字段；
-   可用于候选召回的索引元数据。

LanceDB 不拥有以下权力：

-   决定一条记忆是否真实存在；
-   决定记忆是否有效；
-   决定谁可以看到记忆；
-   决定是否删除或撤回记忆；
-   绕过 M05 直接向聊天 LLM 提供内容。

### 写入和删除原则

新增记忆：

1.  SQLite 事务写入权威记忆和 Outbox 任务；
2.  索引任务将向量写入 LanceDB；
3.  成功后将任务标记完成；
4.  任务需具备幂等 ID、revision 检查和重试能力。

删除或撤回：

1.  先在 SQLite 将记忆标记为不可访问或失效；
2.  再异步清理 LanceDB；
3.  即使 LanceDB 清理失败，旧向量也不能让记忆重新变得可用。

恢复：

-   LanceDB 可以从 SQLite 权威数据重建；
-   索引重建不能改变 SQLite 的权限和有效状态。

## 8. 技术选型待验证项

尚未完成实际安装或运行验证：

-   `better-sqlite3` 与 Node `node:sqlite` 的取舍；
-   Node `v22.22.2` 下 SQLite 方案的 API 稳定性、性能与兼容性；
-   LanceDB JavaScript SDK 在当前 Windows + Node
    环境中的安装和运行兼容性；
-   native 依赖、安装体积、内存、磁盘、冷启动和查询延迟；
-   DSH 是否存在适合 M03 的独立模型调用接口；
-   DSH 是否支持独立 Prompt、模型指定、结构化 JSON 输出和超时/重试；
-   当前维护脚本、外围组件及其他 state 写入者的完整情况。

技术选型阶段可以做资料研究和定向只读验证，但不得将"方案选择"自动视为安装授权。

# 第五部分：M03 记忆提取设计

## 9. M03 的定位

M03 是一个**候选记忆提取器**，不是记忆数据库写入器，也不是权限决策器。

输入：经过来源和隐私预筛选的有限聊天片段。

输出：带有原始消息证据、时间和主体信息的结构化候选记忆。

后续路径：

``` text
M03 候选提取
   ↓
M04 去重、合并、冲突和价值审核
   ↓
M05 权限与可见性判断
   ↓
M01 SQLite 权威保存
   ↓
M02 LanceDB 建立可重建索引
```

## 10. M03 的五个阶段

### 阶段 1：确定性规则预筛选（不调用 LLM）

职责：

-   过滤空消息、系统通知、撤回通知、机器人自身消息等；
-   根据消息 ID、内容指纹和时间窗口去重；
-   检查来源是否允许进入记忆处理；
-   在调用模型前检查会话和内容的隐私处理边界；
-   纯表情、无上下文短句可以暂缓，但不能简单按长度一刀切。

此层不负责理解深层语义，也不决定某句话是否值得永久保存。

### 阶段 2：消息缓冲和任务组织

-   按会话组织消息；
-   使用有限时间窗口或消息数量触发批次；
-   保留 speaker、时间、conversation_id、message_id；
-   允许跨批次提供有限上下文；
-   失败任务可重试；
-   后台处理不能阻塞实时聊天。

### 阶段 3：独立轻量 LLM 结构化提取

建议记忆类型：

-   `fact`
-   `preference`
-   `event`
-   `plan`
-   `goal`
-   `relationship`
-   `state`

模型只输出候选，不直接写数据库、不决定权限、不执行删除。

建议候选结构：

``` json
{
  "type": "plan",
  "subject": "owner",
  "content": "正在考虑赴德国攻读硕士",
  "evidence": ["message_102", "message_105"],
  "valid_time": {
    "start": "2026-10-30",
    "end": null
  },
  "certainty": "explicit",
  "importance": "medium",
  "source": "conversation",
  "evidence_action": "confirm",
  "related_memory_candidates": ["memory_018"]
}
```

### 阶段 4：程序校验

-   JSON 和 Schema 校验；
-   type、certainty、evidence_action 等枚举校验；
-   检查消息 ID 是否真实存在；
-   检查 subject 与来源发言者是否匹配；
-   要求候选内容能由证据支持；
-   不接受模型自行补充的事实；
-   不将模型自报置信度数字直接视为真实准确率。

### 阶段 5：候选关联和提交 M04

M03 可以根据候选内容指出可能关联的旧记忆，但只能提供候选
ID，不能自行决定更新、覆盖或重新激活。

## 11. M03 的证据动作

建议使用：

  ------------------------------------------------------------------------------------------
  `evidence_action`       含义                    默认处理
  ----------------------- ----------------------- ------------------------------------------
  `mention`               普通提及                不刷新确认时间

  `reinforce`             新证据支持旧记忆        更新支持证据，是否刷新确认时间由规则决定

  `confirm`               用户明确确认            可进入再激活审核

  `revise`                用户修正旧信息          进入版本更新审核

  `contradict`            与旧记忆冲突            进入冲突审核

  `revoke`                用户明确撤回或否定      更新当前有效状态，保留历史
  ------------------------------------------------------------------------------------------

模型提出动作，M04
根据原始证据审核。不得让模型仅凭语气猜测"用户已经改变想法"。

## 12. M03 的独立模型调用接口

建议设计 `MemoryExtractionAdapter`：

``` text
M03
 ↓
MemoryExtractionAdapter
 ↓
DSH 独立模型调用接口（待确认）
 ↓
轻量模型 + 专用 Prompt
 ↓
结构化候选 JSON
```

如果 DSH 没有合适的独立调用接口，再单独评估其他调用方式。

当前**尚未确认 DSH
的接口是否存在**，因此不能把调用方式定为已实现，也不能现在假设它支持指定模型、独立
Prompt 和 JSON Schema。

# 第六部分：A/B 双层动态遗忘与激活

## 13. 核心原则

**记忆的存储强度不等于当前召回优先级。**

-   记忆可以长期保存；
-   当前召回优先级随时间和新证据变化；
-   时间衰减默认只影响排序，不直接修改 embedding；
-   低激活度不等于删除；
-   检索过不等于用户确认过。

## 14. A/B 层职责

### A 层：长期语义记忆

主要保存：

-   稳定事实；
-   稳定偏好；
-   重要事件；
-   长期目标；
-   长期计划；
-   关系信息。

策略：

-   慢衰减；
-   重要事实可采用固定保留策略；
-   计划和目标需要定期复核；
-   事件可以长期保留历史；
-   用户提供新证据后可重新激活或更新。

### B 层：短期社交状态

主要保存：

-   `activeTopic`
-   `pendingThought`
-   `memberImpression`

策略：

-   快衰减；
-   话题变化时旧话题迅速降权；
-   过期状态退出活动集合；
-   临时印象必须持续受到新证据修正；
-   不因系统反复读取而无限续期。

## 15. 时间衰减函数

初始建议使用指数半衰期模型：

\[ D(m,t)=2\^{-`\frac{\Delta t}{H_m}`{=tex}} \]

其中：

-   (`\Delta `{=tex}t)：距离最近一次有效确认或对应证据时间；
-   (H_m)：该类型记忆的半衰期；
-   (D)：时间权重，范围为 0 到 1。

仅用于初步设计的示例参数：

  记忆类型                示例半衰期
  --------------------- ------------
  A：稳定事实                 365 天
  A：稳定偏好                 180 天
  A：长期目标                  60 天
  A：进行中计划                30 天
  B：activeTopic              6 小时
  B：pendingThought          24 小时
  B：memberImpression          14 天

这些数值**不是最终参数**，必须用真实聊天样本和召回评测校准。

## 16. 时间字段必须分离

  字段                   含义                         是否刷新衰减锚点
  ---------------------- ---------------------------- --------------------
  `created_at`           首次创建时间                 否
  `last_retrieved_at`    最近被系统检索时间           否
  `last_reinforced_at`   最近获得支持性新证据的时间   按类型规则
  `last_confirmed_at`    最近一次明确确认时间         是
  `valid_from`           信息开始生效时间             不直接等同确认时间
  `valid_until`          信息结束生效时间             用于判断有效性

严禁系统仅因自己检索某条记忆，就刷新 `last_confirmed_at`。

## 17. 动态召回综合评分

先将向量相似度转换到 0～1：

\[ R(m,q)=`\frac{1+\cos(E_m,E_q)}{2}`{=tex} \]

再计算综合分：

\[ S(m,q)=w_rR+w_tD+w_iI+w_cC+w_fF \]

其中：

  符号   含义
  ------ ----------------------------
  R      当前查询与记忆的语义相关性
  D      时间衰减权重
  I      重要性
  C      可靠程度
  F      用户确认或有效证据支持频率

权重之和为 1。A/B 使用不同权重配置。

注意：

-   权限不是评分项，而是硬性过滤条件；
-   系统检索次数不应提高 F；
-   LanceDB 不负责最终评分；
-   M02 负责业务重排序；
-   初始权重待评测集校准；
-   不得因分数低而自动删除长期记忆。

## 18. LanceDB 候选召回注意事项

不能先设置过小的 Top-K，再做时间重排序，否则旧记忆可能在评分前就被排除。

建议：

1.  先进行足够宽的向量候选召回；
2.  必要时结合关键词、实体和历史 ID 辅助检索；
3.  回到 SQLite 获取权威记录；
4.  A/B 分别计算时间和综合权重；
5.  M05 做权限硬过滤；
6.  去重、排序并执行 Token 预算；
7.  将最终记忆文本交给聊天 LLM。

**聊天 LLM 不直接访问 SQLite 或 LanceDB。**

# 第七部分：Memory Reactivation（记忆再激活）

## 19. 目标

当一条长期记忆因长期未确认而进入低激活状态时，用户重新提及相关内容，系统应能够：

-   找到旧记忆；
-   判断新消息与旧记忆的关系；
-   避免重复创建；
-   根据新证据重新激活、更新或结束旧记忆；
-   保留历史和证据链。

## 20. 逻辑状态

建议使用：

  状态           含义                     普通召回
  -------------- ------------------------ ------------------------------------
  `Active`       当前有效、正常参与召回   是
  `Dormant`      当前激活度较低           可通过宽候选检索重新找到
  `Superseded`   已被新版本替代           默认不作为当前事实
  `Archived`     已归档                   不参加普通召回，特殊历史查询可访问

状态和时间分数分离：

-   Dormant 不代表事实错误；
-   Superseded 不代表旧记录删除；
-   Archived 不代表数据库物理删除；
-   低时间权重本身不应自动触发状态变更。

## 21. 再激活规则

  新消息与旧记忆关系     处理
  ---------------------- ----------------------------
  普通提及过去的事       不自动刷新确认时间
  明确再次确认仍然成立   进入再激活审核
  提供支持性新证据       更新证据和支持时间
  补充信息               更新或建立新版本
  与旧信息冲突           M04 冲突审核，保留时间关系
  明确否定或撤回         更新当前有效状态，保留历史

示例：

-   "我之前不是考虑过去德国吗？" → `mention`，不代表现在仍然考虑。
-   "我现在还是想去德国读研。" → `confirm`，可以进入再激活审核。
-   "我现在决定不去德国了。" → `revoke` 或
    `revise`，结束旧计划的当前有效状态，但保留历史。

## 22. 再激活的安全边界

-   M03 只提供关联候选；
-   M04 决定是否为同一记忆、是否重新激活、是否产生新版本；
-   M05 决定当前会话是否可见；
-   M01 保存最终状态；
-   M02 更新检索索引；
-   不能在后台审核完成前把未经确认的新事实写入权威记忆；
-   后台失败不能阻断正常聊天。

   ↓

# R2 外部架构借鉴与计划调整清单

**来源：** DeepSeek `dsh-superagent-prototype`  
**性质：** 设计吸收与计划调整记录  
**状态：** 待评审，不构成实施授权

## 一、强烈值得吸收：替换原计划中的对应设计

以下内容不再仅作为参考建议，而是建议纳入 R2 的新设计基线，替换原计划中较粗略的对应方案。

### S-01：M03 从简单批量触发升级为持久化任务模型

**原计划方向：**
- 根据消息数量、时间或空闲状态触发批量提取。
- 执行提取并保存结果。
- 失败后重试。

**调整后的方向：**
引入 `ExtractionJob / ExtractionBatch` 任务实体。

至少记录：
- `job_id`、`batch_id`
- 来源会话与消息范围
- 任务状态
- 创建时间、开始时间、完成时间
- 提取模型及调用次数
- 重试次数与失败原因
- 提取结果及证据消息 ID
- 权限策略版本

任务状态建议：

`pending → running → succeeded / failed / cancelled`

中断时允许进入可恢复状态。

**吸收理由：**
任务不再只是一次函数调用，而是具有明确身份、状态和生命周期的工作单元。这样才能可靠地处理异步执行、重试、审计和恢复。

**影响模块：** M03、M01、M17。

### S-02：异步副作用统一采用事务内登记、提交后执行

**原计划方向：**
- SQLite 保存权威记忆。
- LanceDB 保存可重建的向量索引。
- 两者通过异步流程保持一致。

**调整后的方向：**
采用 Outbox / Effects 思路：

1. SQLite 事务内写入权威数据。
2. 同一事务内登记待执行的索引任务。
3. 事务提交后，由后台消费者执行 LanceDB 写入。
4. 完成后记录任务结果与执行回执。
5. 失败后按策略重试。

必须具备：
- 幂等键；
- 重试次数与退避策略；
- 失败记录；
- 可恢复的任务状态；
- 索引任务与权威记忆之间的关联。

**吸收理由：**
避免出现 SQLite 已提交、LanceDB 尚未更新，而系统又无法判断后续应该补做还是重做的情况。

**影响模块：** M01、M17；不改变 SQLite 为权威存储、LanceDB 为可重建索引的基本原则。

### S-03：M17 从启动恢复扩展为完整任务恢复机制

**原计划方向：**
- 系统启动时检查未完成任务。
- 对中断操作进行恢复。

**调整后的方向：**
恢复机制不只处理启动时的异常，还应覆盖任务执行生命周期：

- 进程意外退出；
- 模型调用超时；
- 索引写入失败；
- 任务执行中断；
- 任务提交后回执丢失；
- 重试时发生重复请求。

恢复时必须先判断任务是否已经产生权威写入，不能简单地重新执行整个任务。

**吸收理由：**
将“恢复”从启动时的一次性检查，提升为任务系统的可靠性保障。

**影响模块：** M17、M01、M03。

### S-04：M05 权限判断引入策略版本与执行前复核

**原计划方向：**
- 通过 M05 统一判断记忆的主体、会话和可见性权限。
- 不允许未经授权的记忆进入检索和注入流程。

**调整后的方向：**
任务创建时记录权限策略版本及授权依据。

在以下节点重新检查权限：
- 任务实际开始执行前；
- 提取结果准备写入权威存储前；
- 记忆准备进入会话上下文前。

如果权限已经撤销或发生变化，旧任务不能凭创建时的授权继续写入或传播。

**吸收理由：**
异步任务可能在创建后很久才执行，创建时有权限不代表执行时仍有权限。

**影响模块：** M05、M03、M01、M11、M12。

## 四、对 R2 原架构的影响

**保持不变：**
- SQLite 是权威记忆存储。
- LanceDB 是可重建的检索索引。
- M05 是权限判断边界。
- M03 负责候选提取，不负责最终权限裁决。
- M04 负责记忆合并、冲突和状态调整。
- 聊天 LLM 不直接访问数据库。
- 空记忆库仍然是合法初始状态。

**需要调整的计划：**
- M03：从简单批量提取改为持久化任务驱动。
- M01：补充事务内 Outbox 登记与提交后异步执行的约束。
- M17：从启动恢复扩展为任务生命周期恢复。
- M05：补充策略版本记录与执行前权限复核。

这些属于现有模块职责的深化，不新增一批独立 M 模块。
