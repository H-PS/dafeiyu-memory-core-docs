# 算法可替代性审查范围 · ALGORITHM-REVIEW-SCOPE

> **审查目标（先读）**：本次审查**不是**要求所有函数都插件化，也**不是**重写 R3 架构。目标是判断——**关键算法能否在保持稳定契约的条件下独立升级**。即：换掉 embedding 模型、换掉 reranker、换掉抽取策略时，是否需要改动调用方、是否需要破坏已有数据、是否会产生不可回滚的状态。
>
> **材料边界**：B 包全部为本项目**已落盘的 R3 设计原文**（无转录问题，SHA256 与源一致）。但 R3 是**设计文档**，不是已实现系统——凡涉及"实际如何运行"的判断，一律标为实施待核实。

## 二、必须逐项核对的九个审查问题

### 1. 算法实现与模块接口是否真正分离

**核对点**：M03 §11"可调整接口"是否只给了参数清单而无契约（方法签名/输入输出/失败语义）；M04 §6.2 Model Gateway 是否为唯一 LLM 入口（D-AP-02 已裁决"接受 M04 §6.2 作为唯一 LLM Gateway 实现入口"，**Embedding Provider 归 M01**）；M01 D16/D17 的 embedding 生成是否被抽象为可替换 provider。

**关键判断**：分离不是"有接口名"就算，而是**调用方是否只依赖契约**。若 M02 直接读取 M01 的表结构、或直接调用某具体 embedding SDK，即为伪分离。

### 2. 是否存在具体模型、算法或供应商的隐性绑定

**核对点**：M01 D16（Embedding 模型管理）是否写死了模型名/维度；D18（向量索引类型）是否绑定具体索引实现（如仅 faiss/hnswlib 其一）；M02 D3 的多通道策略是否绑定具体 FTS 实现（D21 中文全文检索）；M03 §12 是否绑定具体 LLM；M04 §6.3 分级路由是否绑定具体模型族；`R3-Pluggable-Capability-Design.md` §2 能力契约是否要求 provider 声明自己的算法/版本。

**纪律**：文档中"参考某某方案"不等于绑定；要求给出**契约层是否强制**的证据。

### 3. Embedding 更换后的向量维度、索引重建与历史数据兼容

**核对点**（本轮重点，M01）：
- D15（向量索引单位）与 D19（向量记录结构）是否记录 `model_id` / `dim` / `version`；
- D17（Embedding 生成与更新）是否定义"换模型后旧向量如何处理"（并存/迁移/失效）；
- D23（索引同步与重建）是否给出重建触发与幂等性；
- D9（Schema 与迁移版本）是否支持多模型并存的双写期；
- D8（备份恢复）在换模型后的恢复语义。

**判断标准**：**能否在不丢失历史记忆、不停机、可回滚的前提下更换 embedding**。若文档只写了"重建索引"而未定义新旧向量共存与查询路由，则为设计缺口。

### 4. 检索、排序、抽取算法的独立替换边界

**核对点**：M02 D1（两阶段混合检索）/D3（多通道）/D4（候选排序）三者的替换是否互不牵连；`R3-Capability-Ownership-Matrix` 载明"检索 11 项全部归 M02（编排权威）"——**这是替换边界的关键事实**：编排权威在 M02，所以替换某一路召回不应改动 M01/M03/M04；M03 §7 分流与 §6 评分是"抽取算法"，替换它是否改变候选数据结构（§10 冻结？）。

### 5. 新旧算法并行、Shadow 对照和灰度切换

**核对点**：`R3-Pluggable-Capability-Design.md` §3（注册/发现/选择）是否支持同能力多 provider 并存与按比例路由；§4（健康/降级/回退）；`R3-Distributed-Evolution-Roadmap` §2.2"现在就必须设计的留门"；I-4 裁决（强制影子模式，≥2 周/≥75% 仅为最低观察条件）；X-1 裁决（delta-only 影子验证，不改变 M02 最终排序结果）。

**关键判断**：影子对照要求**同一输入跑两条算法链并比对**——文档是否定义了比对口径（差异分类、抽样、分母）？I-4 提到"抽样口径、类别分母、第二标注者、κ≥0.6"——这些是**心理层**的门禁，能否复用到算法替换，需明确判定（不得默认复用）。

### 6. 算法版本、模型版本、参数版本的可追踪性

**核对点**：优化-5 裁决（接口名称实现期确定，但**必须提前建立稳定、唯一、可追踪的参数 ID 规范**）；台账 §3d 记载"参数可观测规范（11 属性/三层次）登记为新增设计缺口，随 U 系呈报"——**即该规范尚未产出**；M01 D19 向量记录是否含版本；M04 §6.5 模型输出管理是否记录模型版本。

**判断标准**：能否回答"这条记忆的向量是由哪个模型、哪个参数版本生成的"。若不能，则为设计缺口（且与台账已登记缺口一致——不得重复编号，引用即可）。

### 7. 迁移失败、降级与回滚

**核对点**：M01 D9（Schema 迁移版本）、D37（目录迁移）、D26（导入导出）、D29（故障降级与恢复）；M02 D9（检索失败与降级）；M04 §6.4（降级策略）、§7.5（阶段恢复）；`R3-Pluggable-Capability-Design.md` §4。

**判断标准**：换 embedding 半途失败时，系统能否回到"旧模型可用"状态；是否存在单向不可逆迁移步骤（如原地删除旧向量列）。

### 8. 算法替换是否可能影响 M05 权限、数据归属、事实可信度等稳定业务规则

**核对点**：M05 §9（派生数据与轻量权限策略）、§10（统一权限判定接口）、§13（持久化与备份恢复）；D-AP-07（C40 权限引擎**不可插拔**）；I-5（心理状态机不直接产生记忆候选）；J2（情绪标注须区分"用户事实"与"模型推断"，并保留来源和版本）；M04 §4.3（Observation 形成规则）/§4.4（纠正机制）。

**关键风险**：换抽取算法可能改变"事实/推断"的判定 → 影响 J2 的标注纪律与 M05 的可见性判定。判断文档是否把"事实 vs 推断"锚定在**不可插拔的业务规则**上，而非算法实现。

### 9. 哪些抽象值得保留，哪些抽象会造成不必要的复杂度

**核对点**：`R3-Pluggable-Capability-Design.md` §6（能力分类 5 级）——5 级分类是否真的都有必要；§7 拔除测试（T13 系列）；D-AP-07（接受五级可插拔分类）；优化-4（首版拔除测试从 7 条外部依赖起步，保留后续扩展范围）；`R3-Distributed-Evolution-Roadmap` §2.3（现在不做的）。

**判断标准**：抽象层数是否与实际替换需求匹配；是否存在"为可插拔而可插拔"（例如给只有单一实现的组件定义 provider 接口）。

## 四、审查输出要求

1. **每个算法组件**给出：文档中的实际调用关系（上游调用方 → 组件 → 下游依赖）、契约是否稳定、替换时需要改动的范围；
2. **不得**仅因算法有名字就认定为独立组件——必须保留其实际调用链与上下游契约（任务第四节要求）；
3. **不得自行推断不存在的接口**；原文未提供的，标"原文未提供"；
4. 结论分类：可独立替换 / 需新增契约 / 存在隐性绑定 / 依赖实施核查 / 原文缺失；
5. 对"哪些抽象值得保留"给出**可否决的建议**（允许说"某级分类无必要"），但须给出依据。
