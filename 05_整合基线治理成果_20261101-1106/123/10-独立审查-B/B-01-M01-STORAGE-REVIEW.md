## 1. M01 当前设计概览

M01 是 Memory Core 的持久化与索引基础设施层（`m01.md` L69–98）。**它不含业务语义算法**——不判断记忆真实性、不判断是否保留、不判断是否合并、不自行决定权限（L98）。因此其"算法"实为三类：**存储组织、索引构建与同步、检索基础设施执行**。

双存储（D1）：`memory.sqlite` 为**唯一权威数据源**（L108/L141），LanceDB 为检索型向量存储（L123–131），`cache.sqlite` 为可重建缓存、不承载权威数据（L142）。二者**不假设跨库原子事务**，靠 Outbox + 幂等 + 重试 + 重建实现最终一致（L133）。

三通道（D14）：向量（LanceDB）/ 全文（FTS5）/ 结构化（SQLite）；融合与排序归 M02（L388）。

关键决策索引：D1 双存储 L104｜D2 存储对象 L146｜D4 数据组织 L214｜D5 ID L247｜D6 事务 L266｜D7 删除 L294｜D8 备份 L573｜D9 迁移版本 L621｜D14–D23 索引 L376–567｜D25 接口 L882｜D30 容量 L860｜D31 验收 L976。

**补读条款（任务 1）**：D2 对象表**不含任何运行时态对象**（`K-1` 要求的 KV 落位仍缺失，不新增编号）；D8 恢复 8 步设计良好但第 5 步语义见 §6；D9 未含"迁移失败回滚"显式步骤；D26 导出字段**不含向量溯源信息**；D29 降级表**未覆盖"半迁移"中间态**；D37 有"关闭连接"前置但**未要求确认 `-wal`/`-shm` 已消失**。

## 3. B-010 核查结论

**问：现有数据结构能否回答"某条向量由哪个模型、哪套参数、哪种文本处理规则生成"？**
**答：不足以。**

| 溯源要素 | D16 要求 | D19 有字段 | 判定 |
|---|---|---|---|
| 模型名称 | 是 | ✅ `embedding_model` | 可回答 |
| 模型版本 | 是 | ❌ 与 Embedding 版本混用 | **不可回答** |
| 模型参数版本 | 否 | ❌ | 原文未要求（归 `优化-5`，规范未产出 B-017） |
| 向量维度 | **是** | ❌ 无 `dim` | 行级不可回答（仅表 schema 可推） |
| 投影版本 | 否 | ❌ | 不可回答（D-AP-04 落地后变必需） |
| 文本预处理版本 | 否 | ❌ | 不可回答 |
| 分块规则版本 | 否 | ❌ | 不可回答（D15 要 `chunk_id`，D19 **无此字段**） |
| 归一化方式 | 否 | ❌ | **完全缺失** |
| 原文/投影版本关联 | 否 | ⚠️ `content_hash` | 部分可答，**覆盖范围未定义** |

**核心矛盾**：D16 四项 vs D19 两项。后果有二：① `embedding_version` 一名两义（模型版本 vs 流水线版本），**写入不报错，将来无法区分**；② 维度运行时被知道（D11 L736 校验）却**未持久化**。

**最值得注意的静默失效点**：全文对归一化/度量零规定。不同模型输出是否已归一化并不一致；写入侧归一化而查询侧未归一化（或反之）**不会报错，只会静默返回错误排序**。而 D16 明确允许换模型——**D16 L409「不同模型向量不能混用」缺少可执行的校验依据**。

**建议补字段**（不修改 Schema，仅为建议）：`dim`、`metric`、`normalized`、`model_version`/`pipeline_version` 分离、`chunk_id`、`chunker_version`、`projection_version`、明确 `content_hash` 语义。

**定级**：P1 · 已确认（阶段 0"潜在风险"→ 本阶段确认）。**需用户裁决：是。**

## 4. B-011 核查结论

**问：现有设计是否支持安全迁移，还是仅预留可能性？**
**答：仅预留可能性，不支持安全迁移。**

| # | 迁移问题 | 原文 | 判定 |
|---|---|---|---|
| 1 | 新旧向量能否并存 | D16 L412、D23 L567 | 仅"两个索引空间"，**术语未定义**（表/库/目录？） |
| 2 | 维度不同如何存储 | 无 | **未回答**。官方核实：LanceDB 向量列定长、维度不可原地 cast → **必须新建表** |
| 3 | 查询如何选索引 | 无 | **完全未回答**（m02 全文不提 embedding/维度/索引版本）→ **最大缺口** |
| 4 | 窗口内新增写哪边 | 无 | **未回答**。写旧→新空间缺数据；写新→回滚丢数据，**二选一必有一失** |
| 5 | 如何避免残留旧模型 | D20 `embedding_version` 可过滤 | **部分**。无"一空间一模型"不变量，混写不被结构性拒绝 |
| 6 | 如何增量重建 | D17 批次/重试/断点 | **部分**。只覆盖新记忆，**不覆盖历史换模型** |
| 7 | 如何识别完成 | 无 | **未回答**（"验证"内容未定义） |
| 8 | 如何回滚 | D16 L413 保留旧索引 | **部分且有破绽**：可用性取决于第 4 问 |
| 9 | 失败如何保持一致 | D16/D23 蓝绿 | ✅ **设计正确**（未验证的新空间不对外服务） |
| 10 | 需否双写/双读/路由 | 无 | 可推知倾向**单写蓝绿**，合理；但**补偿步骤（切换前追赶）不存在** |

**专项判断**：设计在"不同模型不可混用"的**原则**上正确，但**缺少执行机制**——无空间↔模型不变量、无维度/度量字段、无查询侧绑定。**即使 dim 相同也不可比**，而系统**无任何字段能检测混用已发生**。

**已具备**：蓝绿思想、保留旧索引、全量重建、失败不污染在服务索引（四点良好）。
**缺失（按严重度）**：①查询侧路由 ②窗口写入归属与追赶 ③"索引空间"定义 ④完成判据 ⑤一空间一模型不变量 ⑥溯源字段。

**定级**：P1 · 已确认缺口。**需用户裁决：是**（查询侧路由**移交阶段 2**，本阶段不越界）。

## 5. B-012 核查结论

**双方原文**

- **正式裁决**（`adjudication-ledger.md` §3b L71–76，第二轮 2026-11-02）：「有规范摘要时采用**摘要+cue 作为索引主体，正文降为元数据**」／「**无摘要时须定义回退策略**」／「不授权实施」。
- **模块设计**（D22 L538–547）：标题纳入／**正文纳入**／**摘要视情况纳入**／标签纳入；字段表**无 cue**。

**性质**：D-AP-04 = **用户正式裁决**（附条件、不授权实施）；D22 = **候选稿条文**（L5、L1186）。按台账优先，**方向以 D-AP-04 为准**。

**冲突点**：正文定位**直接相反**；摘要"主体"vs"可选"；cue 缺项；回退策略未履行裁决要求。补充事实：m01 **全文未引用 D-AP-04**；m02 `摘要` **零命中**；§十一 L1188 称「未改变任何已确认决策的实质内容」，与现状关系**不明**（两种解释都成立，本审查不代为选择）。

**优先级冲突存在，但性质是"裁决已接受、正文待补"的时序冲突**，不是"谁对谁错"。D-AP-04 明文"不授权实施"，故**不能**据此认定 D22 违规；但"须定义回退策略"是**待履行义务**，正文未履行。

**回退策略：无明确定义**（m01/m02 均无，且**未列入 §十 开放项**——说明尚未被识别，而非已知待定）。

**摘要缺失影响面**：检索中（可由 FTS5 部分补偿）；上下文构建中；数据完整性低（投影可重建）；**索引一致性中高**（同索引混有"摘要型/正文型"异质文档，相似度分数不可比）；重建成本中（一次性）。

**缓和因素（应写明）**：D21 L516–524 把 FTS5 定位为覆盖「人名、地点、专有名词、精确关键词、型号和数字」——**正文退出语义索引后精确信息仍可兜底**。故 D-AP-04 在工程上**自洽**，前提是回退策略定义清楚。这是**正面判断**，非质疑。

**回退策略可能引入不一致的三条路径**：① 同索引异质文档（与"不同模型不可混用"同构）；② 补摘要导致投影漂移，而 D19 无 `projection_version` 可区分；③ 两路输入不一致破坏 RRF 融合前提。

**定级**：P1 · 已确认。**需用户裁决：是**（回退策略具体形式，三选项见 §10.3）。

## 6. D8 备份恢复审查

**优点（先肯定）**：① 恢复顺序定义为"跨模块统一权威流程"（L602）；② **删除/撤销先于索引恢复**（第 3、4 步在第 5 步前），机制上防短暂泄露；③ `cache.sqlite` **文件级**结构性排除，不依赖备份工具逐表能力（L591–596）；④ 明确禁止裸复制运行中文件（L598，与官方一致）；⑤ T11/T12 把"缓存不含于备份""缓存不授予权限"变成可测条目。

**四个缺口**

| # | 缺口 | 依据 | 后果 |
|---|---|---|---|
| 1 | 备份清单**未显式含 `manifest/`** | D8 9 项末项为"必要的版本信息"（含糊）；D10 L662–664 定义 `manifest/`；D9 L626 要求管模型/索引版本 | 恢复后**失去"当前索引由哪个模型产生"的登记**，与 B-010 叠加则无法判断索引是否匹配 |
| 2 | 第 5 步「恢复**或**重建 LanceDB」**语义不等价、无选择条件** | L608 | 恢复旧备份 + 选"恢复"→可能带**旧模型向量**服务新版本记录 |
| 3 | 恢复流程**无任何索引↔权威一致性校验** | L604–611 | 上述不一致**在数据层不可检测**（因 B-010 缺字段） |
| 4 | 验收项**未覆盖"恢复后索引一致"** | T07 只管数据/权限/删除；T08 只证明"能重建" | 可测但未测的空白，补测成本极低 |

**结论**：D8 的**框架健全**，缺口集中在"**派生索引与权威记录的代际一致性**"这一条线 → 归入 **B-019（P1）**。

## 7. 存储与索引权威关系

| 组件 | 权威？ | 依据 | 结论 |
|---|---|---|---|
| `memory.sqlite` | ✅ **唯一权威** | L108/L141/L679 | 9 类对象齐备 |
| `cache.sqlite` | ❌ 可丢弃 | L142/L168–173/L680 | 已明文禁止作恢复来源（L195） |
| FTS5 | ❌ 派生 | L383/L516 | 可从权威完整重建（官方 `rebuild`） |

| Search Document | ❌ 派生投影 | L534/L549 | 更新触发有，**版本字段无** |
| Outbox | 权威库内事件日志 | L120/L229/L555 | 方向正确，**防复活有缺口**（B-018） |
| 备份 | 权威副本 | L575–598 | 权威覆盖完整；**`manifest/` 未纳入**（B-019） |

**写入顺序与事务边界：设计正确。** 业务行与 Outbox 行**同事务**（D6 L268–278）消除双事务丢失窗口；派生索引**不参与**该事务（正确，跨库 2PC 不可行也不必要）；代价是最终一致，由 D36（固定视图+实时权限复核）与 D29（按故障范围降级）承担——**这一组设计自洽**。唯一缺口：D6 **未规定 Outbox 载荷是否携带 `source_version`**，而 D23"版本防覆盖"以此为前提（B-018 技术基础）。

| 检查项 | 结论 |
|---|---|
| Outbox 失败恢复 | ✅ 齐备（重试/重启恢复/全量重建/堆积保留）；重试上限与死信去向两处表述不一，属文字级 |
| 重复事件处理 | ✅ 幂等方向正确；⚠️ 版本防覆盖**依赖事件携带版本**，未明确 |
| 索引重建 | ✅ 蓝绿正确；⚠️ "验证"内容未定义 |
| 删除后派生清理 | ⚠️ **FTS5 侧有实现缺口**（B-022） |
| 恢复后索引一致性 | ❌ **无校验、无验收**（B-019） |

**外部核实（官方文档，2026-11-03）**——要点：

1. **FTS5 `rebuild`** 先删全部索引再按内容表重建；contentless 表不支持 → 证明 FTS5 可完整重建。
2. **分词器是建表选项**（`tokenize=`）→ **推论**：换分词器**必须重建表**，须在建索引前定选型。
3. **FTS5 `secure-delete` 默认关闭**：删除只追加 delete-key，**旧词条保留到 merge**，「任何能访问数据库的人都可以轻易重建已删除行的内容」→ **B-022 直接依据**。
4. **WAL 文件属数据库持久状态**：与库分离可能丢失已提交事务或损坏 → D37 须确认 `-wal`/`-shm` 已消失。
5. **WAL**：读不阻塞写、写不阻塞读，但**同一时刻只有一个写者**，且**不支持网络文件系统** → 支撑 D12 正确性；也说明多机部署**必然要求换存储引擎**（非配置问题）。
6. **Backup API** 完成后为**位级一致快照**，可增量 → 支撑 D8 选型正确。
7. **VACUUM** 清除所有已删除痕迹，需**最多 2 倍**空间 → B-022 缓解手段，且与 D29 磁盘降级相关。
8. **`PRAGMA secure_delete` 默认 off** → B-022 依据。
9. **外键默认关闭**，须**逐连接**开启 → D5 L257/D11 L741 **不会自动生效**；属实施细节，不单列设计问题。
10. **LanceDB 向量列定长、维度不可原地 cast**（官方三步：加新列→删旧列→改名）→ **B-011 第 1、2 问直接依据**。
11. **LanceDB 支持 IVF_FLAT/IVF_PQ/IVF_HNSW_SQ** → D18 未来选项真实可得。

**未采用**：任何第三方博客数据、benchmark 分数、延迟数字、模型横评（B-015 执行）。

**一条理论推导（已标注，非实测）**：FLAT 单次查询 **O(N·d)**。在 Roadmap「单机/万级记忆」量级下可接受，但**这只是量级判断**。D18 要求"按真实测试数据比较"的纪律正确，**本审查不提供也未编造任何性能数字**。

**分级理由要点**

- **SQLite（A）**：四条件同时成立——单机单实例（D34）、万级数据、需 ACID 保证业务行+Outbox 原子、需可靠备份。官方证实 WAL"多读单写"与 D12 **完全对齐**（非照抄）。

- **FTS5（A）**：D21 定位判断准确（不做语义引擎）。需补的是删除语义（B-022）。
- **分词器（A）**：官方事实——**换分词器 = 删表重建**，故必须在首次建索引前定选型，不是"以后再说"。
- **Embedding 模型**：**方向 A**（D16 六条原则全对）；**选型 D**（§十 未定；B-005 已排除示例值）。**本审查不推荐任何具体模型**——无自有测试集（D-AP-06）、外部数据不可横比、选型应由 M02 效果驱动而 M02 尚是 Draft。**前置条件：先补 B-010/B-011，再定模型。**
- **FLAT（A，明确维持）**：本阶段**最应肯定**的决策。ANN 在当前量级收益为负、会引入新调参维度。D18 的"按真实测试数据再定"是**教科书级延后决策**，应作其他模块范例。唯一建议：补**可判定触发器**（与 D-AP-08 一致），当前只有"以后"。
- **Search Document（A）**：可替代性设计的**关键接缝**（共同输入），**值得保留，不应简化掉**。

### 10.1 阶段 1 重点问题回答
