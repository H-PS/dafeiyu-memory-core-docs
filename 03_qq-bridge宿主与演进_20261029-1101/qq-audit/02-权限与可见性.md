## 一、权限体系全景（五道闸 + 三处豁免）

```
                    ┌─────────────────────────────────────────────┐
QQ 消息 ──────────► │ 闸1 准入：allowed() / modeAllowed()          │  谁能触发 agent
                    ├─────────────────────────────────────────────┤
                    │ 闸2 工具面：tools.restrict + tools.guard     │  agent 能做什么
                    ├─────────────────────────────────────────────┤
                    │ 闸3 数据面：key 等值 + visibility/approved   │  能读到哪条记忆
                    ├─────────────────────────────────────────────┤
                    │ 闸4 出站：SENSITIVE_RE + 令牌脱敏 + CQ 转义   │  能说什么
                    ├─────────────────────────────────────────────┤
                    │ 闸5 本机入口：控制台令牌 + Host + CSRF        │  谁能改系统
                    └─────────────────────────────────────────────┘
                                     ▲
                     三处豁免：ownerQQ（审批/命令/静默）+ 控制台令牌（管理端）+ 回环地址
```

## 二、闸 1 · 准入（谁能触发 agent）

| 机制 | 位置 | 行为 | 证据强度 |
|---|---|---|---|
| 白名单/黑名单 | `allowed() bridge.js:1358` | deny 优先；`allow` 空 → `allowAllWhenEmpty`（默认 false = 全拒） | 【已确认】逐行读 |
| 模式门 | `modeAllowed() :2666` | `closed-agent` 只放行 `private:<ownerQQ>`；其余模式走 `allowed()` | 【已确认】 |
| 二次准入 | `isSessionAllowedInCurrentMode() :2713` | key 必须匹配 `^(group\|private):\d+$` 后再过 modeAllowed | 【已确认】 |
| 配置 fail-fast | `loadConfig()` | 配置缺失/解析失败直接退出 | 【已确认】`SECURITY_BASELINE.md` §2.1 |
| key 规范化 | `canonicalV2Key() :1370` | 去前导零、拒 0，防"同一会话多个别名" | 【已确认】 |

### 2.1 三个容易误判的点

1. **deny 是硬否决**，不是"deny 里没有但 allow 里有"就行。两者同时存在时 deny 赢。
2. **空白名单 = 全拒**（默认）。这是 fail-closed，与很多项目"默认全放行"相反。
3. **ownerQQ 不在白名单层豁免**。主人自己的私聊号也必须写进 `allow.private`（当前 `config.json:29-32` 已写 [OWNER_QQ] / [SECOND_QQ]）。管理员特权体现在闸 3 之后的业务分支，**不在准入层**。

## 三、闸 2 · 工具面（agent 能做什么）

**唯一权威实现**：`plugins/qq-agent-presets/qq-tool-restrict.mjs`（`dsh/agent-presets/*/qq-tool-restrict.mjs` 只是 re-export 壳）。

### 3.1 两道子闸

| 子闸 | 位置 | 时机 | 作用 |
|---|---|---|---|
| `tools.restrict({deny:[name]})` | `:282`，名单 `KNOWN_DANGEROUS_GLOBAL_TOOLS :182-208` | 注册期 | 把危险工具**从模型 schema 里隐藏**（模型看不到，不会诱导调用） |
| `tools.guard(exec => …)` | `:322` | 执行期 | 精确白名单：不在范围内**一律拒绝执行** |

### 3.2 执行期白名单（完整清单）

```js
SAFE_PREFIXES = [                       // qq-tool-restrict.mjs:215-220
  'mcp__snowluma__',        // 主力：聊天/记忆/表情/语音
  'mcp__snowluma-host__',   // 只有一个 snowluma_status
  'mcp__web-search-safe__', // 只读联网
  'mcp__diary__',           // 日记（只写）
]
SAFE_EXACT = new Set(['ask_user_question', 'todo_write'])   // :224-227
```

**这条对 Memory V2 直接有关**：

- 新增记忆工具如果挂在 `mcp__snowluma__` 命名空间下（即 `mcp-snowluma-safe.js` 里注册），**不需要改 guard**，白名单前缀天然覆盖。
- 如果新建独立 MCP server（如 `mcp__memory__`），**必须改 `SAFE_PREFIXES`**——这是安全边界的变更，属于需要评审的动作，不是"顺手加一行"。

### 3.3 restrict 名单规模与维护方式

- 约 **100 个名字**（`:120-208`），逐条注明来源包与判定理由。
- 维护铁律（`:32-41`）：**名字必须对着已安装 DSH 的真实工具清单核对**，因为 `tools.restrict()` 对不存在的名字会抛错、被逐个 `try/catch` 吞掉 → 假名 = 静默失效。
- 对账工具：`node scripts/scan-dsh-tool-names.mjs`，**每次升级 DSH 后必须跑**。
- 失败会落盘到 `state/tool-restrict.log`（只保留最近 20 行，`:259`）。

**已知实测风险**（`:230-240`）：2026-10-18 发现重启后新会话 schema 里 `dev_*` 仍有 18 个，说明 restrict 曾整批没生效且被吞。所以才加了"3 秒后重试失败项 + 落盘诊断"。

### 3.4 被明确禁掉、与记忆相关的工具

| 被禁工具 | 为什么与记忆有关 |
|---|---|
| `session_search` / `session_trace` / `session_event_read` / `session_event_search` / `session_event_trace` | 能跨会话读事件正文 = 能把别的聊天记录递给 QQ 群。**因此模型永远无法自己查 DSH 会话历史** |
| `read_mcp_resource` / `list_mcp_resources` | `server` 参数可指向任意 MCP，等于绕过工具白名单 |
| `working_directory` | 全局层默认启用，会暴露本机路径 |

**【已确认推论】**：因为 `session_*` 全被禁，模型对"历史"的唯一信息来源就是 bridge 提供的 `recentMessages` / `unread` / `getPrompt` / `memory` 四类工具。**Memory V2 的召回不是"替代 DSH 的历史检索"，而是唯一可行的补充路径。**

## 四、闸 3 · 数据面（能读到哪条记忆）—— 现存最大缺口

### 4.1 现有实现（逐行确认）

```js
// memory-vector.js:171-178
export function searchVectorMemory(key, topic, topKOverride) {
  const rows = loadRows().filter((r) => r.key === key && Array.isArray(r.vec));   // ① key 等值
  if (!rows.length) return Promise.resolve([]);
  const isOwnerPrivate = key.startsWith('private:');                              // ② 私聊判定
  const visible = isOwnerPrivate
    ? rows
    : rows.filter((r) => r.visibility === 'group_shared' && r.share_review_status === 'approved'); // ③ 群聊双闸
  ...
}
```

| 层 | 机制 | 状态 |
|---|---|---|
| ① 会话隔离 | `r.key === key` 严格相等 | ✅ 成立（私聊记忆不可能被群 key 命中） |
| ② 私聊判定 | `key.startsWith('private:')` | ✅ 已在 P0 修复（原来是硬编码主人 QQ，别人私聊查不到自己的记忆） |
| ③ 群聊双闸 | `visibility==='group_shared'` **且** `share_review_status==='approved'` | ⚠️ **这就是"群聊记忆恒不可检索"的根因**（见 4.2） |

### 4.2 已知结构缺陷（两条，均已在前序审计记录在案）

**缺陷 1：群聊双闸导致群内自产记忆不可检索**

- 写入侧：`appendVectorMemory`（`memory-vector.js:149-163`）新记录默认 `share_review_status:'not_requested'`。
- 读取侧：群 key 必须 `approved`。
- 分享申请端点：`bridge.js:6892-6895` **明确拒绝 private key**，只允许 group key 申请，且要人工逐条审批。
- ⇒ 群聊里写进去的记忆，不经审批就永远检索不到。

项目全景 §五 P0-3 已记载同一现象（"群聊当前 0 条记忆可检索"），并指出真实原因："key 与 approved 双闸门同时收紧"。**至今未修**。

**缺陷 2：记忆层不认识"调用者是谁"**

- `canRead` 这一层不存在。当前只有 key 等值 + 双闸两个条件。
- 后果：同一个 key 下，无论调用者是模型、管理端还是脚本，看到的都是同一批数据。**没有 "caller" 维度**。
- 目前没出事，是因为管理端走的是另一个端点（`/api/memory/admin`），且群聊那条路被闸死。

### 4.3 白名单与记忆读取的关系（关键结论）

| 问题 | 结论 | 证据 |
|---|---|---|
| 会话被移出白名单后，它的记忆还能被检索吗 | **检索入口被堵，但数据仍在** | 入口：`handleIncoming` 的 `modeAllowed` 会直接 return；数据：A 层无 `active` 标志，`searchVectorMemory` 不查白名单 |
| 白名单是否影响记忆可见性 | **不影响**（两者解耦） | `allowed()` 只在准入与发送处调用（5 个调用点，`:2672/4226/4348/6599/11323`），记忆路径不调用 |
| 这是缺陷还是设计 | 【推断】是设计 | 白名单是"谁能跟机器人说话"，不是"机器人能记得谁" |

> 这条对 Memory V2 有直接含义：**不要把 `allowed()` 当成记忆权限用**。会话级准入（是否允许对话）与记忆级可见（哪条记忆可被注入）是两个正交维度，混在一起会出现"删了白名单就丢记忆"或"加回白名单就复活旧记忆"的意外。

## 五、闸 4 · 出站（能说什么）

| 机制 | 位置 | 行为 |
|---|---|---|
| 敏感拦截 | `auditAndSend` / `SENSITIVE_RE` / `assertOutboundAuditOk` | 命中本机路径/UNC/凭据赋值形态 → **整条不发**；语音按文件名审计；错误文本、审批理由、工具名同样过审 |
| 令牌脱敏 | `redactKnownTokensOnly` + `onebotSend` | 所有已知 agent token 出站前脱敏；若文本里**仍出现**已知令牌 → **直接抛错不发** |
| CQ 注入 | `onebotSend` | 出站文本一律包成 `{type:'text'}` 段，`[CQ:` → `[CQ：` 转义 |
| @ 限制 | `onebotSend` | `atUserId` 只接受正整数，**禁止 @all** |
| 限流 | `socialV2.send.*` / `voice.*` / `sticker.collect.*` | 每分钟/每小时硬上限 |

**已知残余风险（官方文档自认）**：`SECURITY_BASELINE.md` §三 R1 —— 敏感审计是**启发式**，能抓"带赋值关系的凭据"和本机路径，抓不到任意形态的秘密。

## 六、闸 5 · 本机入口（控制台）

| 机制 | 行为 |
|---|---|
| 只监听回环 | `server.listen(port, '127.0.0.1')`，永不绑 `0.0.0.0` |
| 令牌门 | **所有**路由（读+写）都要 `x-console-token` 或 `?token=`；未配置时启动生成 192 bit 随机值（`config.json:46` 已配） |
| 定长比较 | `crypto.timingSafeEqual`，先比长度 |
| Host 校验 | 必须 `127.0.0.1:<port>` / `localhost` / `[::1]`，否则 403（防 DNS rebinding） |
| CSRF | 非 GET 必须 `content-type: application/json`；带 `Origin` 时 host 必须本机 |
| agent token 隔离 | 带 `x-agent-token` 的请求**默认拒绝**，仅放行 `/api/status`、`/api/socialV2/*`、`/api/send/*`、`/api/images/*`、`/api/authorize/read`；管理端点（人格/提示词/白名单/重启/令牌）一律 403 |
| 空令牌拒绝 | `x-agent-token === ''` 一律 403（防"空 = 管理端"绕过） |
| 请求体限制 | >1MB → 413；30 秒读取超时 |

### 6.1 记忆端点的实际鉴权（三重，已逐行确认）

```js
// bridge.js:6862-6878  GET /api/socialV2/memory-vector
if (!key) → 400
if (!token || !agentTokenOk(key, token)) → 403      // ① 令牌与 key 绑定
if (!v2SessionAllowed(key)) → 403                   // ② 会话允许（**是否含白名单：见下**）
if (!v2ToolEnabled('memory')) → 403                 // ③ 工具开关
if (!topic) → 400
searchVectorMemory(key, topic, 5)
```

⚠️ **U-4（无法确认）**：`v2SessionAllowed(key)` 的实现未读到，**不确定它是否包含 `allowed(kind,id)` 白名单校验**。这影响"白名单与记忆读取边界"的结论强度，列为待核查项（见 06 文档 §五）。

**【已确认】** 同一端点还区分了"错误码语义"：
- 向量检索抛错 → `500 {ok:false, error:'向量检索失败'}`
- 检索成功但无命中 → `200 {ok:true, count:0, hits:[]}`
（这是 P0 阶段特意区分的，避免"失败被当成没找到"）

## 八、身份传递链（谁能证明自己是谁）

```
QQ event.user_id ──► isOwner 布尔 ──► 业务分支（审批/命令/静默）
                              └──► 写入记忆时的 origin.sender【当前未记录】

agent 身份 ──► prompt 里的【会话令牌】(:10674)
            ──► 模型把它作为工具参数 token 传入（40+ 工具 schema）
            ──► MCP 放入 x-agent-token 头
            ──► bridge agentTokenOk(key, token) 校验
```

**两个结构性弱点（已确认）**：

1. **令牌靠模型携带**。模型可能忘传（导致 403）、可能传错（别人的 key）、也可能被提示注入诱导泄露。脱敏 (`redactKnownTokensOnly`) 只是兜底。
2. **发送者身份不进记忆**。当前 A 层记录里**没有**`origin.sender`（`memory-vector.js:155-158` 的 row 只有 key/text/time/vec/share_review_status）。⇒ 无法回答"这条是谁说的"，也无法按来源做权限判定。

## 九、可见性矩阵（现状，不是设计目标）

| 数据 | 群聊能否看到 | 私聊能否看到 | 管理端 | 证据 |

## 十、给 Memory V2 的三条硬约束（结论）

1. **不要另造一套准入**。`allowed()` + `modeAllowed()` 已经覆盖"谁能对话"，Memory V2 只需在**读取侧**补一个 `canRead(record, ctx)`，两个维度正交。
2. **群聊可见性必须换成"来源 + 内容分级"**，不能继续用 `approved` 单闸——单闸的语义是"人工审过"，它无法表达"群内自产的非敏感内容"。
3. **写入必须补 `origin.sender` 与 `origin.groupId`**，否则永远无法回答"这条是谁在哪个群说的"，后续任何来源维度的权限判定都无从做起。
