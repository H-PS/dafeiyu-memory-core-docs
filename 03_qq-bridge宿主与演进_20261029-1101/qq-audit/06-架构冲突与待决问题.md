# 06 · 架构冲突与待决问题

> 只列**证据支持**的冲突。每条给：现象 → 证据 → 与 Memory V2 的哪一处冲突 → 建议处置（不是实施）。
> 严重度：**P0** = 按原设计实施会直接坏功能或破安全；**P1** = 会造成返工或语义混乱；**P2** = 需要知晓的约束。

---

## 一、冲突清单

### C-1 · 人格注入频率 ⟷ Block Ledger 降频（**P0，最严重**）

| 项 | 内容 |
|---|---|
| 现象 | `buildWakePromptV2` 每轮注入人格全文（~1,380 字符）。Memory V2 的 Block Ledger 设计为 `personaAnchorEveryTurns: 12`（第 2 轮起不再发全文，只发一行锚点） |
| 证据 | ① `bridge.js:10671` `roleLine` 每轮含 `currentRoleHintV2()` 全文<br>② `项目全景-记忆链路` 阶段 2 关键突破原文：「人格**全文注入**（原来只给一句"调 qq_get_prompt 查看"，模型不调就看不到）」——这条被列为"人格立住"的五个突破之一<br>③ `config.json:13` `role.maxInjectChars: 6000` 说明开发者有意给足空间 |
| 冲突点 | Ledger 的核心假设是"静态块发一次就够"，而本项目的实践证据是"不发就漂"。若照 12 轮锚点实施，**极可能重演"人格不生效"** |
| 建议处置 | ① 人格块**不纳入 Ledger 降频**（保持每轮），只把"表情清单 / 黑话表 / 睡眠规则 / 首回复节奏"这些**规则类**块纳入<br>② 若一定要降频，先做 A/B：同一剧本 40 轮，锚点 12 轮 vs 每轮，用盲评判人格一致性<br>③ 这一步不做实测就上，是在拿一条已验证的结论去赌 |
| 影响 | 若按原设计：省 ~1,000 token/轮，但人格漂移风险不可控；若按建议：省 ~1,900 token/轮（去掉规则类块），收益仍是主要部分 |

### C-2 · `retireSession` 重置 agentToken ⟷ `rotationTx` 第 5 步（**P0，已由证据确认**）

| 项 | 内容 |
|---|---|
| 现象 | Memory V2 的会话轮转流程第 5 步是 `retireSession(key)`，第 6 步清 ledger 并注入 digest |
| 证据 | `bridge.js:2793-2797`：<br>`st.agentToken = crypto.randomBytes(24).toString('hex')`<br>`rememberAgentToken(key, st.agentToken)`<br>`st.bootstrapSent = false`<br>`st.modelSeenSeqs = new Set()`<br>另外 `/reset` 走的是 `forgetAgentToken(key)`（`:11308`）——**两种退役路径对 token 的处理不一致** |
| 冲突点 | 轮转后 agent 手里的旧 token 立刻失效，而新 token 只在下一轮 prompt 的【会话令牌】块里出现。若 Ledger 把 credential 块设为"只发一次"，**轮转后模型将不再拿到新 token ⇒ 所有工具调用 403** |
| 建议处置 | ① 轮转必须**强制重置 credential 块的 ledger 记录**（`epoch++` 时清 blocks，这一点原设计有写，但没点明"因为 token 会变"）<br>② 两种退役路径（`retireSession` vs `/reset`）对 token 的处理不一致，需统一或明确记录在案<br>③ 这条同时说明：**Memory V2 的凭据带外绑定（S-13）在本项目里价值更高**——带外绑定后，轮转不再影响凭据 |
| 影响 | 不做：轮转后功能静默失效，表现为"她突然不能存记忆了"，且错误被审计层隐藏（项目全景 §八 已知坑） |

### C-3 · 群聊双闸 ⟷ D-24 三字段权限模型（**P0**）

| 项 | 内容 |
|---|---|
| 现象 | 群内自产记忆默认 `not_requested` → 检索侧要求 `approved` → **群聊永远查不到** |
| 证据 | 写：`memory-vector.js:157`（默认 `not_requested`）<br>读：`memory-vector.js:176-177`（group key 需 `group_shared && approved`）<br>申请：`bridge.js:6892-6895`（明确拒绝 private key，group key 只能申请、不能自批）<br>历史记录：`项目全景` §五 P0-3「群聊当前 0 条记忆可检索」，至今未修 |
| 冲突点 | Memory V2 已把 D-24 重新定义为"来源 + 内容分级 + 审核状态"三字段，但**现有代码是单闸（approved）**。若只改 Schema 不改这道 if，三字段永远不生效 |
| 建议处置 | 最小改动点只有三处：`memory-vector.js:157`（写入默认）、`:176-177`（读取过滤）、`:217`（管理端过滤）。但**必须先有 `contentClass` 分类器**，否则"改成默认可见"会立刻把私事推到群里 |
| 影响 | 顺序反了就是事故：先开可见性、后补分类器 = 一次真实的隐私泄露 |

### C-4 · 白名单是"准入"，不是"记忆权限"（**P1**）

| 项 | 内容 |
|---|---|
| 现象 | `allowed()` 只在 5 个位置被调用（`:2672 / 4226 / 4348 / 6599 / 11323`），**记忆读取路径完全不调用** |
| 证据 | 见 02 文档 §4.3；`memory-vector.js` 全文无 `allowed` 引用 |
| 冲突点 | Memory V2 的 `canRead(record, ctx)` 若只看 `key`/`scope`，会出现"会话已被移出白名单，但它的记忆在管理端与内部 API 里依旧可读"。这**可能是有意的**（数据不该因为拉黑而丢失），但必须显式决定 |
| 建议处置 | 明确两条正交维度：<br>· 准入 = 能不能跟机器人说话（`allowed`）<br>· 可见 = 哪条记忆能被注入（`canRead`）<br>并在文档里写清"白名单变更不删除、不隐藏记忆"。**不要把 `allowed()` 塞进 `canRead()`**，那会让"临时拉黑"变成"永久失忆" |
| 影响 | 语义混乱 + 未来排障困难（"为什么她被拉黑后还记得我" 是正常行为，不是 bug） |

### C-5 · key 生成规则必须复用 `canonicalV2Key`（**P1**）

| 项 | 内容 |
|---|---|
| 现象 | 现有 key 规范化：`canonicalV2Key()`（`bridge.js:1370`）只接受 `^(group\|private):\d+$`，去前导零、拒 0、拒非安全整数 |
| 证据 | `:1370-1376`；`convKey(kind,id)` 在 `:11200` 使用 |
| 冲突点 | Memory V2 的 `SCHEMA.md` 写 `key: "group:123456"` 但未声明规范化规则。若新模块自造 key（如保留前导零、或允许 `private:abc`），会出现**同一会话两个别名**，导致记忆分裂 |
| 建议处置 | 所有新模块统一调 `canonicalV2Key()`，且**导入历史数据时必须先规范化**（历史上是否有别名：`项目全景` §4.4 提到"数值型 key 规范化（group:0123 = group:123，防别名）"已做过一次，说明这个问题真实发生过） |

### C-6 · `/reset` 的现状语义 ⟷ D-23（**P1，但证据已可回答问题**）

| 项 | 内容 |
|---|---|
| 现象 | `/reset` 清 ~25 个内存结构 + `socialV2.conversations.delete(key)`（清 B 层）+ `forgetAgentToken`，**完全不碰 A 层** |
| 证据 | `bridge.js:11268-11319`，全段无 `memory-vector` 调用；`saveSocialV2State()` 只写 S 层 |
| 结论 | **D-23 的答案已经存在**：现状 = `reset` 不清 A 层。若 Memory V2 默认"清 A"，是**行为变更**，不是"补全语义" |
| 建议处置 | 保持现状（不清），另设显式 `purge`。理由：用户已习惯"reset 只重开上下文"，且项目全景 §六 用户待办里有"别 reset"这种话（说明 reset 曾被当作"忘掉刚才聊的"用） |

### C-7 · `prompt-dump.log` 落盘完整明文（含令牌）（**P1 安全**）

| 项 | 内容 |
|---|---|
| 现象 | `deliverPromptNow` 每次都 `fs.appendFileSync('state/prompt-dump.log', …完整 promptText…)`（`:9485-9487`），而 promptText 含【会话令牌】块 |
| 证据 | `:9485`；`:10674` tokenLine |
| 冲突点 | Memory V2 若把"记忆全文 + 召回结果"注入 prompt，这些内容也会被完整落盘 ⇒ **`prompt-dump.log` 将成为一份没有权限控制的记忆副本** |
| 建议处置 | ① 这是既有风险（不是 Memory V2 引入），但注入量增加会放大它<br>② 至少确认 `state/` ACL 已收紧（`hardenStateDirAcl` 有跑）<br>③ 若要改：dump 时对 credential 块做替换，或改为只 dump 块名+长度<br>④ 这条属于"实施前应决策"，不是 Memory V2 范围内必须改的 |

### C-8 · 日记只写不读 ⟷ Reflect 想拿日记做素材（**P2**）

| 项 | 内容 |
|---|---|
| 现象 | `mcp-diary.js` 只有 `qq_write_diary`，无读工具；且模型没有 `read`/`glob`（被 restrict 禁） |
| 证据 | `mcp-diary.js:5-8` 注释「只能追加，不能覆盖、不能读、不能删」；`qq-tool-restrict.mjs:124-126` 禁 `read`/`glob` |
| 冲突点 | 若 Reflect 要"从日记提炼观察"，必须新增读路径 ⇒ 日记（含私密细节）进入 prompt ⇒ 与"隐私尺度"这条用户待决项（项目全景 §十 第 5 条"#004 日记内容的隐私尺度"）直接冲突 |
| 建议处置 | M2 阶段**不要把日记纳入 Reflect 输入**。日记是"她写给自己的"，不是"可被检索的记忆"。若未来要，需要独立的权限通道 |

### C-9 · 两套审核队列会并存（**P1**）

| 项 | 内容 |
|---|---|
| 现象 | 现有：`share_review_status`（`not_requested/pending/approved/rejected`）+ 控制台"记忆分享审核"面板（v23） |
| 冲突点 | Memory V2 引入 `review.status` + `reviewQueue`（含 quarantine / observation / conflict 三类）⇒ **同一个控制台会出现两个"待审核"入口**，语义还不一样（分享审 = 跨会话共享；quarantine = 内容敏感隔离） |
| 建议处置 | ① 明确两者语义不同，**不是重复**：分享审决定"能否跨会话共享"，quarantine 决定"是否连本会话都不给看"<br>② 但 UI 必须合并为一个"待处理"列表，用类型字段区分；否则没人会去看第二个<br>③ 迁移时把历史 `pending` 映射到新队列的 `share` 类型 |

### C-10 · 新增独立 MCP server 会被 guard 拒（**P2 约束**）

| 项 | 内容 |
|---|---|
| 现象 | `SAFE_PREFIXES` 只允许 4 个前缀（`qq-tool-restrict.mjs:215-220`），执行期 `guard` 对不在范围内的一律拒绝（`:322-328`） |
| 结论 | ① 记忆工具挂在 `mcp__snowluma__*` 下 → **零改动**<br>② 新建 `mcp__memory__` → 必须改 `SAFE_PREFIXES`（安全边界变更，需评审 + 回归） |
| 建议 | 走 ①。不要为了"模块清晰"新建 server——那会动到项目最硬的一道边界 |

### C-11 · `social-v2.json` 被 43 处整文件重写 ⟷ Memory V2 依赖 S 层（**P1**）

| 项 | 内容 |
|---|---|
| 现象 | S 层（`social-v2.json`）承载 B 层记忆 + 会话状态 + token + wakeConfig，被 43 处整文件重写覆盖（Memory V2 前序审计结论） |
| 冲突点 | Memory V2 要在 S 层新增 `promptLedger` / `rotationTx` / `clearEpoch` / `reviewQueue` / `pendingEmbed`。**这些字段一旦被某处旧代码的"读-改-写"覆盖，会静默丢失** |
| 建议处置 | ① 拆分优先级：`agentToken`、`interactionCount`、`promptLedger`、`rotationTx` 先各自独立文件<br>② 若不拆，必须给 S 层写路径加"字段级合并"保护（读最新 → 只改自己的字段 → 写回），但这仍需排查 43 处<br>③ 这是 Memory V2 里**最容易被低估的工作量** |

见 05 文档 §四。要点：`token-ledger` 是会计，`estimateTokens` 是预算员，报告里必须分开写。

## 五、给 Memory V2 的三条修订建议（不含实施）
