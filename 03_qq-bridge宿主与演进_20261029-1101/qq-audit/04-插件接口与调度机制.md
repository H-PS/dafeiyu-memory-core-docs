## 一、四个 MCP Server（模型的全部外部能力）

| Server | 文件 | 行数 | 工具数 | 注册名（供 guard 匹配） | 能力性质 |
|---|---|---|---|---|---|
| snowluma-safe | `src/mcp-snowluma-safe.js` | 1,465 | 40+ | `mcp__snowluma__*` | 聊天/记忆/表情/语音/群操作（**主力**） |
| snowluma-host | `src/mcp-host-server.js` | — | **1** | `mcp__snowluma-host__*` | 只有 `snowluma_status`（只读探活） |
| web-search-safe | `src/mcp-web-search-safe.js` | — | 少量 | `mcp__web-search-safe__*` | 只读联网（走 `safe-fetch.js`） |
| diary | `src/mcp-diary.js` | ~120 | **1** | `mcp__diary__*` | `qq_write_diary`，只写不读 |

### 1.1 snowluma-safe 的三重鉴权（所有工具共用）

```js
// 以 memory-vector 为例，bridge.js:6862-6870
token = req.headers['x-agent-token']
if (!token || !agentTokenOk(key, token)) → 403      // ① 令牌与 key 绑定
if (!v2SessionAllowed(key)) → 403                  // ② 会话允许（实现未读，U-4）
if (!v2ToolEnabled('memory')) → 403                // ③ 工具开关（config.socialV2.tools.*）
```

**令牌来源**：prompt 的【会话令牌】（`:10674`）→ 模型作为工具参数 `token` 传入 → MCP 放进 `x-agent-token` 头。

### 1.2 工具开关粒度

`config.json:118+` `socialV2.tools.{getPrompt,getUnread,getRecent,socialState,sendGroup,sendPrivate,reply,sendBurst,sendMessage,waitMessages,feedback,getMyRecent,…}`，逐工具布尔开关，由 `v2ToolEnabled()` 校验。

**含义**：Memory V2 新增 `qq_memory_recall` 时，应同时进这个开关表，否则无法单独关闭。

### 1.3 diary 的特殊性（对 Memory V2 有直接影响）

```js
// mcp-diary.js:1-8 注释
// - 只暴露一个写工具 qq_write_diary
// - 路径写死 <项目根>/diary/YYYY-MM-DD.md
// - 不接受路径参数、不接受文件名参数
// - 只能追加，不能覆盖、不能读、不能删
// - 单条 ≤2000 字；单日文件 ≤100KB
```

**结论**：日记是**单向漏斗**。模型写进去就再也读不出来（没有读工具，也没有 `read` 本地工具）。
⇒ Memory V2 若要把日记作为 Reflect 的素材，**必须新增读路径**，而新增读路径意味着：日记里的私密内容会进入 prompt。这是一个需要显式决策的风险点（06 文档 C-8）。

## 二、两个 DSH 插件

| 插件 | 位置 | 提供什么 | 限制 |
|---|---|---|---|
| `qq-mode-console` | `plugins/qq-mode-console/lib/index.js` + `cordis.patch.yml` | 暴露 `qq-mode` settings 命名空间（模式读写） | **只有 host 半，浏览器 UI 卡片未实现**（FOLDER_MAP 明确记载） |
| `qq-agent-presets` | `plugins/qq-agent-presets/` | 注册 `qq-chat` / `qq-chat-v2` 两个 preset 行；携带**唯一权威** `qq-tool-restrict.mjs` 实现 | 改了要重装/重启 DSH |

### 2.1 preset 的生成链（改规则必须走这条）

```
dsh/agent-presets/qq-chat-v2/agent.cordis.yml          ← 权威源（24,721 字节）
        │  node scripts/build-agent-preset-patches.mjs
        ▼
plugins/qq-agent-presets/presets/qq-chat-v2.patch.yml  ← 生成物（23,386 字节）
        │  ← ~/.dsh/plugins/qq-agent-presets 是 **junction**，realpath 指向项目 plugins
        ▼
DSH 加载（需重启 DSH 生效）
```

**关键事实**：`~/.dsh/plugins/qq-agent-presets` 是符号链接/junction，不是副本。所以"改项目里的 patch 文件"= 改 DSH 实际加载的文件，但**仍需重启 DSH**。

### 2.2 人格层 vs 仿真层的生效差异

`项目全景` §7.1 第 4 条：「人格层保存即生效，仿真层需重启 DSH」。

- 人格卡 `roles/*.md` → 控制台保存即生效（下一轮注入读到新内容）。
- preset / 工具守卫 / MCP 挂载 → 改完必须重启 DSH。

**对 Memory V2 的含义**：如果 Block Ledger 要读"规则块"的 hash，必须知道规则改动的生效时机是"重启 DSH"，否则会出现 ledger 认为没变、实际已变（或反之）的错配。

## 三、定时任务：全项目只有 4 个 setInterval

| # | 位置 | 周期 | 做什么 |
|---|---|---|---|
| T-1 | `bridge.js:2949` | 5 s | `checkDsh`：DSH 健康探测 |
| T-2 | `bridge.js:3109` | `SNOWLUMA_STATUS_POLL_MS` | `pollSnowlumaStatus`：SnowLuma 在线状态 |
| T-3 | `bridge.js:3111` | 30 s | `reportSnowlumaHealth`：上报健康 |
| T-4 | `bridge.js:9745` | 5 s | `socialLoopTick`：**社交状态机主循环** |

`src/` 下 `setInterval|setTimeout` 总计（次）：`bridge.js` 25、`voice-core.js` 3、`safe-fetch.js` 2、`self-test.js` 2、`dsh-client.js` 1、`mcp-snowluma-safe.js` 1、`media-normalize.js` 1、`web-search.js` 1。其中绝大多数 `setTimeout` 是一次性延迟（限流退避、定时发送、ephemeral timer），不是周期任务。

### 3.1 socialLoopTick 的负担

它是**唯一周期性的业务逻辑循环**，每 5 秒对全部活跃会话做：

- 社交阶段判定（观望 → 活跃 → 退场）
- 触发概率抽签
- 退场超时判定（`triggerActiveDurationExit`）
- 冷场/主动开话题判定
- 唤醒租约检查

**对 Memory V2 的含义**：Retain（每条消息后）与 Reflect（周期性整理）如果也塞进这个循环，会与它抢同一帧 CPU。而 `SECURITY_BASELINE` 的改动检查单第 5 条明确要求"新增的定时器在会话退役与进程退出路径上都清理"，说明定时器泄漏在本项目是已知敏感点（`cancelSocialTimers` / `clearSocialV2Timers` / `disarmPendingWakeLease` 三个清理函数的存在就是证据）。

## 四、队列与异步：五种，无通用任务队列

| # | 队列 | 位置/类型 | 容量 | 持久化 | 失败行为 |
|---|---|---|---|---|---|
| Q-1 | prompt 串行队列 | `promptQueues`（Map<key, {queue,...}>） | — | ❌ 内存 | 逐项 reject |
| Q-2 | 离线消息队列 | `queued`（Map<key, items[]>） | **50/会话** | ❌ 内存 | **进程退出即丢**（SECURITY R5） |
| Q-3 | 待审批/待回答 | `pending`（Map<key, entry>） | 1/会话 | ⚠️ 部分（`questionTimeoutMs=300000`） | 超时处理 |
| Q-4 | 唤醒租约 | `pendingWakeKeys` + `pendingWakeLease` | — | ❌ | `disarmPendingWakeLease` |
| Q-5 | 重试队列 | `enqueueForRetry` | — | ❌ | 依赖会话重建成功 |

**没有的**：
- 通用工作队列（无优先级、无重试策略、无 backpressure）
- 任务持久化（除 token 账本与状态文件外，所有队列都在内存）
- 取消/超时统一抽象（每处各写一套 `clearTimeout`）

**对 Memory V2 的含义**：Retain/Reflect 如果需要一个"后台任务队列"，**这是纯新建**，不能"复用现有队列"——现有五个队列都是场景专用的，语义无法承载"按优先级处理记忆抽取"。

## 七、对 Memory V2 的四条结论

1. **MCP 不需要新建 server**，只要进 `mcp__snowluma__` 命名空间，guard 天然放行（`SAFE_PREFIXES` 已覆盖）。这是最低摩擦路径。
2. **工具开关要成对**：新工具必须同时进 `socialV2.tools.*`，否则无法单独停用。
3. **队列是新做**：没有任何现有队列能承载"按优先级处理记忆任务"。但可以直接复用 `token-ledger` 的"append + 定期 compact + 淘汰保总量"范式。
4. **定时任务必须避开 socialLoopTick**：它是唯一业务周期循环，已被状态机占满；再加逻辑要么降频，要么用独立的 `setInterval` 并在 `retireSession` / 进程退出路径上显式清理（这是本项目既有铁律）。
