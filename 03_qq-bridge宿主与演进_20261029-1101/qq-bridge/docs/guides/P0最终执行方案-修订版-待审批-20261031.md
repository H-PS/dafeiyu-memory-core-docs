# 二、A/B 记忆生命周期一致性审查（本轮新增）

## 2.1 qq_memory_remove：两层如何定位、删除、执行顺序

【已确认】当前实际行为：

```
MCP 端（mcp-snowluma-safe.js:1019-1030）
  → 只发一个 POST /api/socialV2/memory-remove（带 token）
  → 没有任何 A 层联动

B 层（bridge.js:6808-6833）
  → 定位：按 key + category + content（activeTopic/pendingThought 用 content 全等）
          或 key + category + target（memberImpression 用 target 名）
  → 删除：st.activeTopics.filter(...) / st.pendingThoughts.filter(...) / delete st.memberImpressions[target]
  → 落盘：saveSocialV2State()
  → 【不碰 A 层】

A 层（memory-vector.js）
  → 完全没有被 qq_memory_remove 调用
```

**结论【已确认】**：`qq_memory_remove` 只删 B 层，A 层对应记录**原样保留**。这就是"删掉的印象还能被向量检索到"的根因。

## 2.2 qq_memory_clear：清理范围是否严格限定当前 key

【已确认】`bridge.js:6834-6850`：

```
定位：getSocialV2State(key)  ← 按 key 取该会话状态
清理：st.activeTopics=[] / st.pendingThoughts=[] / st.memberImpressions={}
落盘：saveSocialV2State()

A 层：完全未联动
```

**清理范围严格限定当前 key 的 B 层状态**【已确认】——它只操作 `getSocialV2State(key)` 返回的那一个会话对象，不会跨用户/跨群。**但 A 层同样未清理**，留下该 key 下的全部向量记录。

## 2.3 qq_memory_append：两层写入是否可能部分成功

【已确认】**可能部分成功。** 执行顺序：

```
MCP 端（mcp-snowluma-safe.js:937-950）：
  ① 先 POST /api/socialV2/memory-append（B 层，带 token，三重校验）  :939
     → 成功返回 data
  ② 再进程内 appendVectorMemory(key, `${category}: ${content}`)       :946
     → 若 embed 失败或 infoOK 拒绝，走 catch 只 console.error，不影响返回
```

**部分成功场景**：
- B 层写成功 + A 层 embed 失败（Ollama 挂了 / 超时）→ B 层有、A 层无 → **"她记了但检索不到"**
- B 层写成功 + A 层 infoOK 拒绝（太短）→ 同上
- B 层失败（403/400）→ :939 抛错 → 走 :951 catch → A 层**不会执行** → B 层无、A 层无（一致，无残留）

**结论【已确认】**：只有"B 成功 + A 失败"这一种部分成功方向，且**静默**（只 console.error，模型收到的仍是 B 层成功的结果）。

## 2.4 qq_memory_edit：是否存在、是否同步、embedding 是否重算

【已确认】**不存在 `qq_memory_edit` 这个 MCP 工具。** 但存在两个独立的"编辑"入口：

| 入口 | 层 | 位置 | 行为 |
|---|---|---|---|
| `/api/socialV2/memory-update` | B 层 | bridge.js:6715 | 改 st.activeTopics/pendingThoughts/memberImpressions 字段，`saveSocialV2State` |
| `/api/memory/admin` op=edit | A 层 | bridge.js:6688 → `editVectorMemory` | 改 text + **重算 embedding**（memory-vector.js:297-310） |

**两者完全独立，无任何联动**【已确认】：
- B 层 update 不碰 A 层，A 层的旧 text 和旧向量原样保留。
- A 层 admin edit 不碰 B 层。
- 只有 A 层 edit 会重算 embedding（`editVectorMemory` 里 `await embed(clean)`）；B 层 update 无 embedding 概念。

## 2.5 A/B 是否有共同记录 ID

【已确认】**没有。**

| 层 | 定位依据 | 唯一性 |
|---|---|---|
| A 层 | `key` + `text`（全等，见 findMemoryRow :210-233 的 4 级匹配） | 无 ID，text 变化即失联 |
| B 层 | `key` + `category` + `content`（或 `target`） | 无 ID，content 变化即失联 |

**仅靠 key+text 匹配的风险【已确认】**：
1. 同一 key 下两条 text 相同（可能吗？infoOK 不查重，理论上可重复写入）→ 匹配会命中多条。
2. B 层 content 和 A 层 text 之间**没有对应关系**——A 层 text 是 `${category}: ${content}` 的拼接（mcp:946），但 B 层 content 一旦被 update 改过，A 层 text 还是旧的，**key+text 就对不上了**。
3. 无法追踪"这条 A 记录对应哪条 B 记录"，同步删除/修改无从下手。

## 2.6 一层成功另一层失败时如何报告、是否留残留

【已确认】三种操作的报告方式：

| 操作 | 报告 | 残留风险 |
|---|---|---|
| append（A 失败） | 只 console.error，返回 B 层成功 | **有**：B 有 A 无，静默 |
| remove（只删 B） | 返回 `ok:true` + formatMemoryV2 | **有**：A 层残留，用户以为删干净了 |
| clear（只清 B） | 返回 `ok:true` | **有**：A 层整库残留 |

**结论【已确认】**：当前系统**没有任何机制**检测或报告"A/B 不一致"，残留是**静默且无法被用户发现**的。

## 2.7 是否可复用现有 bridge 接口实现同步

【已确认】**可以，且是最自然的做法。**

```
已有可复用的 A 层操作（都在 bridge 的 /api/memory/admin 里，或 memory-vector.js 导出）：
  removeVectorMemoryExact(key, text)     :286
  editVectorMemory(key, oldText, newText) :297
  listVectorMemory({key})                 :185
  appendVectorMemory(key, text)           :124

B 层端点（bridge.js）里，在 saveSocialV2State() 前后加 A 层联动即可：
  memory-remove  → 删 B 层后，调 removeVectorMemoryExact 删 A 层
  memory-clear   → 清 B 层后，按 key 删 A 层全部（需新增"按 key 删全部"的函数）
  memory-append  → B 层成功后，改为在 bridge 进程内写 A 层（而非 MCP 进程内）
```

**关键**：A 层操作函数都在 `memory-vector.js`，bridge 已经 import 了它们（bridge.js:15），所以"把 A 层写/删/改挪进 bridge 的 B 层端点"是零新增依赖的。

# 三、A/B 同步的推荐修复方案

## 3.1 设计原则（明确约束）

```
1. 不得扩大删除范围：同步只删"同一 key 下、能精确匹配的那一条"，绝不做模糊批量删。
2. 不引入新的共享机制。
3. 不保证原子性时明确说明——两层是独立文件，无法在单个 write 里同时写两个文件，
   只能做到"尽力一致 + 失败可发现 + 可补偿"。
4. 不清理历史残留：本轮只修"未来的操作会同步"，不回头清已有残留（除非你另行批准）。
```

## 3.2 具体方案

### remove 同步

```
改 bridge.js /api/socialV2/memory-remove：
  B 层删除后，若 A 层存在对应记录，调 removeVectorMemoryExact 删除。
  定位 A 层记录：key + `${category}: ${content}`（因为 append 时 text 就是这个拼接格式）。
  但 memberImpression 的 text 拼接含 extra.target，需确认实际拼接格式【待验证】。
```

### clear 同步

```
改 bridge.js /api/socialV2/memory-clear：
  清 B 层后，删除该 key 下 A 层全部记录。
  需新增 memory-vector.js 的 removeAllVectorMemory(key) 函数（当前无此函数）。
```

### append 改到 bridge 内

```
改 mcp-snowluma-safe.js qq_memory_append：
  不再在 MCP 进程内调 appendVectorMemory（:946）。
  改为由 bridge 的 memory-append 端点在 B 层成功后、进程内写 A 层。
  （与 query/share 的"上移"同构，统一所有 A 层操作都归 bridge。）
```

### edit 同步（可选，本轮评估）

```
B 层 memory-update 与 A 层 admin edit 的联动较复杂（字段映射不同、embedding 重算），
本轮【建议延后】，只修 remove/clear/append 三个最常用的生命周期操作。
```

## 3.3 不能保证原子性的说明

【已确认】A 层（memory-vectors.jsonl）与 B 层（social-v2.json）是两个独立文件，各自 `writeFileSync` / `appendFileSync`。**无法在单个系统调用里原子地同时改两个文件。** 因此：

- 本方案只承诺"**最终一致 + 失败可发现**"，不承诺"强原子"。
- 具体做法：先写 A 层、再写 B 层（或反之），任一步失败时，在返回里带上 `aSynced: false` 标记，让调用方/日志可见。
- 补偿：提供"对账"能力（可选，本轮可延后）——`listVectorMemory({key})` 与 B 层状态对比，报告差异。

```
历史残留（本轮不清理，仅记录）：

  本轮【不】回溯清理，等你另行批准。

对账（可选，延后）：
  新增 /api/memory/reconcile 端点，报告 key 下 A/B 差异，不自动删。
```

## 4.4 B6/C3 路径区分

【修订】明确区分两条调用路径，说明 HTTP 鉴权改造到底保护了什么：

```
路径 1：MCP 工具正常调用（模型 → qq_memory_query/share_request → HTTP → bridge）
  → 这是【模型可控的路径】，本次 HTTP 鉴权改造保护的就是它。
  → 改造后：模型无论传什么 key，都被 agentTokenOk 拦住，无法越权。

路径 2：内部函数直接调用（memory-vector.js 的导出函数被 JS 代码直接 import 调用）
  → 这是【代码路径，非模型路径】，HTTP 鉴权管不到。
  → 当前直接调用方：mcp-snowluma-safe.js（改造后不再直调）、seed-group-owner.mjs（需禁用）。
  → 【待验证】改造后是否还有其它内部直调残留，需全仓库搜确认。

结论：HTTP 鉴权改造保护的是"路径 1（模型越权）"。
      路径 2（内部代码越权）不靠 HTTP 鉴权解决，靠"清点所有直调方 + 禁用脚本"解决，
      且仍需后续审计（见 V6）。
```
