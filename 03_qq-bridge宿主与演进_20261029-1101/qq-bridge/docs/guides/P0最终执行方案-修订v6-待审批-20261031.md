# 大肥鱼 P0 v6 补充审查：严格读取缓存与 append 完整回滚

本轮仍然只读审查，不修改代码、数据、配置，不重启服务。

v6 原有 F1～F8 范围保持不变，不增加新功能。

## 1. 修复 loadRowsStrict 的缓存绕过问题

v6 的 loadRowsStrict 仍然存在：

```
if (mtime === cache.mtime) return cache.rows;
```

但普通 loadRows 会静默跳过 JSON 坏行，并可能将不完整结果写入缓存。

请检查以下情况：

1. 普通 loadRows 已经缓存了跳过坏行后的结果。
2. 文件 mtime 未变化。
3. 随后调用 loadRowsStrict。
4. 是否直接返回普通缓存，从而没有检查坏行？

另外检查文件不存在时，是否可能因 cache.mtime 为 0 而返回旧缓存。

要求提出最小修复方案：

- 严格读取不能无条件信任普通读取产生的缓存。
- 文件不存在必须可靠地识别为正常空结果。
- JSON 解析失败、文件读取失败必须向上传播。
- 严格读取成功后再更新缓存。
- 不改变普通 loadRows 的现有行为。

## 2. append 回滚必须恢复完整原状态

v6 已确认 appendMemoryV2 可能涉及：

- existing 去重；
- 24 小时清理；
- 长度裁剪；
- 不同记忆类型的不同处理。

请检查 appendMemoryV2 实际修改了哪些字段、是否可能修改多个数组。

不能仅通过 pop() 撤销新增记录，因为清理和裁剪可能已经删除原有记录。

要求：

- 在 append 前保存本次可能被修改字段的完整快照。
- strict 落盘失败时恢复这些字段。
- 不必深拷贝整个 socialV2，只覆盖实际受影响字段。
- 确认恢复后，B 层内存与操作前一致。
- 检查是否存在其他副作用无法通过字段快照恢复。

## 3. 回滚失败语义

确认 append/remove/clear 的回滚失败时：

- 是否有独立日志记录原始错误和回滚错误？
- 接口是否会错误地报告普通失败，而实际内存状态未知？
- 是否需要在结果中增加明确的 rollbackFailed 状态？

不要求新增自动恢复机制，只要求错误可识别。
