# 一、群共享机制核查

## 1.1 approveShare 是否只改 visibility 和 status，不碰 key

【已确认】**是。** `memory-vector.js:252-266` 的 `approveShare` 完整实现：

```
findMemoryRow(rows, key, text)   ← 用 key 定位记录
r.share_review_status = 'approved'   :259
r.visibility = 'group_shared'        :260
r.share_reviewed_at = Date.now()     :261
（可选）r.share_review_note          :262
atomicRewrite(rows)                  :264
```

**全程没有改写 `r.key`。** `rejectShare`（:269-283）同理，只把 visibility 回退 owner_private，不碰 key。

**结论**：`approveShare` 是"就地改字段"，不是"复制到 group key"。这直接决定了下面 1.4 的结论。

## 1.2 group 查询是否始终执行 key 全等过滤

【已确认】**是。** `memory-vector.js:147`：

```js
const rows = loadRows().filter((r) => r.key === key && Array.isArray(r.vec));
```

这是检索的唯一入口，key 全等是硬过滤。之后 :149-152 的 visibility 过滤是在"已经 key 匹配的子集"上做的。

**关键推论**：一条 `key=private:<ownerQQ>` 的记录，无论 visibility 是什么，**永远进不了 `key=group:<群号>` 查询的候选集**。

## 1.3 是否存在其他机制让 private key 的 approved 记忆被群检索

【已确认】**不存在。** 全仓库搜索 `group_shared`，只有 `memory-vector.js` 一处涉及（×5），且全部是"读/判断 visibility 字段"，没有任何"当 visibility=group_shared 时把记录复制/镜像到 group key"的代码。

检索入口全仓库只有一个：`searchVectorMemory`（memory-vector.js:146），其调用方只有：
- `mcp-snowluma-safe.js:996`（qq_memory_query）
- `seed-group-owner.mjs:56`（一次性脚本，非运行时）

**结论**：当前不存在任何"共享副本"或"共享索引"机制。`approved + group_shared` 的 private 记录，就是一条"字段自相矛盾但实际哪里都检索不到（群）也检索得到（主人私聊）"的记录。

## 1.4 测试矩阵"群聊查询 approved 共享记忆"是否真的可实现

【已确认】**当前不可实现，且是结构性矛盾。**

上一版测试矩阵第 2 条：

```
场景：群聊查自己的群记忆
预期：✅ 返回该群 approved 的共享记忆
```

**这个预期在现设计下永远无法满足**，原因是：

```
要让群聊查到一条记忆，需同时满足：
  ① r.key === 'group:<群号>'        （:147 硬过滤）
  ② r.visibility === 'group_shared'  （:152）
  ③ r.share_review_status === 'approved'  （:152）

而现有数据的 key 分布：
  group 记录（37 条）：visibility 有 group_shared 的 30 条，但 share_review_status 全是 unset
  private 记录（65 条）：唯一 approved 的 #101，但 key 是 private，过不了 ①
```

所以无论怎么调，群聊能检索到的 approved 共享记忆 = **0 条**。这是一个**设计层面的死锁**：

> 审批流（approveShare）会把 visibility 置 group_shared，但**它不会、也不能改变 key**。而群检索又要求 key 必须是 group:。于是「private 记忆被批准共享」这个动作，产生的是一条 key 仍是 private、因此群永远查不到的记录。审批通过了，等于没通过。

**这就是 #101 的本质问题，也是整个"分享审核"功能设计缺陷的根源。**

## 1.5 两个方案对比：群共享副本 vs 共享索引

### 方案 A：群共享副本

**做法**：approveShare 批准一条 private 记忆时，**复制一份**到目标群的 key 下。

```
原记录（private:<owner>）  保留不动
副本记录（group:<群号>）    新建，text 相同（或改写），visibility=group_shared，approved
```

| 维度 | 评价 |
|---|---|
| 权限边界 | ✅ 清晰：原记录私，副本公，各归各的 key |
| 数据结构 | 改 approveShare 需知道"共享到哪个群"（当前函数签名没有 groupId 参数，需扩展） |
| 实现复杂度 | 中：要加 groupId 参数、写副本逻辑、副本与原记录的生命周期绑定（原记录删除/改写时副本怎么办？） |
| 风险 | 副本与原记录脱钩后，原记录改写/删除不会同步到副本 → 需要额外的同步或"副本=快照"语义 |

### 方案 B：共享索引（独立共享表）

**做法**：新增一个 `shared-memories.jsonl` 或内存索引，记录"哪条记忆被批准共享到哪个群"，检索时群查询额外查这个索引。

```
共享索引：[{ sourceKey, sourceText, sharedTo: 'group:xxx', approvedAt }]
群检索：key 全等过滤 → 再查共享索引里 sharedTo=本群 的条目
```

| 维度 | 评价 |
|---|---|
| 权限边界 | ✅ 更灵活：一条记忆可共享到多个群，撤销只需删索引行 |
| 数据结构 | 新增一张表/文件，与主库解耦 |
| 实现复杂度 | 高：要新增存储、检索时双路合并、审批/拒绝的索引增删 |
| 风险 | 索引与主库一致性（原记录删了，索引悬空）；检索性能（每次群查询都要扫索引） |

### 对比结论

| | 副本 | 索引 |
|---|---|---|
| 权限边界 | 好（物理隔离） | 好（逻辑隔离） |
| 复杂度 | 中 | 高 |
| 一致性风险 | 副本脱钩 | 索引悬空 |
| 适合场景 | **共享目标固定、记忆不多** | 一条记忆共享多群、需要精细撤销 |

**本轮建议**：两个都不实现（任务要求"本轮不实现任何方案"）。但**结论要写死**：当前"approveShare 就地改 visibility 不改 key"的机制，在"群检索要求 key 全等"的前提下，**是自相矛盾的**。P0 修复必须先把"群共享到底怎么落地"这个设计问题定下来，否则 #101 修了也是错的。

**最简可行方向（供后续决策，非本轮）**：短期最省事的做法是**放弃"private 记忆跨群共享"这个语义**——群共享只对"本来就是 group key 的记录"有意义（即：群内产生的记忆，批准后在群内可见）。private 记忆共享到群，这个需求本身可以砍掉或延后。

# 二、Token 唯一性核查

## 2.1 生成方式

【已确认】token 由 `crypto.randomBytes(n).toString('hex')` 生成，共三处：

| 位置 | 长度 | 场景 |
|---|---|---|
| bridge.js:2795 | 24 字节（48 hex 字符） | `retireSession` 时轮换 |
| bridge.js:8509 | 16 字节（32 hex 字符） | `ensureWakeableV2` 新建会话 |
| bridge.js:8561-8563 | 16 字节 | `loadSocialV2State` 加载时补 token |

## 2.2 token 是否全局唯一

【已确认】**有去重，但不彻底。**

- 加载时（:8561-8565）有 `seenTokens` 集合，遇到重复会重新生成。**但这个去重只对"同一次加载循环内的会话"生效。**
- 新建会话（:8509）**没有查重**，直接 `randomBytes(16)`，理论上可能撞上已存在的 token（概率极低：2^128 空间）。
- 轮换（:2795）同样**没有查重**。

**结论**：token 是 128-bit 随机值，碰撞概率可以忽略（16 字节 hex = 128 bit 熵，实际不可能碰撞）。`seenTokens` 去重是防御性兜底，不是唯一性保证的依赖。

## 2.3 是否存在重复 token 的可能

【已确认】理论上存在（randomBytes 有极小碰撞概率 + 加载去重只覆盖批次内），但**实际风险可忽略**。真正需要关注的是下面 2.4 的"旧 token 残留"问题，而非碰撞。

## 2.4 token 是否在会话关闭后继续有效

【已确认】**是，但会被主动轮换。** 关键代码 `bridge.js:2792-2799`：

```js
const st = socialV2.conversations.get(key);
if (st) {
  st.agentToken = crypto.randomBytes(24).toString('hex');  // 轮换新 token
  rememberAgentToken(key, st.agentToken);
  ...
}
```

会话退役/关闭时会**轮换 token**，旧 token 失效。但注意：

- 轮换动作发生在 `retireSession`（:2780 附近），不是"会话关闭"的每个路径都触发。
- 如果会话只是"暂时不活跃"而非"退役"，token 不会变。
- `rememberAgentToken`（:540-548）会保留"当前代 + 上一代"token 在脱敏集合里，但**上一代 token 的调用权限已被撤销**（因为 `agentTokenOk` 只认 `st.agentToken` 当前值）。

**结论**：token 在会话退役时会失效（轮换）。但"退役"的触发时机（模式切换、白名单变化、/reset）需要精确理解，否则可能误判"会话没关"。

## 2.5 通过 token 反查 key 是否可靠

【已确认】**当前不可靠，因为没有反向索引。** `isLiveAgentToken`（:3159-3165）是遍历所有会话找 token：

```js
const isLiveAgentToken = (token) => {
  for (const st of socialV2.conversations.values()) {
    if (st?.agentToken && tokenEq(token, st.agentToken)) return true;
  }
  return false;
};
```

它只返回"token 是否有效"，**不返回对应的 key**。要反查 key，需另写遍历逻辑（把匹配的 key 返回）。这在会话少时可行（当前 2 个会话），会话多时是 O(n)。

## 2.6 直接使用 agentTokenOk(key, token) 是否足够

【已确认】**足够，且是更简单的方案。**

`agentTokenOk(key, token)`（:3146-3150）已经做了完整校验：

```js
const agentTokenOk = (key, token) => {
  const canonical = canonicalV2Key(key);
  const st = socialV2.conversations.get(canonical ?? key);
  return !!st && !!st.agentToken && tokenEq(token, st.agentToken);
};
```

它把"模型传入的 key"规范化后，直接查该 key 的会话，比对 token。**这天然就是"验证传入 key"的方案**，不需要反查。

## 2.7 两种方案对比："服务端反查 key" vs "验证传入 key"

| 维度 | 服务端反查 key | 验证传入 key（agentTokenOk） |
|---|---|---|
| 做法 | token → 遍历找 key → 用服务端 key 检索 | 直接 `agentTokenOk(传入key, token)` 校验 |
| 优点 | 模型连 key 都不用传对 | 代码零新增，复用现成函数 |
| 缺点 | 需新增反查函数；O(n) 遍历；多会话时慢 | 仍依赖模型传对 key（但传错会被 403 拦） |
| 安全性 | 略高（key 完全不信任模型） | 足够（key 必须匹配 token 才放行） |
| 实现成本 | 高 | **低** |

**结论（修正上一版倾向）**：上一版方案推荐"服务端反查 key（忽略模型 key）"，**本轮改为推荐"验证传入 key（直接 agentTokenOk）"**。理由：

1. `agentTokenOk` 已经存在且被 20+ 个端点复用，直接用零成本。
2. "反查 key"需要新增遍历函数，且多会话时 O(n)，当前无反向索引。
3. "验证传入 key"已经能挡住跨会话越权（传错 key → token 不匹配 → 403），安全性等价。

**唯一需要补的**：`agentTokenOk` 只校验"key↔token 绑定"，不校验"这个 key 是否仍在白名单/当前模式允许范围内"（那是 `v2SessionAllowed` 的职责）。所以 A 层端点要**同时**调 `agentTokenOk` + `v2SessionAllowed` + `v2ToolEnabled`，三者缺一不可——这正好是 B 层端点现成的三重校验，直接复制即可。

【已确认】**建议：是，但优先级低于"读取"和"分享申请"。** 理由：

- 写入方向（append）当前**依赖 B 层前置校验**（mcp:939 → :946），与 query 同构，风险等级相同（都是"间接受保护，函数本身无边界"）。
- 写入的越权后果是"污染数据"（往别人的 key 塞记忆），比读取更隐蔽（不会立即暴露，但会让记忆库越来越脏）。
- 但当前唯一能触发越权写的是 `seed-group-owner.mjs`（脚本，非运行时），运行时路径 mcp:946 受 B 层保护。

**修订建议**：上一版把 append 列为"待验证 V2"，本轮结论是**确认需要一并处理**，但可以放在 P0 修复的第二批（先修 query + share_request，再修 append）。三者的共同解法都是"把进程内函数调用改成走 bridge 的 HTTP 端点"。

# 四、#101 数据修复核查

## 4.1 subjectId 是否允许使用内部稳定 ID

【已确认】**允许，且应该用。** `subjectId` 的全部消费点只有两处：

```
memory-vector.js:190  .filter(r => !filter.subjectId || r.subjectId === filter.subjectId)  ← 列表过滤，全等比较
memory-vector.js:195  subjectId: r.subjectId || 'unknown'                                    ← 输出默认值
bridge.js:6673        subjectId: body.subjectId || undefined                                  ← 管理端查询参数透传
```

**没有任何代码把 subjectId 当作 QQ 号解析、拼 key、或做数字运算。** 它就是个不透明字符串，用作"这个记忆关于谁"的标识。所以：

- 用内部稳定 ID（如 `owner`、`bot:da-fei-yu`、或某个自定 ID）完全可行。
- 甚至当前 #006/#007 里 subjectId 存的是 QQ 号（`[OWNER_QQ]` 等），这**本身就不是好做法**——因为 subjectId 会被 `listVectorMemory` 原样输出到管理端列表，等于又一处 QQ 号暴露点。

## 4.2 是否存在其他代码依赖 subjectId 为 QQ 号

【已确认】**不存在。** 见 4.1，两处消费都是"全等比较 + 字符串透传"，无数字语义。

## 4.3 #101 正文是否准确表达"主人希望被称为网管"

【已确认】原文：

```
[真实姓名]（<QQ>），电脑的主人。嫌叫全名伤人，让我给他起个称呼，我定了叫"网管"。
```

语义拆解：
- 主语"我"= 机器人（大肥鱼）
- "让他给他起个称呼" → "给他（主人）起称呼"
- "我定了叫网管" → 机器人给主人定的称呼是"网管"

**所以"网管"是主人的称呼，不是机器人的名字。** 这个语义是**准确**的。

但有一个**易被误解的隐患**：如果未来这条记忆被某处检索到并让模型"描述自己的称呼"，模型可能把"我定了叫网管"里的"我"错认成机器人自己（因为记忆里"我"的指代在多条记录里不一致——有的"我"是机器人，有的"我"是主人）。这是记忆里人称指代混乱的典型问题。

**修订建议**：改写 #101 时，把指代写明确，避免"我"的歧义。例如：

```
主人（[真实姓名]）是电脑的主人。嫌叫全名伤人，让大肥鱼给他起个称呼，大肥鱼定了叫"网管"。
```

（去掉 QQ 号 + 把"我"改成"大肥鱼"，消除指代歧义）

## 4.4 是否应彻底避免在记忆正文存 QQ 号

【已确认】**应彻底避免。** 理由：

1. 记忆正文会被 `searchVectorMemory` 检索后**原样注入模型**（mcp:997），一旦命中就是完整 QQ 号进模型上下文。
2. 记忆正文会被 `listVectorMemory` 原样输出到管理端（memory-vector.js:194 `text: r.text`）。
3. QQ 号在记忆里没有任何语义检索价值（检索靠向量相似度，不靠数字精确匹配）。

**结论**：记忆正文**永不存 QQ 号**。身份信息放 `subjectId`（用内部稳定 ID）+ `subjectName`（用称呼），不放正文。

## 6.3 设计矛盾清单（明确指出，不粉饰）

## 最关键的一句话结论

> 上一版方案把"群共享"当成一个可以修好的功能，但本轮核查发现：**"群共享"在当前代码里是一个自相矛盾的设计**——approveShare 改 visibility 不改 key，而群检索又要求 key 全等，所以"批准共享"这个动作从机制上就无法让群查到。
