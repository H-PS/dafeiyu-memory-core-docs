# 一、remove 的逻辑矛盾修正

## 1.1 明确区分两种"找不到"

【已确认】A 层 `removeVectorMemoryExact`（memory-vector.js:286）找不到时返回 `null`（不是抛错）。但"找不到"要区分两种来源：

| 情况 | 判定 | 处理 |
|---|---|---|
| **A 层无对应记录**（查询结果为空，正常） | 视为"已无对应记录" | 继续删除 B |
| **A 层读写异常**（文件读失败 / 解析失败 / rename 失败） | 视为异常 | **停止 B 删除，返回失败** |

**实现要求**：A 层删除函数必须能区分"正常空结果"和"异常"。当前 `removeVectorMemoryExact` 用 `return null` 表示找不到，无法区分异常——**需在函数层新增异常语义**（抛错或返回 `{error}`），而不是复用 `null`。

## 1.2 正确顺序（先算 bRemoved，再删 A，再删 B）

【已确认】remove 端点当前代码结构（bridge.js:6808-6833）是"先改 B 层内存 → 再 save"。修正后的顺序必须改为：

```
① 计算 B 层本次实际匹配数量 bRemoved
   = st.activeTopics 中 text === content 的条数（filter 前的 count）
   （或 pendingThoughts / memberImpressions 同理）

② bRemoved === 0 → 不修改 A，返回"未找到"（404）

③ bRemoved > 0 → A 层删除 min(bRemoved, A层匹配数) 条
   - A 层无对应记录（正常空）→ aSynced:true，继续
   - A 层异常 → 停止，返回失败，B 不执行

④ A 层处理完成后，再提交 B 层删除
   - B 删除成功 → 整体成功
   - B 删除失败 → 部分成功（aSynced:true + 整体失败）
```

**是否符合实际代码结构【待验证】**：当前 remove 端点把 B 层删除逻辑内联在端点里（:6823-6830），改成"先算 bRemoved 再删 A 再删 B"需要重排这段代码。bRemoved 的计算可以从 `st.activeTopics.filter(...)` 之前先 `count`，结构上可行，但需实现时确认。

## 1.3 修订 remove 测试矩阵

| # | 场景 | 预期 |
|---|---|---|
| R1 | A 无对应记录（正常空）+ B 有记录 | A 视为已一致，B 正常删除，返回成功 |
| R2 | A 层读写异常 | **B 不执行删除**，返回失败 |
| R3 | bRemoved=0 | 不修改 A，返回 404 未找到 |
| R4 | bRemoved=2，A 匹配 3 条 | A 删 2 条（留 1），B 删 2 |
| R5 | bRemoved=2，A 匹配 1 条 | A 删 1，B 删 2 |
| R6 | A 删成功 + B 删失败 | 报告部分成功（aSynced:true + 整体失败） |
| R7 | 两层都成功 | 正常完成 |

# 二、saveSocialV2State 吞错问题（本轮重点核查）

## 2.1 调用位置统计

【已确认】`saveSocialV2State()` 全仓库 **43 处调用**，分布在：

| 调用场景 | 代表性位置 |
|---|---|
| 会话退役/轮换 | :2801 |
| markRead / getPrompt / getUnread 等状态工具 | :4583 :4820 :5174 :5195 :5310 等 |
| 发送消息后 | :5344 :5440 :5820 :5830 :5866 等 |
| 黑话学习 | :6778 附近 |
| **memory remove** | :6830 |
| **memory clear** | :6847 |
| 唤醒/主动检查 | :9956 :9998 :10025 等 |
| 退出前落盘 | :7246 |

## 2.2 是否有其他接口依赖吞错行为

【已确认】**是，绝大多数依赖。** 43 处调用里，除了 memory remove/clear 和退出落盘，其余 ~40 处都是"尽力落盘"语义——它们改完内存后顺带 save，save 失败不应中断主流程（否则 markRead、send 这类接口会因磁盘抖动而报错）。

**结论**：**不能直接改 `saveSocialV2State` 让它抛错**，否则影响 40+ 个接口。

## 2.3 appendMemoryV2 / remove / clear 是否受影响

【已确认】分三种情况：

| 操作 | B 层落盘情况 | 受吞错影响 |
|---|---|---|
| **append** | **根本没有调用 saveSocialV2State**（:6641 只调 appendMemoryV2 改内存，:6642 直接 sendJson） | **比吞错更严重：append 时 B 层根本不落盘**，靠后续某个操作触发 save 才持久化 |
| **remove** | :6830 调 saveSocialV2State | 受吞错影响：磁盘写失败时接口仍返回 ok:true |
| **clear** | :6847 调 saveSocialV2State | 同上 |

**关键新发现【已确认】**：`append` 端点在 :6640-6642 **没有 saveSocialV2State 调用**。`appendMemoryV2`（:8919）只改内存 `st.activeTopics` 等，不落盘。`getSocialV2State`（:8491）也不 save。**所以 append 的 B 层写入是"内存已改、磁盘未写"，持久化完全依赖后续任意一次 saveSocialV2State 触发。**

## 2.4 B 层磁盘写入失败时，bridge 是否仍返回成功

【已确认】**是。** 两种路径：

- **append**：不落盘，`sendJson({ok:true})` 无条件成功。内存改了，磁盘没写。
- **remove/clear**：`saveSocialV2State` 吞错（:8689-8691 只 log），端点返回 ok:true。内存改了，磁盘没写。

## 2.5 最小修改方案

**核心原则：不改 `saveSocialV2State` 的全局行为，只让 memory 三个端点能感知落盘结果。**

### 方案：新增一个"可抛错的落盘"变体，只给 memory 端点用

```js
// 新增（不改原函数）：
function saveSocialV2StateStrict() {
  try {
    const obj = { paused: socialV2.paused, conversations: ... };  // 复用原序列化
    atomicWriteJson(SOCIAL_V2_FILE, obj);  // 失败会 throw，不吞
    return true;
  } catch (error) {
    return false;  // 或直接 throw，由调用方决定
  }
}
```

- **append 端点**：`appendMemoryV2` 后，调 `saveSocialV2StateStrict()`，根据返回值决定 `bSynced:true/false`。
- **remove/clear 端点**：B 层删除后，调 `saveSocialV2StateStrict()`，返回 `bSynced`。
- **其他 40+ 处**：继续用原 `saveSocialV2State()`（吞错），行为不变。

**评估对其他接口的影响【已确认】**：零影响——原 `saveSocialV2State` 保持不变，新增变体只在 3 个 memory 端点用。

### 附：append 必须检查 B 层真正落盘

【已确认】按上述方案，append 端点从"不落盘"改为"调 strict 落盘 + 检查结果"，**补上了缺失的持久化步骤**，且能返回 bSynced。这是本轮 append 修复的额外收益（原来 append 连落盘都没有）。
