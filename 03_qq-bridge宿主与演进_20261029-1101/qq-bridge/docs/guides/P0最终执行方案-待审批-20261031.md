# 一、isOwnerPrivate 核查结果

## 1.1 定义与调用位置

【已确认】`isOwnerPrivate` **不是函数**，是 `searchVectorMemory` 内的局部常量，全项目仅 1 处定义 + 1 处使用：

```
memory-vector.js:149  const isOwnerPrivate = key.startsWith('private:') && key.endsWith('[OWNER_QQ]');
memory-vector.js:150  const visible = isOwnerPrivate ? rows : rows.filter(...);
```

**无其他调用位置。** 全仓库搜 `isOwnerPrivate` 只有这 2 行。

## 1.2 关键发现：硬编码不跟配置走

【已确认】

```
config.json 顶层有 ownerQQ = [OWNER_QQ]
但 memory-vector.js 只读 config 的 memoryVector 段（:28-32）
isOwnerPrivate 里的 '[OWNER_QQ]' 是【写死的字面量】，不读 config.ownerQQ
```

**后果**：如果主人换了 QQ 号（改 config.ownerQQ），这个判断**不会跟着变**，仍然只认旧号 [OWNER_QQ]。这是硬编码的第二个危害（第一个是"别人私聊查不到自己记忆"）。

## 1.3 改为 `key.startsWith('private:')` 后，影响哪些行为

| 行为 | 当前（硬编码） | 改为 startsWith 后 | 影响评估 |
|---|---|---|---|
| 主人私聊检索 | 全部可见 ✅ | 全部可见 ✅ | 无变化 |
| **其他用户私聊检索** | ❌ 落到"要求 approved"分支 → 查不到自己记忆 | ✅ 全部可见 | **修复**（P0-漏洞4） |
| 群聊检索 | 落到"approved 过滤" | 同左，无变化 | 无变化 |
| 删除（removeVectorMemoryExact） | 不经过 isOwnerPrivate，纯 key 全等 | 无影响 | 无变化 |
| 审核（approve/reject） | 不经过 isOwnerPrivate | 无影响 | 无变化 |
| 管理端 list | 不经过 isOwnerPrivate | 无影响 | 无变化 |

【已确认】`isOwnerPrivate` 只在 `searchVectorMemory` 的可见性过滤里用，**不涉及删除、审核、管理端**。那些操作走的是 `findMemoryRow`（key+text 全等）和 `listVectorMemory`（可选过滤），与 isOwnerPrivate 无关。

## 1.4 是否建议修改的结论

【已确认】**建议修改，但必须与"鉴权上移"同步落地。**

理由：
1. 硬编码 `[OWNER_QQ]` 是明显 bug（不跟 config 走，换号即失效）。
2. 改 `startsWith('private:')` 语义正确：私聊记忆天然只属于该私聊主体，本就该"谁查谁可见"。
3. **但**：一旦改成"任何 private key 都全部可见"，若 A 层检索仍无鉴权（模型可传任意 key），等于**放大了越权面**——原来只有主人 QQ 能全看，现在任意 private key 都能全看。

所以修改顺序必须是：**先上移鉴权（让 A 层检索只能由"验证通过的 key"触发），再改 isOwnerPrivate。** 两步不可颠倒，也不可只做其一。
