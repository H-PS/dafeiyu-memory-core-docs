# 一、漏洞复现

## 漏洞 1：`qq_memory_query` 的 A 层检索缺独立鉴权

### 调用链【已确认】

```
模型调用 qq_memory_query(key, token, topic)
  ↓ mcp-snowluma-safe.js:989-991
  先 GET /api/socialV2/memory?key=<模型传的key>   [B 层，带 x-agent-token]
     ↓ bridge.js:6786-6788 三重校验：
       agentTokenOk(key, token)   ← 令牌↔key 绑定
       v2SessionAllowed(key)      ← 会话白名单
       v2ToolEnabled('memory')    ← 工具开关
     （key 不匹配令牌 → 403，抛错）
  ↓ 若 B 层成功（= key 与 token 绑定有效）
  mcp-snowluma-safe.js:996 searchVectorMemory(key, topic, 5)  [A 层，进程内]
     ↓ memory-vector.js:147  rows.filter(r => r.key === key)  ← key 全等过滤
     ↓ memory-vector.js:149-152 isOwnerPrivate 判断 → 可见性过滤
     ↓ embed(topic) → cosSim → 返回
```

### 触发条件【已确认】

关键点在于：**B 层校验的 `key` 和 A 层检索的 `key` 是同一个变量（都来自模型参数），但两个调用是分离的。**

漏洞场景不是"绕过 B 层"，而是**时序漏洞**：

- B 层请求在 :991 发出，A 层检索在 :996 执行。
- 若 B 层请求**成功**（说明 key↔token 绑定有效），此时 A 层用同一个 key 检索**是安全的**。
- 若 B 层请求**失败**（403），:991 抛错，进入 :1003 catch，A 层**根本不会执行**。

**所以严格来说，`qq_memory_query` 当前的 A 层检索是"间接受保护"的**——因为 B 层请求前置且失败会短路。这与审计报告的"零鉴权"结论需要修正：

> **修正【已确认】**：`qq_memory_query` 的 A 层检索**不是完全零鉴权**，而是**依赖"B 层请求失败会短路"这个隐式前置条件**。真正的风险在漏洞 2（`share_request`）和"B 层请求返回 200 但 A 层 key 被改"这类边界情况——虽然当前代码里两个 key 是同一个变量，无法在中间改，但这个"隐式依赖"脆弱，一旦未来有人重构拆开两个 key，就会重新暴露。

**但仍有真实风险【已确认】**：`searchVectorMemory` 是导出函数，任何进程内代码（包括未来新增的工具、`seed-group-owner.mjs` 这类脚本）都可以绕过 B 层直接调用它，传入任意 key。当前唯一调用方 `mcp:996` 是受 B 层前置保护的，但**这个保护是"调用方的纪律"，不是"函数的边界"**。

### 影响范围【已确认】

- 当前运行时：风险低（B 层前置短路有效）。
- 未来扩展：风险高（函数本身无边界，新增调用方即暴露）。
- `seed-group-owner.mjs` 已是实锤的"绕过 B 层直写 A 层"先例（虽然它是写不是读）。

## 漏洞 2：`qq_memory_share_request` 完全无鉴权

### 调用链【已确认】

```
模型调用 qq_memory_share_request(key, token, text)
  ↓ mcp-snowluma-safe.js:967 requestShare(key, text)   ← 进程内直接调用
     ↓ memory-vector.js:236-249 findMemoryRow + 标记 pending
  ✗ 没有任何 HTTP 请求，没有任何 token 校验
```

对比：`qq_memory_append` 先发 B 层请求（:939，带 token），`qq_memory_query` 先发 B 层请求（:991）。**唯独 `share_request` 是纯进程内调用，连一次 token 校验都没有。**

### 触发条件【已确认】

任何持有 MCP 工具调用能力的上下文（群聊、私聊），模型传任意 `key` + 任意 `text`，只要能定位到一条记忆，就能把它标记为 `pending`（虽然最终批准仍需控制台，但"发起申请"这个动作本身已越界，且会让主人看到一条来路不明的待审记录）。

### 影响范围【已确认】

- 直接：可对任意 key 的记忆发起分享申请（骚扰/试探性越权）。
- 间接：`requestShare` 内部 `findMemoryRow` 会遍历 `loadRows()`，等于**把"某条记忆是否存在"这个信息泄露给了任意调用方**（返回 pending vs 未找到，是两回事）。

## 漏洞 3：#101 元数据矛盾 + 含 QQ 号

### 现状【已确认】

```

     缺 category/subjectType/sourceType/needs_review/subjectId/subjectName
     text 含主人完整 QQ 号
```

### 矛盾本质【已确认】

- `key=private:...` 说"这是私聊记忆"。
- `visibility=group_shared` 说"这是要共享的"。
- 但检索第一道是 `r.key === key`（memory-vector.js:147），所以**群聊查询（key=group:...）永远够不到它**；私聊查询（key=private:ownerQQ）又能查到它——两条路都自相矛盾。

### 风险【已确认】

- 主人私聊检索时，这条（含 QQ 号）会命中并注入模型——这是预期内的（主人自己查）。
- 群聊检索时够不到——所以**当前不会直接泄漏 QQ 号到群聊**。
- 但它是唯一 approved 的记录，如果未来修了漏洞 1（让 A 层可跨 key），它就是第一个泄漏点。

# 二、推荐修复架构

## 2.1 核心原则：**服务端确定可访问 key，不信任模型传入的 key**

当前系统其实已经有正确的鉴权原语，只是 A 层没用上：

```
已有原语（bridge.js）：
  canonicalV2Key(key)         :1370   正则约束 key 格式
  agentTokenOk(key, token)    :3146   token ↔ 会话 key 绑定（定长比较）
  v2SessionAllowed(key)       :3167   会话白名单
  v2ToolEnabled('memory')     :3116   工具开关
  socialV2.conversations      Map<canonicalKey, {agentToken, ...}>   ← 权威的"令牌→会话"映射
```

**方案核心：把 A 层向量检索/分享申请从 MCP 进程内挪进 bridge 的 HTTP 端点，让它们复用 B 层已经存在的那套三重校验。** 这样"谁可以查谁的记忆"由服务端的 `socialV2.conversations` 决定，而不是由模型传来的 key 字符串决定。

## 2.2 鉴权层定位

| 层 | 职责 | 现状 | 修复后 |
|---|---|---|---|
| B 层 HTTP（bridge） | token↔key 绑定 + 会话白名单 + 工具开关 | ✅ 已有 | 保持不变，作为唯一鉴权点 |
| A 层函数（memory-vector.js） | 纯数据操作，不含鉴权 | 导出函数可被任意调用 | **改为"受信任输入"模式**：函数不再接受外部 key，只接受服务端已验证的 key |
| MCP 工具（mcp-snowluma-safe.js） | 把模型请求转发给 bridge | 直接进程内调 A 层 | 改为只发 HTTP 请求，A 层逻辑移到 bridge 端点内 |

## 2.3 可访问 key 的确定方式

```
服务端权威映射：
  socialV2.conversations : Map<canonicalKey, { agentToken, ... }>

给定一个 token：
  遍历 conversations，找到 agentToken === token 的那个会话 → 得到该会话的 canonicalKey
  这个 key 就是"当前主体唯一可访问的 key"

模型传入的 key 仅用于：
  ① 校验它与 token 对应的会话 key 是否一致（不一致 → 403）
  ② 或者干脆忽略模型 key，直接用服务端从 token 反查出的 key
```

**推荐用方案②**（忽略模型 key，服务端反查），最彻底——模型连"猜 key"的机会都没有。

## 2.4 私有记忆可见性修正

把 `isOwnerPrivate` 从"硬编码主人 QQ"改为"按 key 前缀判断"：

```js
// 修正后（伪代码）
const isPrivate = key.startsWith('private:');   // 任何私聊 key
const visible = isPrivate
  ? rows                                        // 私聊：全部可见（只属于自己）
  : rows.filter(r => r.visibility === 'group_shared' && r.share_review_status === 'approved');
```

这样：
- 主人私聊 → 全部可见 ✅
- 其他用户私聊 → 全部可见（自己的）✅
- 群聊 → 只 approved 的 group_shared ✅

# 三、文件修改计划

> 以下均为**计划**，未实施。每个改动标注【预期行为】。

## 3.1 `src/bridge.js` — 新增 2 个 HTTP 端点

### 新增 `GET /api/socialV2/memory-vector`（向量检索，替代进程内 searchVectorMemory）

- **位置**：紧邻现有 `/api/socialV2/memory`（:6782）之后。
- **鉴权**：复制 :6786-6788 的三重校验（agentTokenOk → v2SessionAllowed → v2ToolEnabled）。
- **逻辑**：
  1. 从 `x-agent-token` 反查 canonicalKey（或直接用 `agentTokenOk` 校验模型 key）。
  2. 调用 `searchVectorMemory(canonicalKey, topic, topK)`。
  3. 返回 hits。
- **预期行为**：A 层检索只接受服务端从 token 确定的 key；模型传错 key 直接 403，不触发检索。

### 新增 `POST /api/socialV2/memory-share-request`（分享申请，替代进程内 requestShare）

- **鉴权**：同上三重校验。
- **逻辑**：校验通过后调 `requestShare(canonicalKey, text)`。
- **预期行为**：只有当前会话的 token 能对自己的记忆发起分享申请；越权 key 直接 403。

### 修改 `memory-vector.js` 的 `searchVectorMemory` / `requestShare` 签名【可选，降低风险】

- **方案 A（推荐，改动小）**：函数签名不变，但**调用方只有 bridge 端点**（MCP 不再直接 import 调用）。函数仍然"信任传入的 key"，但这个 key 现在是服务端校验过的。
- **方案 B（彻底）**：函数内去掉 `isOwnerPrivate` 硬编码，改为 `key.startsWith('private:')`；并在函数顶部加断言"调用方是受信路径"。但 JS 无强隔离，断言意义有限。
- **结论**：采用方案 A（把鉴权边界上移到 bridge），同时顺带修 `isOwnerPrivate`（见 3.3）。

## 3.2 `src/mcp-snowluma-safe.js` — 改 2 个工具的实现

### `qq_memory_query`（:978）

- **改**：删除 :994-1001 的进程内 `searchVectorMemory` 调用；改为在 :991 的 B 层请求之后，**再发一个 `GET /api/socialV2/memory-vector?key=...&topic=...` 请求**（带同一 token）。
- **预期行为**：A 层检索也走 HTTP，统一经过服务端三重校验；失败时降级为纯 B 层列表（保留现有降级语义）。

### `qq_memory_share_request`（:957）

- **改**：删除 :967 的进程内 `requestShare` 调用；改为 `POST /api/socialV2/memory-share-request`（带 token）。
- **预期行为**：分享申请必须先通过 token↔key 绑定校验。

## 3.3 `src/memory-vector.js` — 修 `isOwnerPrivate`

- **改**：`const isPrivate = key.startsWith('private:');`（去掉 `endsWith('<ownerQQ>')` 硬编码）。
- **预期行为**：任何私聊 key 都走"全部可见"，解决漏洞 4。
- **注意**：此改动依赖 3.1 的鉴权上移才安全——因为一旦"任何私聊 key 都全部可见"，若 A 层仍无鉴权，越权读更严重。**必须与 3.1 同步落地，不可单独先改这个。**

## 3.4 `seed-group-owner.mjs` — 防误执行
