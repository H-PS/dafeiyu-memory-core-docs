## 2.3 是否只执行 filter/push/splice/替换

【已确认】`appendMemoryV2` 对数组的操作：
- `filter`（24h 清理，:8925/:8928）
- `push`（新增，:8941/:8957）
- `splice`（超 20 裁剪，:8948/:8964）
- 对已有元素：**改内部属性**（existing 分支，:8934-8939/:8953-8955）

**结论**：不只是 filter/push/splice，还会**改已有元素的内部属性**。

## 2.4 浅拷贝 `map(t => ({...t}))` 是否足够

【已确认，需精确说明】：

- `pendingThought` 元素全简单类型，`map(t => ({...t}))` **够用**（无嵌套，改的是标量）。
- `activeTopic` 元素含 `participants: string[]`（嵌套数组）。但**关键点**：
  - `existing.participants = [...set]` 是**整体替换**（新数组），不是原地 `push` 修改原数组。
  - 快照时 `{...t}` 里的 `participants` 引用的是**快照时刻的旧数组**。
  - 之后 `existing.participants = 新数组` 是给 `existing`（原对象）换引用，**不影响快照里 `participipants` 指向的旧数组**。
  - 所以浅拷贝的快照里，`participants` 仍指向旧数组，回滚时 `st.activeTopics = snapshot.activeTopics` 会把元素换回旧引用，`participants` 也回到旧数组 → **正确还原**。

**结论【已确认】**：`map(t => ({...t}))` 浅拷贝**在本场景下够用**，因为 `participants` 是"整体替换"而非"原地改"，浅拷贝保留的旧数组引用正好是回滚需要的。但为稳妥，建议对 `activeTopic` 元素做 `participants: [...t.participants]` 显式拷贝，避免未来有人改成原地 push 时埋雷。

## 2.5 memberImpressions 快照

【已确认】`memberImpressions` 是嵌套对象（`{ target: { traits: string[], interactionCount, lastSeenAt } }`），且 `appendMemoryV2` 会：

- `delete st.memberImpressions[oldTarget]`（:8981）

**结论**：memberImpressions 用 `JSON.parse(JSON.stringify(...))` 深拷贝快照（v6 已定），**保持深拷贝不变**。

# 三、loadRowsStrict 文件存在判断

## 3.1 代码依据【已确认】

原 `loadRows`（:44-58）用 `!mtime` 判断文件不存在（:48），存在隐患：`mtime=0` 时（文件不存在）与 `cache.mtime=0` 相等，可能命中旧缓存。

## 3.2 修正：分开文件存在判断与 mtime 判断

```js
function loadRowsStrict() {
  const exists = fs.existsSync(VEC_FILE);          // ① 先判文件是否存在
  if (!exists) {
    cache = { mtime: 0, rows: [] };                // ② 不存在：重置缓存 + 返回空
    return [];
  }
  const mtime = fs.statSync(VEC_FILE).mtimeMs;     // ③ 存在：读 mtime（失败会抛错）
  const rows = [];
  const lines = fs.readFileSync(VEC_FILE, 'utf8').split('\n');  // ④ 读取，失败抛错
  for (const line of lines) {
    if (!line.trim()) continue;
    rows.push(JSON.parse(line));                   // ⑤ 解析失败抛错
  }
  cache = { mtime, rows };                         // ⑥ 成功后更新缓存
  return rows;
}
```

**要点**：
- 用 `fs.existsSync` 而非 `!mtime` 判断文件存在，二者分离。
- 不存在 → 重置缓存 + 返回 `[]`（正常空）。
- 存在 → 每次严格读（不命中缓存），失败抛错。
- 成功 → 更新缓存。
