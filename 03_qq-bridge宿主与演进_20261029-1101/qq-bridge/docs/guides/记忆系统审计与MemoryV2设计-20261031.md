# 一、当前系统架构与实际运行流程

## 1.1 三层结构（实际）

```
┌─ C 层：DSH Session（原始对话历史）───────────────────────────┐
│  ~/.dsh/sessions/<workspace>/session-<uuid>/session.v4.jsonl.zstd │
│  例：--D-qq-bridge-state-agents-- 最大 725,980 字节（10-31 03:08）│
│  投影缓存：~/.dsh/storages/session_projcache/sessions/*.json      │
│  职责：完整对话流，供 DSH 重建上下文                             │
└───────────────────────┬──────────────────────────────────────┘
                        │ 模型每轮读上下文（受 compaction 裁剪）
┌───────────────────────▼──────────────────────────────────────┐
│ B 层：SocialV2（短期社交状态）                                 │
│  state/social-v2.json                                         │
│  activeTopics / pendingThoughts / memberImpressions           │
│  recentMessages(100) / unread(4,25) / wakeConfig / 各种时间戳  │
│  职责：她"此刻在想什么、记得谁"                                 │
└───────────────────────┬──────────────────────────────────────┘
                        │ 仅 qq_memory_append / query 显式读写
┌───────────────────────▼──────────────────────────────────────┐
│ A 层：向量长期记忆                                             │
│  state/memory-vectors.jsonl（一行一条 JSON）                    │
│  { key, text, time, vec[1024], share_review_status, ... }      │
│  embedding：本机 Ollama bge-m3（127.0.0.1:11434）              │
│  职责：跨会话语义回忆                                          │
└──────────────────────────────────────────────────────────────┘
```

## 1.2 运行时数据流（写入）

```
模型调 qq_memory_append(key, token, category, content, extra)
  ↓ MCP: agentApi POST /api/socialV2/memory-append   [带 x-agent-token]
  ↓ bridge 端点：三重鉴权（agentTokenOk → v2SessionAllowed → v2ToolEnabled）
  ↓ ① 快照 B 层三字段
  ↓ ② appendMemoryV2(st, category, content, extra)   ← 只改内存
  ↓ ③ appendVectorMemory(key, `${category}: ${content}`)  ← A 层，含 embed()
  ↓ ④ saveSocialV2StateStrict()                      ← B 层严格落盘
  ↓ 失败回滚 B 快照（A 不回滚）
  ↓ 返回 { ok, aSynced, bSynced, partial, rollbackError? }
```

## 1.3 运行时数据流（读取）

```
模型调 qq_memory_query(key, token, category?, topic?)
  ↓ ① agentApi GET /api/socialV2/memory?key=...     ← B 层轻量记忆
  ↓ ② 若有 topic：agentApi GET /api/socialV2/memory-vector?key=&topic=
  ↓    bridge → searchVectorMemory(key, topic, 5)
  ↓    loadRows() → filter(key 全等) → filter(visibility) → cosSim → topK
```

### 关键代码缺陷（A 层）

**缺陷 A1：`findMemoryRow` 第 4 级归一化会抹掉所有数字**

```js
// :249-251
const norm = (s) => String(s).replace(/^(activeTopic|pendingThought|memberImpression):\s*/, '')
  .replace(/[\s，。、；：""''「」\(\)（）！？,.!?:;'"-]/g, '')
  .replace(/\d+/g, '');     // ← 所有数字被删除
```

后果：`"用户用 [GPU]"` 与 `"用户用 [GPU]"` 归一化后都是 `"用户用RTXTi"`，**互相包含 → 误判为同一条**。分享申请/审批可能定位到错误的记录。

触发条件：两条记忆仅数字不同，且长度≥8。
影响：`requestShare` / `approveShare` / `rejectShare` 可能操作错行。

**缺陷 A2：`atomicRewrite` 固定 tmp 文件名 → 并发写冲突**

```js
// :376-380
function atomicRewrite(rows) {
  const tmp = VEC_FILE + '.tmp';        // ← 固定名，无 pid/随机后缀
  fs.writeFileSync(tmp, ...);
  fs.renameSync(tmp, VEC_FILE);
}
```

后果：两个请求同时 rewrite 时，A 写入 tmp，B 覆盖 tmp，A rename 的是 **B 的内容**，B rename 时 tmp 已不存在 → 抛错或数据错乱。
对比：`bridge.js` 的 `atomicWriteJson` 用了 `${file}.${pid}.${random}.tmp`（:184），A 层这里是**唯一没加固的写路径**。

触发条件：两个写操作（remove/clear/edit/approve）在毫秒级并发。
影响：可能丢记录或写错内容。

**缺陷 A3：检索用容错读，坏行静默跳过**

```js
// :172  searchVectorMemory 用 loadRows()
const rows = loadRows().filter(...);   // loadRows 内部 try{JSON.parse}catch{} 静默跳过
```

后果：JSONL 有坏行时，检索「少了几条」但完全无感知，不报错。
对比：remove/clear 已改用 `loadRowsStrict`（抛错），**检索路径没改**。

**缺陷 A4：无稳定 ID**

记录只有 `key + text + time` 三要素，没有 `id`。删除只能靠 `key+text` 全等匹配（:313），同 text 多条时只能删第一条（`removeVectorMemoryExact`）或按 N 条删（`removeNAll`），无法指定"删哪一条"。

**缺陷 A5：`category` 不是独立字段**

写入时（mcp append）拼成 `` `${category}: ${content}` `` 塞进 `text`，导致：
- 检索返回的 `text` 带前缀，注入模型时多几个字
- 删除时要用 `"activeTopic: 原文"` 才能匹配（这就是 Q5 memberImpression 问题的根因）

**缺陷 A6：`needs_review` 只在管理端列表过滤，检索完全不看**

```js
// :216  listVectorMemory 里
.filter((r) => (filter.needs_review === undefined || (r.needs_review ?? true) === filter.needs_review))
// :172-177  searchVectorMemory 里 —— 完全没读 needs_review
```

后果：标了 `needs_review:true` 的记录照样被检索命中并注入模型。

### B 层的关键发现

**发现 B1：B 层有文本级去重，A 层没有** `[已实现]`

```js
// :9218  activeTopic
const existing = st.activeTopics.find((t) => t && String(t.text || '') === text);
// :9237  pendingThought
const existing = st.pendingThoughts.find((t) => t && String(t.text || '') === text);
```

同 text 不新增，只更新时间戳。**所以"写入去重缺失"这条缺口，A 层成立、B 层不成立**——但两层标准不一致本身就是问题。

**发现 B2：每次 append 都会顺带全局清理** `[存在缺陷]`

```js
// :9210-9215  append 开头无条件执行
st.pendingThoughts = st.pendingThoughts.filter(过期);
st.activeTopics = st.activeTopics.filter(24h未提);
```

后果：写一条 "activeTopic" 会顺带删掉所有过期的 "pendingThought"。这是隐式副作用——写 A 类数据改 B 类数据。若这一步之后 strict 落盘失败，虽然回滚了快照，但**清理已经发生过一次**（快照恢复能还原，逻辑上 OK，但语义上是"写一条改多类"）。

**发现 B3：`memberImpressions` 无过期机制** `[部分实现]`

印象只在超 50 个时按 `lastSeenAt` 淘汰最旧。单个印象的 `traits` 永不过期，可能长期保留过时判断（"他很菜"这种会一直留着）。

**发现 B4：B 层与 A 层无关联字段** `[未实现]`

`memberImpressions[name]` 与 A 层 `text="memberImpression: xxx"` 之间**没有任何 ID 关联**，只能靠文本猜。

**发现 B5：数据损坏恢复** `[部分实现]`

- 读：`readJsonSafe(SOCIAL_V2_FILE, null)` — 损坏时返回 null，走默认空状态
- 写：`atomicWriteJson`（pid+随机 tmp + renameWithRetry）— 写中断安全
- 但：**损坏时静默回退空状态**，等于丢掉全部 B 层记忆，且不报错

# 三、六项已知缺口专项核查

## Q1：缺少归档机制 → **属实**

- **代码位置**：`memory-vector.js` 全文无 `archived`/`archivedAt` 字段；`searchVectorMemory`（:171-199）只过滤 `key` 和 `visibility`，**无状态排除**。
- **实际行为**：一条记忆只有"存在"或"物理删除"两种状态，没有中间态。
- **触发条件**：任何想"先留着但别再被检索"的需求 → 做不到，只能删。
- **影响**：模型可能反复检索到过时/不该引用的旧记忆。
- **其他路径**：`listVectorMemory` 支持 `needs_review`/`share_review_status` 过滤，但**那只影响控制台列表，不影响检索**。
- **结论**：`[未实现]`，确认。

## Q2：缺少写入去重 → **半属实（A 层属实，B 层不属实）**

- **A 层**：`appendVectorMemory`（:149-163）直接 `appendFileSync`，**没有任何查重**。
  - 触发：同一句话写两次 → 库里两条完全相同。
  - 影响：检索时同一内容占两个 topK 名额；上下文被重复内容占用。
- **B 层**：`appendMemoryV2` 有 `existing` 查找（:9218/:9237），同 text 只更新时间戳。
  - 但 `memberImpressions` 的 traits 用 `!traits.includes()` 去重（:9257），也是文本级。
- **其他路径**：`infoOK()` 只拦太短，不拦重复。
- **结论**：A 层 `[存在缺陷]`，B 层 `[已实现]`（但两层标准不一致是设计问题）。

## Q3：缺少自动重试与恢复 → **属实**

- **代码位置**：全项目搜无 `operationId`、无 `retryQueue`、无持久化任务队列。
- **实际行为**：
  - append A 失败 → 端点返回 `aSynced:false`，**不重试**，靠人看。
  - remove/clear B 落盘失败 → 回滚内存 + 返回 `bSynced:false`，**不重试**。
  - 程序崩溃 → 已写入的 A 层记录保留（appendFileSync 已落盘），但 B 层可能没落盘 → 不一致且无补偿。
- **影响**：部分成功靠人工发现，长期运行可能积累 A/B 不一致。
- **其他路径**：`dailyBackup` 提供每日快照兜底（但只保 7 天，且只在 append 前触发）。
- **结论**：`[未实现]`，确认。

## Q4：A/B 层编辑不同步 → **属实**

- **代码位置**：
  - B 层编辑：`bridge.js` `/api/socialV2/memory-update`（改 `activeTopics[idx].text` 等）
  - A 层编辑：`memory-vector.js:editVectorMemory`（:361-374）
  - **两者互不调用**
- **实际行为**：改 B 层记忆文本 → A 层对应的 `"activeTopic: 旧文本"` 原样保留。下次检索会命中旧文本，且无法再用新文本删到它。
- **触发条件**：任何 B 层 update 操作。
- **影响**：检索到已改过的旧内容；删除时对不上。
- **其他路径**：无。
- **结论**：`[存在缺陷]`，确认。

## Q5：memberImpression 的 A 层删除文本/target 不匹配 → **属实**

- **代码位置**：
  - 写入：`mcp-snowluma-safe.js` append → `appendVectorMemory(key, `${category}: ${content}`)`。memberImpression 时 A 层 text = `"memberImpression: <content>"`（content 是印象标签）
  - B 层存：`st.memberImpressions[target]`（target 是群友名）
  - 删除：remove 端点 `category='memberImpression'` 时只有 `target`，**没有 content**
- **实际行为**：remove memberImpression 只删 B 层，A 层跳过（阶段 7B 已明确实现），返回 `aSynced:'n/a'`。
- **触发条件**：任何 memberImpression 删除。
- **影响**：A 层该印象的向量记录永久残留，检索可能命中已"删除"的印象。
- **其他路径**：`removeAllVectorMemory(key)` 能整 key 清，但会误删其他类别。
- **结论**：`[存在缺陷]`，确认。根因是 Q5 缺陷 A5（category 不是独立字段）。

## Q6：时间字段只记录写入时间 → **属实**

- **代码位置**：`appendVectorMemory` 的 `time: time ?? Date.now()`（:156）；无 `occurredAt`。
- **实际行为**：`time` 是**写入时刻**。若她回忆"上周发生的事"，时间字段记的是"今天写这条"。
- **影响**：
  - 检索结果里的 `time` 会误导模型（以为是发生时间）
  - 无法做时间衰减、无法按事件时间排序
  - 无法回答"这件事是什么时候发生的"
- **其他路径**：`bridge.js` 的 `dailyBackup` 用文件名日期，与记忆 time 无关。
- **结论**：`[存在缺陷]`，确认。

# 五、当前算法评价（事实冲突与记忆更新）

## 5.1 六个场景的实际表现

| 场景 | 当前系统实际表现 | 标签 |
|---|---|---|
| **设备变化**（[GPU] → 5070Ti） | 两条**同时存在**，检索时**都返回**，模型看到矛盾信息 | `[存在缺陷]` |
| **偏好随时间改变** | 同上，新旧偏好并存 | `[存在缺陷]` |
| **旧事实被新事实替代** | **不会替代**，只追加 | `[未实现]` |
| **同一事实多个时间版本** | 全留，无版本标记，无法判断哪个是当前 | `[未实现]` |
| **同一事件重复提及** | A 层存多条重复；B 层同 text 去重 | `[部分实现]` |
| **两条相似但相反** | 余弦相似度**看不出否定**，"喜欢香菜"和"讨厌香菜"向量接近，topK 可能同时返回 | `[存在缺陷]` |

## 5.2 核心判断

**当前系统会同时保留互相矛盾的有效记忆，并在检索时混合注入。** 确认无误。

原因：
1. 无 `factKey`/`supersededBy` 概念，新事实不顶替旧事实
2. 余弦相似度对否定词不敏感（"喜欢"和"讨厌"在 embedding 空间接近）
3. 阈值 0.3 偏低，容易把弱相关内容也拉进来
4. 无时间衰减/时效权重，旧记忆和新记忆同分竞争

**风险示例**：
```
库里：
  "主人用 [GPU]"（3 个月前）
  "主人升级到 [GPU]"（昨天）
检索 "主人的显卡"：
  → 两条都命中（相似度都 > 0.3）
  → 都注入上下文
  → 模型可能说"你用 5060Ti"（错）
```

# 六、Memory V2 总体架构（设计）

## 6.1 设计原则

```
1. 不推翻现有三层结构（A/B/C 职责已清晰），只补强 A 层
2. 不引入外部依赖（不加向量库、不加 reranker 服务）
3. 权限过滤独立于相似度（现有已满足，V2 保持）
4. 所有"自动判断"必须可追溯、可回滚
5. 宁可保留待确认，不自动删
```

## 6.2 V2 架构图

```
写入链路（新增三层处理）
  append
    ↓ ① 规范化（去 CQ 码、trim、截断）
    ↓ ② 精确去重（scope + normalizedText 全等 → 更新而非新增）
    ↓ ③ 语义候选（同 scope 内 cosSim > 0.85 → 进入候选）
    ↓ ④ 事实判断（有 factKey 则比较；无则按 type 决策）
    ↓ ⑤ 写入（新增 / 更新 / 标记 superseded）
    ↓ ⑥ 双写（A 层向量 + B 层状态，带 operationId 幂等）

读取链路（新增过滤层）
  query
    ↓ ① 权限过滤（scope + visibility，先于打分）← 不可省
    ↓ ② 状态过滤（status=active，排除 archived/deleted）
    ↓ ③ 时效过滤（expiredAt < now 排除）
    ↓ ④ 向量打分（cosSim）
    ↓ ⑤ 排序（score × 时效权重 × 类型权重）
    ↓ ⑥ topK + superseded 处理（被替代的只在明确问"历史"时返回）
```

# 八、写入、更新、删除、检索流程（V2 设计）

## 8.1 写入三层去重

### 第一层：文本规范化 + 精确去重（自动）

```js
normalize(text) = text
  .replace(/\[CQ:[^\]]*\]/g, '')      // 去 CQ 码
  .trim()
  .replace(/\s+/g, ' ')                // 折叠空白
// 不去标点、不去数字（吸取 A1 缺陷的教训）

// 精确去重条件：同 scope + 同 type + normalizedText 全等 + status=active
// 命中 → 更新 updatedAt / occurredAt，不新增
```

**安全边界**：
- 不同 `scope` 不合并（群 A 和群 B 相同内容各自独立）
- 不同 `subjectId` 不合并
- 不同 `type` 不合并

### 第二层：语义候选发现（自动，但只做"候选"）

```js
候选条件：同 scope && 同 type && cosSim > 0.85 && status=active
产出：候选列表（不自动合并，交给第三层判断）
```

**为什么 0.85 而非 0.3**：0.3 是"检索阈值"（要宽），0.85 是"同一件事阈值"（要严）。两者不能混用。

### 第三层：事实冲突判断（半自动）

```
决策表：
┌─────────────────────────┬──────────────────────────┐
│ 条件                     │ 动作                      │
├─────────────────────────┼──────────────────────────┤
│ 有相同 factKey           │ 新记忆 supersedes 旧的     │
│  │                       │ 旧 status=superseded      │
│  │                       │ 旧 supersededBy=新.id     │
├─────────────────────────┼──────────────────────────┤
│ 无 factKey，但 type=fact │ 保留两条 + 标 needs_review │
│ 且语义高度相似           │ 进控制台待人工确认          │
├─────────────────────────┼──────────────────────────┤
│ type=event / temporary   │ 直接新增（事件不冲突）      │
├─────────────────────────┼──────────────────────────┤
│ type=preference           │ 有 factKey 则替代         │
│                          │ 无则保留两条 + 时间比较    │
├─────────────────────────┼──────────────────────────┤
│ 检测到否定词差异          │ **绝不自动合并**，保留两条  │
│ （"喜欢"/"不喜欢"）       │ 标 needs_review            │
└─────────────────────────┴──────────────────────────┘
```

**否定句检测（最小实现）**：
```js
const NEGATORS = ['不', '没', '别', '无', '非', '未'];
// 两条文本若一条含否定词、另一条不含，且其余部分高度相似 → 判为"相反"，不自动处理
```

**明确不自动处理的**：
- 语义相似但 factKey 不同 → 保留
- 时间不同 → 保留（可能是不同时期的事实）
- 无法判断是否同一事实 → 保留 + needs_review

## 8.2 事实更新与版本管理

### 示例推演：[GPU] → 5070Ti

```
写入 1（3 个月前）：
  { id: mem_001, type: fact, factKey: 'owner.gpu',
    content: '主人用 [GPU]', status: active, occurredAt: 3个月前 }

写入 2（今天）：'主人升级到 [GPU]'
  ① 规范化 → 无精确匹配
  ② 语义候选 → 与 mem_001 cosSim 0.91 > 0.85，进候选
  ③ factKey 判断 → 模型传了 factKey='owner.gpu'，与 mem_001 相同
  ④ 动作：
     mem_001: status='superseded', supersededBy='mem_002', archivedAt=now
     mem_002: { id: mem_002, factKey:'owner.gpu', status:'active',
                supersedes:'mem_001', occurredAt: now }

检索 "主人的显卡"：
  ① 权限过滤 → 通过
  ② 状态过滤 → mem_001 是 superseded，默认排除
  ③ 向量打分 → mem_002 命中
  → 只返回 5070Ti  ✅

检索 "主人以前用什么显卡"：
  → 检测到"以前"时间语义 → 放宽状态过滤，包含 superseded
  → 返回 mem_001（标注"已于 X 时间被替代"）
```

### 避免误判"同一事实"

```
必须三道闸门同时满足才认定同一事实：
  ① factKey 完全相同（模型显式传，或规则推导）
  ② 语义相似度 > 0.85
  ③ 否定极性一致（都有否定词 或 都无）

任一不满足 → 保留原记录，不 supersede
```

## 8.3 删除与归档

### 逻辑删除 vs 物理删除

| 类型 | 解决什么 | 实现 |
|---|---|---|
| **逻辑删除** `status=deleted` + `deletedAt` | 防"删除后又被重试任务/重复写入复活"；保留审计线索 | 写 JSONL 时 status 改 deleted，检索排除 |
| **物理删除** | 真删（用户明确要求/合规） | `removeVectorMemoryExact` 按 id 精确删，同时清 `supersededBy` 引用 |

**默认走逻辑删除**，物理删除需要显式参数。

### 归档

```js
archived: status='archived' + archivedAt=now + reason
检索：默认排除 archived（除非显式 includeArchived）
恢复：status='active', archivedAt=null
```

**归档 ≠ 删除**：归档可恢复、可检索（显式）；删除不可恢复（逻辑删除仍在库里但永不注入）。

### 删除完整流程（V2）

```
1. 鉴权（端点三重校验）
2. 定位（按 id 精确，无 id 才回退 key+text）
3. 检查关联（是否有 supersededBy 指向它、是否有 sourceMemoryIds 引用）
   ├─ 被引用 → 拒绝删除 或 级联清理引用
   └─ 无引用 → 继续
4. 标记 status=deleted + deletedAt
5. 清向量索引（V2 第一批还是 JSONL，直接改 status 即可）
6. 落盘（strict，失败回滚）
7. 返回 { ok, aSynced, bSynced, partial }
```

## 8.4 检索算法优化（评估）

以当前实现为基线（纯向量 + key 过滤 + visibility 过滤）：

| 方案 | 收益 | 成本 | 复杂度 | 适用条件 |
|---|---|---|---|---|
| **纯向量（现状）** | 已能用，零成本 | 0 | 低 | 记忆 < 500 条 |
| **+ 状态/类型/时间过滤** | **最高性价比**：解决矛盾注入、过时记忆 | 极低（改 filter） | 低 | **V2 第一批必做** |
| **+ BM25 混合** | 精确词（人名/型号/ID）命中率提升 | 中（要分词、建倒排） | 中 | 记忆 > 500 条且经常查精确词 |
| **+ Reranker** | 排序质量提升 | 高（要跑模型，本地要多一个服务） | 高 | 只在前两者都不够时考虑 |
| 换向量库（Faiss/Qdrant） | 规模上千后检索快 | 高（引入依赖、部署） | 高 | 记忆 > 5000 条 |

**结论**：V2 第一批**只做"状态/类型/时间过滤"**，不引入 BM25/Reranker/向量库。理由是记忆量小（当前 0 条，预期几百条），瓶颈不在算法而在数据模型。

**特别强调**：权限过滤必须独立于相似度——当前实现已满足（先 filter key，再算 cosSim，:172-177），V2 保持这个顺序，且**新增的 scope 过滤也必须在打分前**。

# 九、可靠性与恢复机制（V2 设计）

## 9.1 核心机制

```
operationId：每次写入生成 `op_<timestamp>_<rand8>`，随记录持久化
memoryId：`mem_<timestamp>_<rand6>`
幂等：同 operationId 重复执行 → 检测已存在则跳过（不重复写）
持久化任务队列：state/memory-queue.jsonl（待重试的操作）
重试：最多 3 次，间隔 1s / 5s / 30s（指数退避）
失败记录：state/memory-failures.jsonl（人可查）
```

## 9.2 异常场景推演

### 场景 1：A 层成功、B 层失败

```
当前：A 已写、B 回滚、返回 aSynced:true bSynced:false partial:true，不重试
V2：  同 response，但写入 memory-queue.jsonl（op=op_xxx, stage='b-pending'）
      下次启动或定时器扫队列 → 重试 B 层
      重试前先检查：该 op 是否已被"删除操作"撤销 → 是则丢弃任务
风险：B 层重试时 A 层可能已被删 → 需先查 A 层存在性
```

### 场景 2：B 层成功、A 层 Embedding 失败

```
当前：B 已写、A 未写、返回 aSynced:false bSynced:true partial:true，不重试
V2：  写队列（stage='a-pending', content 存队列里）
      重试时重新 embed（Ollama 可能已恢复）
      超过 3 次 → 移入 memory-failures.jsonl + 控制台可见
风险：content 存队列 = 明文落盘，需注意隐私（与 A 层同权限）
```

### 场景 3：写入过程中程序崩溃

```
当前：appendFileSync 是原子写入（单次 write syscall），半行风险低但存在
V2：  写入前写 WAL（state/memory-wal.jsonl，记 op + 完整行）
      重启时扫 WAL：有 op 无对应记录 → 补写
      有记录无 op 完成标记 → 标记完成
风险：WAL 本身也可能半行 → 用"整行 + 校验和"格式
```

### 场景 4：删除过程中崩溃

```
当前：atomicRewrite 用固定 tmp，崩溃留下 .tmp 垃圾
V2：  tmp 加 pid+随机后缀
      删除先写 status=deleted（逻辑删）→ 落盘 → 再异步物理清
      崩溃后重启：逻辑删除已生效（不会复活），物理清理可重入
```

### 场景 5：删除完成后旧重试任务重新执行

```
当前：无任务队列，不存在此问题（但也没有重试能力）
V2：  重试任务执行前，必须检查：
        ① 该 memoryId 是否存在
        ② 若 status=deleted → 丢弃任务，不重写  ← 关键防护
        ③ 若 op 已被标记完成 → 丢弃
      这是防"已删除记忆复活"的核心闸门
```

| S10 | 归档记录被检索 | 无归档概念，全部返回 | status 过滤排除 | 过时注入 | 状态过滤 | 归档一条后检索 |
| S11 | 已删记忆被重试重写 | 无重试，不会复活 | 重试前查 status=deleted → 丢弃 | **复活** | **关键闸门** | 删后手动跑队列 |
| S12 | B 层状态过期 | 24h/expiresAt 自动过滤 | 同 + 显式 TTL 字段 | 无 | 已有机制 | 造过期数据查清理 |
| S13 | Session 历史缺失 | A 层记忆仍在，仅丢最近对话 | 同 | 无 | 三层独立 | 删 session 文件 |

**额外场景**：

| # | 触发条件 | 当前表现 | V2 预期 |
|---|---|---|---|
| S14 | 多操作同时编辑同一条 | `atomicRewrite` 固定 tmp → 可能丢数据 | tmp 唯一化 + 乐观锁（updatedAt 比对） |
| S15 | 一条记忆被 superseded 后又想恢复 | 无此概念 | status 改回 active，清 supersededBy |

## 11.2 旧数据迁移

**当前实际数据状态（已核实）**：
```
A 层 memory-vectors.jsonl：0 字节（空）
B 层 social-v2.json：activeTopics=0, pendingThoughts=0, memberImpressions=0
                     recentMessages=100/46, unread=4/25（运行数据，非记忆）
```

**结论：A 层无数据需迁移，B 层无记忆数据需迁移。**

但**不能假定永远如此**——若迁移前又有新数据写入，需要：
```
迁移规则：
  旧 { key, text, time, vec }
  → 新 { id: 生成, type: 从 text 前缀推断(activeTopic→event 等), 
         scope: key 原样, status: 'active', content: 去前缀后的 text,
         createdAt: time, occurredAt: null, source: 'migration',
         vec, vecModel: 'bge-m3', normalizedText: 规范化(content) }
```
**迁移前必须备份**，且迁移脚本要可重入（按 id 去重）。

## 11.3 兼容性风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 旧 MCP 工具参数不变 | 模型可能仍在用旧参数（无 type/factKey） | type 默认推断，factKey 缺省 null（不启用事实替换） |
| 控制台 UI 读旧字段 | `listVectorMemory` 返回结构变化 | 保留旧字段名做别名字段 |
| 分享审批依赖 text 匹配 | V2 改用 id 后，`findMemoryRow` 需保留兼容 | 保留 key+text 回退路径 |
| preset 里的记忆工具说明 | 需同步更新 description | 单独一步，不改工具名 |

## 11.4 回滚方案

```
每批改动前：备份 memory-vector.js + 数据文件
回滚：代码用备份覆盖 + 数据用迁移前快照覆盖
风险：迁移后新写入的数据在回滚时会丢失（格式不兼容）
缓解：迁移采用"新增字段，不改旧字段"策略 → 旧代码读新文件仍可用
```

## 11.5 分批实施顺序

| 批次 | 内容 | 验收标准 |
|---|---|---|
| **P1** | 数据模型扩展（id/type/scope/status/occurredAt/factKey/supersededBy）+ 检索状态过滤 | 新写入带全部字段；archived/deleted 不被检索；旧数据兼容 |
| **P2** | 写入去重（三层）+ factKey 事实替换 | 同文不重复；有 factKey 时旧标 superseded |
| **P3** | 逻辑删除 + 归档 + 恢复 | 删除可回滚；归档可恢复；retry 不复活已删 |
| **P4** | WAL + 重试队列 + 失败记录 | 崩溃后可恢复；部分成功自动补偿 |
| **P5** | 检索优化（时间衰减 + 类型权重） | 新旧事实同分时新的优先 |
| **P6**（可选） | BM25 混合检索 | 精确词命中率提升 |
