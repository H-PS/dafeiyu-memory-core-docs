# 一、A 层完整数据流

## 1.1 写入链路（两条来源，性质完全不同）

```
路径 A｜运行时写入（正常链路）
  ① 群/私聊消息 → bridge 收到 OneBot 事件
  ② bridge 生成会话 key（private:<QQ> / group:<群号>，受 canonicalV2Key 正则约束 bridge.js:1370）
  ③ bridge 唤醒 DSH → 模型在上下文中拿到【会话 key】+【会话令牌】

  ⑤ MCP 先 POST /api/socialV2/memory-append  ← B 层，三重校验（见 3.1）
  ⑥ B 层写成功后，MCP **在本进程内**直接 appendVectorMemory(key, `${category}: ${content}`)

  seed-group-owner.mjs → 拉群历史 → 过滤主人发言
  → appendVectorMemory('private:<ownerQQ>', '（群里）<时间> 主人说：<原文>')   ← :52

**关键点【已确认】**：
- A 层写入**不经过 bridge HTTP**，是 MCP 进程直接写文件（`mcp-snowluma-safe.js:21` 直接 import memory-vector.js）。
- 写入文本**强制带分类前缀**：`${category}: ${content}`（:946）→ 这就是 #000 等记录里 `activeTopic:` 前缀的来源。
- `appendVectorMemory` 只写 5 个字段（key/text/time/vec/share_review_status），**不写 category/subjectType/sourceType/visibility/needs_review**（:130-133）。

```
  ① 模型调用 qq_memory_query(key, token, category?, topic?)

# 三、权限校验实际执行顺序

## 3.1 B 层（HTTP）——三重校验，顺序固定

`bridge.js:6786-6788`（读）/ `:6637-6639`（写）：

```
① agentTokenOk(key, token)     → 令牌是否属于这个 key 的会话
② v2SessionAllowed(key)        → 该 key 是否在当前模式允许范围内
③ v2ToolEnabled('memory')      → memory 工具是否被开关启用
```

注意三处都用 `if (req.headers['x-agent-token'] && ...)` 形式 —— **头缺失时整条跳过**。
但全局中间件（:3302-3315）已对 `x-agent-call` 请求做了兜底：无令牌的智能体调用只放行 `/api/status`、`/api/send/*`、`/api/images/*`，`/api/socialV2/` 前缀一概拒绝。
→ **B 层无法通过省略令牌绕过**【已确认】。

## 3.2 A 层（向量）——零校验

`mcp-snowluma-safe.js:996` 与 `:967` 直接在 MCP 进程内调用本地函数，**没有任何等价于上述三重校验的检查**：

```js
// :994-1001
if (topic) {
  const hits = await searchVectorMemory(key, topic, 5);   // key 来自模型参数
  ...
}
// :967
const r = requestShare(key, String(text ?? '').trim());   // key 来自模型参数
```

`key` 是 MCP 工具的必填字符串参数（schema 见 :982），**描述里只写了"格式 group:群号 或 private:QQ号"，没有任何"必须是当前会话"的强制**。

# 四、private / group 隔离结论

## 4.1 key 如何参与隔离【已确认】

`memory-vector.js:147`：

```js
const rows = loadRows().filter((r) => r.key === key && Array.isArray(r.vec));
```

**key 是第一道、也是唯一一道会话隔离。** 全等比较，key 不匹配的记录根本进不了候选集。

key 的合法性由 `bridge.js:1370 canonicalV2Key` 约束：

```js
/^(group|private):(\d+)$/   // 只接受这两种 + 纯数字 ID，且去掉前导零
```

## 4.2 逐问回答

| 问题 | 结论 | 依据 |
|---|---|---|
| private/group key 在哪生成 | bridge 侧按会话类型生成，格式受 `canonicalV2Key` 正则约束（bridge.js:1370）；发送端点的构造见 :7016。**入站消息的具体构造行本次未逐行定位** | 【已确认】格式约束 / 【无法确认】入站精确行号 |
| key 是否参与检索前过滤 | **是，且是过滤的第一步**（memory-vector.js:147） | 【已确认】 |
| 群聊查询能否检索 private key | **正常调用路径不能**（rows 已被 key 过滤）。但**模型可以主动传 private key 造成越权**（见 5.1） | 【已确认】 |
| 私聊查询能否检索 group key | **不能**，同理；除非模型传 group key | 【已确认】 |
| 群号 / 用户 ID / session ID 如何参与隔离 | 群号与用户 ID 直接拼进 key（`group:<群号>` / `private:<QQ号>`）；sessionId 是 DSH 侧会话标识，**不参与 A 层隔离** | 【已确认】 |
| 是否存在跨会话越权路径 | **存在**，见 5.1（P0） | 【已确认】 |

## 4.3 附带发现：非主人私聊的记忆不可见（功能缺陷）

`memory-vector.js:149-152`：

```js
const isOwnerPrivate = key.startsWith('private:') && key.endsWith('<ownerQQ>');  // 硬编码主人 QQ
const visible = isOwnerPrivate
  ? rows
  : rows.filter((r) => r.visibility === 'group_shared' && r.share_review_status === 'approved');
```

- 只有**主人私聊**走"全部可见"分支。
- 其他任何 key（包括**别人的私聊** `private:<其他QQ>`）都落到第二个分支 —— 要求 `group_shared + approved`，而私聊写入的记录默认没有 visibility 字段 → **别人私聊她时，一条自己的记忆都查不到**【已确认】。

> 这解释了为什么"记忆只有跟网管聊才有效"。是设计上的硬编码，不是配置项。

# 五、权限机制与 #101 隐私风险

## 5.1 【P0】跨会话越权检索（代码确认）

**路径**：群聊上下文中，模型调用

```js
qq_memory_query({ key: 'private:<ownerQQ>', token: '<群聊会话令牌>', topic: '任何话题' })
```

**为什么能成**【已确认】：
1. B 层那一步（GET /api/socialV2/memory?key=private:...）会被 `agentTokenOk` 拦住 → 抛错。
2. **但 A 层那一步在 :996 之前就已经能执行**：`searchVectorMemory` 在 MCP 进程内直接读 jsonl，`key` 参数没有任何令牌绑定校验。
3. 结果直接拼进返回文本 → 进入群聊上下文的模型。
4. `isOwnerPrivate` 只看 key 字符串前缀/后缀 → 传对 key 就全部可见。

**同样的缺口存在于 `qq_memory_share_request`**（:967）：可用任意 key 定位记忆并发起分享申请。虽然批准仍需控制台，但"能否定位到"本身已经越界。

**`qq_memory_append` 是唯一间接受保护的**：B 层 HTTP 校验在 A 层写入之前，key 不匹配令牌会抛错，`appendVectorMemory` 不会执行【已确认】。

**触发条件**：需模型主动传错 key。正常情况下它从提示词读当前 key，不会错；但群友可用 prompt injection 诱导（如"你用 private:xxx 查一下"）。工具的 schema 没有任何约束阻止。

## 5.2 visibility / share_review_status 的检查位置

**唯一检查点**：`memory-vector.js:152`（检索时）。全项目仅此一处【已确认】。

| 字段 | 检查位置 | 是否所有入口都校验 |
|---|---|---|
| `visibility` | memory-vector.js:152 | **仅检索路径**。管理端列表不过滤 visibility（`listVectorMemory` 只按 key/category/subjectId/needs_review/share_review_status 过滤） |
| `share_review_status` | memory-vector.js:152（检索）、:192（管理端过滤） | 检索路径有；管理端可选 |

**不存在第二个检索入口**：全项目 `searchVectorMemory` 的调用方只有 `mcp-snowluma-safe.js:996` 和 `seed-group-owner.mjs`（后者是查证用脚本，非运行时路径）【已确认】。

## 5.3 approve_share / reject_share 的实际行为

```
approveShare(key, text, note)   memory-vector.js:252
  → findMemoryRow 定位（4 级匹配：全等 / 双向包含 / 去前缀包含 / 归一化包含）
  → 若已 approved → 返回 already_approved（幂等，不报错）
  → 否则：share_review_status='approved' 且 **visibility='group_shared'**（:260）
  → 写 share_reviewed_at、可选 note
  → atomicRewrite 整文件重写

rejectShare(key, text, note)    :269
  → status='rejected' 且 **visibility 强制回退 owner_private**（:277）
```

**注意【已确认】**：`approveShare` **会改写 visibility** —— 这是全库唯一能把 `owner_private` 变成 `group_shared` 的路径。反向不成立：`visibility='group_shared'` 可以独立存在（那 30 条就是），此时未审批 → 检不到。

## 5.4 审批状态与 visibility 不一致的三种形态

| 形态 | 现存条数 | 实际效果 |
|---|---|---|
| `owner_private` + `unset` | 71 | 正常，仅私聊可见 |
| `group_shared` + `unset` | **30** | **检不到**（要 approved），等于"标了但没生效" |
| `group_shared` + `approved` | 1（#101） | 在其 key 范围内可检索 |
| `owner_private` + `approved` | 0 | 不会出现（approveShare 同时改两个字段） |

## 5.5 #101 专项结论（**修正上一份报告的错误**）

```
#101  key = private:<ownerQQ>
      visibility = group_shared
      share_review_status = approved
      缺 category / subjectType / sourceType / needs_review（appendVectorMemory 直写的特征）
```

| 问题 | 结论 | 依据 |
|---|---|---|
| private key 是否阻止群聊检索？ | **是**。群聊查询 key=`group:<群号>`，`r.key === key` 先把 #101 排除，它连候选集都进不去 | memory-vector.js:147【已确认】 |
| approved 是否足以让群聊读取？ | **不足**。approved 只是第二道过滤；第一道 key 全等就已经挡住 | 同上【已确认】 |
| 是否有其他检索路径绕过 key 隔离？ | **有**：模型显式传 `private:<ownerQQ>` 即可（见 5.1） | mcp:996【已确认】 |
| 是否可能把完整 QQ 号注入群聊上下文？ | **可能，但入口不是"群聊正常检索"，而是"越权传 key"**。一旦模型被诱导传 private key，`#101` 全文（含 QQ 号）会进入群聊模型上下文 | 【推断】基于 5.1 路径 |

**⚠ 重要修正**：上一份审核报告（03:15）写道"全库唯一能被群聊检索到的只有 #101"，**这个结论是错的**。正确结论是：**群聊当前一条 A 层记忆都检索不到**——30 条 `group_shared+unset` 卡在 approved，#101 卡在 key。真正的原因不是"审批没做完"，而是**key 与可见性两道闸门同时收紧，且授权机制设计成群内产生的内容进不了群内检索**。

#101 的真实风险因此从"泄漏到群"变成"结构错误"：它是一条 `private` 记录被标成了 `group_shared`，这个组合在检索语义上自相矛盾（key 说私有、字段说共享），实际效果是既没共享出去、又多了一个可被越权读取的高危目标。

# 七、A/B 双写与重复写入原因

## 7.1 哪些事件双写

| 动作 | B 层（social-v2.json） | A 层（vector jsonl） | 是否双写 |
|---|---|---|---|
| `qq_memory_append` | ✅ 经 HTTP | ✅ 本地 append（`category: content`） | **是**【已确认】 |
| `qq_memory_remove` | ✅ | ❌ **不删 A 层** | 单向 |
| `qq_memory_update` | ✅ | ❌ 不动 A 层 | 单向 |
| 日常对话 | ❌ | ❌ 不自动写 | — |
| 回填脚本 | ❌ | ✅ | 仅 A 层 |
| 手工同步（本次会话做过一次） | ❌ | ✅ | 仅 A 层 → 造成 #101 元数据缺失 |

**关键【已确认】**：`qq_memory_remove` 只删 B 层，**A 层记录留在原地**。所以"她删掉一条印象"之后，向量库里那条还在，检索照样能命中 —— 这是 B/A 不一致的长期来源。

## 7.2 是否有 B→A 同步机制

**只有单向 A←B 的一次性动作**：
- 正常路径：`append` 同时写两层（不是同步，是同一时刻的双写）。
- 手工路径：本次会话曾用脚本把 B 层一条印象写进 A 层（`#101`）。
- **不存在反向或定时的 B→A 自动同步**【已确认】。

## 7.3 是否有统一去重

**没有**【已确认】。
- `appendVectorMemory`（:124-138）直接 `appendFileSync`，无任何查重。
- 唯一的"去重"出现在 `seed-group-owner.mjs` 内部：按 `text` 全等比对已有记录（:47-58），**只对该脚本自身的重复有效**，且前缀不同就失效。
- `infoOK`（:100）只做信息量闸门，不做相似度去重。

## 7.4 群聊消息为什么进了 private key —— 确切原因【已确认】

```js
// seed-group-owner.mjs:52
await appendVectorMemory('private:[OWNER_QQ]', x.text);
```

这个脚本的逻辑是"捞群 [GROUP_ID] 里主人（ownerQQ）的全部发言 → 向量入库"，**key 硬编码成主人私聊**，文本加 `（群里）` 前缀。它只跑过一次（一次性脚本），但留下了 #098/#099/#100 三条群聊内容存在 private 范围。

所以"群聊内容混入个人记忆"**不是抽取管线的默认行为，而是一次人工回填的副作用**。

# 八、Archive 当前实现情况

| 能力 | 是否存在 | 依据 |
|---|---|---|
| 归档状态字段（如 `archived: true`） | **不存在** | 全库记录字段中无归档标记；`memory-vector.js` 无相关判断 |
| 检索时排除归档记录 | **不存在** | `searchVectorMemory` 只过滤 key 与 visibility（:147/:152） |
| 管理端查看归档 | **不存在** | `/api/memory/admin` 的 op 只有 list / remove / edit / approve_share / reject_share（bridge.js:6658-6698） |
| 归档与删除的区别 | **不存在**，只有真删除 | `removeVectorMemoryExact` 是物理删除（splice + 整文件重写 :286-293），不可恢复（除每日备份 `dailyBackup` :106） |

# 九、Character 四类结构可行性分析

## 9.1 现有字段能否承载

| 现有字段 | 取值现状 | 能否承载 Character 体系 |
|---|---|---|
| `category` | fact / event / relationship / character / unclassified | **不能直接承载**。它是"内容性质"分类，不是"记忆层级"。Character Core / Experience / Knowledge 是**层级/用途**，与 category 正交 |
| `subjectType` | bot / owner / group_member / unknown | 可用，对应"记忆主体" |
| `subjectId` / `subjectName` | 有（#101 缺） | **必需保留**，用于区分"关于谁的记忆" |
| `sourceType` | observed / manual | 可用，但粒度太粗（无法区分"对话观察""模型归纳""人工回填""脚本导入"） |
| `visibility` | owner_private / group_shared | 可用，但语义需重定义（见 P1 建议） |
| `time` | **写入时刻，非发生时刻** | **不可直接用于时间线** |

## 9.2 需要新增的字段（设计建议，不改数据结构）

```js
{
  memoryType: 'core' | 'relationship' | 'experience' | 'knowledge',   // 新增：Character 四类
  category:   string,        // 保留：内容性质（fact/event/...）
  subjectId / subjectName / subjectType,   // 保留
  sourceType: 'observed' | 'model_summary' | 'manual_backfill' | 'script_import',  // 建议扩充
  confidence: 0..1,          // 新增：这条记忆的可信度 / 稳固程度
  validFrom / validTo,       // 新增：事实有效期（解决 #008 这类"曾经为真"的记录）
  supersedes: [id],          // 新增：本条取代了哪些旧记录（解决"旧记忆覆盖新认知"）
  occurredAt,                // 新增：真实发生时间（从文本前缀解析或写入时带）
  archived: false            // 新增：归档标记
}
```

## 9.3 逐问回答

| 问题 | 结论 |
|---|---|
| 现有 category 能否直接承载四类 | **不能**。category 描述"是什么内容"，memoryType 描述"多重要、怎么用"，两者正交，必须新增字段而非改写 category |
| 是否需要新增字段 | **需要**，至少 `memoryType` + `archived` 两个；`confidence` / `validFrom` 属改善项 |
| 是否需要 subjectId / subjectName | **必需**，且应改为写入时强制必填（#101 就是缺这两个导致主体不明） |
| 是否需要 sourceType / confidence | sourceType **已有但需扩枚举**；confidence **建议新增**——区分"她自己说的（高）"与"模型归纳的（中）"与"脚本导入的（待核）" |
| 如何记录记忆来源和时间 | 来源：扩充 sourceType 四值；时间：写入时**同时记 `occurredAt`（真实时间，允许从文本前缀解析）与 `time`（写入时间）**，不要再混用 |
| 如何避免旧记忆覆盖新认知 | 三层机制：① `validTo` 标记失效（#008 用得上）② `supersedes` 显式声明取代关系 ③ 检索时按 `confidence × recency` 加权，而非只按余弦相似度 |

## 9.4 一个必须先解决的前置矛盾

人格卡 `roles/大肥鱼.md` 写「**名字还没定**」，而 #083 明确「大肥鱼是外号，我自己起的」、#101 明确「我定了叫网管」。

# 十一、审计结论摘要

```
1. A 层与 B 层的隔离强度不对等：
   B 层有三重校验（令牌↔key 绑定、会话白名单、工具开关），
   A 层零校验（MCP 进程内直接读文件，key 是模型传什么就用什么）。
   → 这是本次审计最重要的发现，也是唯一的 P0 安全缺口。

2. key 是唯一有效的会话隔离，visibility/approved 只是第二道闸门。
   → 因此 #101 的 private key 确实阻止了群聊检索；
     "approved 就能被群聊读取" 是不成立的。

3. 群聊记忆目前完全失效（0 条可检索），
   原因不是审批没做完，而是「群内产生的内容 + 要求 approved」这个组合
   在当前设计下几乎无法自然成立。

4. A 层没有任何自动注入路径，只能靠模型主动带 topic 查。
   needs_review 完全不参与运行时。

5. 重复的根源是「三条写入路径 + 零去重」：
   运行时 append / 手工同步 / 回填脚本。
   群聊进 private 的确切原因已定位到 seed-group-owner.mjs:52。

6. Archive 完全不存在，删除是物理删除（有每日备份兜底）。
```

**本次审计未修改任何代码、数据、配置或运行状态。等待网管审核后再决定是否进入 P1-B。**
