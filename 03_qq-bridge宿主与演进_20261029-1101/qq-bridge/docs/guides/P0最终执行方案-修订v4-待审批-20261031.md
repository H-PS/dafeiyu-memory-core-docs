# 一、一致性承诺（本轮修正）

**原表述"最终一致"不成立，统一修正为：**

> **实现 A/B 尽力同步与失败可发现，不保证自动恢复和最终一致。部分成功需要人工处理或后续对账机制修复。**

理由【已确认】：
- append 失败后**不自动重试**（embed 失败通常 Ollama 不可用，立即重试无益）。
- remove/clear **没有持久化待处理队列**（进程重启后部分成功的状态会丢）。
- 对账机制**本轮不做**。

**append 重复写入风险【已确认】**：append 失败后再次调用，若 B 层已写入、A 层未写入，再次调用会**再次写 B 层**（B 层无查重，`appendMemoryV2` 会再 push 一条），造成 B 层重复记录。此风险需在交付说明中明确提示。

# 二、A/B 一致性（append / remove / clear）

## 2.1 当前实际行为（已确认）

| 操作 | B 层 | A 层 | 同步状态 |
|---|---|---|---|
| append | bridge.js:6641 `appendMemoryV2` → saveSocialV2State | MCP 进程内 `appendVectorMemory`（mcp:946） | 双写，可部分成功，A 失败静默 |
| remove | bridge.js:6824-6830 filter 删 → saveSocialV2State | **无** | 否（A 残留） |
| clear | bridge.js:6844-6847 清 → saveSocialV2State | **无** | 否（A 残留） |

## 2.2 remove 的失败场景（本轮修正）

【已确认】执行顺序定为**先 A 后 B**，因此不存在"B 删除成功、A 删除失败"的正常场景。四个场景：

| 场景 | 行为 | 报告 |
|---|---|---|
| A 删除失败（找不到/异常） | **B 不执行删除** | 整体失败，返回错误 |
| A 删除成功 + B 删除失败 | 明确报告部分成功 | `aSynced:true` + 整体失败 + B 层可重试 |
| A 不存在对应记录 | 视为"已无对应记录"，**继续删除 B** | `aSynced:true`（视为已一致） |
| 两层均成功 | 正常完成 | `aSynced:true` + 整体成功 |

**关键语义【已确认】**：`aSynced` 只代表 **A 层状态**，**不能代替整体操作结果**。整体结果由返回的 `ok` / 错误信息决定。

## 2.3 重复记录删除数量（本轮明确）

【已确认】B 层 remove 用 `filter((t) => t.text !== content)`，删**所有**匹配记录（不是删一条）。A 层 `removeVectorMemoryExact` 删**第一条**匹配。

**修正后的对齐规则【必须】**：**A 层删除数量 ≤ B 层本次实际删除数量**。

```
举例：
  B 有 2 条，A 有 3 条相同记录 → 本次 A 最多删 2 条（留 1 条）
  B 有 2 条，A 有 1 条相同记录 → A 删 1 条，B 删 2 条
  B 有 0 条（找不到），A 有 N 条 → B 返回 404，A 层不动
```

**禁止无条件删除 A 层所有相同文本记录。** 实现时需先算出 B 层本次实际删除数量 `bRemoved`，再在 A 层删 `min(bRemoved, A层匹配数)` 条。

## 2.4 removeAllVectorMemory 的跨 key 防护（本轮修正）

【已确认】`canonicalV2Key`（bridge.js:1370）**只能验证 key 格式**（`group|private:\d+`），**不能验证调用者权限**。

**修正后的实现约束**：
- `removeAllVectorMemory` 必须**限制为 bridge 内部使用**（模块私有函数，或加"仅 bridge 调用"的约定）。
- **权限校验由 bridge 端点负责**（三重校验：agentTokenOk + v2SessionAllowed + v2ToolEnabled），函数本身**不做权限校验、不承诺安全**。
- **不设计"函数级跨用户授权测试"**（那是无法实现的——A 层函数天然无鉴权上下文，测试它"拒绝跨 key"是测一个不存在的能力）。
- D6 测试改为：**验证 bridge 端点对跨 key 的 403 拒绝**（在端点层测，不在函数层测）。

## 2.5 clear 的失败状态（本轮确认）

【已确认】回答三个问题：

1. **B 层内存状态是否已被修改？**
   是。remove/clear 的代码顺序是"先改 `st.activeTopics` 等内存数组（:6824-6829 / :6844-6847），再调 `saveSocialV2State()`（:6830 / :6847）"。所以 save 失败时，**内存已变**。

2. **saveSocialV2State 失败后，下一次重试是否还能正确处理？**
   `saveSocialV2State` 的 try/catch（:8660-8691）**吞掉了 `atomicWriteJson` 抛出的错误**（:8689-8691 只 `log` 不抛）。所以磁盘写失败时：**接口照常返回 `ok:true`，但磁盘未落盘、内存已改**。下一次读状态时（`loadSocialV2State`）会从磁盘读到旧值，内存的改动丢失。

3. **是否会出现"接口返回失败但内存和磁盘状态不同"？**
   **不会返回失败，但会出现"返回成功、磁盘没跟上"**。更准确说：**接口返回 ok:true，但磁盘仍是旧状态**——这是比"返回失败"更隐蔽的不一致。

**本轮处理**：在 clear/remove 的 A/B 同步实现里，`saveSocialV2State` 的失败**不能再被静默吞掉**——需要在端点层捕获并返回失败状态（而非依赖 saveSocialV2State 内部的 log）。【待验证】改造 saveSocialV2State 的失败传播方式，还是只在端点层加检测。

## 2.6 append 重试行为（本轮补充测试）

【已确认】当前 append 无重试、无自动补偿。修复后：

| 验证点 | 预期 |

| serializeModelData 透传 | 【已确认】`serializeModelData = JSON.stringify(compactModelData(...))`，`compactModelData` 是保留字段的递归映射（qq-model-view.js:118-134），**aSynced/aError 会完整透传**，不会被丢弃 |
