# 一、重要更正：append 端点其实会落盘

【已确认，更正 v5/v6 的结论】`appendMemoryV2` 的**最后一行**（bridge.js:8985）是 `saveSocialV2State();`。

之前 v5/v6 判断"append 端点不落盘"，是因为只看了端点体（:6640-6642），**没看到 save 在 `appendMemoryV2` 函数体内**。

正确结论：

```
append 端点（:6640-6641）：
  const st = getSocialV2State(key);
  appendMemoryV2(st, category, content, extra);
     ↓ appendMemoryV2 内部（:8919-8985）
     改 pendingThoughts / activeTopics / memberImpressions
     ↓ 最后一行 :8985
     saveSocialV2State();   ← 落盘在这里（吞错版）
```

所以：
- **append 是落盘的**（在 appendMemoryV2 末尾），不是 v5/v6 说的"不落盘"。
- 但它用的是**吞错版** `saveSocialV2State`，磁盘写失败时被吞、接口仍返回成功——这个"吞错"问题依然成立。
- 而且：**append 端点和 appendMemoryV2 都各自落盘？** 不——端点体（:6641）只调 appendMemoryV2，save 只在 appendMemoryV2 内 :8985 一次。所以 append 落盘一次。

**对 v6 方案的修正**：append 的"补落盘"需求不存在了（它本来就在 appendMemoryV2 末尾落盘）。但"吞错改可发现"的需求仍然成立——需要把 appendMemoryV2 末尾的 `saveSocialV2State()` 换成 `saveSocialV2StateStrict()`（或让端点能感知结果）。

# 二、loadRowsStrict 的缓存绕过问题

## 2.1 代码依据【已确认】

`loadRows`（memory-vector.js:44-58）：

```js
function loadRows() {
  try {
    const mtime = fs.existsSync(VEC_FILE) ? fs.statSync(VEC_FILE).mtimeMs : 0;
    if (mtime === cache.mtime) return cache.rows;   // ← 缓存命中，直接返回
    if (!mtime) { cache = { mtime: 0, rows: [] }; return []; }  // 文件不存在
    const rows = [];
    const lines = fs.readFileSync(VEC_FILE, 'utf8').split('\n');
    for (const line of lines) {
      if (!line.trim()) continue;
      try { rows.push(JSON.parse(line)); } catch {}   // ← 坏行静默跳过
    }
    cache = { mtime, rows };   // ← 跳过坏行的不完整结果写入缓存
    return rows;
  } catch { return []; }   // ← 读取失败吞成 []
}
```

v6 的 `loadRowsStrict` 草案仍保留了 `if (mtime === cache.mtime) return cache.rows;` 这一行。

## 2.2 缓存绕过问题（四个确认点）

| # | 场景 | 结果【已确认】 |
|---|---|---|
| 1 | 普通 loadRows 已缓存"跳过坏行后的不完整结果" | 是。:53 跳过坏行，:55 把不完整 rows 写入 cache |
| 2 | 文件 mtime 未变化 | 是。文件没动，mtime 不变 |
| 3 | 随后调 loadRowsStrict | 若复用 `mtime === cache.mtime`，**直接返回普通缓存的不完整结果，不检查坏行** |
| 4 | 文件不存在时，cache.mtime 为 0 返回旧缓存？ | **是潜在 bug**。`cache.mtime=0` 且下次 `mtime=0`（文件不存在）时，`mtime === cache.mtime`（0===0）为真，返回 `cache.rows`——但此时 cache.rows 可能是**上一次文件存在时的旧数据**。不过原 loadRows 在 :48 有 `if(!mtime){cache={mtime:0,rows:[]};return []}` 兜底，但**这行在缓存命中判断之后**，所以顺序是：先命中缓存（:47），再判断 !mtime（:48）。如果 cache.mtime 是 0 且当前 mtime 是 0，:47 命中，返回旧 rows，:48 永远不执行。**这是原 loadRows 的既有隐患，loadRowsStrict 不能继承。**

## 2.3 最小修复方案

```js
function loadRowsStrict() {
  const mtime = fs.existsSync(VEC_FILE) ? fs.statSync(VEC_FILE).mtimeMs : 0;
  if (!mtime) { cache = { mtime: 0, rows: [] }; return []; }  // 文件不存在 → 正常空，且重置缓存
  // 严格读：不信任普通缓存的"跳过坏行"结果，重新读文件
  const rows = [];
  const lines = fs.readFileSync(VEC_FILE, 'utf8').split('\n');  // 读取失败抛错
  for (const line of lines) {
    if (!line.trim()) continue;
    rows.push(JSON.parse(line));  // 解析失败抛错（不再静默 skip）
  }
  cache = { mtime, rows };   // 严格读成功后才更新缓存
  return rows;
}
```

**要点**：
1. **严格读不命中缓存**——每次 `loadRowsStrict` 都重新读文件（去掉 `mtime === cache.mtime` 短路）。代价是严格读稍慢，但严格读只用于 remove/clear 等低频写操作，可接受。
2. **文件不存在**：先判 `!mtime`，返回 `[]` 且重置缓存为 `{mtime:0, rows:[]}`，避免返回旧缓存。
3. **解析失败/读取失败**：直接抛错（无 catch 折叠）。
4. **成功后更新缓存**：`cache = {mtime, rows}`，且严格读的结果是"完整无坏行"的，覆盖普通缓存的"跳过坏行"结果。
5. **不改变普通 loadRows**：普通 loadRows 保持原样（静默 skip 坏行、吞异常），供 searchVectorMemory 等检索路径继续用。

# 三、append 回滚必须恢复完整原状态

## 3.1 appendMemoryV2 实际修改的字段【已确认】

`appendMemoryV2`（:8919-8985）修改**三个字段**，且都有"清理/裁剪"副作用：

| 字段 | 修改动作 | 是否可能删原有记录 |
|---|---|---|
| `st.pendingThoughts` | ① 24h 清理 `filter`（:8925）② 可能 push（:8957）③ 可能 splice 超 20（:8964） | **是**：① filter 掉过期项，③ splice 掉超出 20 的项 |
| `st.activeTopics` | ① 24h 清理 filter（:8928）② 可能 push（:8941）③ 可能 splice 超 20（:8948） | **是**：①③ 会删 |
| `st.memberImpressions` | ① 可能新建/改 target（:8972）② 可能 delete 超 50（:8981） | **是**：② 会删 |

**结论【已确认】**：`appendMemoryV2` 修改**多个数组/对象**，且 24h 清理和长度裁剪会**删除原有记录**。**仅靠 pop() 撤销新增记录是错的**——因为清理/裁剪已经动了其他记录。

## 3.2 最小修复方案：字段级快照

```js
// append 端点内（或 appendMemoryV2 调用前）：
const snapshot = {
  pendingThoughts: Array.isArray(st.pendingThoughts) ? st.pendingThoughts.map(t => ({...t})) : undefined,
  activeTopics: Array.isArray(st.activeTopics) ? st.activeTopics.map(t => ({...t})) : undefined,
  memberImpressions: st.memberImpressions ? JSON.parse(JSON.stringify(st.memberImpressions)) : undefined
};

appendMemoryV2(st, category, content, extra);   // 内部 :8985 落盘（吞错）

try {
  saveSocialV2StateStrict();   // 严格落盘，失败 throw
} catch (e) {
  // 回滚：恢复三个字段
  if (snapshot.pendingThoughts !== undefined) st.pendingThoughts = snapshot.pendingThoughts;
  if (snapshot.activeTopics !== undefined) st.activeTopics = snapshot.activeTopics;
  if (snapshot.memberImpressions !== undefined) st.memberImpressions = snapshot.memberImpressions;
  // 回滚后，B 层内存 = 操作前
  throw e;   // 继续向上抛，端点返回失败
}
```

**要点**：
1. 快照只覆盖 3 个受影响字段，**不深拷贝整个 socialV2**。
2. `memberImpressions` 是嵌套对象，用 `JSON.parse(JSON.stringify())` 深拷贝（它只含简单类型）。
3. `pendingThoughts`/`activeTopics` 是对象数组，`map(t => ({...t}))` 浅拷贝每个元素即可（元素字段是简单类型，无嵌套）。
4. 回滚后，`st` 的三个字段恢复原值，B 层内存 = 操作前。

## 3.3 是否有无法通过字段快照恢复的副作用

【已确认】检查 `appendMemoryV2` 的全部副作用：

| 副作用 | 能否被字段快照恢复 |
|---|---|
| pendingThoughts 改动 | ✅ 能（快照恢复） |
| activeTopics 改动 | ✅ 能 |
| memberImpressions 改动 | ✅ 能 |
| :8985 saveSocialV2State（吞错） | ⚠️ 落盘结果无法"回滚"——若已写盘成功，回滚内存后磁盘和内存不一致。**但本场景是 strict 落盘失败，说明磁盘没写成功**，所以无此问题 |
| 其他副作用 | 无（appendMemoryV2 只动这 3 个字段 + 末尾 save） |

**结论**：字段快照可完整恢复 B 层内存状态，无遗漏副作用。

**一个边界【待验证】**：`appendMemoryV2` 末尾的 `saveSocialV2State()`（吞错版）在 strict 落盘**之前**已经执行了一次吞错落盘。如果这次吞错落盘**恰好成功**（磁盘写进去了），随后 strict 落盘又失败（比如磁盘随后才满），则回滚内存后**磁盘上已经有 append 后的状态**，内存回滚了、磁盘没回滚 → 不一致。这个窗口很窄（两次落盘之间），但理论上存在。**最小处理**：把 `appendMemoryV2` 末尾的吞错 save 移除，改为只由调用方（端点）做一次 strict 落盘，避免双写。

# 四、回滚失败语义

## 4.1 代码依据【已确认】

当前无回滚逻辑（回滚是本方案新增的），所以"回滚失败"是新增逻辑的边界。

## 4.2 三个确认点

| # | 问题 | 结论 |
|---|---|---|
| 1 | 是否有独立日志记录原始错误和回滚错误 | **当前无**（无回滚逻辑）。需在方案中加：`log('回滚失败:', ...)` 与原始错误分开记录 |
| 2 | 接口是否错误报告普通失败，而实际内存未知 | **需预防**。回滚失败时，内存状态未知，若接口只返回"失败"，调用方以为内存也回滚了，实际可能没回滚 |
| 3 | 是否需要 rollbackFailed 状态 | **建议加**。回滚失败时返回 `rollbackFailed: true`，让调用方知道"失败 + 内存状态不确定" |

## 4.3 最小方案

```js
try {
  saveSocialV2StateStrict();
} catch (e) {
  // 原始错误
  let rollbackFailed = false;
  try {
    // 回滚字段
    st.activeTopics = snapshot.activeTopics;  // 等
  } catch (e2) {
    rollbackFailed = true;
    log('回滚失败（原始错误: %s）:', e?.message, e2?.message);
  }
  sendJson({ ok: false, aSynced: ..., bSynced: false, partial: true, rollbackFailed, error: e?.message });
  return;
}
```

- 原始错误和回滚错误**分开记录**。
- 回滚失败时 `rollbackFailed: true`，调用方可识别"内存状态未知"。
- 不新增自动恢复，只要求**错误可识别**。

# 五、两个问题的最小修正方案汇总

```

```
