# 二、A/B 生命周期一致性（append / remove / clear 三项）

## 2.1 当前实际行为（已确认）

| 操作 | B 层 | A 层 | 是否同步 |
|---|---|---|---|
| append | bridge.js:6641 `appendMemoryV2` → saveSocialV2State | MCP 进程内 `appendVectorMemory`（mcp:946） | 双写，但分两个进程/两次写，可部分成功 |
| remove | bridge.js:6824-6830 删 B 层 → saveSocialV2State | **无** | 否（A 层残留） |
| clear | bridge.js:6844-6847 清 B 层 → saveSocialV2State | **无** | 否（A 层残留） |

## 2.2 A/B 失败恢复专项审查（本轮重点）

### 2.2.1 append 部分成功后的重试机制

【已确认】当前无重试机制。流程：

```
MCP 端：B 层 HTTP 成功 → 进程内 appendVectorMemory
  appendVectorMemory 内部：embed（可能失败/超时）→ appendFileSync（可能失败）
  失败时：catch 只 console.error，返回仍走 B 层成功结果
```

**已确认的问题**：B 成功 + A 失败时，**没有重试、没有标记、没有补偿**，残留"B 有 A 无"且静默。

**修复方向**：
- 把 A 层写入收进 bridge 的 append 端点（与 B 层同进程）。
- A 层失败时，返回里加 `aSynced: false` + `aError: <原因>`。
- 【不自动重试】——因为 embed 失败通常是 Ollama 不可用，立即重试大概率也失败；改为"标记失败 + 日志"，靠后续对账补（对账本轮不实现，仅记录）。

### 2.2.2 remove 删除一层成功、另一层失败后的恢复

【已确认】当前 remove 只动 B 层，A 层完全不动，所以"B 成功 + A 失败"的窗口不存在（因为 A 层根本没被调用）。

**修复后**（本轮要做的）：remove 会同时动两层，出现新窗口：

```
顺序建议：先删 A 层，再删 B 层
  → 若 A 删成功、B 删失败：返回 aSynced:true 但整体失败，B 层记录还在（下次可重试）
  → 若 A 删失败（没找到对应记录）：说明 A 层本就没有对应，可视为已同步（返回 ok）
  → 若 A 删成功、B 删也成功：完全同步 ✅
```

**关键设计**：A 层用 `removeVectorMemoryExact(key, text)` 是"精确匹配"，找不到时返回 `null`（不是错误）。所以"A 层没有对应记录"不算失败，应视为"已一致"，不阻塞 B 层删除。

### 2.2.3 clear 部分成功后的恢复

【已确认】当前 clear 只动 B 层。

**修复后**：clear 需要新增 `removeAllVectorMemory(key)`（按 key 删全部，当前不存在此函数）。

```
顺序建议：先清 A 层（removeAllVectorMemory(key)），再清 B 层
  → A 清成功、B 清失败：A 已空、B 还在 → 返回 aSynced:true 但整体失败，B 可重试
  → 两层都成功：完全同步 ✅
```

**防护【必须】**：`removeAllVectorMemory(key)` 必须**严格按 key 全等**过滤，且 key 需先过 `canonicalV2Key` 校验，**绝不允许空 key 或模糊匹配**（见 2.2.5）。

### 2.2.4 重复记录的精确删除策略

【已确认】`removeVectorMemoryExact(key, text)`（memory-vector.js:286-294）用 `key + text` 全等匹配，找到第一条就 `splice` 删掉。**如果同一 key 下有多条 text 完全相同的记录，只删第一条，其余保留。**

**风险【已确认】**：当前 infoOK 不查重，理论上同一 key 可写入多条相同 text。此时：
- `qq_memory_remove` 删 B 层一条，A 层对应 `removeVectorMemoryExact` 只删第一条，**可能留重复残留**。

**修复方向（本轮）**：remove 同步时，A 层删除改为"删全部匹配的"（新增 `removeAllVectorMemoryExact(key, text)` 或循环删除），与 B 层"filter 全删"语义对齐。**但这要谨慎**：不得因此扩大到"删了不该删的"。做法是——A 层删除数量 = 与 B 层删除数量对齐：B 层 `filter` 删了几条，A 层就删几条匹配的。

【待验证】B 层 remove 的 filter 语义（`String(t.text) !== content` 删全部匹配）与 A 层"删一条"的不对称，需在实现时确认对齐方式。

### 2.2.5 空 key 和跨 key 清理防护

【已确认】当前 B 层 clear/remove 已有防护：
- remove（bridge.js:6814）`if (!key || !category)` 拦空 key
- clear（bridge.js:6838）`if (!key)` 拦空 key
- 两端点都有 `agentTokenOk(key, token)` + `v2SessionAllowed(key)`，跨 key 会被拦

**A 层新增的 `removeAllVectorMemory(key)` 必须补齐同等防护**：
- key 先过 `canonicalV2Key`（:1370），非法/空 key 直接拒绝。
- 函数内 `filter(r => r.key === key)`，绝不用 `startsWith` 或模糊匹配。
- 【待验证】A 层函数本身无鉴权（当前设计），因此必须**只被 bridge 端点调用**，不能被 MCP 直接 import 调用——这依赖"鉴权上移"完成。

### 2.2.6 MCP 是否正确传递 aSynced

【已确认】当前 MCP 端 `qq_memory_append/remove/clear` 都是 `return serializeModelData(data)`，直接把 bridge 返回的 JSON 序列化给模型。所以：

- 只要 bridge 端点在返回里加了 `aSynced` 字段，MCP 端**无需改动**就能透传给模型（`serializeModelData` 会带上）。
- 【待验证】`serializeModelData` 对新增字段的序列化行为，需确认不会丢弃。

**结论**：aSynced 的传递路径是"bridge 返回 → MCP serialize → 模型"，天然可用，MCP 端零改动。

【已确认 + 用户决定】edit 本轮不修。因此：

```

  → 改 B 层记忆 ≠ A 层也改了
```
