## 一、核心结论：三层分工，各管一件事

| 层 | 承载 | 回答的问题 | 位置 |
|---|---|---|---|
| **Obsidian** | 设计、文档、决策、复盘 | **我们为什么这样设计** | 本地 vault（Markdown） |
| **QQ Bridge** | A 层向量记忆、B 层社交状态、C 层聊天历史 | **她实际记得什么** | `state/*.json` / `.jsonl` |
| **DSH** | System Prompt、人格卡、工具协议、行为规则 | **她按什么设定行动** | `roles/*.md` + preset |

**关键纪律：Obsidian 不是向量库，不参与运行时，不会让机器人「自动获得记忆」。** 两套记忆不混：

```
Obsidian  = 项目知识（给人和 Agent 查资料用，静态、可读、可版本化）
A 层向量库 = 她的日常长时记忆（运行时检索，语义召回，动态演化）
```

> 前者是「档案馆」，后者是「海马体」。混用会导致：她的记忆里塞满架构决策，或者你的文档被反复改写。

## 三、最值得用的三个功能

### 3.1 关系图谱（Graph View）

把「人格卡 → 记忆系统 → 工具协议 → 问题复盘」用双链连起来后，图谱会直接呈现项目的知识骨架。

典型用法：点开「记忆分享机制」，一眼看到它被哪份复盘引用、受哪条权限规则约束、对应哪段代码模块。

### 3.2 双向链接（`[[...]]`）

```markdown
在 02-记忆系统/A层-向量记忆.md 里写：
  分享审批的实现见 [[记忆分享机制]]，踩过的坑见 [[2026-10-31-记忆分享8个坑]]。
```

好处：改一个概念，所有引用处都能反查到；不用维护目录索引。

### 3.3 Markdown + 版本记录

人格卡是最需要版本化的东西。建议每次改人格都留一份带日期的副本或用 Git 管理 vault：

```
01-人格设计/
├── 人格卡-大肥鱼.md          ← 当前版本
└── 历史/
    ├── 人格卡-大肥鱼-20261030.md
    └── 人格卡-大肥鱼-20261031.md
```

> 附加收益：vault 目录直接初始化成 Git 仓库，每次改动都有 diff，比聊天记录可靠得多。

## 四、强制机制：每次改代码都交一份变更记录

**这是整个方案里价值最高的一条。** 约定：以后每次让我改代码，除代码本身外必须额外交付这份记录，存进 `05-问题复盘/` 或对应模块目录。

### 模板

```markdown
# 变更记录

- 日期：2026-10-31
- 修改模块：src/memory-vector.js / public/console.html
- 修改原因：分享申请匹配不上、控制台无审批入口

## 修改内容
- findMemoryRow 增加第 4 级归一化匹配（去标点/数字）
- 新增 /api/memory/admin 的 x-console-token 鉴权路径

## 影响范围
- 影响：qq_memory_share_request 的匹配成功率
- 不影响：检索打分逻辑、A 层既有数据

## 测试结果
- 逐字原文 → pending ✅
- 漏 QQ 号改写版 → pending ✅
- 过于模糊 → 找不到 ✅（符合预期）

## 回滚方式
- 解压 v22-share-match-lv4.zip 覆盖 src/memory-vector.js
- 重启 qq-bridge
```

### 为什么要强制

```
① 三个月后你不会记得「为什么当初要加第 4 级匹配」
② Agent 每次新会话都要重新理解项目，变更记录是最便宜的上下文
③ 出问题时能精确回滚到某个 zip，而不是靠记忆
④ 决策链可追溯：为什么选 A 不选 B，比代码本身更值钱
```

## 六、明确不做什么（防止跑偏）

```
✗ 不用 Obsidian 替代 A 层向量库（它不是向量库，没有语义检索）
✗ 不把项目文档向量化进她的记忆（会挤占记忆配额、污染人设）
✗ 不指望 Obsidian 让机器人「自动获得记忆」（它只是静态文件）
✗ 不在文档里写会频繁变动的运行时数据（QQ 号、令牌、会话 key）
✗ 本次不创建任何目录、不安装软件、不改任何配置
```
