# E-2 · `memory_tier` 的转换规则

## 问题

`memory_tier` 三值（L1/L2/L3），要求与 `status` 正交且可独立维护。**它到底能不能变、由谁变、按什么条件变？**

## 实证 — 我此前的说法需要修正

我在前几轮报告里写的是"全部 24 份文档中没有任何一处定义 tier 转换规则"。**这个说法过强，是错的。**

实测结果：语料中存在**相当多** tier 规则，只是**分散且不在状态机里**：

| 位置 | 内容 |
|---|---|
| `11` §7.12 L493-506 | **3×6 矩阵**：`semantic_type` × `tier`，每格标注 `●`常见 / `○`可能 / `—`罕见，并附注"典型基准，**非硬绑定**" |
| `11` L510 | 矩阵只是默认倾向；**最终 `tier` MUST 由 M04 整合裁决**，M03 只给 `lifecycle_candidate` |
| `11` L514 | **`L1` 数据 MUST NOT 自动晋升 `L3`**（X-2：Session 结束丢弃短期状态，L1 仅预留） |
| `11` L513 | **MUST NOT** 因内容"重要"就直接置 L3；**MUST** 有稳定/明确/多次/用户明确要求等依据 |
| `11` L512 | **MUST NOT** 把 L1 等同于"可丢弃" |
| `11` L511 | **MUST NOT** 以 tier 决定读取优先级 |
| `11` L597 | tier **MUST NOT** 作为读取闸门（授权后 L1 可直读，L3 也不能绕过权限） |
| `11` L632 | **MUST NOT** 用 tier 作为排序主权重 |
| `11` L348 | `L1`/`L2` 状态 **MUST** 有过期/复核机制 |
| `SM-1`…`SM-8` | **零处** tier 边（这是真的：状态机完全没有 tier 轴） |

所以准确的说法是：**tier 的"默认倾向矩阵 + 五条约束规则 + 决策者归属"都已存在，但缺少三样东西**——
1. **谁在什么时候执行提升/降级**（只有"由 M04 裁决"这一句，没有条件表）；
2. **L2→L3 的具体门槛**（L513 给了依据类型，但没有可判定的判据）；
3. **降级路径**（只有 L1 不得自动升 L3，没有 L3→L2、L2→L1 的任何规定）。

执行验证佐证了这一点：`parent.reeval.tier_promotion_refused` —— 状态机中 L2→L3 被拒（`VALIDATION_ERROR`），因为**状态机没有转录任何 tier 边**。

## 选项

| 选项 | 做法 | 后果 |
|---|---|---|
| **B1（推荐）** | 把 `11 §7.12` 已有的矩阵与五条规则**提升为权威位置**（`01`/`02`），补上"执行者 + 可判定判据 + 降级路径"，并镜像进 `SM-1` | 大部分材料已存在，工作量是**搬迁+补齐**，不是从零设计；转换成为可测对象 |
| B2 | 声明 tier **创建时固定**，仅 `status` 可变 | 最简，但与 `11` L510（M04 裁决）和 L348（L1/L2 须有过期复核）直接冲突，须推翻两条既有规则 |
| B3 | V1 把 tier **当纯标签** | 诚实，但与 L514（禁 L1→L3）和 L513（L3 须有依据）冲突 |

## 推荐：B1

B1 是唯一与现有材料一致的选择：`11` 号已经写了决策者（M04）、矩阵、和四条禁止。缺的只是**三个具体空洞**。B2/B3 都需要**推翻既有已写规则**，代价更大且会削弱过期机制。

## 修正记录

本文件上一版写"全库零处定义"，并据此把 E-2 定性为"设计完全缺失"。**那是不准确的。** 真实情况是：规则存在但分散、且状态机未转录。这个差别很重要——它把 E-2 从"从零设计"降级为"整合+补三个空洞"。

（误判原因是我的检索只查了 `tier.*转换|tier.*晋升` 这类语法，而没有读 `11` §7.12 的矩阵段落本身。）

## 影响

不解决则：过期（L348 要求）、提升（L510 指定 M04）、降级（无规定）**三件事都无法实现**，且 `SM-1` 与 `11` 的规则**互相矛盾**（前者无 tier 轴，后者要求 M04 裁决）。

# E-3 · `content_kind` 废除还是必填

## 问题

同一套文档同时主张废除与强制。

## 实证（直接读文件）

**主张废除：**
- `00-总体架构与设计原则.md` L7："`content_kind` 废弃"
- `00` L76："| content_kind（八值） | **废弃** → semantic_type + semantic_tags + source_type |"
- `DD-AUTHORITY-V2.md` L291："`content_kind(fact/opinion/…)` | **废弃** → source_type + semantic_tags"

**主张必填：**
- `01-记忆本体与数据模型.md` L161："**MUST** 区分两个独立分类维度：`type` 与 `content_kind`，**MUST NOT** 合并"
- `01` §7.3 专章定义八类
- `01` L206：对 `content_kind ∈ {hypothesis, inference}` 施加**规范性禁止**
- `02-核心算法规范.md` L630 **要求**该字段
- `memory-object.schema.json`：`required` **包含** `content_kind`，枚举为 `fact,opinion,preference,intent,hypothesis,inference,event,procedure`

（这一条由我直接读 schema 确认：`required includes content_kind: True`）

## 这不是措辞差异

它决定了每一个记忆对象**是否有第八个必填字段**。两种选择都能自圆其说——这正是契约不可用的定义。

## 选项

| 选项 | 做法 | 后果 |
|---|---|---|
| **C1（推荐）** | 执行 V2 废除：从 `01`/`02`/`memory-object.schema.json` 移除 `content_kind`，其语义由 `semantic_type` + `semantic_tags` + `source_type` 承载 | 与"V2 为准"的最高权威一致；需迁移映射（已有：§4.2 给出 `inference/hypothesis → ASSISTANT_INFERRED`） |
| C2 | 保留 `content_kind` 并撤回废除声明 | 需改 3 处权威文本，并解释为何 V2 判它废弃 |

## 推荐：C1

`DD-AUTHORITY-V2` 是自称最高权威且 APPROVED 的文件，它说废弃。且 `01 §7.3` 的八类与 `semantic_type` 六类高度重叠——保留两套正交分类只会制造歧义。

## 需要你确认

C1 意味着**删除一个必填字段**，属于破坏性 schema 变更。迁移映射已存在，但**存量数据如何处置**需要你定调（当前无存量数据，所以成本最低——现在做是最好时机）。

# E-4 · 两个对象模型谁权威

## 问题

`contracts/schemas/` 同时发两份"记忆对象"契约，**均无弃用标记**。

## 实证

| 文件 | 标题 | 大小 | 状态 |
|---|---|---|---|
| `memory-object.schema.json` | Memory Object | 6 839 B | v1 复合存储视图 |
| `memory-unit.schema.json` | Memory Unit | 14 655 B | V2 28 字段对象 |

差异不只是大小：
- `memory-object` 仍**接受**已退役的 `type: "episodic"`（`DRIFT-MEMORY-OBJECT-01`，已由 fixture 证明）
- `memory-unit` **拒绝**该值
- `memory-unit` 自带 `$comment` 列出 8 项 MUST-reject 规则，`memory-object` 没有这种严谨度

**后果**：一个 schema 驱动的实现者会**随机选一个**，而两者互不兼容。

## 选项

| 选项 | 做法 | 后果 |
|---|---|---|
| **D1（推荐）** | `memory-unit` 为权威；`memory-object` 标 `deprecated` 并注明"仅存储层复合视图，不得作为对外契约" | 一处标记即可解除歧义；保留存储视图的合法用途 |
| D2 | 删除 `memory-object` | 需先确认没有存储路径依赖它 |
| D3 | 两者共存并声明"看场景" | 最坏：歧义保留，且实现者仍需自行判断 |

## 推荐：D1

`01` 号 L3 已经写明"MemoryObject 保留为**存储层复合视图**，对外与 Pipeline 使用 **MemoryUnit**"。所以 D1 不是新决策，只是**把已有意图写进契约标记**。

# E-5 · 备份保留期

## 问题

备份保留多久？删除后多久必须不可恢复？

## 实证

| 检查 | 结果 |
|---|---|
| 全库 `retention_policy` 受控词表 | **未定义**（`01` L427 只说"受控词表"，词表本身不存在） |
| `storage.schema.json` 有 retention 键？ | **没有**（keys: `authority, sqlite, lancedb, fts5, outbox, worker`） |
| `security.schema.json` 的 `retention_days` | 存在，但属 **`audit`** 对象（默认 365，范围 30–3650）——**审计日志保留，不是备份保留** |
| 文档中的备份保留 | `04` L51/L241 只说"备份保留策略"是**待定项**，无数值 |

**365 天这个数字极易被误读为备份保留期，实际上它是审计日志。** 这个混淆本身就是一个陷阱。

## 为什么我不给数字

编造一个保留期等于**虚构清除政策**——而清除政策牵涉到"已删数据必须不可恢复"的承诺。这个承诺一旦写错，是合规事故，不是工程瑕疵。

## 选项（需你定，我不推荐具体天数）

| 选项 | 取向 | 代价 |
|---|---|---|
| R-1 | **短**（如 7–30 天） | 存储省；但误删恢复窗口短，且备份恢复后可能已无历史 |
| R-2 | **中**（如 90 天） | 平衡；仍是承诺，需写入 `storage.schema.json` |
| R-3 | **长**（如 1 年） | 恢复力强；但"已删数据仍可恢复"与删除承诺冲突 |
| R-4 | **不设上限，按删除墓碑强制清除** | 与 `SM-7` 删除传播一致，但需要"备份中也清除"的实现，成本最高 |

## 必须一并决定的三件事

1. **备份保留期天数**（必须写进 `storage.schema.json`，现在没有这个键）。
2. **删除与备份的冲突规则**：恢复旧备份会复活已删记忆（`OI-R-12`，已实测复现）。要么备份里也执行墓碑，要么规定"恢复后必须重放墓碑/撤销集"。
3. **审计保留（365 天）是否需要与备份保留对齐**——目前它们是两个独立数字，容易被当成一个。

# E-6 · 向量通道：scan-only 还是 indexed

## 问题

LanceDB 的检索路径该用全量扫描（精确但慢），还是用 ANN 索引（快但近似）？

## 实证

| 事实 | 数值 / 来源 |
|---|---|
| 设计要求 | `02` L252："LanceDB **FLAT** 八项验证（P0 门禁）"；L257：FLAT 必须与暴力全量 Top-K **完全一致** |
| 设计否决 | `02` L68："Cross-Encoder / **ANN** / 图检索 | **REJECTED（当前范围）**" |
| 设计的硬门 | `02` L20："若 FLAT 无法证明为精确检索 ⇒ 向量检索验收 **BLOCKED**" |
| 实测：索引选项 | `createIndex()` **忽略** `indexType` 与 `distanceType`，三种请求全部返回 `IvfPq`/`L2`（我独立复现） |
| 实测：ANN 召回 | recall@10 = **0.30**，且 `nprobes` 1→32 **无变化**（参数失效） |
| 实测：扫描路径精确性 | 小/中规模固定数据集上成立 |
| 实测：cosine 越界 | 自匹配距离 **−1.19e-7**（负值），3/1000 低于 0 |

## 关键洞察

**设计文档其实已经答了这个问题：ANN 在当前范围是 REJECTED。** 但契约里同时存在 `ann_enabled` 与 `search_mode` 两个配置键（默认值均为空），且注册表把 `storage.lancedb.search_mode` 映射为 `vector.index_mode` 并注明"索引模式（flat）"。

所以**不是设计未决，而是设计已决、契约未同步**——这是 E-6 与 E-2/E-3 不同的地方。

## 选项

| 选项 | 做法 | 后果 |
|---|---|---|
| **F1（推荐）** | 明确 **scan-only**：移除/禁用 `ann_enabled`，`search_mode` 固定 `flat`，并在契约里写明"索引路径不得启用" | 与 `02` L68 的 REJECTED 一致；精确性成立；代价是 O(N·d) 全扫 |
| F2 | 启用 indexed，附**实测召回门禁** | 但实测召回 0.30，任何合理门槛都过不了；且 `createIndex` 参数失效，无法调优 |
| F3 | 超过某规模阈值才建索引 | 技术上合理，但需要先修复 SDK 缺陷并证明该阈值的召回可接受——目前做不到 |

## 推荐：F1

不是因为扫描更好，而是因为**当前 SDK 的索引路径既不可精确、也不可调优**：`indexType`/`distanceType` 被忽略、`nprobes` 失效、召回 0.30。在这个状态下启用索引等于主动降低检索质量。

## 遗留风险（F1 也要承担）

- 全扫是 **O(N·d)**，10 万条 1024 维向量每次查询约 1 亿次浮点运算。必须实测延迟是否落在 `retrieval.timeout_ms = 3000` 以内——**这个数我没有测**，属于未验证项。
- `createIndex` 缺陷应在未来 SDK 版本重测；若届时参数生效，F2 可重新评估。
- 索引路径的 tie-breaking 是**插入顺序**，不可复现——即使将来启用索引，排序稳定性也必须由下游 RRF 自己保证。

# 六项决策的相互依赖

```
E-1（哪套文档权威）
  └─> E-4（A 内部哪个对象模型权威）
        └─> E-3（content_kind 存废，取决于选定对象模型）
  └─> E-2（tier 规则，取决于哪套文档的 tier 语义）
E-6（向量策略）— 独立，但受 02 已决 REJECTED 约束
E-5（保留期）— 独立，纯运营决策
```

**最低解锁路径**：先定 **E-1**，其次 **E-4 + E-3**（一次改完，因为都落在同一批 schema），再定 **E-2**。E-5 与 E-6 可并行。

## 哪些可以现在就定

| 决策 | 是否阻塞开工 |
|---|---|
| E-1 | **是** —— 权威不明，后续全部无依据 |
| E-2 | **是** —— 过期/提升无法实现 |
| E-3 | **是** —— 决定对象是否有第八个必填字段 |
| E-4 | **是** —— schema 驱动实现会随机选一个 |
| E-5 | 否（但必须在接真实数据前定） |
| E-6 | 否（`02` 已决 scan-only，只需同步契约） |
