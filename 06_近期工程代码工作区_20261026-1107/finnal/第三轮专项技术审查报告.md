### 3.4 新问题：`getContent` 缺失时的静默退化

`store.ts:2677–2681`：

```ts
private getContent(hash: string): string | null {
    const row = this.db.prepare("SELECT bytes FROM content WHERE hash = ?").get(hash) ...
    if (!row) return null;      ← 只返回 null，不抛、不记日志
    return Buffer.from(row.bytes).toString("utf8");
}
```

调用侧 `store.ts:3013`：`content: this.hydrateMedia(this.getContent(...) ?? "")`。
`store.ts:3154`：`summary: this.getContent(summary_hash) ?? ""`。

**后果**：若 CAS 行被 `releaseContent` 的 delete-on-zero 清掉（`store.ts:790–808`，注释写明 `#3987/#4242` 曾在真实语料留下 11.32 GB 孤儿），而 `messages` 行仍在（FK 若未强制或历史遗留），读取得到 **空字符串**，没有任何异常信号。

**对桥接的直接威胁**：`sha256("")` 会产生一个合法、稳定、可入库的 `content_hash`，对应一条 **`original_text` 为空的 Evidence**。13 号 §7.2 要求 `original_text` 必填且为原句，这构成事实上的空证据污染，且不会报错。

**P0 必须加的自检**：桥接侧对每条候选原句做 `sha256(original_text)` 回算，与 `messages.content_hash` 比对；不一致或为空 ⇒ 拒绝写入并告警（对齐 13 §7.4.2 第 4 条 "`integrity_error`"）。

### 3.5 新问题：`ts` 不是"发生时刻"

`store.ts:1038`：

```ts
.run(..., typeof m.ts === "number" ? m.ts : batchTs);
```

`batchTs = Date.now()`（`store.ts:1031`，注释："one wall-clock sample per save batch — rows without a per-message first-sight stamp all carry the same second"）。

`MessageRow.ts` 注释（`store.ts`）自称：

> Ingest input: taken from the message's first-sight stamp when present, **else the per-batch sampled now**.

**结论**：`messages.ts` 有两种来源语义 —— "首见戳" 或 "**保存时刻**"。后者与消息真实发生时间可能相差任意时长（debounce 500ms 起，长可到下次触发保存）。

**对 Evidence 的约束**：13 号 §7.2 字段纪律第 2 条明确：

> `timestamp` 未知 **MUST** 为 null，**MUST NOT** 填推测时间。

因此**不得**把 `messages.ts` 直接写入 `Evidence.timestamp`。必须能区分"首见戳"与"批采样"，否则只能写 `null`。而库里**没有标记列**区分二者 ⇒ **当前无法区分**（未证实项 U-A）。

### 3.6 `retired_at` 的真实语义（推翻第二轮用法）

DDL：`retired_at INTEGER`（`schema.ts:151`）。
CHANGELOG:98 原文：

> 权威集清扫改墓碑(D4-2)：proxy 会话每轮全量保存不再物理 DELETE 缺席行，改为 `retired_at` 墓碑 —— rewind/undo 的历史在统一存储里**耐久保留**；同一身份回来时**原地复活**（保原 seq，含 complete

复活路径 `store.ts:925`：`UPDATE messages SET retired_at = NULL WHERE session_id = ? AND seq = ?`。
`getMessages` 默认过滤：`store.ts:2992` `AND retired_at IS NULL`。

**结论**：`retired_at` = **"该消息不在客户端本轮权威集里"**，语义是**视图缺席**，不是**数据删除**。它不是删除墓碑，且可被撤销。
⇒ 第二轮结论 #6「`retiredAt` 可可靠驱动 Evidence 撤销」**已证伪**。

### 4.3 `supersedes_block_id` 是死列（第二轮假设被推翻）

唯一写入路径 `ingest.ts:425`：

```ts
supersedesBlockId: null,        ← 硬编码
```

全仓检索结果：该列只在 `export.ts:292` 读取、`mysql.ts` / `store.ts` 的 upsert/restore 中原样透传，**没有任何生产者写入非 null 值**。

**结论**：`supersedes_block_id` 对新数据恒为 NULL。
⇒ 第二轮「refold 通过 `supersedes_block_id` 建立替代关系」**已证伪**。Refold 产生的是一个**与旧块无关联的新块**，只能靠 `payload_json` 的 id 集合重叠来推断关系。

### 4.4 `payload_json` 是否足以恢复 `directMessageIds`？

**足以。** 三方证据：

1. 写入：`ingest.ts:429` `payloadJson: JSON.stringify(b)`，`b` 是 `session.state.blocks` 中的**逐字 `CompressionBlock`**（`ingest.ts:402`）。
2. 读取：`store.ts:3141` 直选 `payload_json`，`BlockRow.payloadJson` 注释："Verbatim serialized CompressionBlock (includes summary)"。
3. **生产代码自己就这么用**：`store.ts:1103–1104`
   ```ts
   const cov = JSON.parse(b.payloadJson) as { effectiveMessageIds?: string[]; directMessageIds?: string[] };
   for (const id of [...(cov.effectiveMessageIds ?? []), ...(cov.directMessageIds ?? [])]) wanted.add(id);
   ```

**但有一个静默失败点**：同一段代码 `store.ts:1105` 是 `catch { /* malformed payload: no covered ids to resolve */ }` —— `payload_json` 解析失败时**静默当作无覆盖**，不报错。桥接若依赖它，必须自己抛错而非吞掉。

### 4.5 `start_seq` / `end_seq` 可能是 `-1`

`ingest.ts:407–414`：

```ts
let startSeq = -1; let endSeq = -1;
for (const id of b.effectiveMessageIds) {
    const s = seqById.get(id);
    if (s === undefined) continue;      ← 该 id 无行则跳过
    ...
}
```

`seqById` 只含**本 plan 的 log**（`ingest.ts:399–400`）。若覆盖 id 在本轮 log 中不存在（导入前折叠、被裁剪），则 `start/end` 保留 `-1` 哨兵。

`store.ts:1092–1095` 注释亦确认：`-1` 是 "no claim" 哨兵，且 upsert 的 `CASE` 在 `excluded.start_seq >= 0` 时才覆盖，否则保留旧值。

**结论**：`start_seq`/`end_seq` **不是**可靠的覆盖区间证据。按 `start_seq` 排序的对账策略在 `-1` 行上无定义序。⇒ 第二轮「按 `start_seq` 升序处理」**部分证伪**。

### 5.4 群私聊混用风险

- `convKey` 已带 `kind` 前缀（`group:` / `private:`）⇒ **键空间不撞**（事实，`bridge.js:1220`）。
- 但 `state.sessions` 是**单层映射**：`retireSession(key)` 后重建会产生**新 sessionId**，旧 session 的 blocks 留在旧 `session_id` 下，**不迁移**。
- ⇒ 桥接若以 `session_id` 为幂等键的一部分，同一群在 retire 前后会被视为**两个不同来源**，同一段历史不会被重复桥接（可接受），但**历史证据会分散在多个 session 命名空间**下，`related_evidence` 反查需跨 session 聚合。
- **私聊与群聊隔离**：`convKey` 区分充分，`04 §7.5-7`（群聊/私人记忆不得互串）在**键层面**可满足；但是否满足还需 `scope` 正确派生，见 §6.5。

## 6. 幂等身份分析

### 6.1 Block Identity

| 项 | 结论 | 依据 |
|---|---|---|
| 唯一性范围 | `(session_id, block_id)` | `schema.ts:173` PK |
| 重建行为 | refold 产生**新 blockId**，旧行可能被物理删除 | `ingest.ts:402`、`store.ts:1081` |
| 替代关系 | **无**（`supersedes_block_id` 恒 null） | `ingest.ts:425` |
| 编号复用 | `sessions.next_block_id` 单调；但 rebase/fork 后子会话可能从 1 起 | `schema.ts:121`、`cloneSessionRows` |

⇒ `block_id` **不可单独**作为跨时间身份。

### 6.2 Evidence Identity

同一原始消息可能被：父块 direct、子块 direct、refold 新块覆盖。三种情形下 `msg_id` 相同、`block_id` 不同。

**推荐判定**：Evidence 的身份应锚定在**消息**，不是块。

### 6.3 Source Locator

| 组成 | 稳定性 | 风险 |
|---|---|---|
| `session_id` | 稳定 | retire 后变 ⇒ 旧 locator 指向旧命名空间（可接受，历史不变） |
| `seq` | 稳定（复活保原 seq） | ✅ 最可靠 |
| `msg_id` | ⚠️ 可重铸 | 单独用会断 |
| `ledgerSeq` | ⚠️ 与 `seq` 是否恒等**未验证** | `types.ts` 注释称 `ref = store row seq + 1`，但 `seq` 受 `pluginSnapshot`/`decompositionLog` 前置插入影响（`ingest.ts:208–212`） |

⇒ 推荐 `source_locator = "<session_id>:<seq>"`，并把 `msg_id` 作为**辅助**（可空、可漂移）。

### 6.4 Content Hash

| 问题 | 分析 | 结论 |
|---|---|---|
| 是否含消息身份 | **含**（`JSON.stringify(m)` 内含 `m.id`） | 是 |
| 是否含顺序 | **不含**（顺序在 `seq`，不在 blob 内） | 否 |
| 同一句被重复发送 | 两个 `msg_id` ⇒ 两个不同 blob ⇒ **两个不同 hash** | **不会误合并** |
| 同一消息被不同块覆盖 | 同一行 ⇒ 同一 hash | 天然去重 |
| Block 重建但原句不变 | 消息行不变 ⇒ hash 不变 | ✅ 稳定 |
| 消息 id 重铸 | blob 内 id 变 ⇒ hash 变 | ⚠️ 会误判为新证据 |
| Fork 后重新摄取 | 新 `session_id`、新 seq；blob 可能相同（若 id 继承） | ⚠️ 跨会话去重需 `session_id` 参与 |

### 6.5 八种场景的幂等处置

| 场景 | 会否重复桥接 | 会否漏 | 处置 |
|---|---|---|---|
| 同一句话用户重复发送 | 否（hash 不同） | 否 | 无需特殊处理 |
| 同一消息被不同块覆盖 | 是（父子都含） | 否 | **按消息级去重**，非按块 |
| Block 重建但原句不变 | 是（新 blockId） | 否 | 幂等键**不含 block_id** |
| Block 编号复用但内容变 | 否（hash 变） | 否 | 含 `content_hash` 可区分 |
| Fork / Rebase 后重新摄取 | 是（新 session_id） | 否 | 需显式白名单；默认不桥 fork 子 |
| 消息被撤销（retired） | 否 | **可能误撤销** | **不得**据此撤销 Evidence |
| 原文 Blob 缺失 | — | **是（静默空串）** | 写前回算 hash 校验 |
| 哈希存在但原文不可恢复 | — | 是 | 同上，拒写并告警 |

### 6.6 推荐定义（含未冻结标记）

| 对象 | 推荐定义 | 状态 |
|---|---|---|
| **Block Identity** | `(session_id, block_id)` 仅用于**库内定位**，**不作**幂等键 | 可冻结（结构事实） |
| **Evidence Identity** | `(session_id, seq)` —— 消息级，不含 block | **待裁决**（需 U-D 验证 seq 在复活/重排下唯一） |
| **Source Locator** | `"<session_id>:<seq>"`，`msg_id` 作辅助可空字段 | 可冻结（结构事实） |
| **对账幂等键** | `sha256(session_id ‖ seq ‖ content_hash)` | **待裁决**（`content_hash` 含 id，id 重铸会换键 ⇒ 需 U-E 量化重铸频率） |

**第二轮 bridge_key 作废**：原式 `sha256(session_id ‖ block_id ‖ covered_hash)` 两个分量都不稳（`block_id` 会换、`covered_hash` 依赖 id）。**已证伪**。

## 7. 第二轮结论复核表

| # | 第二轮结论 | 复核判定 | 依据与理由 |
|---|---|---|---|
| 1 | index.db 适合作为 Evidence 派生数据源 | **部分证实** | 结构与内容足够（§3.1、§4.4）。但：`blocks` 行会被物理删除（`store.ts:1081`）、`content` 有 delete-on-zero（`store.ts:806`）、加密模式无库（`persist.ts:566`）、`ts` 语义不可信（§3.5）。**"适合"需限定为"在块存活期内适合"** |
| 2 | 只读 SQLite 连接可安全并发 | **部分证实** | WAL + `busy_timeout=5000`（`schema.ts` `storagePragmas`）；且官方明确"多进程写一个 index.db 是受支持拓扑（#5082/#5091）"，`StorageSecondWriterError` 已 `@deprecated` 且"不再有任何路径抛出"（`store.ts:394–405`）。**但**：存在 `<db>.lock` 与 `foreignLockHolder`（`store.ts:425–426`）、有 split-brain 检测；**无任何运行时验证** ⇒ 只读并发仍属未证实 U-F |
| 3 | `directMessageIds` 足以消除嵌套重复 | **已证实（静态）** | `payload_json` 逐字含直系数组（§4.4）；`decompress.ts:212` 用 `nestedCovered` 专门排除子块。**唯一保留**：需确认两条消息不会同属两个块的 direct（理论互斥，未实测） |
| 4 | `bridge_key` 可实现稳定幂等 | **已证伪** | `covered_hash = sha256(JSON.stringify({effectiveMessageIds, directMessageIds}))`（`ingest.ts:406/428`）依赖 id；id 可重铸（`#4390`）。`block_id` 亦随 refold 变。见 §6.6 |
| 5 | `active=1` 足以筛选待桥接 Block | **部分证实（偏向不足）** | `active` 由 payload 带入（`ingest.ts:426`），`deactivateBlock` 会置 0 但**行仍保留**（`decompress.ts:73`）。若按 `active=1` 过滤，会**漏掉"曾折叠后停用"的块**——这些块覆盖的消息此刻并未被折叠，但历史上被折叠过。正确判据是"**该块是否已桥接**"，不是 `active` |
| 6 | `retiredAt` 可可靠驱动 Evidence 撤销 | **已证伪** | `retired_at` 是**视图缺席**墓碑，可被 `UPDATE ... = NULL` 原地复活（`store.ts:925`），CHANGELOG:98 明写"耐久保留/原地复活"。用它撤销会**误撤后又需恢复**，且它从未表达"删除" |
| 7 | `BILI_ENCRYPTION_KEY` 生效时能可靠关闭桥接 | **部分证实** | 条件可检测：`unifiedBlockedByEncryption = storageMode !== "legacy" && key !== null`（`persist.ts:566`），并打 warn（`:568`），此时**整个 sidecar 不打开、无 index.db**。但"可靠关闭"依赖桥接侧自检（env + 库不存在 + 日志三重判据），当前**无实现、无验证** |

**统计**：已证实 1 / 部分证实 4 / 已证伪 2 / 未证实 0（另有 4 项独立未证实散布于 §3、§5）。

## 12. 最终可行性结论

### 12.1 数据源可用性（本轮核心问题）

**结论：可用，但可用性是有条件、有时限、有静默陷阱的。**

| 能力 | 判定 | 限定条件 |
|---|---|---|
| 恢复完整原始 `CoreMessage` | ✅ **可** | `content` CAS 行未被 delete-on-zero 清除 |
| 不依赖摘要恢复原句 | ✅ **可** | 摘要与原句分属两条独立引用 |
| 恢复覆盖关系 | ✅ **可** | 仅经 `payload_json`；解析失败需自抛错 |
| 恢复折叠区间 | ⚠️ **部分** | `start/end_seq` 可为 `-1` |
| 恢复发生时间 | ❌ **不可靠** | 需能区分首见戳与批采样（当前不能） |
| 恢复群/租户身份 | ❌ **不可** | 内核无此概念，宿主仅一半可得 |
