# R4.1 审计工作环境与命令执行约束

本提示词适用于 R4.1 项目的全部审计工作，包括 A 包 Event-L3 和 B 包 Memory Core。

## 一、核心要求

在审计、阅读、分析和交付文件的过程中：

**尽可能避免使用 PowerShell。优先使用原生文件工具、编辑器和 Python 完成工作。**

原因：PowerShell 在中文编码、引号转义、特殊字符、路径解析、多行文本、管道和文件写入方面容易出现意外问题，可能导致文件内容损坏、编码变化或审计结果失真。

不得为了方便而使用复杂 PowerShell 命令替代可靠的文件操作方式。

## 二、工具使用优先级

按照以下顺序选择工具：

1. Claude 自身提供的文件读取、文件搜索和文件编辑工具。
2. VS Code 或其他可靠文本编辑器。
3. Python 标准库进行文件读取、哈希计算、目录遍历和必要的文本处理。
4. 其他能够明确保证编码和文件完整性的工具。
5. PowerShell，仅在以上方式无法完成任务时使用。

## 三、PowerShell 使用限制

尽量避免以下操作：

- 使用 PowerShell 的 `Set-Content`、`Add-Content`、`Out-File` 直接写入重要设计文件。
- 使用复杂的 `Get-Content` 管道进行多文件批量处理。
- 使用多层引号、反引号和变量展开构造复杂命令。
- 通过 PowerShell 批量替换 Markdown 内容。
- 通过 PowerShell 拼接包含大量中文的多行文本。
- 使用不明确的默认编码读写文件。
- 使用未经核验的路径拼接或通配符批量操作。
- 将命令输出直接重定向覆盖原文件。

如确实必须使用 PowerShell：

1. 先说明为什么其他方式无法完成。
2. 明确指定文件路径和编码。
3. 不直接覆盖原始输入文件。
4. 先对副本操作。
5. 操作后检查文件内容、编码和 SHA256。
6. 发现异常立即停止，不继续批量操作。

## 四、文件读取与编码要求

1. 读取 Markdown、TXT、JSON、CSV 等文件时，明确识别编码。
2. 优先保留原始 UTF-8 或 UTF-8 BOM 格式，不得无故转换。
3. 不得因为终端显示乱码就认定文件本身乱码。
4. 遇到中文乱码，应通过编辑器或 Python 重新核验原始字节。
5. 不得擅自删除 BOM、修改换行符或统一格式。
6. 对关键输入文件，操作前后记录 SHA256。
7. 读取文件时不得因终端输出长度限制而误认为文件已经完整读取。

## 五、文件修改与保护

当前审计阶段以只读审查为原则。

- 不修改原始输入。
- 不覆盖历史报告。
- 不修改正式裁决台账。
- 不修改设计文件、源码、配置和运行数据。
- 如阶段任务明确要求交付新报告，只创建指定的新文件。
- 修改已有进度文件必须符合当前阶段原定授权。
- 所有输出文件与输入文件分离保存。

禁止使用可能造成大范围影响的批量替换、递归删除、目录清理或自动格式化操作。

## 六、命令执行与结果核验

每次执行命令前，先判断是否真的有必要。

如果只是阅读、搜索、比较、统计或计算哈希，优先使用文件工具或 Python。

如果命令执行失败：

- 不要连续尝试不同的复杂 PowerShell 写法。
- 不要通过强制转换编码来掩盖问题。
- 不要假设失败命令没有产生任何副作用。
- 先检查目标文件和目录状态。
- 确认安全后再选择替代方式。

任何命令输出都不能直接代替对实际文件的核验。

## 七、审计纪律

本提示词不改变各审计线的任务范围、阶段编号、问题编号和交付要求。

不因为工具使用限制而：

- 跳过文件核验。
- 省略证据引用。
- 缩减审计范围。
- 编造无法取得的结果。
- 声称未执行的测试已经通过。

无法安全完成的操作，应如实记录为未完成，并说明原因。

## 八、最终要求

本项目优先保证：

**文件完整性 > 操作便利性；审计可追溯性 > 执行速度；真实证据 > 命令执行数量。**

尽量不使用 PowerShell。能用文件工具完成的，不调用终端；能用 Python 安全完成的，不使用复杂 Shell 命令。

完成当前阶段任务后，检查所有交付文件确实存在、内容完整、编码正常，并确认原始输入没有被修改。
