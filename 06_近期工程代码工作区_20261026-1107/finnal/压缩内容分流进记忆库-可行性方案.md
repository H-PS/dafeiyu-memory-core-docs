## 0. 一句话结论

**可行，而且不需要改它的压缩算法。** 分流点已经存在于宿主提交区（`src/stream.ts:1309–1321`）——那一处循环同时握着**原文消息数组**和**新建 block 的覆盖集合**。你要的能力是在那里加一个"旁路投递"，而不是在 `compress.ts` 里插节点。

但有一条**不可妥协的约束**：分流必须发生在**压缩提交之前**，且必须携带 `CoreMessage[]` 原文。只拿 `summary` 去建记忆库，会直接违反 13 号文件"Evidence 必须保留原句、可反向追溯"的硬性要求——摘要已经丢失原句，反查会全部失效。

## 1. 已核实的事实基础（全部来自源码，非 README）

### 1.1 内核与宿主的职责切分

`kernel/src/content-store.ts` 文件头原文：

> 纯数据 + 纯函数，**零 I/O**（"the core holds no state and performs no I/O"）。宿主用自己的机制持久化这个结构。

**推论**：内核只做计算，不认识任何存储后端。**记忆库必须挂在宿主层（`src/`），不是内核层（`kernel/src/`）。** 这是本方案能成立的结构前提。

### 1.2 压缩提交的完整时序（`src/stream.ts`）

| 行号 | 动作 |
|---|---|
| 1147 | `ranges = supersededRes.translatedRanges` — ref 归一化 |
| 1154–1160 | scope gate（`compress.requireRecommendation`） |
| 1173–1181 | stub 重投拒绝 |
| **1183–1188** | **`ctx.core.applyCompression({ranges, messages, state, config})`** ← 摘要与原文在此同时在手 |
| 1204–1226 | coverage 单调性回闸 |
| 1265–1285 | no-net-shrink 回闸 |
| **1287** | **`ctx.session.state = res.state`** ← 提交点 |
| **1309–1321** | **遍历 `res.state.blocks` 新 block，`collectBlockContent` 取原文 → `cacheBlockContent`** |
| 1329–1333 | `storeCoveredOriginals(...)` → CCR 内容存储（仅 `ccrEnabled` 时） |

**结论**：1309–1321 是唯一同时具备「原文 `CoreMessage[]` + 新 block 覆盖 id 集 + 已通过全部闸门」的位置。

### 1.3 可直接复用的三个现成件

| 现成件 | 位置 | 对本方案的价值 |
|---|---|---|
| `storeCoveredOriginals(store, messages, state, blockIds, countTokens)` | `kernel/src/ccr.ts:606` | **它已经在做"取被折叠消息的原文"**。内部 `covered` 集合 = `block.effectiveMessageIds`，遍历 `messages` 取 `stripLeadingTag(m.text)`，并跳过 `contentType === "reasoning"`。这就是分流器的取数逻辑，**可以直接照抄语义** |
| `collectBlockContent(state, block, messages, {full})` | `kernel/src/decompress.ts:176` | 提供两个视图：`full=true` 取全部原句，`full=false` 只取直接消息（嵌套子块保留摘要）。对应你的 `read_mode` 四值 |
| `ApplyCompressionInput.protectedMessageIds?: Set<string>` | `kernel/src/compress.ts:150` | **内核本来就支持"某些消息不许压缩"**。可形成闭环：已入记忆库的消息加入此集合，避免重复折叠 |

### 1.4 CoreMessage 可提供的溯源字段

`kernel/src/types.ts` 的 `CoreMessage` 包含：`id` / `role` / `contentType` / `text` / `toolName` / `toolCallId` / `ledgerSeq` / `tsStamps`（在 state 上）/ `summaryOfBlockId`。

**对 R4.1 的意义**：`id` + `ledgerSeq` + 时间戳，足以构造你 `Evidence.origin {messageSeq, sender, at, channel}` 的前半段。**缺口是 `sender` 与 `channel`**——内核不认识"谁说的"和"哪个群"，这两项必须由宿主在传入前补齐。

## 2. 三种分流位置对比

| 方案 | 插入点 | 拿到什么 | 改动面 | 判定 |
|---|---|---|---|---|
| **A. 提交前旁路（推荐）** | `stream.ts:1309–1321` 循环内，`cacheBlockContent` 之后 | 原文 `messages` + `blockId` + `effectiveMessageIds` + `summary` + `topic` | `src/` 单点，约 60–150 行 | ✅ 语义完整，可回滚 |
| **B. 包装 applyCompression（否决）** | 覆写 `ctx.core.applyCompression` | 原文 + ranges + 全部闸门前的**未决**结果 | `src/`，需接管返回值 | ❌ 该调用会被 coverage/no-net-shrink 回闸拒绝，**会写入从未真正折叠的内容** |
| **C. 改内核（否决）** | `kernel/src/compress.ts` 插 pipeline 节点 | 最全 | 2500 行 + 130 回归测试 | ❌ 违反零 I/O 契约，上游更新冲突成本极高 |

**B 为何必须否决**：`applyCompression` 是纯函数，调用后还有 4 道闸门可能让它被拒绝（coverage regression、no-net-shrink、stub 重投、scope）。若在包装层就写入记忆库，会出现「记忆库有、上下文没折叠」的**账实不符**——这正好是你 `DESIGN-STATUS` 里严禁的状态。

## 3. 推荐方案 A 的详细设计

### 3.1 插入点（伪代码，仅为说明，未落盘）

```
// stream.ts，紧跟 L1320 的 cacheBlockContent 之后
for (const b of res.state.blocks) {
    if (beforeIds.has(b.blockId)) continue;

    // ...既有 cacheBlockContent 逻辑不变...

    // 【新增】旁路投递：仅在此处，原文与覆盖集同时在手
    void memoryBridge.offer({
        blockId:         b.blockId,
        summary:         b.summary,
        topic:           b.topic,
        effectiveIds:    b.effectiveMessageIds,
        originals:       collectBlockContent(res.state, b, contentSource, { full: true }),
        sessionKey:      ctx.session.key,        // ← 隔离键，见 3.3
        tenantId:        ctx.session.tenantId,
    });
}
```

### 3.2 投递内容的三段拆分（对应你的数据模型）

| 段 | 来源 | 灌入 R4.1 的哪个对象 |
|---|---|---|
| 原句 | `collectBlockContent(..., {full:true})` 逐条 `message.text` | **Evidence**（`evidence_refs` + `span`），这是 `related_evidence` 反向追溯的唯一来源 |
| 归属 | `block.effectiveMessageIds` ↔ `message.id/ledgerSeq` | **MemoryUnit.evidence_refs** 的绑定关系 |
| 语义摘要 | `b.summary` / `b.topic` | 只作 **M03 候选**的输入，**不得**直接成为 MemoryUnit 正文（它是模型生成的，等同 `ASSISTANT_INFERRED`） |

**这一步的关键判断**：摘要的 `source_type` 必须是 `ASSISTANT_INFERRED` 或 `SYSTEM_GENERATED`，绝不能标 `USER_EXPLICIT`。否则就是它自己在 `compression-rules.ts` 里记录的那次事故的重演（见 §5）。

### 3.3 隔离键是硬门槛

`ctx.session` 提供会话级键，但**你的 04 §7.5 第 8 条要求同一 bot 多个群不得因共享进程而共享上下文**。内核不知道"群"的概念，`session` 粒度可能等于或粗于群粒度。

**MUST**：投递前按 `(tenant_id, bot_id, group_id, session_id)` 复核。若宿主层拿不到 `group_id`，此方案**不得启用**——否则会把 A 群的历史写进 B 群的记忆库，这是不可接受的权限越界。

### 3.4 与 `protectedMessageIds` 的闭环（可选，强烈建议）

已成功落入记忆库并 `COMMITTED` 的消息 id，可回填到下一次 `applyCompression` 的 `protectedMessageIds`，使其**不再被折叠**。好处：

- 避免同一段内容被折叠两次（一次进记忆库、一次进摘要）
- 上下文里始终保留原始句，符合你"不把过去的全部聊天塞进上下文"的初衷——记忆库负责长期，上下文负责当前

**但必须验证**：`protectedMessageIds` 在 `unit-projection.ts:264` 是按 **ref（mNNNNN）** 消费的，不是 raw id。回填前需做 id → ref 转换。

## 4. 可行性分级与风险

| 维度 | 评估 |
|---|---|
| 技术可行性 | **高**。插入点存在、取数函数现成、不改内核契约 |
| 改动量 | **小**。`src/` 单函数，60–150 行 + 宿主侧桥接 |
| 回滚成本 | **低**。加开关（环境变量/配置项），关闭即恢复原行为 |
| 上游更新冲突 | **中**。`stream.ts` 是活跃文件（1500+ 行，含 20+ issue 引用），每次升级需人工合并 |
| 许可证 | **需署名**。LICENSE 为 MIT + 附加条款：产品面向终端用户可见时，须在首页/文档/About 之一标注使用 billion-context 并附链接。QQ 机器人属"用户可见"，**必须署名** |
| 稳定性 | **注意**。4083 star / **832 open issues**，迭代快 |
| 性能 | **需实测**。投递必须异步且不得阻塞压缩提交路径，否则压缩延迟会叠加记忆写入延迟 |

### 已知风险清单

1. **重复投递**：同一 blockId 可能因 refold 再次出现。`storeCoveredOriginals` 用 first-write-wins，你的桥接层必须同样做幂等（建议以 `(session_id, block_id)` 为幂等键）。
2. **generation boundary**：宿主 rebase 会把 ref 重置为 m00001，内容存储随之重置。记忆库的幂等键**不能**用 ref，必须用 raw id 或 content hash。
3. **reasoning 内容不可投递**：`storeCoveredOriginals` 明确跳过 `contentType === "reasoning"`。你的桥接应保持同样纪律，thinking 不进入记忆库。
4. **空视图折叠**：`#3982` 记录过 EMPTY-view fold 从统一存储恢复源的情况，此时 `ctx.messages` 为空，须回退到 `ctx.compressMessages`。这行代码 `stream.ts:1309` 已经处理（`contentSource` 三元），照抄即可。
