# R4.1 审计报告精简与证据保留规范

适用于 A 包、B 包及后续所有审计阶段。

## 一、篇幅要求

1. 每份正式审计报告不超过 1000 行。
2. 建议控制在 300～600 行。
3. 禁止为了缩短篇幅删除关键技术判断、证据、问题依据和限制条件。
4. 优先删除重复解释、冗长背景、重复引用和无实际价值的过程叙述。
5. 多个相似问题可以合并描述，但必须保留各自的问题编号和独立影响。
6. 不得通过省略关键内容、使用含糊概括或大量引用外部文件来满足行数限制。

## 二、必须保留的信息

每份报告必须保留：

### 1. 审查基本信息
- 审查对象及版本。
- 审查范围。
- 使用的材料及其路径。
- 审查日期。
- 审查限制和未执行事项。

### 2. 关键证据
每项重要结论必须能够追溯到证据。

尽可能记录：
- 文件名。
- 章节、标题或行号。
- 关键原文摘录（只保留必要部分）。
- 对应的哈希或版本信息（适用时）。
- 证据能够证明什么。
- 证据不能证明什么。

不得只写「已核查」「符合要求」「存在问题」，却不给出依据。

### 3. 技术判断
必须区分：

- 〔事实〕材料明确记载或实际核实的内容。
- 〔推导〕基于现有事实得到的技术判断。
- 〔设计缺口〕当前设计未定义或未闭合的内容。
- 〔依赖实现〕需要通过代码或运行测试才能确认的内容。
- 〔无法核实〕缺少材料或证据，当前无法判断的内容。

### 4. 问题登记
每项问题至少包含：

- 问题编号。
- 严重程度。
- 问题描述。
- 证据依据。
- 技术影响。
- 对 V1 的影响分类：
  - V1 必须
  - V1 可以简化
  - V1 预留
  - Future
- 建议处理方向。
- 是否需要用户裁决。

### 5. 未解决事项
保留：
- 材料缺口。
- 尚未验证的假设。
- 存在争议的结论。
- 对后续阶段的依赖。
- 需要用户决定的问题。

不得将未解决事项伪装成已完成。

## 三、证据表达方式

优先采用精简证据格式：

| 项目 | 内容 |
|---|---|
| 结论 | 具体判断 |
| 依据 | 文件及章节/行号 |
| 证据 | 必要原文或核查结果 |
| 限制 | 当前证据不能证明的内容 |
| 影响 | 对 V1 或 Future 的影响 |

复杂问题可以展开说明，不要求所有问题机械使用表格。

对于关键结论，必须保留足够的原始证据，使其他审查人员能够复核。

## 四、禁止的精简方式

不得：

1. 删除问题编号。
2. 删除关键原文或证据定位。
3. 将多个不同问题合并到无法区分的描述中。
4. 删除重要的反例、边界条件和失败情况。
5. 将推测改写成事实。
6. 将静态检查改写成运行验证。
7. 将建议改写成正式裁决。
8. 只保留结论而删除推导依据。
9. 用「详见其他报告」代替当前报告必须具备的核心证据。
10. 为压缩行数而删除 Future 方向及其技术依据。

## 五、附属材料管理

允许将不影响独立复核的详细材料放入独立附件，例如：

- 完整候选方案对比表。
- 大型字段清单。
- 重复性核查记录。
- 完整命令输出。
- 辅助计算过程。

但正式报告必须保留：
- 附件名称。
- 附件用途。
- 对应问题编号。
- 关键结论摘要。

如果附件不是正式交付的一部分，不能将其作为唯一证据来源。

## 六、提交前检查

生成报告前，检查：

- [ ] 不超过 1000 行。
- [ ] 审查范围没有遗漏。
- [ ] 所有重要结论都有证据定位。
- [ ] 事实、推导和建议已区分。
- [ ] 问题编号完整且没有冲突。
- [ ] 材料缺口和无法核实事项均已保留。
- [ ] V1 与 Future 分类完整。
- [ ] 未将未经验证的内容标记为已验证。
- [ ] 报告可以脱离执行过程独立阅读和复核。

**最终原则：压缩文字，不压缩证据；压缩重复，不压缩判断；报告从简，但必须能够独立审计和复核。**
