## 一、参数 ID 规范（草案 · 11 属性）

**命名格式**：`<模块>.<命名空间>.<参数名>`，全小写下划线，示例如 `m02.fusion.rrf_k`。

| 属性 | 要求 |
|---|---|
| 1 参数 ID | 唯一、稳定、可追踪（改名不改身份——优化-5） |
| 2 参数名称 | 人类可理解 |
| 3 所属模块 | 唯一归属或明确共享关系 |
| 4 默认值 | 有明确依据（实测/论文缺省/工程经验——标注来源类型） |
| 5 合法范围 | 明确边界与类型 |
| 6 当前值 | 可读取可展示 |
| 7 生效状态 | 区分配置值与实际生效值（版本化原子生效后） |
| 8 影响范围 | 明确影响哪些模块/流程 |
| 9 修改权限 | 明确谁可改（安全硬约束不可由模型/普通配置修改） |
| 10 修改副作用 | 是否需迁移/重建/重启 |
| 11 验证方法 | 可观察的验证指标 |

**三层次**：可观察（查看参数与运行状态）→ 可配置（受控接口修改，M04 §13 校验-版本-原子生效-失败回退）→ 可验证（调整前后效果比较）。三者不必同时开放但设计必须预留。

## 三、Token 计量（优化-1 已裁：归 R3 核心）

必须区分五类消耗：**系统提示词 / 聊天历史 / 记忆检索注入 / 实际注入内容 / 模块调用（Gateway 侧计量）**。V1 最低要求：

- 每轮记录：注入条数、注入 token、检索耗时、命中渠道分布。
- 日聚合：Retain 批次数、提取 token、整合调用 token。
- 注入 token 中位数与 p95 进健康指标（与预算联动）。
- **持久化落点缺口（红队 RT-15 → N-16）**：五类计量+日聚合在 m01 D4 权威表清单中无 metrics 表——V1 表设计须补计量持久化落点，否则计量数据随进程丢失（14 §六 N-16 待裁）。

## 四、日志与健康监控

**统一日志字段**（m04 §14.1）：request_id/task_id/turn_id/module/stage/policy_version/view_version/duration_ms/status/error_code。

**分级审计**（m04 §14.2）：普通 Recall 精简元数据；权限拒绝、删除、纠正、异常记详细审计事件；不默认保存完整正文/凭据（m05 §14 同向；日志不得成为已删内容旁路——m01 D39）。

**健康三态**：normal/degraded/abnormal（M01 D28 + M04 §14.3 合并枚举）。缓存库异常不降级整体健康（只降命中率）；权限/删除不确定是 P0 阻断而非降级。监控不阻塞主流程。

**可追踪检索过程**（宗旨要求）：每轮 Recall 保留结构化选择依据（相关性/时间/来源/关系/版本）于 Core 内部——调试/审计/明确请求时展开，默认不向 DSH 暴露（m04 §十）。

## 五、可观察性验收标准（V1）

| # | 标准 |
|---:|---|
| 1 | 全部 V1 核心参数可经统一接口读取（ID/默认/当前/生效状态/范围） |
| 2 | 配置变更产生新版本记录（操作者/时间/原因），失败自动回退 |
| 3 | 每轮注入的 token/条数/渠道分布可查询 |
| 4 | 检索失败/降级/权限拒绝可从日志还原现场（request_id 串联） |
| 5 | 影子模式 diff 日志只含 metadata（W-2 已裁），读取需判权 |
| 6 | 删除/撤销/恢复操作留审计事件链 |
| 7 | 任何"参数调了但看不出效果"的情况视为可观察性缺陷 |

## 六、检索评测 harness〔Agent E 缺口 1 的新增提案，待裁〕
