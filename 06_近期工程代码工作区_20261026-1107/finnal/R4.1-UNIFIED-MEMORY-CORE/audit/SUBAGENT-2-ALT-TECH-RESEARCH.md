## 1. 存储与索引

### 1.1 规模估算〔成立〕
- 5 万条 × 约 200 字 ≈ 30MB 正文；768 维 float32：5 万×768×4B ≈ 154MB；单库约 200–300MB。〔估算〕
- 精确 KNN = 3840 万次乘加。热态量级：1 千条 2–5ms、1 万条 10–20ms、5 万条 20–60ms；冷启动 3–5 倍。〔估算，须实测〕
- 关键：LanceDB FLAT 与 sqlite-vec/应用层余弦**数学等价**（都是精确最近邻），5 万条上没有谁"更准"；LanceDB 的收益不在检索质量，而在索引隔离与未来 ANN。〔成立〕

### 1.2 四维权衡

| 维度 | 单文件 SQLite（BLOB 或 sqlite-vec） | 现状 SQLite+LanceDB+Outbox |
|---|---|---|
| 部署 | 1 进程 1 文件；扩展约 100KB，Windows 需 asarUnpack（若随 DSH 打包） | 第二引擎/目录；Node SDK 迭代快且出现过平台裁剪〔外部：发布说明，需核实版本〕 |
| 一致性 | 记忆/向量/FTS 同事务，**Outbox 可整体不启用** | 跨库最终一致：Outbox+幂等+防覆盖+重建+DLQ+两套健康降级 |
| 检索质量 | 精确 KNN（同 LanceDB FLAT） | 同左；将来可 IVF/HNSW |
| 备份恢复 | 一文件一备份一恢复 | 两份产物、两套版本、重建验证 |
| 模型迁移 | 新表/新列回填（5 万条 3–10 分钟离线）+rename | 新索引空间验证后切换更自然 ← **唯一实质优势** |

### 1.3 建议〔保留单库，LanceDB 降为适配器预留〕
- 建议 V1 单文件 `memory.sqlite`；向量二选一，统一藏在 Index Adapter 后：a) sqlite-vec（SQL 层 KNN、分区/元数据过滤、默认暴力、新版已有可选 ANN/量化〔外部：项目仓库，需锁版本〕）；b) 应用层余弦（向量存 BLOB，先按 scope/subject/时间 SQL 预过滤再算，零原生资产，最易拔除）〔工程经验〕。
- Outbox 表可留结构，V1 不作关键路径（单库可同事务同步 FTS）。
- **最大实现风险（原设计未钉死）**：m01 D21 只说"可替换分词器"。FTS5 默认 unicode61 会把整句中文切成一个 token，"科技"搜不到"华中科技大学"；必须显式 `tokenize='trigram'`（SQLite 3.34+，CJK 子串可用；索引膨胀、查询词 <3 字不命中）〔外部：SQLite 文档/工程实践〕。
- 迁回双库触发（任一）：向量 >20 万；暴力检索 p95 >150–200ms 且量化/预过滤后仍不达标；需 ANN；需多模型并行或在线换模型且不能停写回填；需多进程/远程向量服务；单库备份 >2GB 或 >1 分钟。

## 2. 检索融合

### 2.1 "四渠道 RRF"是误读风险〔成立〕
- m02 D3 把四类并列交给 RRF。但结构化（时间/类型/状态）本质是布尔约束，做成名次后"按时间排第 50 的那条"会拿非零分、可能压过语义第 1——布尔命中不该有"第 50 名"。
- 关系扩展按 m02 D5 本就是"直接命中不足时按需 L1/L2"，属融合**之后**的扩展，不是并列榜单。
- 建议：结构化→SQL 硬过滤；向量+BM25→RRF；关系→扩展后一次性加分（有上限）。把"量纲不可比"缩到两个真列表。

### 2.2 RRF 与归一化求和〔有条件成立〕
- "min-max 后求和"的失败是结构性的：BM25 常有稀有词独占的高分长尾，min-max 把第 2 名压到≈0，退化为单列表独裁；余弦分布窄（0.31–0.36）时 min-max 又把噪声拉满。RRF 用名次绕开分布形状，这才是它"简单可靠"的真实来源，不是参数巧合。〔工程推理〕
- k 敏感度：k=60 是 2009 年论文的缺省值，不是扫参结论；2023 TOIS 的分析直接报告"RRF 对参数敏感"，与"k 附近不敏感"的通行说法相反〔外部：Bruch/Gai/Ingber, TOIS 42(1), 2023〕。→ 保留 60 作为**无数据时的中性缺省**合理；但不能引论文当结论，V1 别调它，只把原始名次落盘以便离线重放。
- 两个被忽略的隐含偏差：① **列表深度即权重**：Σ₁..₂₀₀ 1/(60+i)≈1.47 vs 10 条列表≈0.15，深列表系统性占优 → 融合前必须**等深截断**（各取 50）；② **一致性偏好**：两列表各第 40 名（2/100=0.020）>单列表第 1 名（1/61=0.016），头部精度被稀释 → 若要"向量优先"用 wᵢ/(k+rank)，默认 w=1，靠评测集"单列 rank1"样本再定。
- **学习型融合：V1 不引入**〔成立〕。无标注对、单用户日查询量撑不起训练、二路可调空间小；收益个位数指标，成本是模型+训练+版本三套设施。触发：≥2k 标注查询-结果对+评测 harness 稳定+RRF 进入平台期。

### 2.3 必须补的缺口
RRF 只给相对分，撑不起 m02 D21 的高/中/低置信度。建议融合外加**绝对门槛**（cosine<τ_v 或 BM25<τ_b 不入上下文，τ 离线标定），否则"最好的坏候选"会被当成高置信。〔建议〕

## 3. 记忆提取

### 3.1 现状代价〔估算〕
每批一次 LLM（内容+5 个 0–5 分+claim_type）。300 条/天、批 20 → 15 批 × ≈3k tokens ≈ 45k tokens/天，未计 M04 逐候选整合。

### 3.2 三层闸门〔有条件成立〕
- L0 规则丢弃（≈0 token）：寒暄、问句、单词回复、纯表情、与既有记忆近重复（hash 或向量>0.95 且无新增实体）。
- L1 规则成候选：显式指令（"记住/我上次说/别再"）、稳定自述谓词（"我是/我住/我养/我讨厌"）、纠正标记（"不对/其实是/我说错了"）、含日期数字的计划、被反复提及的实体。
- L2 灰区（约 10–25% 批次）→ 经 M04 Gateway 只要"内容+claim_type+一句理由"；五维规则补全：R=类型先验+是否被要求记住；P=类型半衰期先验；E=claim_type+独立来源数+显式标记；T=是否含时间指代；U=与既有记忆相似度（高相似=低 U）。总分公式与 3.5/2.0 分流**完全不变**。
- 兼容性：m03 §10 已写"模型提供建议、Core 重算总分、Core 定 routing"，§15-5 冻结的是"五维评估"而非"模型打五维分"，故**兼容**；但 §10 措辞会让实现者仍做全量打分，建议补一句"模型可只提供内容与 claim_type，缺失维度由规则补全"（措辞补充，不改决策）。
- 诚实边界：**"覆盖 80%"是假设**。可检验定义应为"L0+L1 跳过 LLM 的批次占比 ≥80%，且 200 批标注漏检率 ≤10%"，参照物是"全量 LLM 提取"而非真值。

## 4. 生命周期与时间

### 4.1 字段≠机制〔有条件成立〕
- 四时间字段近乎零成本（5 万行×4 列），**不建议删**；昂贵的是"版本表+版本解析+依赖重算+视图重建"。
- 建议最小状态机：`status ∈ {current, superseded, deleted}`，`expired` 由 `effective_to < now` **派生**；纠正在一个事务内：旧行置 superseded/effective_to/superseded_by+插新行+追加 `memory_history` 快照；读路径永远读 head、不回放版本。
- 纯两态不够：`expired`（计划完成/状态结束）与 `superseded`（信念被替代）召回语义不同——历史查询允许返回 expired，却不该把 superseded 当"当时也没发生"。最小是 **3 态+1 派生**〔成立〕。
- 收益/代价：状态机与读路径明显更省，保留可审计历史；代价是放弃"任意时点全量重建"，只能快照近似——单用户 V1 几乎用不到。〔建议〕

### 4.2 两个时间风险〔成立〕
1. `valid_from` 由 LLM 推断=伪造精度，与"不乱说"冲突。建议默认 `effective_from = 消息 event_time`，仅用户显式给时间时覆盖，并加 `time_precision ∈ {exact, day, month, year, unknown}`。
2. m03 输入是"批次级单一 event_time"，20 条跨 2 小时的消息被压成同一时刻；建议保留逐条消息时间，记忆取首条或区间。

## 5. 心理层

### 5.1 判定〔成立〕
X-1 已定 delta-only、无排序权 → 今天对结果影响是 0。而 PSYCH-PIPELINE 第 5 步（衰减/干扰/情绪一致/扩散/侧抑制/去重/容量）与 m02 检索职责**重叠**，同时启用会出现双重衰减、双重去重、两个排序权威（违反"边界清晰"）。成本：`focus()` 1k 条 47ms、5 万条 984ms（文档自测）〔外部：项目内部实测〕，进请求路径比整个检索还贵。

### 5.2 最简路线〔简化〕
- 砍：候选生成、排序权重、容量/抑制/隧道硬闸门、自我安抚槽位、顶点记账对检索的影响。
- 留：PAD+E/L 状态机（µs 级/事件）、≤50 字 hint、温度系数（"人格 300 : 此刻 50"是文档自己的原则）、呈现层 fidelity（full/gist/trace/faded）——按"年龄+类型半衰期"O(1) 算，不需要七步链。
- 影子必须**离线**：delta-only 若在请求内计算仍要付 47–984ms；只落日志、离线重放比较。

### 5.3 代价
- 失去情绪一致召回 → 叙述情感连贯下降，"不乱说"不受损。
- 失去容量/抑制 → 注入条数变固定，用 top-k+token 上限兜（m02 D7 已有）。
- 失去"记忆强度"动态 → 简化衰减已覆盖主要收益。
- **最大代价是没有 A/B 基线**，事后无法证明心理层"提升智能"；离线影子日志必须留，成本近零、保住未来证据。

## 6. 反方视角

### 6.1 过度设计 Top 3

**1) cache.sqlite**〔砍掉 V1〕：单库召回 20–100ms 量级，缓存省几十毫秒；代价是第三个一致性域、备份排除、健康例外、两条验收项、失效出错会把已删记忆候选带回。V1 简化：进程内 LRU（键=归一化查询+scope+data_version，TTL 60s，容量 200），不落盘。恢复触发：p95>300ms 或 Embedding 受限使候选生成昂贵，且命中率>30%。

**2) 视图版本化+原子发布+任务 DAG/检查点**〔简化〕：单写者、短事务、≤5 万行时"当前视图"是读取时投影；原子发布解决的是"构建跨多事务、耗时数分钟"，此处不存在。V1 简化：单调 data_version+单事务读+乐观版本校验。恢复触发：多进程共享/单次视图构建>2s/需跨请求长快照。

**3) 参数面过大**〔简化〕：单用户日查询几十次无法标定十余参数。V1 简化：**只冻 4 个数**（top-k=8、注入 token≤600、每路候选 50、k=60），其余写死常量并标"未标定"；唯一门槛指标=是否召回正确。恢复触发：≥200 条标注查询+可重放日志后，一次只解冻一个。

### 6.2 设计不足 Top 3

**1) 度量与验收缺失**：无标注集、无 Recall@k/MRR 定义、无无记忆基线、无 token 指标——"四渠道值不值、心理层值不值、五维权重对不对"全部无法裁决。建议：100–200 条 query→期望 memory_id 标注集；固定脚本输出 Recall@5、MRR、错误召回率、注入 token 中位数、p95 延迟；渠道消融作准入证据。

**2) 删除-撤销-备份的反复活闭环不闭合**：m01 D8 要求恢复时"以最新有效删除状态为准"，但恢复对象就是承载删除状态的同一库——从 7 天前备份恢复，删除记录也回到 7 天前；备份周期/保留数量仍开放；已删内容可长期存活于备份与 evidence 原文。建议：①独立追加式墓碑账本（单独备份不回滚，恢复时重放）；②evidence 定保留期与"要求忘记"物理清理路径；③明确"备份窗口内被删内容随窗口过期消失"。

**3) 写入侧预算与第三方断言污染**：a) 活跃群 500–1000 条/天 → 25–50 个提取批次，无日预算、无背压、无积压降级。b) m03 的 claim_type 描述证据性质而非"谁对谁断言"——群成员说"A 其实很有钱"会以 explicit 进 group 记忆，之后在 A 在场时注入，M05 只有 scope 没有第三人陈述规则，是"不乱说"的正面漏洞。建议：a) 日 token 预算+优先级+积压时增大批/降频；b) 加 `assertion_source ∈ {self, other, bot_inferred}`，硬规则：关于在场第三人的 other 断言不入 fact 层（只能 uncertain 或带"据 X 说"），并对同一 (author→subject) 重复矛盾断言节流。
