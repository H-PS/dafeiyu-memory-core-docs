# 03-DATA-FLOW-AND-LIFECYCLE · 完整运行闭环与记忆生命周期

> 依据：m02 §三（检索时序）、m03 §2（批次）、m04 §四/§九（整合与生命周期）、m01 D7/D8（删除与恢复）、v4.6 候选（两阶段事件）、A/B 审查修订（B-060 补检索后权威校验、S5 系列落点）。
> 本文件定义**从用户消息到记忆产生、存储、检索、使用、修正、淘汰的完整闭环**，含全部异常路径。

---

## 一、正常主流程（Recall 读路径 + Retain 写路径分离）

```
【读路径 Recall —— 同步，先于回复生成】
用户 QQ 消息
  → ① Bridge 接收：解析可信身份（user_id/chat_type/chat_id/group_id/request_id）
  → ② **M02 触发判定**（D2 唯一权威；Bridge 仅收集并转发消息信号，不做判定——红队 RT-08 修正）：
       提及过去经历/人物/偏好/计划？模糊指代？话题延续？需历史信息才可答？
       否 → 跳过自动检索（普通闲聊不强制检索）
       是 → ③ Bridge 将检索请求（含可信身份，DSH 不得自定身份）交 M02
  → ④ M05 权限检查（检索范围先判权）
  → ⑤ M02 检索调度：向量+FTS 两路召回（N-1 提案·待裁；裁决前 m02 D3 四渠道为基线）＋结构化硬过滤＋关系扩展（M04 一跳，M02 持预算，默认 L0）
  → ⑥ RRF 融合 + 规则排序（三因子：相关性/时间/置信分层——五因子待字段裁决）+ 去重
  → ⑦ 【修订 B-060】检索后权威校验：回 SQLite 查最新生命周期状态 + M05 逐条判权
  → ⑧ 四预算裁剪（候选数/最终条数/Token/扩展深度）→ Memory Context（纯数据）
  → ⑨ Bridge 注入 DSH（人设+记忆+当前消息）
  → ⑩ DSH 理解意图；上下文不足时主动 memory_search（经 Bridge 转交=新请求边界，重新判权）
  → ⑪ DSH 生成回复 → Bridge 发送 QQ
       〔红队 RT-18 注：下述⑫⑬与⑨的组装同点产生——列表序号仅为呈现顺序，非时序先后〕
  → ⑫ 【候选·Event-L3】第一阶段观察记录 prompt/assembled（组装完成后产生，E-1/E-2 扩展未落地）
  → ⑬ 【候选·Event-L3】Bridge 核验检查 I/II/III → 整体有效性 passed 且版本 complete
       → 第二阶段有效 L3 确认记录（仅覆盖明确列出的 complete 版本）
       【F-CK-1~10 未核查前此链路不可用；整体 not_executable/failed → 无确认记录】

【写路径 Retain —— 异步，不阻塞回复】
本轮聊天内容
  → 异步提交 Retain（失败不阻塞正常聊天）
  → M03 批次提取（同会话/同主体/兼容权限；不加载全史）
       LLM 经 M04 Gateway 产候选（claim_type: explicit/inferred/uncertain，留 source_refs）
  → M03 五维初评（R/P/E/T/U 加权 0.25/0.20/0.25/0.15/0.15）+ 硬性约束校验
  → 三档分流：review(≥3.5)→M04 / observe(2.0~3.4)暂存 / reject(<2.0)
  → M04 终审：与旧记忆比较（duplicate/complement/temporal_evolution/contradiction/topic_related）
       → 新建 / 合并 / 修订（用户纠正优先，旧版标 superseded）/ 冲突进 uncertain
       → Observation 更新（可追溯 Fact/Event/Evidence）→ 依赖重算
  → M05 判权（写入 scope/owner 校验，B-065 补设计）
  → M01 事务写入（版本递增+Outbox 事件+Change Log 同事务）
  → 索引同步（后台幂等任务：LanceDB/FTS5；删除优先；失败重试）
  → cache.sqlite 对应条目失效（M02 判定失效，M01 执行清理）
```

**核心不变量**：Recall 与 Retain 分离——当前对话内容不因进入上下文就自动成为正式记忆；检索结果不直接修改正式记忆（只能形成反馈候选交 M03/M04）。

## 二、记忆对象生命周期（四维状态，m04 §九）

| 维度 | 状态 | 判定方 |
|---|---|---|
| 审核状态 | candidate / pending / approved | M03 分流 → M04 终审 |
| 有效状态 | active / expired / superseded | M04 判断（时间四字段：recorded_at/valid_from/valid_to/superseded_at） |
| 存储状态 | normal / archived / deleted | M01 持久化执行 |
| 权限状态 | authorized / revoked | M05 判定 |

**版本链**：用户纠正 → 保留原始记录 + 旧版标 superseded/corrected + 创建新版本 + 记录纠正来源 → 受影响 Observation 依赖重算（证据不足→uncertain；内容变化→重生成）。旧任务不得覆盖新版本（乐观并发）。

**删除流程**（五方分工）：M04 判断入删除生命周期 → M05 判权 → M01 事务标记 Deleted+版本递增 → Recall 立即屏蔽 → 后台清理 LanceDB/FTS/缓存/派生 → 检查关联 Observation/Relation/Cue Anchor → 清理失败继续重试、不恢复访问。已删除内容不得经索引重建、缓存恢复、历史版本或备份复活（M01 D8）。

## 四、请求内判权复用与失效（M05 §10.4 统一口径）

- 同一 request_id 内，相同 `(actor, memory_id, action, scope)` 且 `policy_version`/`permission_version` 未变、对象无删除/状态变化 → 可复用判定结果。
- 必须重判 8 类：新对象首次进入 / 新增关系扩展对象 / 新 request_id / 权限版本变化 / 共享撤销失效 / 删除或状态变化 / 新 actor/action/scope / 其他任何使授权依据失效的事件（成员资格过期、群解散、所有者变更、上游不可信）。
- 跨请求一律不复用；缓存命中不等于授权（数据缓存≠授权缓存）。

## 五、Session 级上下文复用规则

- 同话题连续对话：已注入**内容**可复用（不重复检索注入）；信息不足再检索。
- 记忆更新/删除/撤销共享后：旧注入内容不得继续作为有效依据。
- 新会话不继承临时检索结果；主动检索每次调用=新请求边界（M02 D16）。
