## 一分钟结论

**能。** 在现有 A/P/S 架构上可以完成"可靠记忆基础 + 智能召回 + 上下文管理 + 记忆形成 + 基础整理"，不推翻架构、不引入新服务、不新增依赖。

规模：**新增 14 个文件 ≈4,470 行，改动 3 个既有文件（+790/-75）**，单人排期 **16 周**。

唯一真瓶颈（不变）：`buildWakePromptV2`（`bridge.js:10669`）单点注入、无预算、每轮重发静态块，20 轮会话产生约 47,500 token 纯重复。

本轮修订新增的 5 个 P0 结论：

1. **权限与来源必须分离**（四字段），一个 `visibility` 枚举表达不了"从哪来 / 谁能读 / 审没审"。
2. **候选池必须按失败原因物理分离**，否则敏感内容会被"说过三次"洗白。
3. **未经审核的归纳不得进入上下文**（`proposed` 不进召回），降权+标注不够。
4. **索引写异步、删同步**，因为滞后在两个方向上的危害不对称。
5. **安全规则不能写在 prompt 里**，只能写在代码里；`agentToken` 必须移出 prompt。

## 必须先接受的六个判断

不同意任何一条，后面设计要重做。

### 1. 权限 = 来源 + 读取范围 + 内容分级 + 审核状态（四个字段）

`visibility: group_shared` + `share_review_status` 两个字段混表三件事，正是 S-11（群聊记忆恒不可检索）的根因。拆成 `origin.groupId` / `scope.read` / `scope.contentClass` / `review.status`，判定收敛到一个 `canRead()`。

### 2. 群聊记忆必须"分级可见"，不是"要么全可见要么全不可见"

- 群内自产 + 内容 public → 同群立即可召回（修 S-11）
- 内容敏感/判不准 → 降为 `owner_only`，**同群也召回不到**（比原设计更严）
- 跨群 → 无任何自动路径

### 3. 归纳只能"新增"，且未审核的归纳不进上下文

`proposed` 默认完全不进召回与注入。降权 + 标注"（我的印象）"不够——一旦进上下文，模型就分不清"我知道"和"我猜的"。

### 4. 索引写异步、删同步

写滞后 → "刚存的暂时搜不到"，可接受，有 `coveredRev` 尾部扫描兜底。
删滞后 → "删掉的还能搜到"，不可接受。
**危害不对称，所以策略不对称。**

### 5. 安全不靠提示词

越权拦截、key 隔离、内容分级必须在代码层（`canRead`）。prompt 里只放提醒，且不放在一次性注入里——它会被压缩掉。

### 6. 先做减法，再做加法

M1-b（上下文清理）排在 M1-a（召回）之前。否则"加了召回但上下文更脏"互相抵消，且无法归因。
