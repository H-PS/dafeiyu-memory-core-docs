#### 1.1.1 K1 的完整用例集（12 个，不只是"5 个崩溃点"）

上一版只列 5 个崩溃点，未覆盖"恢复过程本身崩"与"重复恢复"。本版补齐：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 崩溃点 1（embed 中） | 无半条记录，A 层条数不变 |
| 2 | 崩溃点 2（WAL pending 写后） | 重放后与正常执行等价 |
| 3 | 崩溃点 3（A 已写、索引未删） | 重放：A 跳过、索引删除生效 |
| 4 | 崩溃点 4（committed 未写） | 重放 effects（全为目标态）→ 补 committed |
| 5 | 崩溃点 5（committed 后、异步项前） | 只补异步项（索引追加/向量补算） |
| 6 | **恢复过程中再次崩溃**（第 3 步后） | 第二次恢复仍等价（幂等） |
| 7 | **同一 pending 重复恢复 3 次** | 结果与恢复 1 次相同（无重复累加） |
| 8 | **pending 与 committed 同时存在同一 opId** | 以 committed 为准，pending 忽略 |
| 9 | **WAL 文件被截断（半行 JSON）** | 该行判为无效，其余正常恢复；记审计 |
| 10 | **WAL 与 A 层不一致（A 有记录、WAL 无）** | 以外来篡改处理：保留 A 记录、补审计、不删除 |
| 11 | **恢复期间收到新写入请求** | 恢复完成前拒绝写入（503 + `retryAfter`），不排队 |
| 12 | **两个进程同时尝试恢复** | `bridge.lock` 保证只有一个；第二个启动失败并给出明确错误 |

判据：12 个场景恢复后均满足"A/P/索引三者对同一 id 的状态一致"。

#### 1.1.2 K3 的权限验证维度（五维，缺一不可）

上一版只验证 `key`。实际越权可能发生在任何一维：

| 维度 | 验证内容 | 用例 |
|---|---|---|
| ① key | `record.key === ctx.key` | 私聊/群 交叉 20 条 |
| ② visibility/scope | `scope.read` + `originGroupId` + `contentClass` | 群 A↔群 B、敏感降级 |
| ③ 来源 | `origin.groupId` 与当前群一致 | 伪造 `scope` 但 `origin` 不同的记录 |
| ④ 生命周期 | `proposed/quarantined/superseded/deleted` 全部不可读 | 逐状态构造 |
| ⑤ 调用者 | `caller ∈ {agent, admin, reflect}` 各自权限不同（agent 不得读 proposed；admin 可读全部） | 同一记录三种 caller 调用 |

**判据**：`eval-privacy` 对五维各跑 ≥8 条用例，违规数必须 = 0。

#### 1.2.1 K11 的三级超时（统一口径）

上一版只写"单通道 300ms"与"合计 200ms"，互相矛盾且缺总控。本版明确：

| 层级 | 阈值 | 超时行为 |
|---|---|---|
| 单通道 | 300ms | 放弃该通道，记 `degraded` |
| 单次 recall 总超时 | 450ms | 立即返回已完成通道的结果 + `degraded:['total_timeout']`，不再等待 |
| 注入路径总预算 | 500ms | 若 recall 未在 500ms 内返回，本轮**跳过召回注入**（不阻塞回复），记审计 |

**指标口径**：
- P95 目标 ≤ 250ms，P99 目标 ≤ 400ms，**均指"单次 recall 从入口到返回"**，不含 embed 冷启动（首次调用单独统计）。
- 报告必须同时给 P50/P95/P99 与样本量，单次测量不算。

#### 1.3.1 K15 的队列策略（修订：不丢最旧）

上一版"队列满时丢弃最旧任务"。问题：被丢的可能是"主人刚说的偏好"这种高价值项，而丢它的原因可能是"群里灌了 200 条闲聊"。

修订为**优先级队列 + 分级背压**：

| 优先级 | 来源 | 队列上限 | 满时行为 |
|---|---|---|---|
| P0 | 模型主动 `qq_memory_append` | 不限（但限流 10/s） | 拒绝并返回 `ok:false`（让模型知道没记住） |
| P1 | Retain 信号强度 ≥0.8（自我披露/承诺） | 200 | 拒绝新任务 + 告警（说明系统过载） |
| P2 | Retain 信号 <0.8 | 500 | 丢弃**本批中最旧的低优先级项**（不是全局最旧） |
| P3 | 候选再评估 / 索引补算 | 1000 | 直接丢弃（可再生） |

原则：**可再生的任务可以丢，不可再生的（原始消息里的事实）不丢。**

### 2.2 D-27 敏感内容隔离后的通知方式

隔离区里的内容主人可能永远不知道。三个选项：

| 选项 | 行为 | 代价 |
|---|---|---|
| A（默认） | 静默入队，管理端可查，不主动提醒 | 主人可能长期不看，隔离区堆积 |

## 5. 结论

### 5.1 是否解决所有 P0 问题

**是（设计层面）。** 逐项对应：

| P0 | 解法 | 落点 |
|---|---|---|
| 群聊权限模型 | 三字段分离（origin/scope/review）+ 内容分级 + `canRead` 单一入口 + 只降不升 | SCHEMA §1/§9、01 §3、02 S-11 |
| Retain 候选池 | 三池物理分离 + 取消自动晋升 + 重复只触发重评估 + embedding 失败可补算 | 06 §4 |
| Reflect | 取消单链聚类（三档 + 一次一对）+ `proposed` 不注入 + 独立证据门槛 + `verifyObservation` + 偏好极性/反向/矛盾 + 统一 `assertion` | 07 §3~§7 |
| 数据一致性 | 写异步/删同步 + `coveredRev` 尾部补偿 + per-key 互斥锁 + fencing token + 统一提交协议 | 01 §4/§5、SCHEMA §7 |
| 上下文安全 | 凭据带外绑定（分两阶段）+ 安全规则移出 prompt + Ledger 能力边界写明 + `rotationTx` 原子恢复 | 05 §2.3/§3/§4/§5.3 |

### 5.2 是否仍存在跨文档矛盾

**没有了已知矛盾，但有三处"依赖未核实事实"的设计点**（见 §6），它们不是矛盾，是待验证。

一致性检查的逐项结论见 `CROSS-DOC-CONSISTENCY.md`：共检查 22 个交叉引用点，全部对齐；3 处历史遗留表述已修正（`auto_shared`、`channelAgreement`、`500 token 预算口径`）。

## 6. 实施前必须重新核查的源码事实

这些不是"设计假设"，是"设计依赖但尚未核实的实现细节"。核查前，相关模块不得排期。

| # | 待核查事实 | 为什么重要 | 若结论不同的影响 | 核查方式 |
|---|---|---|---|---|
| **F-1** | MCP 进程由谁启动、是否一进程一会话、能否注入 per-session 环境变量 | 决定 S-13 目标态走方案①（env）还是②/③（握手/文件） | 影响 `mcp-snowluma-safe.js` 改动量（+120 行 vs +300 行）与 M1 排期 | 查 DSH 的 MCP 启动配置、`.mcp.json` / preset 里的 transport 声明、进程树 |
| **F-2** | `retireSession(key)` 的完整副作用（是否清 S 层字段、是否影响 `agentToken`、是否拒绝在途请求） | 决定 `rotationTx` 的第 5 步是否安全 | 若它会清 token，则轮转后工具调用全 403，轮转方案需重做 | 读 `retireSession` 实现 + 实测轮转一次 |
| **F-3** | DSH 侧是否存在会话历史压缩/截断，压缩比多少 | 决定 Block Ledger 的锚点间隔（12 轮是否够） | 若压缩激进，锚点要降到 8 轮，token 收益下降约 5% | 长会话实测：向同一会话投递 40 次，观察早期消息是否仍可引用 |
| **F-4** | 模型 API 是否返回 `usage.prompt_tokens` | 决定 token 能否实测（影响 #11 的判据强度） | 若不返回，只能用估算，验收降级为"估算下降 ≥45%" | 查一次真实调用的响应体 |

这四项**已写入本轮交付的 `OPEN-DECISIONS.md`**，作为 M0 开工前的 first-action checklist。
