## 1. 五个必须回答的问题

### 1.1 是否解决所有 P0 问题？

**是，设计层面全部解决。** 但其中 1 项（P0-5 的凭据目标态）**只解决了设计，未解决可行性验证**——它依赖 F-1 核查结论。

| P0 | 解法 | 是否闭环 | 残留 |
|---|---|---|---|
| 群聊权限模型 | 四字段分离 + 内容分级 + `canRead` 单入口 + 只降不升 | ✅ 闭环 | D-24-e 阈值待定（参数，非机制） |
| Retain 候选池 | 三池物理分离 + 取消自动晋升 + 重复只触发重评估 + 补算队列 | ✅ 闭环 | 0.92 阈值缺实测依据 |
| Reflect | 三档去重 + `proposed` 不注入 + 独立证据 + `verifyObservation` + 偏好四字段 + 统一 assertion | ✅ 闭环 | `verifyObservation` 可能过严（见 §2.2） |
| 数据一致性 | 写异步/删同步 + coveredRev 补偿 + per-key 锁 + fencing + 统一提交协议 | ✅ 闭环 | 锁实现需自建（无第三方依赖） |
| 上下文安全 | 凭据两阶段 + 安全分层 + Ledger 边界 + rotationTx | ⚠️ **设计闭环，目标态可行性待 F-1** | MCP 进程模型未核实 |

### 1.2 是否仍存在跨文档矛盾？

**没有。** `CROSS-DOC-CONSISTENCY.md` 逐项检查 24 个共享概念：22 处完全一致，2 处为**有意差异**（合并阈值方向相反、排期含缓冲），均已在对应文档写明理由。0 处矛盾，0 处悬空引用。

需要说明的是：上一版有 3 处真实矛盾（索引原子性、`channelAgreement` 重复加权、`auto_shared` 语义混淆），本轮全部消除，并在 `REVISION-LOG.md` 留下记录。

### 1.3 是否可以进入最终设计冻结审核？

**可以，但建议带 3 个前置条件**：

| # | 条件 | 理由 |
|---|---|---|
| 1 | D-22 / D-23 给出方向（哪怕只是"按建议"） | M0 的 edit 与 reset 两处无法定稿 |
| 2 | D-24-e 选一档 | M2 的隔离区规模取决于此，影响验收 #12 的用例设计 |

若这三条不满足，可以冻结**M0 + M1-b + M1-a**（不依赖它们），把 M2 与凭据目标态标为"待定"。

### 1.4 哪些事项仍需主人决策？

见 `OPEN-DECISIONS.md`。摘要：**6 项待决策**（D-22 / D-23 / D-24-e / D-24-f / D-24-g / D-27）+ **3 项建议待确认**（D-21 / D-25 / D-26）。

没有一项是"我不该问但硬要问"——都是产品取向或数据语义，不是技术选择。

## 2. 修订后仍然存在的弱点（诚实清单）

### 2.1 关键阈值缺实测依据

| 阈值 | 当前值 | 依据 | 风险 |
|---|---|---|---|
| Retain 新颖度 | 0.92 | 经验（bge-m3 同义句 0.88-0.96） | 可能过严导致漏记，或过松导致重复 |
| Reflect 完全重复 | 0.99 | 保守取值 | 可能几乎不触发，A1 形同虚设 |
| 观察独立证据 | ≥3 条且 ≥2 天 | 直觉 | 可能太严，观察长期无法生成 |
| 偏好最小出现 | 3 次 / 7 天 | 直觉 | 同上 |
| 注入预算 | 600 token | 占比倒推（约 12%） | 可能偏少，长记忆被截断 |
| 尾部扫描上限 | 500 条 | 估计（异步队列秒级追平） | 极端情况会误触发重建 |

**这不是缺陷，是"必须先跑再调"的诚实标注**。它们全部在配置里，且 `REVISION-LOG` 与 `11-ACCEPTANCE` 都要求用运行数据校准。但如果冻结审核时期望"每个数值都有依据"，那这一版达不到——没有人能在没有真实数据的情况下给出这些数。

### 2.2 `verifyObservation` 可能过严

当前规则：观察文本中每个内容 bigram、数字、专名都必须出现在 evidence 原文里。

后果：**规则版观察只能是模板句**（"X 多次提到「Y」相关（N 次，最近 Z）"）。任何自然的概括（"他在认真准备比赛"）都会被拒，因为"认真""准备"这些词不在证据里。

这是**有意的取舍**：宁可观察笨拙，也不要幻觉。但代价是归纳能力接近于零——它只是"统计+套模板"，不是"理解"。

如果冻结审核认为"这不叫归纳"，那需要放开到"允许 LLM 生成 + 事后抽样人工校验"，风险随之上升。**这是一个需要明确接受或拒绝的取舍，不应含糊过去。**

### 2.3 关键词通道无词典的天花板

bigram + ASCII 词 + 短整词，能满足专名与常见词，但对：
- 同义词（"板子" vs "开发板"）—— 靠语义通道兜
- 长实体（"[长实体示例]"）—— bigram 能覆盖，但区分度弱
- 错别字（用户常打错，如"啊丢no"=Arduino）—— **完全无能力**

错别字这一条本项目实际会遇到（用户打字常带同音错别字）。当前设计没有处理，只能靠语义向量。**这是已知缺口，未解决。**

### 2.4 `proposed` 不注入的副作用

归纳出来的观察在升级前完全不可见。若升级条件（≥5 证据、≥3 独立来源、跨 2 天、48h 无冲突）过严，可能几周都产生不了一条 active 观察。

结果：M2 的"观察归纳"能力在真实使用中可能长期处于"有产出但无效果"的状态。

**缓解**：管理端应提供"proposed 列表 + 一键批准"，让主人能手动推动。这一点在 07 §8 写了，但**没有对应的验收项**——是缺口。

### 2.5 排期仍是估算

16 周 / 56 人日，误差 ±30%。真正的风险不在总量，而在 **M0 第 2 周的"恢复演练"**：如果 WAL 语义在这一步被证明有根本问题，整个 M0 要返工，排期失效。

### 2.6 "0 新增依赖"的隐含成本

不引入第三方库意味着：per-key 互斥锁、BM25、分词、时间解析、JSON 原子写全部自写。总量约 4,470 行里，有约 800 行是"本可以用库解决"的基础设施。

好处是可控、可审计、无供应链风险；坏处是**这些代码的 bug 由我们承担**，尤其锁与原子写。

## 3. 与上一版相比的净变化

| 维度 | 上一版 | 本版 | 判断 |
|---|---|---|---|
| 权限模型字段 | 2（混用） | 4（分离） | 更清晰，多 2 个字段 |
| 生命周期状态 | 5 | 6（+quarantined） | 更细，但状态机复杂度上升 |
| 候选池 | 1 | 3（candidates/quarantine/pendingEmbed） | 更安全，多 2 个文件 |
| Reflect 删除能力 | 隐含可删 | 显式禁止 | 更安全 |
| 索引一致性 | 自相矛盾 | 非对称 + 补偿 | 可实现 |
| 并发控制 | "写前重读" | 锁 + fencing | 正确 |
| 凭据 | 每轮注入 | 两阶段带外 | 更安全，实现待核 |
| 文档数 | 13 | 18 | +SCHEMA +4 份评审件 |
| 代码量估计 | 3,000 行 | 4,470 行 | +49%（主要是权限、验证器、三池） |
| 概念数 | — | 减少 1 个状态值、合并 2 个 effect | 有减有增，净增 |

**结论**：本版更安全、更可实现，但也更重。增加的复杂度集中在"安全"与"可验证"两件事上，没有增加"架构扩张"。这是有意的取舍。

## 5. 一句话结论

> 这一版解决了上一版所有真实矛盾，把"归纳安全"从口号变成了可程序化校验的规则（`verifyObservation` + `proposed` 不注入 + Reflect 无删除权），把"权限"从一个枚举拆成了四个正交字段。
> 代价是更重、阈值更依赖实测、以及一条明确的诚实边界：**在不引入 LLM 归纳的前提下，"观察"只能是统计而非理解。**
> 这一条如果不可接受，需要在冻结前重新讨论 M2 的定位，而不是在实施中偷偷放开。
