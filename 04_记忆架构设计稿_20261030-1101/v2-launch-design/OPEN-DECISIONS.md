### D-22 · `subjectId` 是否可编辑（阻塞 M0）

| 项 | 内容 |
|---|---|
| 背景 | `memory-update` 路径（`bridge.js:6765-6831`）只改 B 层不碰 A 层；A 层的 `subjectId` 一旦落地，是否允许事后改？ |
| 选项 A（建议） | **不可编辑**。改归属 = 删旧建新 + tombstone。理由：`subjectId` 是归属键不是内容，改它等于"这条记忆换了主人"，语义上应留痕 |
| 选项 B | 可编辑，`metaRev++` + 索引重排。灵活，但引入"同一条记忆曾属于 A 后属于 B"的歧义，且禁止/允许的边界难测 |
| 不决策后果 | M0 的 edit 端点无法定稿（拒绝还是允许），M2 的 Reflect 归纳主体判定也无依据 |

### D-23 · `reset` 是否清 A 层（阻塞 M0）

| 项 | 内容 |
|---|---|
| 背景 | `reset`（`bridge.js:4624` 附近）当前整文件重写 S 层。语义上"重置会话"是否等于"清空该会话长期记忆"？ |
| 选项 A | 不清 A 层，只重置会话与 B 层 |
| 选项 B | 清 A 层（等同 clear） |
| 选项 C（建议） | 分两级：`reset`（不清）/ `reset --purge`（清，需二次确认 + 走 clear 的 `clearEpoch` 流程） |
| 不决策后果 | M0 reset 端点无法定稿；若默认按 A 实施而主人期望 B，会有"以为清了其实没清"的风险 |

### D-24-e · 敏感判定的严格程度（阻塞 M2）

| 档位 | 隔离范围 | 代价 |
|---|---|---|
| 宽 | 只挡凭证（手机号/证件/密码/银行卡） | 大量私事会群内可见 |
| **中（建议默认）** | + 住址、医疗、金额、第三人隐私 | 部分正常话题也会被隔离，需人工清理 |
| 严 | + 任何含代词（"他""那个"）、任何主观评价 | 隔离区会爆量，群聊记忆几乎不可用 |

**建议**：先按"中"上线，跑两周看 `quarantine` 增长率与误隔离率，再调。这个数值是**参数**（`retain.classify.strictness`），但第一次选哪档是产品决策。

### D-24-f / D-24-g · 跨群共享与私聊→群

| 项 | 当前实现 | 影响 |
|---|---|---|
| 跨群共享（D-24-f） | 不支持（`scope.copies` 字段预留但**无写入端点**） | 若需要，要新增端点 + 审核流 + 两个新验收项 |
| 私聊→群（D-24-g） | 不支持（`bridge.js:6892` 明确拒绝） | 若需要，风险等级从"中"升到"高"（私聊内容进群），需要额外的人工确认流程 |

**建议**：两者本轮都不做。理由：收益不明，风险确定。

### D-27 · 隔离区是否主动提醒

| 选项 | 行为 | 代价 |
|---|---|---|
| A（建议） | 静默入队，管理端红点 | 主人可能长期不看 |
| B | 每周汇总"有 N 条被隔离" | 需周报机制（+50 行） |
| C | 每条即时私聊提醒 | 打扰，且把敏感内容二次传播到私聊窗口 |

## B 类 · 实施前必须核查的源码事实

> 这四条**不是设计假设**，是"设计依赖但未验证"的实现细节。核查前，相关模块不排期。
> 每条的核查方式都写明了，不需要全仓扫描。

### F-1 · MCP 进程的启动方式与进程模型

| 项 | 内容 |
|---|---|
| 为什么重要 | 决定 S-13 目标态走哪条路。若 MCP 由 bridge 以子进程启动且一进程一会话 → 可用环境变量注入凭据（最简单）；若由 DSH 独立拉起或一进程多会话 → 必须走握手端点或本地 token 文件，改动量翻倍 |
| 影响 | `mcp-snowluma-safe.js` +120 行 vs +300 行；M1 排期 ±3 天 |
| 核查方式 | ① 看 DSH 的 MCP 配置（`.mcp.json` / preset 中的 transport 声明）② 看进程树（bridge 的子进程 vs 独立进程）③ 看是否有 per-session 的 env 注入点 |
| 未核前兜底 | 只做桥侧过渡态（token 每轮→首轮），MCP 侧不动 |

### F-2 · `retireSession(key)` 的完整副作用

| 项 | 内容 |
|---|---|
| 为什么重要 | `rotationTx` 第 5 步依赖它。若它会清 `agentToken`、清 S 层记忆字段、或拒绝在途请求，轮转方案要重做 |
| 具体要知道 | ① 是否清 `st.agentToken` ② 是否清 `recentMessages` / `unread` ③ 是否等待在途投递 ④ 失败时是否可重试 |
| 核查方式 | 读 `retireSession` 实现（`bridge.js` 内，与 `ensureSession` `:8461` 附近）+ 实测轮转一次（非生产环境） |
| 未核前兜底 | `rotationTx` 不做第 5 步（只做 digest 保存），轮转延后到 M1-b 后段 |

### F-3 · DSH 侧是否有会话历史压缩/截断，压缩比多少

| 项 | 内容 |
|---|---|
| 为什么重要 | 决定 Block Ledger 的锚点间隔。若压缩激进（如保留最近 20 条），12 轮锚点不足以维持人格；需降到 8 轮，token 收益下降约 5% |
| 核查方式 | 向同一会话连续投递 40 次，第 40 次时让模型引用第 1 次的内容，看是否还记得 |
| 未核前兜底 | 锚点按 12 轮实现（可配置），上线后用 `#11` 的第 40 轮测试判定是否需要降到 8 |

### F-4 · 模型 API 是否返回 `usage.prompt_tokens`

| 项 | 内容 |
|---|---|
| 为什么重要 | 决定 `#11` 的判据强度。有 usage → 实测；无 usage → 只能估算，验收降级为"估算下降 ≥45%" |
| 核查方式 | 抓一次真实调用的响应体（不落盘，看即可） |
| 未核前兜底 | 用 `estimateTokens` + `calibrationFactor`，报告中明确标注"估算" |
