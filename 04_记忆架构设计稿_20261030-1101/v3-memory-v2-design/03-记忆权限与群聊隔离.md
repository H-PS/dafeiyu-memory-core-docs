# 03 · 记忆权限与群聊隔离

> 对应 R5。本文是隐私的唯一设计依据，任何实现偏离本文即为缺陷。

---

## 一、现状：两个 if 决定了所有可见性

```js
// memory-vector.js:171-178（现状，逐行）
const rows = loadRows().filter((r) => r.key === key && Array.isArray(r.vec));  // ①
const isOwnerPrivate = key.startsWith('private:');                             // ②
const visible = isOwnerPrivate ? rows
  : rows.filter((r) => r.visibility === 'group_shared'
                    && r.share_review_status === 'approved');                   // ③
```

| 缺陷 | 说明 |
|---|---|
| D-1 维度缺失 | 只有"会话键"与"是否 approved"两维。没有来源、没有内容敏感度、没有调用者 |
| D-2 语义混用 | `visibility` 表"可见范围"，`share_review_status` 表"审核状态"，两者被并联当权限用 |
| D-3 群聊死锁 | 写入默认 `not_requested`（`:157`）→ 群内写的记忆永远不满足 ③ → **群聊记忆恒不可检索**（`【审计】06-C-3`） |
| D-4 无内容分级 | 群里聊到的私事会跟着"同群可见"走，只要有人点了 approved |
| D-5 无来源记录 | A 层无 `origin`（`:155-158` row 只有 key/text/time/vec/share_review_status）⇒ 无法回答"谁在哪个群说的" |

## 二、四个正交维度（R5 核心）

```
origin            来源：谁、在哪个会话、哪条消息、什么时候说的
contentClass      内容性质：public / sensitive / uncertain
scope.read        读取范围：owner_only / origin_group
review.status     人工审核状态：not_required / pending / approved / rejected
```

**正交性要求**：任一维度变化不得隐式改变另一维度。特别是：
- `review.status = approved` **不等于** `scope.read` 一定放开（审核只回答"允许不允许"，不回答"范围多大"）。
- `scope.read = origin_group` **不等于** 内容可群见（还须 `contentClass = public`）。

### 2.1 `origin`（来源，不可改）

```jsonc
"origin": {
  "channel": "qq_group" | "qq_private" | "legacy" | "manual" | "reflect",
  "groupId": "123456" | null,     // 群来源；私聊为 null
  "messageSeq": 88123 | null,     // 本地 seq，可回溯原消息
  "senderQq": "[BOT_QQ]" | null,// 提供信息的人
  "at": 1761900000000,            // 事件发生时刻（不是写入时刻）
  "trigger": "retain_rule:commitment" | "tool:qq_memory_append" | "manual" | "reflect"
}
```

**语义约束**：
- `channel='qq_group'` ⇒ `groupId` 必填且非空。
- `channel='qq_private'` ⇒ `groupId` 必须为 null。
- `channel='legacy'` ⇒ 迁移数据；`groupId` 从 key 推导，`senderQq=null`，`at = 原 time`。
- **不可变**：任何更新路径都不得修改 `origin`（只允许 `legacy → 具体值` 的一次性回填，且必须审计）。

### 2.2 `contentClass`（内容分级）

| 值 | 判定 | 触发示例 |
|---|---|---|
| `public` | 无敏感命中 | "这群在筹备漫展" |
| `sensitive` | 命中凭证/证件/住址/真实姓名/金额/账号/医疗/情感隐私/第三人隐私 | 含 11 位手机号、含"他家住…" |
| `uncertain` | 分类器置信不足、含模糊指代（"他""那个"）、含"别告诉别人"类措辞 | "那个事你别跟别人说" |

**分级器是规则版（不是 LLM）**，规则表是封闭集合，写在 `memory-permission.js` 顶部常量，可单测、可复查。命中即降级，**宁可隔离不可放过**。

### 2.3 `scope.read`（读取范围）

| 值 | 含义 | 谁可读 |
|---|---|---|
| `owner_only` | 仅主人私聊 | `private:<botOwner>` 会话 |
| `origin_group` | 仅来源群 | `group:<origin.groupId>` 会话 |

**`owner_only` 的精确定义（R5 要求）**：

```
owner_only  ≠ 发送者私有
owner_only  ≠ 被描述者私有
owner_only  =  仅「机器人主人（config.ownerQQ）的私聊会话」可读
```

三个主体的区分：

| 角色 | 是谁 | 在这个模型里的地位 |
|---|---|---|
| **botOwner** | `config.json:24` `ownerQQ = [OWNER_QQ]` | 唯一的管理主体；`owner_only` 只对他开放 |
| **sender** | `origin.senderQq` | 信息提供者；**不因此获得读取特权** |
| **subject** | 被记忆描述的人（`assertion.assertedBy` / `subjectId`） | **完全无读取权限**；仅作为内容归属标签 |

**为什么要写清这一条**：现状 `isOwnerPrivate = key.startsWith('private:')` 的真实语义是"任意私聊会话"，而白名单里有两个私聊号（`config.json:29-32`：[OWNER_QQ] / [SECOND_QQ]）。所以严格说，现状是"任意白名单私聊都能读全部 owner 级记忆"——这与"主人私有"不是一回事。

Rev3 明确：
- `owner_only` 只对 `private:<botOwner>` 开放。
- 其他私聊号（如 [SECOND_QQ]）**读不到** `owner_only` 记录（除非其自身是 sender 且未来引入 `sender_private`，本版不做）。

这是一次**收紧**，不是放宽。**需要在实施时提示"另一个私聊号会看不到部分记忆"**——这是行为变更，列入 `11` 的 D-28 待确认。

### 2.4 `review.status`（人工审核）

| 值 | 含义 |
|---|---|
| `not_required` | 无需人工审（来源与内容都不触发审核条件） |
| `pending` | 已提交待审（分享申请 / 隔离项待处理） |
| `approved` | 人工批准 |
| `rejected` | 人工驳回 |

**审核只回答"允不允许"，不回答"范围多大"**。`approved` 不改变 `scope.read`；要跨范围必须显式改 `scope.read`（本版无此路径）。

## 三、四字段的允许转移（状态机）

### 3.1 `contentClass` 转移（**只降不升**，INo-15）

```
                ┌──────────┐
                │  public  │
                └────┬─────┘
        自动降级（分类器命中）
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  sensitive     uncertain    sensitive
        │            │
        └────┬───────┘
             │ 只有主人可在管理端提升
             ▼
          public        ← 唯一的人工例外，必须记审计
```

| 转移 | 允许者 | 条件 | 审计 |
|---|---|---|---|
| `public → sensitive/uncertain` | 自动（Retain/Reflect/重新分类） | 规则命中 | 记 `class_downgrade` |
| `sensitive ↔ uncertain` | 自动 | 规则变化 | 记 |
| `sensitive/uncertain → public` | **仅管理端** | 主人显式操作 | 必须记 `class_upgrade_manual` + 理由 |

**禁止**：任何自动流程把 `sensitive` 提回 `public`。

### 3.2 `scope.read` 转移

| 转移 | 允许者 | 条件 | 本版是否存在 |
|---|---|---|---|
| `origin_group → owner_only`（降级） | 自动 | `contentClass` 降级时联动；或来源群被移出白名单 | ✅ 存在 |
| `owner_only → origin_group`（升级） | **仅管理端** | 主人显式批准，且 `contentClass` 必须 = `public` | ⚠️ 端点存在但默认关闭（见 §5.3） |
| 跨群（`origin_group` 换群） | **不允许** | — | ❌ 永不 |

**联动规则（硬）**：

```
if (contentClass !== 'public') scope.read := 'owner_only'   // 自动，不可绕过
```

### 3.3 `review.status` 转移

| 转移 | 触发 |
|---|---|
| `not_required → pending` | 分享申请 / 隔离项入队 |
| `pending → approved` | 管理端批准 |
| `pending → rejected` | 管理端驳回 |
| `approved → pending` | 主人撤回（可选，本版不做） |
| 任何 → `not_required` | 仅当 `scope.read='owner_only'` 且 `contentClass='public'`（即"无需审核也不会外泄"） |

### 3.4 `origin` 不可转移

唯一例外：迁移期 `channel='legacy'` → 具体值，且必须一次性、可审计、幂等。

## 四、`canRead(record, ctx)` —— 注入前的最后一道闸（R5 第 8 条）

```js
// memory-permission.js
function canRead(record, ctx) {
  // ctx = { key, caller: 'agent'|'admin'|'reflect', groupId|null, botOwner }

  // 0) 生命周期硬过滤
  if (record.lifecycle === 'deleted' || record.lifecycle === 'quarantined') return false;
  if (record.lifecycle === 'proposed') return ctx.caller === 'admin' ? false : false; // 见 07：一律不进召回
  if (record.lifecycle === 'superseded') return ctx.caller === 'admin';

  // 1) 会话键必须等值（不可跨 key）
  if (record.key !== ctx.key) return false;

  // 2) 群聊场景：来源群必须一致 + 范围必须是 origin_group + 内容必须 public
  if (ctx.key.startsWith('group:')) {
    if (record.scope.read !== 'origin_group') return false;
    if (record.origin.channel !== 'qq_group') return false;
    if (String(record.origin.groupId) !== String(ctx.groupId)) return false;
    if (record.scope.contentClass !== 'public') return false;
  }

  // 3) 私聊场景：只有 botOwner 的私聊可读（owner_only 的精确定义）
  if (ctx.key.startsWith('private:')) {
    if (ctx.key !== `private:${ctx.botOwner}`) {
      // 非主人私聊：只能读"自己作为 sender 的、且不敏感的"记录（本版不开放，留注释）
      return false;
    }
  }

  // 4) 管理端可读全部（但只用于展示，不得注入）
  if (ctx.caller === 'admin') return true;

  return true;
}
```

### 4.1 判决表（可直接当验收用例）

| # | record.key | scope.read | contentClass | 当前 ctx | 结果 |
|---|---|---|---|---|---|
| 1 | `group:A` | `origin_group` | `public` | `group:A` | ✅ 可读 |
| 2 | `group:A` | `origin_group` | `public` | `group:B` | ❌ |
| 3 | `group:A` | `origin_group` | `sensitive` | `group:A` | ❌（内容分级拦） |
| 4 | `group:A` | `owner_only` | `sensitive` | `group:A` | ❌ |
| 5 | `group:A` | `owner_only` | `sensitive` | `private:owner` | ✅ |
| 6 | `private:owner` | `owner_only` | `public` | `private:owner` | ✅ |
| 7 | `private:owner` | `owner_only` | `public` | `group:A` | ❌ |
| 8 | `group:A` | `origin_group` | `public` | `private:owner` | ❌（key 不等值） |
| 9 | `private:other` | `owner_only` | `public` | `private:other` | ❌（非 botOwner） |
| 10 | 任一 | — | — | `caller='admin'` | ✅（仅展示） |

> **第 8 行的含义**：主人在私聊里读不到群里的记忆。这可能反直觉，但这是"key 严格相等"的直接结果，也是现状行为（`memory-vector.js:172`）。若要改，属于新能力（跨会话读），本版不做。

## 五、死锁的修法（R5 核心：修好但不开口子）

### 5.1 死锁的三个成因（逐条对应）

| 成因 | 位置 | 修法 |
|---|---|---|
| ① 写入默认 `not_requested` | `memory-vector.js:157` | 改为 `review.status := 'not_required'` **仅当** `contentClass==='public'`；否则 `scope.read='owner_only'` 且入 quarantine |
| ② 读取要求 `approved` | `:176-177` | 改为 `canRead()`；条件从"approved"变为"scope.read=origin_group ∧ contentClass=public ∧ 同群" |
| ③ 申请端点拒绝 private | `bridge.js:6892-6895` | **保持不变**（这是正确的：私聊记忆不该申请进群） |

### 5.2 修好之后的可见性对照

| 场景 | 现状 | Rev3 |
|---|---|---|
| 群 A 里聊"这群要办漫展" | 写入 `not_requested` → **不可检索** | `origin_group` + `public` → **立即可检索** |
| 群 A 里聊"XX 的手机号是…" | 写入 `not_requested` → 不可检索 | `owner_only` + `sensitive` → **仍不可检索**，进 quarantine |
| 群 A 里聊"他说他要辞职" | 不可检索 | `owner_only` + `uncertain`（指代不明）→ 不可检索 |
| 私聊里说"我家的猫叫豆豆" | 仅私聊可读 | 不变（`owner_only`） |
| 群 A 的记忆出现在群 B | 不可能 | 不可能（`origin.groupId` 严格相等） |

**关键点**：修好的是"同群内、非敏感、自产"这一类；**所有跨边界方向全部保持关闭**。这就是 R5 第 1 条"群内自产不等于可无限共享"。

### 5.3 `owner_only → origin_group` 的端点为什么默认关闭

技术上需要一个"主人批准把某条隔离项放回群里"的出口（否则 quarantine 只能删）。但：
- 一旦开启，就有"人审出错 → 隐私泄露"的风险；
- 现阶段没有任何真实需求（因为 `public` 内容根本不需要审批）。

**决定**：端点实现但 `config.permission.allowOwnerPromote = false` 默认关闭；打开需要显式配置 + 审计告警。列入 `11` 的 D-29。

## 六、R5 九条要求的逐条落实

| # | 要求 | 落实 | 证据/机制 |
|---|---|---|---|
| 1 | 群内自产不等于可无限制共享 | `scope.read` 至多 `origin_group`；跨群恒 false | §2.3 / §4 判决表 #2 |
| 2 | 私聊内容不得自动变群可读 | `key` 严格相等 + `contentClass` 联动 + 无 private→group 路径 | §4 #7；`bridge.js:6892` 保持拒绝 |
| 3 | 群 A 内容不得自动变群 B | `origin.groupId` 严格相等 | §4 #2 |
| 4 | 敏感与第三人隐私不进普通留存 | `contentClass` 判定 → `owner_only` + quarantine | §2.2 / §5 |
| 5 | 权限失败不得变成可自动晋升的普通候选 | **物理分离两个文件**：`candidates.jsonl`（新颖度/价值失败）vs `quarantine.jsonl`（权限失败） | `05` §4 |
| 6 | 无自动跨群共享 | `scope.copies` 字段**不实现**（`01` §2 已划掉） | 本版无该端点 |
| 7 | 无自动私聊→群 | 同上 | — |
| 8 | 注入前最终 `canRead` | `memory-recall.js` 的 `assertReadable()`（五维）+ 注入前二次校验 | §4 / `06` §6 |
| 9 | 白名单不得替代记忆可见性 | `allowed()` 与 `canRead()` 完全解耦，互不调用 | `【审计】06-C-4` |

### 6.1 关于第 9 条的补充说明

**为什么不能把白名单塞进 `canRead`**：

- 白名单的语义是"允许这个会话与机器人对话"，可随时增删（运维动作）。
- `canRead` 的语义是"这条记忆能被谁看到"，属数据属性。
- 若合并：一次误删白名单 = 该会话所有记忆"消失"（但数据还在，造成"数据在但读不到"的幽灵状态，且恢复白名单后又"复活"，不可预期）。

⇒ **两个正交维度，各自独立判断**。这一点写进 `01` INo 与验收。

## 七、三个必须拒绝的"简化方案"

| 方案 | 为什么拒绝 |
|---|---|
| **把 `not_requested` 改成 `approved`** | 等于把"没审"伪装成"审过了"；且 `approved` 是跨范围语义，会把私事推到群里（R5 明确禁止） |
| **在 `canRead` 里复用 `allowed()`** | 见 §6.1；会让运维动作破坏数据可见性 |
| **用 key 前缀判 `owner_only`**（现状 `key.startsWith('private:')`） | 白名单有两个私聊号，会被当成"都是主人"；必须用 `key === private:<botOwner>` |

## 八、需要额外的数据字段（相对现状）

| 字段 | 现状 | Rev3 | 迁移 |
|---|---|---|---|
| `origin.groupId` / `channel` / `senderQq` / `at` | 无 | 必填（新记录） | 历史记录填 `channel='legacy'`，`groupId` 从 key 推导 |
| `contentClass` | 无 | 三态 | 历史记录统一 `uncertain`（保守，不自动放开） |
| `scope.read` | 有 `visibility`（两值） | 两值但语义重定义 | `owner_private → owner_only`；`group_shared → origin_group` |
| `review.status` | 有 `share_review_status`（四值） | 四值，语义收窄为"仅审核" | 原映射：`approved→approved`，其余→`pending`（历史记录不自动放开） |
| `scope.copies` | 无 | **不实现** | — |

**迁移原则（重要）**：历史数据一律按**最保守**处理（`uncertain` + `owner_only`），**不批量升级**。理由：历史数据的来源信息已丢失，无法判断是否敏感。

**当前记忆库为 0 条**（冻结时清空），所以这条迁移规则**只对将来导入旧备份时生效**。
