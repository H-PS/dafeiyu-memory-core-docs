## 二、P0-1 · `key` 到底代表什么

### 2.1 定义（唯一口径）

> **`record.key` = 该记忆出生时的会话标识（origin session identity），不是读取者身份。**

| 它是什么 | 它不是什么 |
|---|---|
| 记忆的**归属/出生地**（`group:<gid>` 或 `private:<qq>`） | ❌ 不是"允许谁读"的判据 |
| 与 `origin` 必须自洽的**一致性冗余**（可用于校验数据完整性） | ❌ 不是访问控制列表 |

**派生规则（硬）**：

```
record.key 与 record.origin 必须自洽：
  origin.channel='qq_group'   ⇒ record.key === `group:${origin.groupId}`
  origin.channel='qq_private' ⇒ record.key === `private:${origin.senderQq}`（botOwner 私聊）或对应私聊会话
  origin.channel='legacy'     ⇒ record.key 保留原值，origin 由迁移补齐
不自洽 ⇒ 数据损坏，进隔离区并告警（不猜测修复）
```

### 2.2 读取权从哪来（不从 key 来）

```
读取资格 = f(origin.channel, origin.groupId, scope.read, scope.contentClass, lifecycle)
会话身份（ctx.key）只用于"同源校验"：ctx.key 必须等于 record.key
```

这条把"来源"和"读者"彻底分开：`key` 回答"这条属于谁"，`ctx.key` 回答"谁在问"，两者**必须相等**才可能通过普通读取。

### 2.3 四个必须显式回答的问题（Review 要求）

| # | 问题 | 回答 |
|---|---|---|
| 1 | `record.key` 是来源归属还是读取者身份？ | **来源归属**（§2.1） |
| 2 | bot owner 能否读"群来源 + `owner_only`"的记录？ | **不能**（普通读取）。只能通过管理端 `canReview()` 查看 |
| 3 | 跨 key 的 owner 访问是不是新能力？ | **是**。**当前版本不实施（D1）**，规范保留，不纳入当前实施测试计划；未来版本重新评审 |
| 4 | 这类访问如何审计与测试？ | 若将来实现：必须独立端点 + 逐条审计 `cross_key_read{from,to,memId,reason}` + 专项测试 CK-01~CK-06（规范保留；当前版本不实施，不纳入当前实施测试计划，未来版本重新评审） |

### 2.4 为什么选"不允许跨 key"（而不是"允许主人读"）

| 理由 | 说明 |
|---|---|
| 对称性 | R5 要求"私聊内容永不自动变群可读"。若允许反向（群→私聊），等于承认"群里的第三人隐私可以被搬到私聊"，只是搬给了主人 |
| 第三人权益 | 群里说的私事，**主体往往不是主人**。主人的所有权 ≠ 被描述者的知情同意 |
| 能力必要性 | 主人要看"她被拦下了什么"，管理端列表足够（`canReview`），不需要让模型在私聊里说出来 |
| 实现风险 | 跨 key 读取会让 `canRead` 的 key 断言失效，需要新的一套审计与测试；收益不足以抵消 |
| 可逆性 | 现在不做，将来要做只是加法；现在做了再收回，是破坏性变更 |

> ⚠️ 这条会带来一个需要主人知晓的后果：**群里被降级为 `owner_only` 的记忆，在聊天里永远读不到（包括私聊）**，只能在控制台看。这是**有意的**，**已由主人确认接受（D1，2026-10-31）**，不再作为待决项。

## 三、P0-3 · 字段路径权威表

**唯一口径：分级与范围都在 `scope` 下，`origin` 独立。**

| 概念 | 权威路径 | 类型 | 说明 |
|---|---|---|---|
| 来源通道 | `record.origin.channel` | enum | `qq_group` / `qq_private` / `legacy` / `manual` / `reflect` |
| 来源群 | `record.origin.groupId` | string\|null | `channel='qq_group'` 时必填 |
| 提供者 | `record.origin.senderQq` | string\|null | 谁说的（不是谁被描述） |
| 发生时间 | `record.origin.at` | number | 事件时刻（非写入时刻） |
| **内容分级** | **`record.scope.contentClass`** | enum | `public` / `uncertain` / `sensitive` |
| **读取范围** | **`record.scope.read`** | enum | `owner_only` / `origin_group` |
| 来源群冗余 | `record.scope.originGroupId` | string\|null | 必须等于 `origin.groupId`（自洽校验） |
| 分级理由 | `record.scope.classReason` | string | `none` / `credential` / `third_party` / `address` / `medical` / `finance` / `relationship` / `ambiguous` |
| 审核状态 | `record.review.status` | enum | `not_required` / `pending` / `approved` / `rejected` |
| 生命周期 | `record.lifecycle` | enum | `active` / `stale` / `superseded` / `proposed` / `quarantined` / `deleted` |

### 3.1 禁止的写法（代码审查项）

| 禁止 | 原因 |
|---|---|
| `record.contentClass` | ❌ 根级不存在该字段 |
| `record.visibility` | ❌ 旧字段，迁移后不再读 |
| `record.share_review_status` | ❌ 旧字段，迁移后不再读 |
| `record.originGroupId`（根级） | ❌ 只有 `scope.originGroupId` 与 `origin.groupId` |

**自洽断言**（写进 `commit()` 与迁移脚本）：

```js
assert(record.scope.originGroupId === record.origin.groupId);
assert(record.origin.channel === 'qq_group' ? record.key === `group:${record.origin.groupId}` : true);
assert(record.scope.contentClass !== 'public' ? record.scope.read === 'owner_only' : true);
```

## 四、P0-4 · 保护等级与转移

### 4.1 保护序（唯一口径）

| 等级 | `scope.contentClass` | 含义 | 读取范围（强制） |
|---|---|---|---|
| **0（最低保护）** | `public` | 无敏感命中 | 可为 `origin_group` |
| **1** | `uncertain` | 判不准 / 含模糊指代 / 含"别告诉别人" | **必须** `owner_only` |
| **2（最高保护）** | `sensitive` | 命中凭证/证件/住址/真实姓名/金额/医疗/情感隐私/第三人隐私 | **必须** `owner_only` + 进隔离区 |

**不变式（INo-15）**：`scope.contentClass !== 'public' ⇒ scope.read === 'owner_only'`。任何写入路径不得违反（`commit()` 强制校验，违反则拒绝写入）。

### 4.2 自动转移（只允许不降级）

| 转移 | 允许 | 条件 | 审计 |
|---|---|---|---|
| `public → uncertain` | ✅ 自动 | 规则命中模糊信号 | `class_escalate` |
| `public → sensitive` | ✅ 自动 | 规则命中敏感模式 | `class_escalate` |
| `uncertain → sensitive` | ✅ 自动 | 更强规则命中 | `class_escalate` |
| `uncertain → public` | ❌ | — | — |
| `sensitive → uncertain/public` | ❌ 自动 | 只能人工 | — |
| 同级重复判定 | ✅ 幂等 | 不产生变更 | 无 |

**判定公式**：`newRank >= oldRank` 才允许自动写；`newRank < oldRank` 一律拒绝并要求人工。

### 4.3 人工降级（唯一例外路径）

```
POST /api/memory/classify-override
  需 console token + { memId, contentClass: 目标, reason: 非空字符串(≤200字) }
  仅允许 sensitive/uncertain → public
  二次确认：请求体必须含 confirm: "DOWNGRADE"
  审计（必写，缺一即失败）：{ op:'class_downgrade_manual', memId, from, to, reason, actor, at }
  副作用：若 to='public' 且 origin.channel='qq_group' 且主人选择 → 可同时置 scope.read='origin_group'
         （默认**不**联动，需显式传 scopeRead）
```

**"范围提升"与"分级降级"是两个动作**，不得由一个布尔同时表达（`allowOwnerPromote` 只管 range，不管 class）。

## 五、P0-2 · 两个权限函数

### 5.1 为什么要拆

Rev3 旧 `canRead()`：

```js
if (record.lifecycle === 'proposed') return ctx.caller === 'admin' ? false : false;  // 恒 false
...
if (record.key !== ctx.key) return false;      // ← admin 也被这条挡住
...
if (ctx.caller === 'admin') return true;       // ← 永远到不了
```

两个问题：① `proposed` 分支写成恒 false，与"admin 可查看"矛盾；② admin 的 `return true` 在 key 检查之后，永远不可达。

### 5.2 `canRead(record, ctx)` —— 只服务召回与注入

```js
// ctx: { key, groupId, botOwner, caller: 'agent' | 'reflect' }
// 注意：caller 只接受 agent/reflect。admin 不得调用本函数。
function canRead(record, ctx) {
  if (ctx.caller !== 'agent' && ctx.caller !== 'reflect') return false;   // fail-closed

  // 1) 生命周期：只有 active / stale 可读
  if (record.lifecycle !== 'active' && record.lifecycle !== 'stale') return false;
  //    proposed / quarantined / superseded / deleted 一律 false

  // 2) 同源：key 必须等值（P0-1）
  if (record.key !== ctx.key) return false;

  // 3) 范围：只有 origin_group 可在群里读
  if (String(ctx.key).startsWith('group:')) {
    if (record.scope.read !== 'origin_group') return false;
    if (record.origin.channel !== 'qq_group') return false;
    if (String(record.origin.groupId) !== String(ctx.groupId)) return false;
    if (record.scope.contentClass !== 'public') return false;
  }

  // 4) 私聊：只有 botOwner 的私聊可读
  if (String(ctx.key).startsWith('private:')) {
    if (ctx.key !== `private:${ctx.botOwner}`) return false;
  }

  return true;
}
```

### 5.3 `canReview(record, ctx)` —— 只服务管理端

```js
// ctx: { caller: 'admin', consoleTokenVerified: true }
function canReview(record, ctx) {
  if (ctx.caller !== 'admin') return false;
  if (!ctx.consoleTokenVerified) return false;

  switch (record.lifecycle) {
    case 'active': case 'stale': case 'superseded':
    case 'proposed': case 'quarantined':
      return true;
    case 'deleted':
      return true;      // 但调用方必须只展示元数据 + 标记"已删除"（正文可能已清）
    default:
      return false;
  }
}
```

### 5.4 两条硬规矩

| 规矩 | 说明 |
|---|---|
| **`canReview` 不得用于注入** | 注入路径只调 `canRead`。代码审查项：`buildWakePromptV2` 与 `memory-recall` 内不得出现 `canReview` |
| **管理师查看不等于模型可知** | 控制台能看到隔离内容，不代表模型在任何会话里能读到它。这两条路径在代码上完全分离 |

### 5.5 生命周期 × 调用者矩阵（Review 要求"覆盖全部状态与调用者"）

| lifecycle | `agent`（召回/注入） | `reflect`（后台整理） | `admin`（控制台） | 说明 |
|---|---|---|---|---|
| `active` | ✅（按 §5.2 条件） | ✅ | ✅ | 正常 |
| `stale` | ✅（降权 0.6） | ✅ | ✅ | 过时但可读 |
| `superseded` | ❌ | ❌ | ✅（可查历史） | 终态 |
| `proposed` | ❌ | ✅（可再评估） | ✅（审核） | 不进召回 |
| `quarantined` | ❌ | ❌ | ✅（审核） | 只有人能看到 |
| `deleted` | ❌ | ❌ | ✅（仅元数据） | 正文不保证存在 |

> `reflect` 对 `quarantined` 也不可读：因为它的 `contentClass != public`，且隔离区的判读属于人工职责，不应让自动流程"看见"后再做别的事。

## 六、`canRead` 与准入层的关系（U-9 已确认）

**新证据（本轮定向核实）**：

```js
// bridge.js:3167
const v2SessionAllowed = isSessionAllowedInCurrentMode;
```

而 `isSessionAllowedInCurrentMode`（`:2713`）→ `modeAllowed`（`:2666`）→ `allowed(kind, id, cfg)`（`:1358`）。

⇒ **`v2SessionAllowed()` 确实包含白名单校验**。原审计中的 U-9 从 `【UNCONFIRMED】` 升级为 **【已确认】**。

其含义：

| 层 | 作用 | 是否包含白名单 |
|---|---|---|
| 端点层（`/api/socialV2/*`） | 谁能调这个接口 | ✅ 已包含（经 `v2SessionAllowed`） |
| 记录层（`canRead`） | 这条记忆能被读吗 | ❌ 不包含，**也不应该包含** |

**结论不变**：两层正交。白名单决定"能不能对话/调接口"，`canRead` 决定"能不能读这条"。把 `allowed()` 塞进 `canRead` 会让"临时拉黑 = 永久失忆"，且恢复白名单后记忆"复活"，不可预期。

## 七、群聊死锁的修法（保持 Rev3，不退化）

| 成因 | 位置 | 修法 |
|---|---|---|
| ① 写入默认 `not_requested` | `memory-vector.js:157` | `classify()` 后：`public` → `review.status='not_required'`；非 public → `owner_only` + 隔离 |
| ② 读取要求 `approved` | `:176-177` | 改为 `canRead()`（来源 + 范围 + 分级） |
| ③ 分享申请拒绝 private | `bridge.js:6892-6895` | **保持不动**（私聊记忆不该申请进群） |

**修复后的可见性**：

| 场景 | 现状 | Rev3.1 |
|---|---|---|
| 群 A 聊"这群要办漫展" | 写入后不可检索 | **立即可检索**（origin_group + public） |
| 群 A 聊"XX 手机号是…" | 不可检索 | 仍不可检索（owner_only + sensitive + 隔离） |
| 群 A 的记忆出现在群 B | 不可能 | 不可能 |
| 私聊内容出现在群 | 不可能 | 不可能 |
| **群 A 的 owner_only 在主⼈私聊** | — | **不可检索**（P0-1 的结论），仅控制台可审 |

## 八、P0-5 · 隔离区行为（五问五答）

| # | 问题 | 回答 |
|---|---|---|
| 1 | 隔离记录是否排除在**所有**普通召回之外？ | **是**。`lifecycle='quarantined'` 在 `canRead` 第一关即 false，不区分群/私聊/主人 |
| 2 | 主人如何查看？ | **仅** `canReview()`（控制台 `/api/memory/admin?lifecycle=quarantined`）。聊天里永远看不到 |
| 3 | 批准能否释放隔离？ | **能**。`approve` → `lifecycle: quarantined → active` |
| 4 | 释放是否改变读取范围？ | **默认不变**：释放后仍是 `scope.read='owner_only'`。要变范围是**另一个动作**（`promote`，当前版本关闭：管理端显示"未开放"，后端拒绝 promote 请求） |
| 5 | 能否进入普通候选池？ | **永不**。物理分离：`memory-quarantine.jsonl` ≠ `memory-candidates.jsonl`；无迁移函数、无自动晋升 |

### 8.1 隔离区状态机

```
        Retain 闸4 失败 / 来源不自洽 / 分级异常
                      │
                      ▼
                ┌───────────┐
                │quarantined│
                └─────┬─────┘
        ┌─────────────┼──────────────┐
        │             │              │
   approve        promote        reject
 (当前可用)  (当前关闭·后端拒绝)  (删除该条)
        │             │              │
        ▼             ▼              ▼
   active        active          deleted
 owner_only   origin_group     （移出隔离区）
              +public
```

| 动作 | 前置条件 | 结果 | 审计 |
|---|---|---|---|
| `approve` | `contentClass` 任意 | `active` + `read=owner_only` | `quarantine_approve` |
| `promote` | `contentClass='public'` **且** `allowOwnerPromote=true`。**当前版本关闭（D3）**：**后端直接拒绝 promote 请求（fail-closed）**，不依赖 UI 隐藏或配置默认值；管理端显示"未开放"，配置不提供放开入口 | `active` + `read=origin_group` | `quarantine_promote` |
| `reject` | 任意 | 移出隔离区，`lifecycle='deleted'` | `quarantine_reject` |

**`promote` 的前置条件里"contentClass 必须 public"是硬的**：不允许把敏感内容直接放回群。

### 8.2 隔离区不设 TTL

理由：敏感内容不能因为"过期"被自动清理得不留痕迹，也不能被自动删除（主人可能还没看）。管理端显示"最早未处理天数"，超过 30 天给红点提醒。

## 九、P1-1 · 迁移策略（不再一律 pending）

### 9.1 旧字段映射

| 旧 `share_review_status` | 旧 `visibility` | 新 `review.status` | 新 `scope.read` | 依据 |
|---|---|---|---|---|
| `approved` | `group_shared` | `approved` | `origin_group` | **保留**（有明确人工批准记录） |
| `rejected` | `owner_private` | `rejected` | `owner_only` | **保留**（有明确驳回记录） |
| `pending` | 任意 | `pending` | `owner_only` | **保留**（有申请记录） |
| `not_requested` | `owner_private` | `pending` | `owner_only` | **无可靠历史** → 见 §9.2 |
| `not_requested` | `group_shared` | `pending` | `owner_only` | 同上（`group_shared` 但未申请，属异常组合） |
| 字段缺失 | 任意 | `pending` | `owner_only` | 同上 |

### 9.2 无可靠审核历史的记录（单独策略）

```jsonc
"migration": {
  "policy": "legacy_unverified",     // 标记来源
  "at": 1761900000000,
  "fromFields": { "share_review_status": "not_requested", "visibility": "owner_private" }
}
```

| 项 | 规则 |
|---|---|
| `scope.contentClass` | **统一 `uncertain`**（导致 `read=owner_only`） |
| `review.status` | `pending`（进待办，等人处理） |
| 是否自动放行 | ❌ 永不。即使 `classReason` 判定为无敏感，也保持 `uncertain`（历史无来源信息，无法再判） |
| 是否进隔离区 | **不进**（隔离区是"新写入被判敏感"的去处；历史记录作为"待定"存在 A 层，只是不可召回） |
| 主人要做的事 | 在控制台按 `migration.policy='legacy_unverified'` 筛选，逐条决定：降级为 public（→可群见）或删除 |

**为什么不用隔离区**：隔离区语义是"因敏感被拦"，历史记录是"因无证据无法判断"，两者处置路径不同（前者可 promote，后者必须先降级分级）。

### 9.3 迁移幂等

```js
if (record.migration?.policy === 'legacy_unverified') return;   // 已迁过，跳过
```
