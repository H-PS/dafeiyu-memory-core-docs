# 13 · 待决事项清单（Decision Log）

> 本版（Rev3.1）涉及的产品决策。**默认值 = 若主人不表态时按此实施**。
> 凡标"阻塞"的，未定则对应章节不能进入编码。

## 一、新提出的决策

### R31-D1 · `/reset` 的 token 语义：删除 → 轮换

| 项 | 内容 |
|---|---|
| 现状 | `/reset` 走 `forgetAgentToken(key)` + `socialV2.conversations.delete(key)` ⇒ token 随对象消失（`bridge.js:11308-11309`） |
| 本版提议 | 统一为 `credential.rotate(key,'reset',opId)` ⇒ 换新 + `needsDelivery=true` |
| 外部可观察差异 | 无（旧 token 两种做法都立即失效） |
| 内部差异 | 现状存在"无 token 窗口"（对象删了、新会话未建），窗口内工具调用 403 且无法自愈 |
| 默认 | **轮换** |
| 阻塞 | 否（两种做法都能跑，但需明确选一个，否则 §5.2 的四项细节无法定稿） |
| 若选"删除" | 必须补"删除后立即生成新 token"的补偿步骤，最终效果等同轮换，只是多一次写盘 |

### R31-D2 · 是否引入"跨 key 的主人读取"（新能力）

| 项 | 内容 |
|---|---|
| 内容 | 允许 `private:<botOwner>` 会话召回 `group:*` 来源、`scope.read='owner_only'` 的记录 |
| 默认 | **不引入** |
| 理由 | ① 与"私聊内容永不自动变群可读"不对称；② 群里被描述的主体常是第三人，主人所有权 ≠ 第三人同意；③ 会让 `canRead` 的 key 断言失效，需另建审计与 6 类测试 |
| 若要引入 | 必须：独立端点 `/api/memory/cross-read`、逐条审计 `cross_key_read{from,to,memId,reason}`、测试 CK-01~CK-06、并在 UI 明示"这条来自群 G" |
| 阻塞 | 否（默认不做即可） |

### R31-D3 · 接受"群内 owner_only 在聊天中永不可见"

| 项 | 内容 |
|---|---|
| 内容 | R31-D2 选了"不引入"后，群内被判敏感/不确定的记录，**在群里和主人私聊里都召回不到**，只能控制台看 |
| 默认 | **接受** |
| 影响 | 主人可能觉得"她明明记得却不告诉我"。需在控制台把隔离区做得显眼（红点 + 计数） |
| 若不接受 | 必须改走 R31-D2（跨 key 读取），二者互斥 |
| 阻塞 | 否 |

### R31-D4 · 是否开放 `allowOwnerPromote`（把隔离项放回群）

| 项 | 内容 |
|---|---|
| 内容 | 管理端把 `quarantined` 记录提升为 `origin_group + public` |
| 默认 | **关闭**（`config.permission.allowOwnerPromote=false`） |
| 理由 | 开启后唯一防线是人审，人审出错即隐私泄露；且 `public` 内容根本不需要审批，开启缺少真实需求 |
| 前置 | 即使开启，仍强制要求 `contentClass='public'`（不允许把 sensitive 直接放回群） |
| 阻塞 | 否 |

### R31-D5 · prompt-dump 是否允许 `structure` 模式

| 项 | 内容 |
|---|---|
| 内容 | 除 `meta` 外，额外记录"规则块文本 + 记忆 id/召回 id 列表"（不含任何正文） |
| 默认 | **允许，但默认值仍是 `meta`** |
| 理由 | 排障时经常需要知道"睡眠规则这一轮到底发没发、内容是什么"，而它不含用户隐私 |
| 若不允许 | 只能 `off | meta`，规则块问题需靠一次性内存捕获排查 |
| 阻塞 | 否 |

### R31-D6 · 是否引入 OS 级密钥库（DPAPI / libsecret）保存 token

| 项 | 内容 |
|---|---|
| 现状 | 明文文件 + ACL |
| 默认 | **不引入** |
| 理由 | 跨平台实现差异大、部署门槛升高（`SECURITY_BASELINE` R2 已把这条列为"不修"的取舍） |
| 缓解 | 轮换 + 泄露可检测（出站含 token 直接抛错不发）+ 缩短暴露窗口 |
| 阻塞 | 否 |
