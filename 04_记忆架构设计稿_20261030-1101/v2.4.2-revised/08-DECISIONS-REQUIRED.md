# E. 本版新增决策（4 项）

## D-21 ★ clear 屏障语义（**待批准**，影响产品行为）

| 项 | 内容 |
|---|---|
| 问题 | clear 之前已请求、但尚未完成 embedding 的 append/edit，是否允许在 clear 之后提交？ |
| 方案 A（推荐） | **屏障**：`op.requestSeq < clear.requestSeq` 且未提交 ⇒ clear 提交时丢弃（WAL `aborted(barriered)`），返回 409 `{reason:'cleared_by_barrier'}` |
| 方案 B（V1 语义） | **不屏障**：clear 只删"提交时刻已存在"的记录；之后提交的 append 正常写入 |
| 推荐 | **方案 A**（符合"清了就是清了"的直觉） |
| 但 M0 默认 | **方案 B**（不改 V1 行为，降低风险），响应中提示"clear 不阻止清空后到达的写入" |
| 需要用户明确 | 是。涉及"用户以为清了但还有残留"的语义 |

## D-22 ★ `subjectId` 是否可编辑（**待批准**）

| 项 | 内容 |
|---|---|
| 背景 | V1 `memory-update` 支持 memberImpression 改名（`bridge.js:6812-6819`，N-03） |
| 方案 A（推荐） | **允许**，走独立 `edit_subject` op（`expectedContentRev` 校验），同步更新 P 层 key |
| 方案 B | 禁止（改名 = 删旧 + 建新两条操作） |
| 推荐 | **方案 A**（保留 V1 能力，避免用两条操作模拟） |
| 影响 | A 层 `subjectId` 可变 ⇒ tombstone 需记 `prevSubjectId`（可选）；P 层 key 需原子迁移 |

## D-23 ★ `reset` 是否清 A 层（**待批准**）

| 项 | 内容 |
|---|---|
| 背景 | V1 `bridge.js:4624` `atomicWriteJson(SOCIAL_V2_FILE, { conversations: {} })` 清空**整个** social-v2.json（N-04） |
| 方案 A（推荐） | **不清 A/P**：reset 只重置 S 层会话状态（消息/未读/唤醒配置），**保留记忆** |
| 方案 B | 同时清 A/P（等于"重置一切"） |
| 推荐 | **方案 A**（reset 语义是"重置会话"，不是"忘记一切"） |
| 需要用户明确 | 是。涉及"点 reset 会不会丢记忆" |

## D-24 ★ 是否串行 embedding 以保证提交顺序（**待批准**）

| 项 | 内容 |
|---|---|
| 背景 | P1 在队列外并行 embed ⇒ 提交顺序 = embed 完成顺序 ≠ 请求顺序（02 §5） |
| 方案 A（推荐） | **不串行**（保持并行，记录 requestSeq 供审计；接受"后发可能先提交"） |
| 方案 B | **串行**（按 requestSeq 依次 embed + 提交）⇒ 严格请求顺序，但一个慢 embed 阻塞全部 |
| 推荐 | **方案 A**（性能优先；顺序问题通过 D-21 屏障 + 审计解决） |
| 影响 | 方案 B 会让单次 Ollama 卡顿放大为全局延迟 |
