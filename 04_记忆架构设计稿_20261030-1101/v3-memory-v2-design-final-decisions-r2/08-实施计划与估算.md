## 〇、R2 总体目标

把记忆系统从"单一 social-v2.json 混杂存储"重构为 A/P/S 分层 + 凭据独立 + reset 事务化，同时修复凭据明文落盘（prompt-dump）、token 多处真相源、reset 无事务保证、快照白名单丢字段等已确认安全问题。分 M0（store/permission/credential/prompt-dump）→ M1（recall/retain/reflect）→ M2（resetTx/批次/恢复）三阶段交付。

## 四、迁移与回滚

- **K_pre（迁移前）vs V-8b（迁移后）分离（Issue A）**：
  - **迁移前 `K_pre` 验证**（M0·迁移的门控）：从独立 pre-migration 基线建立 `K_pre`，验证其来源、身份覆盖、完整性；确认 M14 完成、M06 credential 存储就绪、M06-L1 兼容完成。**这是迁移门，不是 V-8b**。
  - **迁移后 V-8b 校验**：完整三 key 集比较（`K_enum ⊇ K_pre`、`K_reg == K_enum`、归属校验），缺/多余 key 即 FAIL；manifest 存在 ≠ 覆盖完整。**V-8b 是迁移后测试，不得当作迁移前门**。
  - 顺序：① 定义 manifest 接口契约（M06 设计一部分）→ ② 迁移前建立 manifest 并校验覆盖（`K_pre` 验证）→ ③ 完成 M06 + M06-L1 → ④ 破坏性迁移 token 出 S → ⑤ 迁移后 V-8b 校验。
- **workspace/reset 迁移期禁用（Issue B，安全关键）**：
  - token 出 S 后，W 的旧实现（`conversations.clear()` + 内存 token 表 clear，`:7493-7495`）**不再能失效全部凭据**（凭据已迁入 credential 存储，而 W 未实现 `retireAll`）。
  - **要求（Issue A 强化）**：破坏性迁移后，W 端点**不得执行其 legacy 实现**，除非其凭据退役行为被证明完整；在其独立事务设计+测试完成前，**必须禁用或 fail-closed**。
  - **禁用是"迁移后恢复服务"的硬前提**：迁移/重启序列不得被判定为安全，除非 W 禁用机制已就位——**任何路径都不得在 token 出 S 后执行 legacy W 实现**。若安全禁用须在迁移前完成，则明确该时点（迁移前禁用 W 并验证）。
  - **禁用机制现状 `UNCONFIRMED`**：当前代码无"迁移期禁用"开关 → 标 UNCONFIRMED，**作为迁移/发布阻断项**（WS-05）。**在禁用机制落地并验证前，不得授权迁移/重启序列为安全**。
  - 重新启用条件：W 独立事务语义（intent/幂等/`retireAll`/恢复/双损）设计完成 + 测试全绿。
  - **不得声称 `credential.retireAll` 存在或幂等**（未证实）。

## 四·B M06 无 journal 的 D-2 保留（Issue B）

**事实（`CONFIRMED`）**：现有 A/B/C reset 端点**不接受/忽略 requestId**（`readBody()` 只取 `key`，如 `/api/session/reset :7390-7391`）→ 现状本就无请求级幂等；`credential.rotate` 的 opId 幂等 ≠ requestId→batch 结果的幂等。

M06-L1 允许旧 reset 端点调 `credential.rotate`（无 journal）时，**不得静默违反 `01` D-2**。两条证据支撑方案：

| 方案 | 说明 | 采用条件 |
|---|---|---|
| **方案 B（fail-closed，采用）** | 现状端点本就不接受 requestId → 无 requestId 时走 `01` D-2 的**非幂等默认**（每次=新操作），**不产生 requestId 幂等冲突**；一旦未来引入 requestId，则 M06 阶段 reset 端点须**fail-closed 拒绝**（无法提供 request-level 保证时） | 现状无 requestId = 天然非幂等，不违反 D-2 |
| 方案 A（轻量幂等层） | M06 期保留轻量持久幂等/重放层 | **仅在"端点开始接受 requestId"时启用**，否则不必要 |

**结论**：M06-L1 在**不引入 requestId 的前提下**不违反 D-2（非幂等默认）。若 M06 阶段某端点开始接受 requestId，则该端点必须 fail-closed 直到轻量幂等层就位。**此边界须在 M06-L1 实施时固化**（RB-04/MIG 测试覆盖）。

### 四·B-1 workspace 禁用的精确生命周期（Issue A）

三个层面必须区分，不得混为一谈：

| 层面 | 内容 |
|---|---|
| **A. M06-L1 字段级兼容** | A/B/C 需 credential 读写适配器；W **不需**字段级适配器（整表 clear）——但这**不构成 W 安全的理由** |
| **B. 迁移安全** | 破坏性 token 迁移**达到"旧实现不安全"状态之前**，必须**阻止 W legacy 执行**；迁移后 W 保持禁用/fail-closed；bridge 在 W 禁用被验证前**不得恢复接收请求**；token 出 S 后任何 legacy W 都不得执行 |
| **C. W 重激活** | W 保持不可用，直到其独立 workspace 事务模型设计+实现+验收完成；**不随 A/B/C 的 M07 激活自动启用** |

**禁用时点（显式）**：① 破坏性迁移**之前**完成禁用并验证；② 贯穿迁移与重启维持；③ 维持到独立 W 发布批准。**当前无端点级禁用机制（`CONFIRMED` 源码：W 是内联路由，无中间件可提前拒绝、无开关）→ 不得声称迁移安全（MIG-16/WS-06）。**

### 四·B-2 M06 显式 requestId 处理（Issue D）

- **M06 无 requestId**：保留现有非幂等行为（每次调用 = 新操作），不违反 D-2。
- **M06 带显式 requestId**：**不得静默忽略**。若 request-level 幂等不可用 → **fail-closed 拒绝**，返回明确错误（"requestId 式 reset 在当前模式不可用"），**拒绝后不轮换、不清理**。现状端点 parser 忽略未知字段（`:7390` 只取 key）——这可能误导调用方以为幂等生效，须在 M06-L1 显式检测 requestId 并拒绝（RB-06）。
- **M07 带 requestId**：仅在 M07 全量激活后启用既定 requestId→batch/结果语义。
- 不改变 `01` D-2。

## 四·C admission barrier 覆盖 M06 过渡期（Issue C）

- PHASE-07/08 的隔离不变式（drain 屏障后旧 prompt 不得进入能用新凭据的投递路径）**同时适用于 M06 无 journal reset 与 M07 事务化 reset**——M06 过渡期同样存在"离线 `queued` 队列重投旧 prompt"的缺口。
- **M06 兼容不得被当作"可运行不安全 reset 的许可"**：在 admission barrier 落地并验证前，受影响 reset 路由**保持 fail-closed**；M06-L1 只改 credential 读写，**不解除** admission barrier 的阻断。
- PHASE-07/08 保持未决（UNCONFIRMED），作为 M06 与 M07 双阶段的激活门。
- token 迁移：维护窗口、bridge 停止，读 S → 写 credential → 删 S 字段；阶段 4 前可回滚（双读），阶段 4 后不可。
- prompt-dump：迁移时先归档并清除含凭据的存量 log，切换 meta 默认。
- journal 幂等索引：压缩不得丢 requestId 索引（D-8）。

## 五、M06→M07 迁移边界（Issue B）

**事实（`CONFIRMED`）**：旧 reset 路径依赖 `socialV2.conversations` 里的 `st.agentToken`（`retireSession :2795`、A `:4613-4614`、B/C 同型、W `:7493-7495` 内存清表）——**token 出 S 后这些旧路径必须同时改造，否则失效**。这使 15 号记录的"兼容 vs 冻结"不再是二选一悬置，而是有确定答案：

| 问题 | 结论 |
|---|---|
| M06 完成、M07 未完成时，允许何种 reset 行为？ | **旧 reset 路径随 M06 同步改造为读写 credential（无事务）**，保持"轮换 + 清理"的既有语义，但不含 journal/幂等/恢复 |
| reset 端点能否只调新 rotate、不套 resetTx？ | 能调 `credential.rotate`（M06 的纯凭证操作），但**不套 resetTx**——即"M06 阶段无事务的轮换"是允许的中间态，`04` §五 UNCONFIRMED 由本节解除为 CONFIRMED |
| 什么被冻结？ | **事务保证被冻结**（journal/幂等/恢复等到 M07）；端点行为（轮换+清理）不冻结 |
| 激活边界（journal-backed 事务切换时点）？ | M07 全量联调 + 恢复演练全绿后一次性切换**三条会话级路径（A/B/C）**；**workspace/reset 不参与此切换**（独立激活，见 §六） |
| 回滚如何避免凭据状态不一致？ | 回滚 = 撤 M07 事务层，端点退回"M06 无事务轮换"；credential 存储层（M06）不回滚（token 已出 S）；**任何阶段端点不得声明 journal 保证而实际未启用** |

> 15 号"UNCONFIRMED"（旧 reset 端点对已出 S credential 的读写方式）本节**解除为 CONFIRMED**：M06 改造 credential 存储层时，旧 reset 端点同步改为读写 credential（无事务），是唯一的可行过渡。

### 5.1 M07 回滚条件（Issue D）

回滚（撤 M07 事务层、退回 M06 无事务轮换）**不得**造成以下任一后果：

| 回滚条件 | 规定 |
|---|---|
| 未决 batch 不得静默丢弃 | 回滚前，所有未完成 batch 必须**先完成或转入受控恢复**；存在 in-flight batch 时回滚被**拒绝**（返回明确错误，要求先收敛） |
| journal/credential/幂等历史保留 | 回滚只撤"端点行为切换"，**不删除** journal、credential、requestId→result 映射 |
| 不丢 requestId→result 映射 | 幂等索引随 journal 保留（D-8），回滚不触发压缩清理 |
| 激活/维护屏障 | 切换端点行为须经**显式激活/维护屏障**（一次性、留审计），不允许无屏障热切换 |
| credential 存储不回退 | token 已出 S，credential 存储层（M06）**不回退**到旧的 S 层 token 模型 |

**回滚后 requestId 幂等不削弱（Issue E）**：撤 M07 事务执行器时，可能连带撤掉"查阅 requestId→result 映射"的组件，违反 `01` D-2。因此回滚必须**保留一个独立于 M07 事务执行器的轻量幂等/重放适配器**（或：在无法维持 D-2 保证时，reset 端点**fail-closed 拒绝**）。两种方案的效果须显式记录，**回滚不得静默削弱 D-2**：
- 方案①（推荐）：保留轻量幂等适配器——同 requestId 仍返回记录结果/续跑、不轮换；新/缺 requestId 维持既定语义；journal 与结果保留不动。
- 方案②（兜底）：若轻量适配器不可行，reset 端点 fail-closed（拒绝接受 reset 请求），直到 M07 恢复。
- 无论哪种，**同 requestId 回滚后不得再次轮换**（RB-04）。

## 六、workspace/reset 事务边界（Issue D）

- workspace/reset 是**独立批次事务模型**，不套 session resetTx phase（B-2 保持）。

### 八·A M15 异常禁用行为（Issue 5）

W 在独立设计/实现/验收完成前**必须禁用**。异常态一律 fail-closed：

| 异常态 | 行为 |
|---|---|
| 禁用状态无法读取 | **按禁用处理** |
| 禁用状态无法验证 | **按禁用处理** |
| 禁用状态不一致 | **按禁用处理** |
| W 路由 | **不得进入 legacy 路径** |
| 普通启动 / 迁移完成 / A/B/C 的 M07 激活 | **不得自动解除 W 禁用** |
| 禁用状态因迁移/重启丢失 | **禁止**（禁用态须持久，见 M15 交付物，验收 M15-04） |
| 无法确认禁用状态时的服务恢复 | **服从迁移安全门，不得绕过检查** |

### 八·B M17 分阶段启动要求（Issue 2）

- **M06 阶段启动**：必要状态 + admission barrier（M16-A）**先恢复，之后才开放受影响路由**。
- **M07 阶段启动**：未完成 resetTx 恢复 + barrier（M16-B）恢复**先于 flushQueue**。
- **恢复失败**：**保持 fail-closed**，不得通过普通启动流程绕过门禁。
- 两阶段要求分开验收，不写成单一笼统步骤。

### 八·C M18 独立证据原则（Issue 4）

- M18 **可以依赖** M14 提供的接口规范、数据结构、验收契约。
- `K_enum` 的**实际枚举来源、生成过程、完整性证据必须独立于 K_pre**。

- **仅仅更换读取方式 / 重复读取同一数据源，不构成独立证据**。
- 独立性与失败模式未被充分证明时，**V-8b 必须保持 UNCONFIRMED**。
