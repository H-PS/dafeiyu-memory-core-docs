## 二、本版最重要的三个判断（需要主人知道）

### 2.1 选择"改表"而不是"改算法"（P0-1）

旧表第 5 行说"主人私聊能读群里的 owner_only"，但算法第一行就要求 `key` 相等——两者不可能同时成立。

**两条路**：
- 改算法（放开跨 key）→ 让 `canRead` 的 key 断言失效，需要另一套审计与测试；
- **改表（本版选择）**→ 主人不能跨 key 读，只能控制台看。

选后者的理由：群里被描述的主体往往**不是主人**，主人的所有权不等于第三人的知情同意；且 R5 要求"私聊内容永不自动变群可读"，反向开洞会让这条不对称。

**代价**：群内被判敏感的记忆，在聊天里永远读不到（含主人私聊）。这是有意的，列入 R31-D3。

### 2.2 凭据必须"一个真相源"（P0-8）

现状 token 有 **3 个赋值点 + 1 个快照拷贝**：

```
:8782  初始化   randomBytes(16)
:2795  轮换     randomBytes(24)     ← Rev3 的双重轮换就冲突在这
:8945  快照拷贝 → 随每次 S 层保存落盘（43 处重写路径都会写一遍凭据）
:11308/:4613  forgetAgentToken（清脱敏集合，配合 conversations.delete）
```

Rev3 的顺序（先 rotate 后 retireSession）会导致：credential 里 T2、S 层 `st.agentToken` 是 T3，模型拿 T2 → 403。

**修法不是调顺序，而是删掉一个真相源**：`:2795` 的内联生成删除，`:8945` 的快照拷贝删除，4 个读取点改 `credential.get()`。

**附带收益**：`social-v2.json` 不再含凭据 ⇒ 备份、日志、快照、第三方同步工具都不会顺手复制 token。

### 2.3 "构造出 prompt" ≠ "交付成功"（P0-7）

Rev3 写"发成功后 `needsDelivery=false`"，但原实现里 prompt 可能：
- 拼好了但因为 `dshReady=false` 进了离线队列（`:9498-9507`）；
- DSH 拒绝（`:9548` `!accepted.result.ok`）；
- 抛错。

三种情况都不该算交付。本版定义五态状态机，只有 `accepted.result.ok === true` 才清标记，其余保持 `needsDelivery=true` 并告警。

### 4.2 凭据字段（影响 05/08）

| 影响 | 处理 |
|---|---|
| `08` 的字段归属矩阵里"agentToken → agent-token.json" | 一致，无需改 |
| `05` 的 `commit()` 不涉及凭据 | 一致 |

## 五、风险提示（本版引入的新风险）

| # | 风险 | 缓解 |
|---|---|---|
| N-1 | 移除 `st.agentToken` 时漏改某个读取点 → 该处拿到 undefined → 401/403 | 4 个读取点已全部列出；`CRED-06/08` 断言；`grep` 归零 |
| N-2 | 快照不再含 token，若有外部工具（脚本/控制台）从 `social-v2.json` 读 token，会读到 undefined | **需核实**：目前未发现外部消费者（`【UNCONFIRMED】U-11`），迁移前须 grep 全仓 `social-v2.json` 的读方 |
| N-3 | `/reset` 改为轮换后，若 reset 事务中途失败，可能"token 换了但会话没清" → 上下文未清但凭据已换 | `resetTx` 按 phase 续跑；该中间态可用（只是没清干净），不算故障 |
| N-4 | `structure` 模式仍会落"规则块文本"，若规则里含用户自定义内容（如自定义睡眠话术），可能带出个人信息 | 规则块来自配置而非聊天；如仍担心，`structure` 也可降为 `meta` |
| N-5 | 一次性内存捕获可能被滥用（连续开启） | 同时仅允许 1 个 key、TTL ≤15min、每次开启写审计、控制台显示"捕获中"标识 |
